# Live2D 重影问题定案与模型特殊性对照（2026-10-16）

本文记录一次"某个 Live2D 模型在网页里重影"的排查结论与可复现证据，供后续遇到同类现象时直接对照。

## 一、现象

- 现象模型：`aimierbeierding_3`（与同源的 `aimierbeierding_3_hx`）
- 表现：头部、肩臂等处的部件呈**半透明覆层**叠加，视觉上像"多画了一层"，即重影
- 同角色的另一套：`aimierbeierding_2` 无此现象

## 二、定案：缺陷在模型数据，不在查看器代码

用**第三方查看器**渲染同一模型做对照：

| 查看器 | 代码来源 | 同一模型的表现 |
|---|---|---|
| 本项目（spine-multi-viewer） | 自研舞台 + pixi-live2d-display 0.4.0 | 重影 |
| Chaoray/AzurLane-Live2D-Viewer v.827 | 独立项目（同为 pixi-live2d-display，PIXI 应用**未开 stencil**） | **同样重影，幅度略小** |

两者实现独立却出现同一异常 ⇒ 该模型自身存在缺陷/异常结构；查看器只影响其**幅度**，不是根因。

## 三、模型特殊性实测（Cubism Core 读出的结构）

| 指标 | `aimierbeierding_2`（正常） | `aimierbeierding_3`（重影） |
|---|---|---|
| moc3 字节 | 600,832 | 2,444,160 |
| 画布 | 3000×3000，ppu 166.67 | 6200×5600，ppu 311.11 |
| 绘制对象 | 206 | **532** |
| 部件 | 40 | **120** |
| 参数 | 138 | **264** |
| **带遮罩绘制对象** | **0** | **18**（`oral`、`eyeball_l/r`、`eyeballhl_*` 等） |
| 遮罩引用总数 | 0 | 19 |
| **默认不透明度 < 1 的绘制对象** | 42（多为 `op=0`，即隐藏备用件） | **110**，且含**常驻半透明层** |
| 常驻半透明层样例 | — | `eyelipdoubleshadow_l_1` = 0.651、`eyelipmain_l` = 0.651 |
| 贴图索引分布 | 0:134 / 1:72（两张图集） | 0:532（单张图集） |

要点：

1. `_3` 是**结构重得多的模型**（绘制对象 2.6 倍、部件 3 倍、参数 1.9 倍），画布尺寸与 ppu 也完全不同。
2. `_3` 是**唯一使用裁剪遮罩**的一方（18 个遮罩对象，`_2` 为 0）——遮罩渲染路径只在它身上被走到。
3. `_3` 有**大量默认半透明的常驻绘制层**，且部件命名直接含 `doubleshadow`（双重阴影）——即美术层本身就存在"叠加/半透明"结构。

## 四、幅度差异的原因（已定案：遮罩缓冲尺寸与模型画布不匹配）

第三方查看器同样重影但更轻，差异落在**裁剪遮罩的渲染缓冲分辨率**上，已用对照实验定案：

- Cubism 的裁剪遮罩先画进一块**独立的渲染缓冲**，框架默认 **256×256**（固定值，与模型无关）；
  再拿这块缓冲去裁剪绘制对象。缓冲越小，遮罩边界越糊，本该被裁掉的部件就裁不干净。
- 本模型 `_3` 的画布是 **6200×5600**（同角色正常模型 `_2` 为 3000×3000），且用了 **9 组遮罩**：
  256 的缓冲要覆盖这么大的画布，遮罩精度严重不足 → 应被遮住的眼皮/头发等叠加层漏出，
  看起来就是半透明覆层（重影）。**画布越大、遮罩组越多，这种"糊"越明显**——这就是幅度差异的来源；
  第三方查看器的遮罩实现/缓冲取值不同，幅度也就不同。
- 对照实验（同一帧冻结，只改缓冲并重建遮罩纹理）：
  | 观测 | 默认 256 | 自适应 1550 |
  | --- | --- | --- |
  | 画面 | 双眼被眼白盖住（瞳色不见）+ 颊部有深色残影 | 双眼正常、残影消失 |
  | 与 256 的逐像素差异 | — | **1186 px / 1920×1080 = 0.057%**，全部落在双眼与口鼻/颊部（遮罩覆盖区） |
  | 运行时缓冲值 `_clippingMaskBufferSize` | 256 | 1550 |
- 修法（`public/live2d-stage.js`）：装载后、首次渲染前，对**确实有遮罩**的模型把缓冲设为
  `clamp(1024, max(画布宽,高)/4, 2048)`（本模型 → 1550），并**置空 `_maskRenderTexture` 让遮罩纹理按新尺寸重建**
  （不重建不生效）；无遮罩模型（`_2`，遮罩组 0）保持默认 256 不动。
  显存代价：256²≈0.25MB → 1550²≈9.6MB（上界 2048²≈16MB），只对有遮罩的模型放宽。
- 仍未验证的次要因素：纹理的预乘 alpha（PMA）合成口径。目前没有观测到它与本重影相关的证据，
  保留为待查项。

本项目当前 `stencil: true`（遮罩必需，否则带遮罩模型会把应裁掉的部件画出来）。是否还要调整 alpha 合成口径，需在对照实验后决定。

## 五、本项目已修的三个真问题（与本模型缺陷无关，但都是真 bug）

1. **幽灵模型叠加**：并发 `show()` 交错时，先完成的一次模型没被销毁，舞台上同时存在两个模型 → 两幅叠加渲染。修法：装载序号守卫 + 挂载前清扫舞台上多余的 Live2D 模型。
2. **遮罩失效（已证伪，见第七节）**：曾按"PIXI 应用未开模板缓冲导致裁剪遮罩不生效"处理（`stencil: true`）。后续实测 `debug().stencilOk` 在 PIXI 默认上下文下即为 `true`，**该改动对渲染无影响**，已随第七节一并停用。
3. **坏动作打断渲染循环**：某个动作用数据与其 moc3 参数表不匹配时，运行时每帧抛 `Cannot read properties of undefined (reading 'time')`，异常打断 PIXI Ticker 的 `requestAnimationFrame` 续期（`started` 仍为 true、`_requestId` 变 null），表现为画面先冻结、其后任何尺寸变化清屏即全黑。修法：给 `ticker.update` 包一层兜底（单帧异常不再断链，并停掉抛错动作 + 补渲染一帧）+ 定时自检重启断链。

## 六、可复用的判定手法

- **结构对照**：拿同角色、同来源的正常模型做基线，比较 绘制对象/部件/参数/遮罩数/默认不透明度/贴图索引 六项，一眼能看出"特殊在哪"。
- **第三方查看器对照**：把模型放到另一套独立实现的查看器里渲染，是区分"模型缺陷"与"查看器缺陷"最快的手段。
- **运行期自检**：`__LIVE2D_STAGE__.debug()` 提供 `live2dModels`（是否多模型叠加）、`stencilOk`（模板缓冲是否可用）、`ticker`（渲染循环是否停摆）、`maskBuf`（裁剪遮罩缓冲的实际尺寸，无遮罩模型为 null）四项，可直接定位上述问题。

## 七、现象描述的修正与后续方向（2026-10-16 追加）

### 7.1 现象描述修正（重要）

此前用「重影」描述该现象**不够准确**。更贴合直观感受的描述是：

> **产生重复贴图，且两个副本的运动轨迹不一致** —— 两个副本各自独立运动。

这个描述把方向从"渲染器把同一份内容画了两遍"改向"**底层存在两个独立对象**（各自有独立的参数控制或物理演算）"，因此更可能是 **`.moc3` 内部包含重复部件/网格，且它们绑定到不同的参数组或物理设定**。

### 7.2 已停用的推测修复

按"遮罩渲染问题"这一方向所做的改动，除"试图解决该现象"外没有其它实际作用，**已统一标记并停用**（`grep -rn "\[重影-推测修复\]"` 可一次找齐）：

- `public/live2d-stage.js`：`stencil: true`、裁剪遮罩缓冲按画布自适应（`applyClippingMaskBuffer`）、"关闭遮罩"开关（`applyClippingMasksMode`/`resolveMasksMode`/`masksModeFromUrl`）及对应的 `debug()` 字段
- `server.mjs`：`/api/live2d/settings` 路由与 `LIVE2D_SETTINGS_FILE`
- `config/live2d.json`：保留文件但标注已停用（无消费方）

**保留、不属该方向**（有独立价值）：渲染循环兜底与看门狗（坏动作打断 rAF 链）、Live2D→Spine 切换不回跳的揭盖保持、`debug()` 其余测量点、展示类型插件开关（`config/plugins.json`）。

### 7.3 后续排查方向（外部建议，尚未在本机验证，仅记录）

1. **Cubism 工程内的重复部件与参数（核心怀疑）**
   - 检查层级面板是否把整个角色（ArtMesh 与 Deformer）复制了一份；
   - 检查参数 ID 是否出现重复（如 `ParamAngleX` 与 `ParamAngleX_2`）；
   - 检查物理设置：物理输入参数是否只绑给了其中一个副本，导致另一个副本不跟随物理；
   - 检查动作文件：动作可能只驱动主参数，而重复部件绑定的是副参数，导致两边动作不同步。
2. **贴图图集与 UV 映射**
   - 查看 `texture_00.png` 等贴图里是否真的画了两份内容；
   - 检查 Texture Atlas 设置：UV 若被映射到同一张贴图的两个不同区域，模型就会被绘制两次。
3. **网络加载与实例化（前端侧）**
   - 用 Network 面板确认 `.moc3`/贴图是否被请求了两次；
   - 检查加载回调是否因文件大、加载慢而触发了两次 `Live2DModel.from()`；
   - 打印 `model.internalModel.coreModel.getDrawableCount()`，若数量约为正常模型的两倍，则指向模型文件本身。
4. **版本兼容性**
   - 若模型使用了较新的 Cubism 特性，而运行期 SDK 较旧，解析 `.moc3` 时可能出现顶点重复类问题；可尝试更换更新的 Cubism Web SDK 再验。

### 7.4 黄金验证法（一步定位）

把该模型放进**官方 Cubism Web Viewer**（或本地 Live2DViewerEX 等权威查看器）渲染：

- 官方同样异常 → 判定为**模型源文件问题**（重复部件/参数绑定），需在 Cubism Editor 中删除多余副本后重新导出 `.moc3`；
- 官方正常、仅本项目异常 → 判定为**本项目的渲染路径问题**（某个特性触发了渲染 bug），此时应以控制台报错为线索继续排查。

本机当前使用的运行期版本（便于与官方对照时记录）：pixi-live2d-display **0.4.0**（内部打包 Cubism 框架）、PIXI **6.5.3**、Cubism Core **4.2.0**、WebGL 2.0（`stencil: true`、`MAX_TEXTURE_SIZE 8192`、`glError = 0`）。

## 八、定量结论：重复呈现来自模型数据（2026-10-16 追加）

### 8.1 模型结构实测（用官方 Cubism Core 直读 `aimierbeierding_3.moc3`，与渲染无关）

| 指标 | 实测值 |
|---|---|
| 绘制对象 / 部件 | 532 / 120 |
| **UV 包围盒重复组** | **121 组，覆盖 252 个绘制对象（占 47%）** —— 同一块图集区域被多个绘制对象复用 |
| 同名前缀族（剥结尾 `_数字`） | 35 族 / 245 个绘制对象；其中 **21 族跨多个部件** |
| 常驻半透明层（不透明度 < 1） | 110 个（含 `op=0` 的纯遮罩层，如 `oralmask`） |
| 名字含 `doubleshadow` | 4 个（`eyelipdoubleshadow_l_1/_l_2/_r_1/_r_2`） |
| 同一部件挂多个绘制对象 | 78 个部件（如 `PartEyeLStand` 9 个） |
| 部件名重复 | 0 组 —— 重复发生在**网格/绘制对象**层，不在部件层 |

跨部件重复的实例：

```
hairback_r_c1 ×28  → hairback_r_c1_4@PartHairBackStand
                     + …_7..15@hairback_r_c1_2_Skinning
                     + …_16..23@hairback_r_c1_5_Skinning …
hairback_l_c1 ×28 / hairback_l_c2 ×20 / hairback_r_c2 ×20 / hairback_r_c3 ×20
florabeltsingel_r ×8 → …_5..8@PartBodyUpperStand + …_13..16@PartChest
```

不同部件各有父级、不透明度与物理绑定 ⇒ **天然可以各自独立运动**，这正是"重复贴图且两个副本运动轨迹不一致"的结构来源。

### 8.2 渲染侧对照：遮罩路径与"重复"无关（实测）

把裁剪遮罩整条路径关掉（`renderer._clippingManager = null`）后重绘，与开着遮罩逐像素比：

```
墨量（非透明像素）：遮罩开 450,998 ／ 遮罩关 450,998   ← 完全相同
画面差异：1,148 px / 1920×1080 = 0.055%，区域为脸部/眼部
```

⇒ 重复层是**无条件绘制**的，与遮罩/渲染路径无关；遮罩只影响眼部约 0.055% 的语义差异。这条量化数据同时说明：此前把方向押在"遮罩缓冲尺寸"上是误诊。

### 8.3 结论

**该模型的重复呈现由模型数据本身造成，不是渲染器造成。** 三条证据交叉：

1. 数据里存在大量"同一图集区域、多个绘制对象"的重复（121 组 / 252 个对象 = 47%），且 21 族**跨部件**；
2. 渲染侧把遮罩路径整体关闭，墨量一个像素不差（仅眼部 0.055% 差异）⇒ 重复与遮罩/渲染器参数无关；
3. 旁证：同一现象在另一台设备（移动端 GPU）与**目录版**资源（不经过本项目任何改动路径）上同样出现。

**标注为推断、尚未坐实的一点**：8.1 中跨部件的副本各自绑定的参数/物理不同，是"运动轨迹不一致"的机制解释；需逐副本追踪参数绑定才能最终确认。
