## 已解（文档写死，无需再猜）

| 原条目 | 文档依据 | 插件侧落地 |
|---|---|---|
| **#1 `file` 参数长什么样** | 资产提供者 §1.1 字段表（rootId/rel 必选，name/size/profile/bytes 可选），「平铺在 file 顶层，没有 ctx 包装」 | `asCtx(file)` 透传；`resolve` 校验 rootId+rel 必选，缺则抛 `ULB_ERR_BAD_ARGS` |
| **#2 没有 `file.bytes` 时取字节通道** | §1.1 取字节两条通道 + 插件契约 §3.6：通道② 唯一合法形态 = `host.fetchFile(rootId, rel) → Promise<Uint8Array>` | `readBundleBytes`：先 `ctx.bytes`，再 `hostApi.fetchFile(rootId, rel)`；hostApi 取法 `ctx.host → host.host → host`（兼容旧嵌套面与新顶层面） |
| **#3 prefix 格式与唯一性** | §1.2 写死：`vfs://<providerId>/<rootId>/<相对目录>/`，全局唯一，重复注册由核心抛错 | `prefix = vfs://unity-live2d-bundle/<rootId>/<relDir>/`（relDir 取 rel 的 dirname，恒以 / 结尾） |
| **#4 files 键能否带子目录** | §1.2「relPath 用 / 分隔，允许子目录」 | 键保持 `textures/tex.png`、`motions/xxx.motion3.json` 原样 |
| **#5 string 值编码** | §1.2「string 按 UTF-8 读回」 | model3/motion3/physics3 以 string（JSON 文本）进 files，核心按 UTF-8 读 |
| **#6 原生文件集 entry 指向** | §1.3 写死：原生包 entry = 包内**实际存在**的 `*.model3.json` 键；Unity 集成版 = 插件**重建**的 `model3.json` 键 | 两条分支已按此实现 |
| **#7 register 要不要带 kind** | 插件契约 §3.2：`produces.kind` 是**唯一来源**；register descriptor 可带 `kind` 便于调试但核心不读 | plugin.json `produces.kind: "live2d"`；register 保留 `kind` 字段（调试用），不影响核心 |
| **#8 canHandle 无字节判 true/false** | 插件契约 §3.1 三行判例表：有 bytes 且魔数匹配→true；不匹配→false；**无 bytes→true（保守放行）** | `canHandle` 按 §3.1 表格逐行实现，注释引条款号 |
| **#9 host.log 注入形态与降级** | **§3.6 写死**：`host.log(level, msg, scope)`；`host` 不可用或没有 `log` ⇒ 允许降级为 `console[level]`，但**不得静默丢弃**；level ∈ debug\|info\|warn\|error，scope 用插件 id | `canHandle` catch 分支按 §3.7 记 debug：`host.log || console.debug` 降级；未注册告警、profile 缺失等既有 console 保留（旧通道），新契约路径日志走 host.log |
| **#10 resolve 成功要不要带 report** | 插件契约 §3.4：「resolve() 成功时只返回 { prefix, files, entry }；旧实现里的 report / 附加字段不再返回（诊断走 host.log）」 | `resolve` 两条分支均严格返回三键，report 不挂 |
| **#11 kind 单值还是数组** | 插件契约 §3.2：「一个插件只声明一个 produces.kind；不唯一则拆多个插件」 | 本插件固定 `live2d`；Spine 包将来另起插件 |
| **#12 失败错误码形状** | 插件契约 §3.4：「失败一律抛 Error 且带 code 字段（码表见 plugin.json errorCodes），核心按 code 决定提示文案」 | 抛 `NS.errors.fail(code, msg)`，code ∈ plugin.json.errorCodes |
| **#14 迁移期双通道** | 插件契约 §3.5：「核心优先调 canHandle/resolve；两者都不存在才算插件无效；旧通道下一个大版本删」 | register 同时带 `probe/open`（兼容）与 `canHandle/resolve`（目标） |
| **#15 prepare/revoke 钩子挂载点** | **§3.8 写死**：新契约下**不存在** prepare/revoke；渲染前要做的事（重建 model3、解纹理与动作）**全部在 resolve() 内完成**；资源释放由核心按 prefix 调 VirtualFS.revoke；「若某插件确需渲染前插一脚，说明产物形态设计有问题（典型：想给加载器装中间件）——那是 VirtualFS 该解决的，不是插件职责」 | `resolve()` 内已完成全部渲染前准备（相对路径 model3 + 纹理 PNG 编码 + motion 转换），files 即最终产物；不暴露 prepare/revoke。旧 `open()` 的 prepare/revoke 钩子仅服务未迁移宿主（§3.5 兼容层），下个大版本随旧通道删除 |
| **#16 profile 怎么传到插件** | 资产提供者 §1.1 字段表含 `profile?: string`（资源根配置透传）+ §3.6「取 profile 数据：插件自读 `profiles/<profile>.json`，缺 profile ⇒ 走默认规则，不报错」 | `resolve` 读 `ctx.profile` 走 `loadProfile`，缺失时 `loadProfile` 返回 `{}`（默认规则），不报错 |
| **#17 canHandle 纯判定边界** | 插件契约 §3.1「允许：读 file 字段（含 file.bytes）做魔数判定；禁止：I/O、修改外部状态、抛异常」 | `canHandle` 内无 I/O，纯内存 `bundleProbe.run` |
| **#18 files 体积上限** | 资产提供者 §1.2「不设单包上限，峰值由核心 revoke 控住（实测碧蓝单包可 40MB+）」 | 不设限，与旧 Blob URL 路径同量级 |
| **#19 取字节通道② 的函数签名** | **§3.6 写死**：`host.fetchFile(rootId, rel) → Promise<Uint8Array>`（直接返回 Uint8Array，不是 `{bytes}`）；host 不可用 ⇒ `resolve` 抛 `ULB_ERR_NO_HOST`（可退化） | `readBundleBytes` 按 §3.6 签名消费：`const bytes = await fetchFile(rootId, rel)` 直接用返回值；`fetchFile` 缺失时抛 `ULB_ERR_NO_HOST`（已加入 errors.js 码表与 plugin.json errorCodes） |
| **#20 canHandle 内部异常合规性** | **§3.7 写死**：「允许：canHandle 内部 try/catch，捕获后 return false。理由：§3.1 禁止的是『把异常抛给宿主』与『产生 I/O』，不是禁止内部容错。要求：catch 分支不得静默——至少在 debug 级别记一条（host.log 或降级 console）」 | `canHandle` catch 后 `return false` + debug 级日志（§3.7 双要求均满足） |
