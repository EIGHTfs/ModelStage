# 卡点清单（B）：只靠契约文档迁移 unity-live2d-bundle 的「要猜 / 说不清 / 必须读核心代码才能定」的地方

> 范围：只读 `doc/契约/插件契约.md`、`doc/契约/资产提供者契约.md` 与 `plugins/unity-live2d-bundle/`；
> 未读 `src/web/engine`、`src/server`（读了就测不出"文档够不够"），下文凡需要读核心才能定的都标了。
> 验收口径：每条 = 卡在哪 → 最后怎么猜的 → 文档该怎么写才不用猜。

## 1. `resolve(file)` 的 `file` 到底长什么样

- **卡在哪**：契约只写 `resolve(file) → { prefix, files, entry }`，没说 `file` 这个参数里有什么字段。
  旧 `open(ctx)` 的 `ctx` 有 `{ rootId, rel, name, size, profile, host }`；新契约 §六写"宿主把 `rootId/rel/name/size/profile` 作为上下文传入"，
  但**没说这些字段是直接挂在 `file` 上，还是 `file` 里再套一层**（比如 `file.meta`、`file.context`），也没说 `file` 是否带字节。
- **怎么猜的**：按"`file` 就是旧 `ctx` 本身"处理——`asCtx(file)` 直接透传，字节走 `file.bytes`，没有 `bytes` 就退 `file.rootId + file.rel` 经 `host.host.fetchFile` 取。
- **文档该怎么写**：在资产提供者契约 §一 里给一个**完整字段表**（必选/可选 + 类型 + 谁填）：
  ```
  file = {
    rootId: string,        // 必选，资源根 id
    rel: string,           // 必选，资源根内相对路径
    name: string,          // 可选，显示名
    size: number,          // 可选
    profile: string,       // 可选，资源根配置选的游戏 profile
    bytes?: Uint8Array    // 可选，宿主可直接给字节（给了就不用 fetch）
  }
  ```
  再补一句"字段平铺在 `file` 顶层，不再有 `file.ctx` 包装"——现在两条读法都对，只能赌。

## 2. 没有 `file.bytes` 时，插件取字节的通道是什么

- **卡在哪**：旧实现 `readBundleBytes(ctx, hostApi)` 走 `ctx.host.fetchFile(rootId, rel)`（宿主注入面里有 `host.host`）。
  新契约 §六只说"资源位置由 `VirtualFS`（核心注册/解析/释放）"、插件"不直接调 `VirtualFS.register`，只交付 `files`"，
  **没说插件怎么把容器字节读进来**：是 `file.bytes` 必给？还是宿主仍会在注册面挂一个 `fetchFile`？还是插件该调 `VirtualFS.read(rootId, rel)`？
- **怎么猜的**：`file.bytes` 优先，缺了就回退旧的 `ctx.host` / 注册面 `host.host` 的 `fetchFile(rootId, rel)`——即假设宿主注入面**保留了取文件能力**，契约只是没写。
- **文档该怎么写**：契约 §六加一行"宿主对 asset-provider 暴露 `host.fetchFile(rootId, rel) → { bytes }`（或 `file.bytes` 二选一）"，
  或明确"`file.bytes` 为必选，宿主负责取字节后传入，插件永不自己 fetch"。二选一写死，插件侧就不会写两条路。

## 3. `prefix` 的格式与唯一性规则

- **卡在哪**：契约说 `prefix` = "VirtualFS 前缀（含插件 id 与资源根，保证唯一）"，但没给**确切格式**：是 `unity-live2d-bundle/<rootId>/<rel>`、
  还是 `/v1/unity-live2d-bundle/...`、`rel` 里的斜杠要不要转义、同插件两次 resolve 同一个包要不要拿到同一个 prefix（幂等性）。
- **怎么猜的**：`unity-live2d-bundle/<rootId>/<rel>`，`rel` 原样保留（含多级目录，不转义）；同包重复 resolve 得同 prefix。
- **文档该怎么写**：给一条**可断言的格式**（如 `^<插件id>/[^/]+/.+$` 或"插件id + '/' + 资源根内路径，不得含 ':' 与查询串"），
  并写清"同一 (rootId, rel) 的多次 resolve 必须返回同一 prefix"（这是核心按 prefix revoke 的前提，AP5 依赖它）。

## 4. `files` 的键（relPath）是否必须与 `entry` 同级、能不能带目录

- **卡在哪**：契约写 `files: Map<relPath, Blob|string>`、`entry` = "渲染入口在 files 内的相对路径"。
  没明说**键能不能含 `/` 子目录**（如 `motions/idle.motion3.json`）。我按"可以带子目录"实现了；若核心把键当**扁平文件名**处理，
  则 Unity 集成版重建 model3 里对 `motions/xxx.motion3.json` 的引用会全解析不到。
- **怎么猜的**：允许子目录（model3 的 FileReferences 本来就带 `textures/texture_00.png` 这种相对路径）。
- **文档该怎么写**：一句话"relPath 是相对 prefix 的路径，可含子目录；VirtualFS.resolve(url) 按原样匹配键"——现在只能靠 VirtualFS 契约猜。

## 5. `files` 里存字符串时，核心按什么编码读回

- **卡在哪**：契约写 `Blob|string`，但没写 `string` 值核心侧怎么进 VirtualFS：按 UTF-8 编码？还是 `string` 只允许给 JSON、核心负责 `JSON.parse`？
  我的实现里 model3.json / motion3.json / physics3.json 都以 `string`（JSON 文本）存。
- **怎么猜的**：核心按 UTF-8 把 `string` 转 Blob 存，读取时原样回传；插件存的是**完整文件内容**。
- **文档该怎么写**：写清"`string` 值按 UTF-8 序列化后与 Blob 同等对待；键是 JSON 文件时插件给序列化后的文本"。

## 6. 两种包型里，原生 Cubism 文件集的 `entry` 该指向哪个键

- **卡在哪**：契约说"entry = 渲染入口（.model3.json / .skel）"。原生包**自带** model3.json，但包内文件名不一定叫 `model3.json`
  （实测样本里叫 `<资源名>.model3.json`）。契约没写"entry 必须等于字面量 `model3.json`"，还是"entry = 包内那个 model3 的键名"。
- **怎么猜的**：`entry` = 包内 model3 文件的**实际键名**（如 `adaerbote_3.model3.json`）；若包内有多份 model3 取第一份。
  Unity 集成版则 entry 固定为重建出来的 `model3.json`。
- **文档该怎么写**：写"entry 是 files 里渲染入口的键名，不必是字面量 model3.json；一个包多入口时取哪个由插件定"。

## 7. `register()` 要不要带 `kind` / `produces.kind` 在注册对象里

- **卡在哪**：资产提供者契约 §一的接口对象里有 `kind: 'live2d' | 'spine'`；但插件契约 §三 的 `register({...})` 示例**没有 `kind` 字段**，
  只写 `id/name/fileKinds/canHandle/resolve`；`kind` 按 §四 来自 `plugin.json` 的 `produces.kind`。
  即：**到底宿主看注册对象还是看清单，没写死**。
- **怎么猜的**：两边都给——`plugin.json` 加 `provides: ["asset-provider"]`（契约 §一 现状列里 asset-provider 已有），
  注册对象里**同时**带 `kind: 'live2d'`（契约 §一 接口对象有它）；清单 `produces.entry` 改成 `resolve(file)`、旧 `open(ctx)` 降为 `legacyEntry`。
- **文档该怎么写**：明确"注册对象的 `kind` 与 `plugin.json.produces.kind` 哪个为准 / 宿主校验哪个"，避免双写不一致时谁赢。

## 8. `canHandle` 没有字节时判 true 还是判 false

- **卡在哪**：契约说 `canHandle` 是**纯判定、无副作用**。但"能不能读"本质要**看容器字节**才知道（旧 `probe` 没字节给 0.5 保守值）。
  没字节时：判 `true` = 把"选谁"推给宿主（契约意图：二值、宿主选）；判 `false` = 插件自认不处理，宿主可能漏掉这个包。
  契约没给"无字节输入"的期望输出。
- **怎么猜的**：无字节一律 `true`——宿主既然按 `fileKinds=['bundle']` 把文件递给 asset-provider，容器归属判定就该在**有字节时**做
  （`bundleProbe.run` → UnityFS+CAB 才 `true`），无字节属于"宿主还没给数据"，插件不应抢答 false 把包挡掉；
  资源根里的 Unity 包**无扩展名**（如 `azurlane_bundle/adaerbote_3`），扩展名白名单会漏掉真包，故不做名称启发；
  读不出由 `resolve()` 抛错兜底（契约 §5.8 禁止半成品）。
- **文档该怎么写**：给三条判例表：① 有字节且 UnityFS+CAB → true；② 有字节但不是 UnityFS/无 CAB → false；③ 无字节 → **（选一个写死）**。

## 9. 契约说"不得用裸 console.log 作为用户可见输出"，但旧代码全是 console.*

- **卡在哪**：插件契约 §六 要求日志走 `host.log(level, msg, scope)`；但注册契约 §三 的注入面示例里**只出现 `host.register`**，
  没写 `host.log` 长什么样、注册时能不能拿到、`scope` 传什么。旧 `index.js` 里 `console.warn`/`console.info` 十几处（未注册告警、profile 缺失、
  装载摘要）——按契约该改，但改不改、宿主没装 `host.log` 时降级到哪，文档没说。
- **怎么猜的**：**本轮保留 `console.*` 不改**（迁移目标是接口形态；日志通道属宿主注入面，契约 §六 写了但 §三 示例没给，
  强行改 `host.log` 在宿主未实现时会直接崩，比 console 更糟）；已在此登记，等宿主侧确认注入面再切。
- **文档该怎么写**：§三 注入面示例补 `host.log(level, msg, scope?)`，并写"宿主未提供 log 时插件可降级 console"。

## 10. `resolve()` 成功路径要不要顺带产出旧 `open()` 的 report 字段

- **卡在哪**：旧 `open(ctx)` 返回一大份 report（container/serialized/moc3/physics3/textures/modelMeta/curveStats/model3/model/urls…），
  前端多个面板（资产报告、曲线统计、模型 meta）消费它。新契约只认 `{prefix, files, entry}`，**没说 report 还要不要、挂在哪**。
  契约 §一 明说产物"固定为文件表 + 入口，插件不再关心渲染器要什么字段"——那 report 就是**被砍掉的能力**。
  但任务要求"保留现有能力"，两句话冲突。
- **怎么猜的**：`resolve()` 返回体**额外带 `report` 字段**（不进契约三键，核心只读 prefix/files/entry 不受影响），
  旧 `open()` 原样保留（兼容层，宿主没迁移时照走旧路径）。若宿主按契约严格校验"多余字段"会被拒，则 report 要挪走——已在 B 里登记，等宿主侧确认。
- **文档该怎么写**：写清"resolve 返回是否允许携带契约外字段（供宿主自选消费），还是严格三键"。

## 11. `kind` 是 `'live2d'` 还是插件同时能出 `'spine'`

- **卡在哪**：本插件 `plugin.json.produces.kind` 旧值缺省（我按 §三 样例补成 `live2d`）。但名表里碧蓝同时有 **Spine 根**（spine-multi-viewer 名字就是 Spine）
  与 **Live2D 根**；Unity 包出的是 Live2D（moc3/motion3），Spine 模型走另一类包。**契约没说一个插件能不能 `produces` 多个 kind、
  还是每个 kind 一个插件**。
- **怎么猜的**：本插件固定 `kind: 'live2d'`；若将来有"Unity 里塞 Spine skel"的包，按 §八（拓展性验证）"新增一个实现 + 补契约"走，
  不在本插件里猜一个 `kind` 数组。
- **文档该怎么写**：写"`produces.kind` 是单值还是数组；一个插件能否同时产 live2d 与 spine"。

## 12. 失败路径的"可退化"边界：resolve 抛错后核心拿什么错误码

- **卡在哪**：插件自描述 `errorCodes`（ULB_ERR_*），但契约 §一 只说"失败**抛带原因的错误**"，没说核心 catch 后认不认这些码、
  要不要 `error.code` 固定枚举、warnings 里 `lastError` 存原文还是存码。
- **怎么猜的**：抛 `Error` 对象上带 `code`（ULB_ERR_*）+ `message`（中文可读），核心按 `e.code` 聚合 warnings；未改旧码表。
- **文档该怎么写**：给"错误对象最小形状 `{ code, message }`"与"核心如何记 lastError（原文/码/截断长度）"。

## 13. `fileKinds` 里 `bundle` 与 `produces.kind` 的耦合校验

- **卡在哪**：插件契约 §二 说"有解析能力时 `fileKinds` 与 `produces` 必填"；§四 说"`bundle` 不得进 `kind`"。
  但**宿主检查哪个**：一个 `fileKinds: []`（demo 插件那样"只注册不参与解析"）的插件能不能声明 `produces.kind`？
  反之有 `produces` 但 `fileKinds` 空会不会被判"半成品"？demo 插件现在 `fileKinds: []` + 无 produces，是合法特例，契约没点名。
- **怎么猜的**：`fileKinds: ['bundle']` + `produces.kind: 'live2d'` 成对出现（本插件）；空 `fileKinds` 视为"不解析"，此时**不得**声明 `produces`（PL1 语义推得）。
- **文档该怎么写**：给"fileKinds 与 produces 的组合矩阵"（空/非空 × 有/无 produces，哪些组合合法）。

## 14. 两个宿主同名 `register` 的时序：脚本注入失败时核心读 `files` 还是 `entry`

- **卡在哪**：插件契约 §三 写"未调用 `register()` → 标记『脚本已加载但没有调用 register()』"，但**没说这种情况下 catalog 条目还露不露、
  渲染层点进去是隐藏还是标不可用**（AP4 只说删目录隐藏条目）。迁移期宿主同时认 `probe/open` 与 `canHandle/resolve`，
  **哪套先被调、另一套缺了算不算注册失败**，文档没说。
- **怎么猜的**：迁移期宿主以**新契约成员**（`canHandle`/`resolve`）为准；`probe`/`open` 是旧通道保留，宿主若还没改仍会走旧通道——
  所以注册对象里**两套成员都给**，谁缺都不算"没注册"（宿主按它认识的那套判）。
- **文档该怎么写**：给"迁移期双通道"的判定优先级与"缺任一成员时的注册态"。

## 15. `prefix` 的生命周期：谁 revoke、什么时候 revoke，插件能不能感知

- **卡在哪**：契约 §一 明确"`prepare()`/`revoke()` 不保留，释放由核心按 `prefix` 调 `VirtualFS.revoke`"。
  但旧 `open()` 的 model 对象上挂了 `prepare`/`revoke` 钩子（`prepareLoader` / Blob URL 回收），**这两条现有能力在新契约下没有挂载点**——
  插件产出的 `files`（Blob）由核心管生死，插件却还想在"渲染前"装 blob 直通适配（`prepareLoader`）。
  契约没给"渲染前钩子"这个扩展点，AP5 又要 prefix revoke 后 Blob 不累积——两件事怎么协调，文档没写。
- **怎么猜的**：本轮**不动** `prepare`/`revoke`（旧 `open()` 路径仍需要它保持页面渲染可用）；`resolve()` 路径不暴露它们（契约不认），
  意味着走新契约的包，blob 直通适配与 URL 回收要等宿主给"渲染前钩子"契约再补——已在 B 里挂账，未实现。
- **文档该怎么写**：增"asset-provider 可声明 `prepare`/`revoke` 扩展点（可选成员，核心在 surface.activate 前后各调一次）"，
  或明确"新契约下插件无生命周期钩子，渲染前准备一律由渲染器自理"。

## 16. 资源根里的 `azurlane_bundle` 走 `resolve` 时 `profile` 字段怎么传到插件

- **卡在哪**：旧 `open(ctx)` 里 `ctx.profile`（资源根配置选的 profile 名，如 `azurlane`）驱动 `loadProfile`。
  新契约 §六 写"差异数据 `profiles/<profile>.json`（资源根配置选）"，但**`resolve(file)` 的 `file` 里带不带 `profile` 字段没写**
  （与 §1 同源：`file` 形状未定）。
- **怎么猜的**：`file.profile` 平铺（同 §1 的字段表），`loadProfile(file.profile)` 照旧。
- **文档该怎么写**：并入 §1 的字段表，把 `profile?: string` 标为"资源根配置透传，可空"。

## 17. `canHandle` 的"纯判定"与"读字节做魔数"的矛盾

- **卡在哪**：契约要求 `canHandle` **无副作用**，但要判 UnityFS 又得**读字节头**（`looksLikeUnityFs` 取前 8 字节）。
  "读内存里的 `file.bytes`"算不算副作用？契约没说"副作用"的边界（I/O 肯定算，读传入参数肯定不算）。
- **怎么猜的**：读 `file.bytes`（宿主给的、已在内存）不算副作用，允许；**发起网络/文件 I/O** 才算，`canHandle` 里不 fetch。
- **文档该怎么写**：一句话"纯判定 = 不产生 I/O / 不改外部状态；读取宿主传入参数（含 bytes）允许"。

## 18. `files` 体积上限：Unity 包解出的纹理可能单张 4096² PNG（几十 MB），核心吃不吃得下

- **卡在哪**：AP5 要求"连开 5 包不累积"，但没说**单包 files 总量上限**；碧蓝一张 4096×4096 纹理压成 PNG 后 ~10-20MB，
  一个包 2 张 + moc3 3MB + 34 个 motion，单包 `files` 可能 40MB+。核心按 prefix 注册 VirtualFS，**内存里 Map<relPath, Blob>**，
  文档没给"超过多少字节就拒绝 / 流式"的口径。
- **怎么猜的**：不设上限（与旧 Blob URL 路径同量级）；靠 AP5 的 prefix revoke 控制峰值。
- **文档该怎么写**：给"单包 files 字节上限"或"无上限、由 revoke 兜底"的明确口径。

## 没卡住、直接照契约实现的点（供交叉核对）

| 点 | 依据 |
|---|---|
| `register` 同步调用、非 ESM 注入式经典脚本 | 插件契约 §三 原文 |
| `id` 重复被拒不覆盖 | 插件契约 §三 规则表 |
| 保留 `probe`/`open` 旧成员做兼容层 | 任务要求"保留现有能力"，宿主未迁移前旧通道仍在用 |
| 两种包型分流（有 model3.json → 原生直用；无 → Unity 集成版重建相对路径 model3） | 资产提供者契约 §一 + 插件现有 index.js 注释的包型定义 |
| 游戏差异走 `profiles/*.json`，代码不写死游戏名 | 插件契约 §5.6 禁止项 + 现有 loadProfile |
| `kind`/`source` 正交，`bundle` 不进 `kind` | 资产提供者契约 §三 原文 |
| `files` 值为真实 Blob/字符串，不塞 Blob URL | 契约 §一 `Map<relPath, Blob|string>`（URL 是旧 open() 的产物，新契约要内容） |
| 失败抛带 `code` 的 Error，不返回缺字段半成品 | 契约 §5.8 + errors.js 现有码表 |
