## 二、旧 `prefix` 缓存：自动失效待频率数据

> 校验与诊断**已上线**：客户端 `1f123cf9`、服务端 `a503f7b8`（命中时校验 prefix，只告警不改行为 + 9 条单测）。
> 原"时序竞争"描述已证伪；真正机制是**同一事实存两份**：prefix 由插件算出，又被 `index.json` 抄了一份，
> 命中时原样返回、不校验。

**剩下这一件（等数据，不是现在做）**：不自动失效的理由是单包解包 9~15s，误判一次就要重解，
代价远大于多几个 HTTP 往返。前置条件是先积累"缓存 prefix 与预期不符"这条 warn 的真实出现次数（日志已就位），
出现 ≥3 次且用户可感知变慢时再决定是否按 fp 失效单条缓存。

## 四、顺手优化项（**不单独排期**，随改动触及的文件顺手处理）

```
以下两类问题量大、单条价值低，但堆着会让代码慢慢变糊 —— 不单独下发任务，
而是在任何一次改动**触及到某个文件**时，顺手把该文件里的这两类处理掉（只限本次真实碰过的文件）。

① 魔数（readability/magic-number-smart，全量审计 693 处）
   · 判据：位掩码/协议常量/数据表**不算**（png.js 的 0xff、common-strings.js 的字符串表都不动）
   · 只处理"出现在 timeout/limit/size/阈值等语义位置、且看不出含义"的数字 → 提命名常量 + 一行注释说明含义
   · 版本号/日期/HTTP 状态码/0 与 1 这类天然合法值不动

② 过短变量名（readability/variable-min-length，全量审计 290 处）
   · 判据：窄作用域里的惯用短名（循环 i/j、坐标 x/y、临时解构）**不算问题**
   · 只处理"跨行存在、或参与业务判断"却用单字母的变量 → 改成能看出含义的名字

纪律：
  · 顺手优化与任务改动**分开说明**（提交信息里单列），便于回看哪些是真正的行为改动
  · 不因顺手优化扩大改动范围：只碰本次已经改到的文件
  · 优化不得改变行为；有疑问就不改（不改都好过改错）
```
