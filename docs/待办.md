## 一、显示缺陷

### 1.1 播放动作时画面「分裂」

**现象**：某类模型播放动作时，画面出现两个错位的形体（早期描述为「重影」，实际是**同一部件被画了两次、
位置错开**，不是半透明叠加）。

**已知**：
- 只在播放动作时出现；静止（暂停在某一帧）看不到 —— 说明与**每帧求值**有关，不是静态资源问题
- 与 PMA 预乘无关的线索：预乘错误通常表现为边缘发黑/发白，不会产生错位体

**排查方向（按可疑度排序）**：
1. 顶点属性槽位重叠：`pixi-app` / Spine 批次里 `a_position` 之外的槽（UV、color、dark color）是否被同一
   缓冲的两次写入覆盖 —— 分裂体常见于「第二组顶点用第一组的变换矩阵」
2. 双渲染：模型是否被同时挂在两个容器（stage + overlay canvas），其中一个用旧变换
3. 动作混合：`mixTime` / 多动画叠加时两条 skeleton 各画一遍（本项目有「播完接谁」的循环语义，需确认不是叠加）

**验收判据**：任选一个能复现的资源，暂停时截图与播放 1 秒后截图逐帧对比 ——
**存在且仅存在一个形体**；且切换动作、切换循环开关都不产生第二个。

### 1.2 部分 Spine 资源出现「眼圈 / 嘴圈」

**现象**：眼周、嘴周出现一圈异色描边（像描了线或透出底色）。

**已知证据**：
- 曾怀疑 PMA 预乘；**棕色尘埃2 的这类问题已修好**（修的是他们那批资源的预乘处理路径）
- 说明不是所有 spine 资源都中招 ⇒ 更可能是**资源本身的 alpha 通道语义差**（预乘 vs 直通混用），
  或某些部件的 atlas 区域边缘有半透明像素被双线性放大后露出来

**排查方向**：
1. 按游戏归类统计：哪些根会出现，是否集中在特定导出工具/版本
2. 对比 `pma` 开关（面板有「PMA 预乘」项）在三档下的差异 —— 若调它能让圈消失/出现，即锁定预乘路径
3. 检查 atlas 页的 `filter`（Linear/Nearest）：眼圈在 Linear 下更明显说明是边缘采样问题（需 padding/bleed 处理）

**验收判据**：同一模型、同一机位，开启/关闭预乘各截一张，眼圈在错误的那一档出现、正确档消失；
且修复后不影响已修好的棕色尘埃2。

## 三、大包首次渲染的长任务（已测一轮：CPU/IO 有真实开销，渲染侧需真机复测）

**测于 2026-10-30，环境：headless chrome + SwiftShader 软渲染 + 3 核** ⇒ 结论必须分两类看。

### 3.1 可信（纯 CPU / IO，与有没有 GPU 无关）

```
解包（worker 内）        unpack.source ≈ 8.1s（files=23）
主线程读包 + postMessage  3,918ms（19.3MB；plugin-host.js:129 读 arrayBuffer → :421 postMessage 给 worker）
PNG 传输                 18.7MB 的 texture_00.png fetch ≈ 1,320ms
散目录 23 个 HTTP 请求    累计 ≈ 3.4s（model3.json 只有 2.6KB 却 802ms；14 个 motion 各 230~283ms）
```

### 3.2 不可信（被软渲染放大，不能当真机判据）

```

⇒ SwiftShader 每帧都慢，几乎肯定是测量环境造成；**改渲染前必须真机复测**
```

### 3.3 候选方向（按职责归属，均未实施）

| 方向 | 归属 | 依据 | 备注 |
|---|---|---|---|
| ① 纹理尺寸由**服务端资产服务**按请求尺寸产出 | 服务端 | 传输+解码可省 1.5~2.5s（CPU 侧） | 解包仍只交原始文件，不改一个像素；需新增尺寸参数与缓存分档 |
| ② 首帧只画主体 + 纹理分批上传 | 渲染层 | 首帧更早可见 | **收益只能在真机量化** |

| ④ worker 自己按 URL 拉包，不在主线程整包读 | 前端装载 | 目标消掉那条 3,918ms | 需 worker 支持按 URL fetch；改动面在 worker 边界 |

给 model2/model3.json 加前端缓存（2.6KB 却 802ms 是服务端首次响应问题）。

## 五、解包超时：13 条 error 全是**后台预热**，改超时不如改分治

**现象（2026-10-30，一份 299 条的 8899 调试日志）**

```
13 条 error 全部是 POST /api/unpack/resolve「signal timed out」（默认 8.5s，且 retries:2）
但用户侧其实很快：
  浏览器 worker 自己解   xianghe_2 11.7MB → 967ms ｜ xinnong_3 13.7MB → 1,917ms ｜ xukufu_2 2.5MB → 1,386ms
  出画时刻              2.3s 点开 → 4.0s 出画
服务端同一批包却要      10.2s（xianghe_2 预热 ms=10,158）｜ 排队后 21.5s（xukufu_2 ms=21,454）
服务端自身 phases       z46_2：readMs 9 ｜ pluginResolveMs 11,979 ｜ writeMs 280
                       ⇒ 慢在**插件 resolve 本体**，不是读盘也不是写盘
```

**根因三条**

```
① 预热复用了前台的超时与重试策略（默认 8.5s + retries:2）
   ⇒ 一次预热 = 最多 3 个请求、3×8.5s 等待、3 条 error 日志
   ⇒ 而服务端并不会因客户端超时停止（resolve 无 abort 处理），它仍会把包解完写进缓存
   ⇒ 所以这些 error 是**纯噪音**，重试还会把串行队列压得更长（自我放大）
② 服务端串行队列：6 次装载会同时排 6 个预热 ⇒ 后面每个都等 >8.5s
③ 重复劳动：浏览器已经解完（1s），服务端再从零解一遍（10~21s）
```

**推荐顺序（按"收益/改动量"排，不是按理论彻底性）**

| 顺序 | 做法 | 判据 |
|---|---|---|
| **①（先做）** | **预热与前台分开治**：warmup 不重试（retries:0）；超时不记 error（降 info，文案说明"服务端仍会解完"）；客户端同时只允许一个预热在途 | 同样操作下 `net.fail` 里的 resolve 超时归零；服务端队列不被重试放大 |
| ~~②（已决定不做）~~ | ~~省掉重复劳动：本地解包成功后不再预热同一个 rel~~ — **保留双解包**，理由见下方「已决定的取舍」 | — |
| **③（治根，改协议）** | **resolve 异步化**：未命中立刻 202 `{state:'unpacking', queuePosition, estimateMs}`，不阻塞 HTTP；客户端订阅/轮询完成事件 | 超时概念不再参与解包；能显示进度；`resolve` 长请求消失 |
| **④（独立立项）** | **查清服务端为何比浏览器慢 10 倍**（同包 10.2s vs 967ms）：vm 沙箱、Buffer 复制、串行排队各占多少 | 若服务端能到 2~3s，①②③ 的压力自然消失；若查不出，则要重新评估"服务端解包缓存"是否值得存在 |

**第二批日志（2026-10-30 14:08，500 条）补充的两条硬证据**

```
① 「预热成功」与「超时」会同时出现 —— 那是**同一次预热的两次尝试**，不是矛盾：
     9.7s  ❌ net.fail resolve  signal timed out      ← 第 1 次尝试被 8.5s 掐断
    11.4s  ✅ unpack.warmup xianghe_2 ms=10158 hit=false  ← 第 2 次（重试）拿到了结果
   原因：scheduleWarmup 显式传了 retries:2，而 postJson 的默认超时是 8500ms、且服务端此时还在解包
   ⇒ **retries 是这些 error 的唯一来源**，去掉重试就不会再出现这种"既超时又成功"

② 同一个 rel 会被**重复预热 4~6 次**（客户端没有按 rel 去重）：
  1000.7s ✅ warmup xukufu_3_hx ms=1969   hit=false
  1000.7s ✅ warmup xukufu_3_hx ms=19933  hit=false
  1000.7s ✅ warmup xukufu_3_hx ms=12770  hit=false
  1000.9s ✅ warmup xukufu_3_hx ms=18598  hit=true
  ⇒ 它们都 join 到服务端**同一个 inflight 解包**（plugin-store 的 inflight Map），
    所以每个都等足 19s、每个都可能被 8.5s 掐断一次、每个再重试一次
  ⇒ 触发点：model-actions.js:393 每次装载都调 warmup()，同一模型被装载多次就排多次
```

### 事件流已实现（C2），但 `phase` 仍是后置的

```
现状：read / resolve / write 三段的耗时都在解包 worker 内部产生，
      主线程只有拿到最终 reply 才知道毫秒数 ⇒ 三条 phase 事件与 done **同一时刻**到达（实测 24.6s 齐发）
影响：事件流的"实时进度"目前只靠 queued/start + 2s 心跳维持观感，分段进度是事后诸葛亮
要真·实时：让 worker 在解包过程中增量上报（与 120s 硬超时、串行队列都要协调），属另一轮
```

### 已决定的取舍：保留"双端同时解包"（2026-10-30）

**背景**：曾考虑让浏览器解完把**产物回传**服务端落盘（省掉服务端重复解包 10~21s），
或退一步"本地解成功后不再预热同一 rel"。两者都**不做**。

**理由**（按权重排）：

```
① 实际使用中**感知不到**双解包的副作用：浏览器那遍 1~2s 出画，服务端那遍是后台任务，
   且预热已按 rel 去重（一个包只解一次），不会成倍放大
② 「该由谁解、什么时候解」这类条件判断**容易出错**：要区分"服务端快/慢、浏览器能不能解、
   缓存有没有、用户是不是马上要"—— 分支一多，判错的排查成本远高于省下的那点 CPU
③ 回传产物要求服务端接受外部写入，必须定信任边界（内容真实性低成本无法校验），
   复杂度与风险都不划算
```

**保留的收益**：服务端解完写缓存 ⇒ 下次（含刷新、换标签页、别的客户端）命中 26ms 直接取。

**另外记一条边界**：前端解包产物**只存在内存 VFS**（无 IndexedDB / Cache API；实测 `/files/*` 是 no-store），
刷新即失 ⇒ 服务端缓存是唯一"跨刷新有效"的那一层，这也是保留双解包的实际价值所在。

**不做的**：只把 8.5s 调大。它能让日志安静，但解决不了"后台任务占用队列、前台请求被拖"的结构问题，
也治不了"同一个包算两遍"。

## 六、`warnings` 里混装「通用能力说明」，与「这一根的问题」同流

**现状**（2026-10-30 由两次实测确认）：

```
GET /api/catalog?root=<任何根>  的 warnings 里必然带一条：
  「有 2 个能解包资源包的插件（unity-live2d-bundle、unity-spine-bundle）：…」
根因：catalog.mjs:522  resolveBundleProvider(plugins) 是 listBundleEntries 的第一句、无条件调用，
      provider.warning 被直接塞进 warnings
⇒ 它与"这根路径不存在/扫描失败"这类根级问题混在同一个数组里
```

**已经在做的规避**：根级问题单独出新字段 `rootWarning`（已完成，见接口清单 §catalog 行），
前端判"这根有没有问题"只认它、**不拿 warnings 拼因果**（拿它会拼出「因为有 2 个插件所以没模型」）。

**剩下这件事没做**（属破坏性变更，等有第二个消费方再动）：

```
把"全局能力说明"从 warnings 移出 → 顶层 capabilities（或 providers 字段）
warnings 从此只装"与本次请求相关的提示"
影响面：所有 warnings 消费方都要跟着改（前端 roster/list.js、url-params、接口文档、测试）
```

**判据（若将来做）**：一个路径正常的根，`warnings` 为空数组；`capabilities` 里有那两条插件说明。

## 七、旧 `prefix` 缓存：校验与诊断已上线，**自动失效待频率数据**

**已完成（2026-10-30，两个提交）**

```
客户端 1f123cf9：miss 的 warn 扩成带 prefix / 该前缀已注册文件数（新增只读 vfs.prefixFileCount）/
                 尝试过的候选列表；前缀 0 文件时单独一句判定语。
                 顺带修 candidatesFor 候选去重（容器模型里 vfsPrefix 与 entryDir 常是同一目录，
                 原来会把同一地址试两遍 ⇒ miss 计数虚高 + 诊断信息误导）。
服务端 a503f7b8：命中时校验 prefix —— expectedPrefix / prefixMismatch 两个导出纯函数 + 一行 warnIfPrefixStale，
                 只告警不改行为（返回值与状态码零变化）；新增 9 条单测（含"现存 24 份缓存全部一致"门禁）。
```

**原"时序竞争"的描述已证伪**：注册与首次 resolve 只差 1ms、键形态逐字一致、四轮实测 miss 均为 0。
真正的机制是**同一事实存两份**：prefix 由插件算出，又被 `index.json` 抄了一份，命中时原样返回、不校验。

**剩下这一件（需要数据，不是现在做）**

```
不自动失效的理由：单包解包 9~15s，一旦误判就把用户已解好的包重解一遍，代价远大于"多几个 HTTP 往返"。
前置条件：先积累"缓存 prefix 与预期不符"这条 warn 的真实出现次数（新日志已就位）。
把出现 ≥3 次且用户可感知变慢的场景再拿出来，决定要不要按 fp 失效单条缓存。
```

**已知边界**：warn 那一层没有自动化（peek 命中需凑齐含 pluginVersion 的指纹，换环境就看运气，
且要动真实缓存）；判据本身已由纯函数单测钉死，外加"现存缓存全部一致"的门禁。
