## 一、PMA「自动」档漏了"运行时是否支持直通"这个判据

**现象**：同一模型（棕色尘埃2 char021301），同一档位「自动」——
面板显示"像素检测: 非预乘 / 直通支持: 支持 / **实际生效: Unpack**"时画面出白斑；
强制选「非预乘」时"实际生效: Straight"，显示正常。

**根因**（`src/web/engine/pma.js` `resolvePmaInfo`）：显式 `straight` 分支会检查 `supportsStraight`，
`auto` 分支**不检查** —— `auto === false`（检测为非预乘）就无条件走 `upload`（上传时预乘）。

```
case 'straight': supportsStraight ? straight : upload(degraded:true)     ← 有判据
case 'auto':     if (auto === false) return upload(...)                  ← 无判据
```

**修法**：`auto === false` 且 `supportsStraight === true` 时，返回与显式 `straight` 相同的对象；
其余分支一律不动（含 `auto === true/null` ⇒ premultiplied 不预乘）。

**验收**：纯函数单测钉四种组合 + 真机上该模型"自动"下应显示 Straight 且与强制非预乘肉眼一致 +
回归 NIKKE c072_00（atlas pma:true）不能变差。

## 二、`index.json` 里的 `pluginId` 与实际产物 `prefix` 不一致（真实 2 例）

**现象**（`test/unpack-prefix-check` 门禁真实命中，非误报）：

```

`pluginId` 是否分别正确；若都写成同一个，即可确认是记录处取错。

## 四、大包首次渲染的长任务（已测一轮：CPU/IO 有真实开销，渲染侧需真机复测）

**测于 2026-10-30，环境：headless chrome + SwiftShader 软渲染 + 3 核** ⇒ 结论必须分两类看。

### 4.1 可信（纯 CPU / IO，与有没有 GPU 无关）

```
解包（worker 内）        unpack.source ≈ 8.1s（files=23）
主线程读包 + postMessage  3,918ms（19.3MB；plugin-host.js:129 读 arrayBuffer → :421 postMessage 给 worker）
PNG 传输                 18.7MB 的 texture_00.png fetch ≈ 1,320ms
散目录 23 个 HTTP 请求    累计 ≈ 3.4s（model3.json 只有 2.6KB 却 802ms；14 个 motion 各 230~283ms）
```

### 4.2 不可信（被软渲染放大，不能当真机判据）

```
纹理上传 / 绘制帧率：mount 后单条 2,148ms、散目录持续 ~125ms/帧（≈8fps）
⇒ SwiftShader 每帧都慢，几乎肯定是测量环境造成；**改渲染前必须真机复测**
```

### 4.3 候选方向（按职责归属，均未实施）

| 方向 | 归属 | 依据 | 备注 |
|---|---|---|---|
| ① 纹理尺寸由**服务端资产服务**按请求尺寸产出 | 服务端 | 传输+解码可省 1.5~2.5s（CPU 侧） | 解包仍只交原始文件，不改一个像素；需新增尺寸参数与缓存分档 |
| ② 首帧只画主体 + 纹理分批上传 | 渲染层 | 首帧更早可见 | **收益只能在真机量化** |
| ③ motion 时长预取延到首帧之后 | 前端装载 | 散目录实测可省 2~3s（3.4s 里 14 个 motion 占大头） | 底栏动作时长晚一拍显示 |
| ④ worker 自己按 URL 拉包，不在主线程整包读 | 前端装载 | 目标消掉那条 3,918ms | 需 worker 支持按 URL fetch；改动面在 worker 边界 |

**不建议**：把 Live2D 初始化/解码/上传搬进解包 worker（越界）；继续优化 LZMA 解压（解包已在 worker）；
给 model2/model3.json 加前端缓存（2.6KB 却 802ms 是服务端首次响应问题）。

## 五、浏览器侧仍无峰值准入（暂缓：等真实案例再动）

> 细节见 `docs/设计/解包搬进worker线程.md` §4.1 与 `docs/参考/接口清单.md` §1.3。

**现状**：

```
唯一闸门 src/web/infra/plugin-host.js:297 只看**压缩后** file.size > MAX_BUNDLE_BYTES(2GB)
:700 注释仍明写「服务端 capacity 不参与前端解包准入」
⇒ 前端 worker 解包能把 renderer 进程顶穿，与服务端有没有峰值表无关

## 六、事件流已上线；只剩「`phase` 后置」一项

> 已完成：预热分治（`24cfbc55`）、事件流契约/设计/服务端/前端（`629479ae` / `cdfd9ece` / `47e9f557`）。
> 已决定不做：产物回传落盘、省掉服务端预热（理由见 5.2）；查清"服务端慢 10 倍"（理由见 5.3）。

### 6.1 `phase` 仍是后置的（真·实时进度需另一轮）

```
read / resolve / write 三段的耗时都在解包 worker 内部产生，主线程只有拿到最终 reply 才知道毫秒数
⇒ 三条 phase 事件与 done 同一时刻到达（实测 24.6s 处 13ms 内齐发）
⇒ 当前进度观感靠 queued/start + 2s 心跳维持；分段耗时只能看 done.phases
要真·实时：让 worker 在解包过程中增量上报（与 120s 硬超时、串行队列都要协调）
```

### 6.2 已决定的取舍：保留"双端同时解包"

**背景**：曾考虑让浏览器解完把**产物回传**服务端落盘（省掉服务端重复解包 10~21s），
或退一步"本地解成功后不再预热同一 rel"。两者都**不做**。

**理由**（按权重排）：

```
① 实际使用中**感知不到**双解包的副作用：浏览器那遍 1~2s 出画，服务端那遍是后台任务，
   且预热已按 rel 去重（一个包只解一次），不会成倍放大
② 「该由谁解、什么时候解」这类条件判断**容易出错**：要区分"服务端快/慢、浏览器能不能解、
   缓存有没有、用户是不是马上要"—— 分支一多，判错的排查成本远高于省下的那点 CPU
③ 回传产物要求服务端接受外部写入，必须定信任边界（内容真实性低成本无法校验），
   复杂度与风险都不划算
```

**保留的收益**：服务端解完写缓存 ⇒ 下次（含刷新、换标签页、别的客户端）命中 26ms 直接取。

**另外记一条边界**：前端解包产物**只存在内存 VFS**（无 IndexedDB / Cache API；实测 `/files/*` 是 no-store），
刷新即失 ⇒ 服务端缓存是唯一"跨刷新有效"的那一层，这也是保留双解包的实际价值所在。

### 6.3 已决定不查：服务端为何比浏览器慢 10 倍

```
理由是部署差异属常态（浏览器按用户配置、服务端按部署配置），不针对某一部署做优化。
且双解包下"服务端慢"只影响缓存填充速度，不影响用户出画（浏览器那遍 1~2s 已完成）。
```

## 七、`warnings` 里混装「通用能力说明」，与「这一根的问题」同流

**现状**（2026-10-30 由两次实测确认）：

```
GET /api/catalog?root=<任何根>  的 warnings 里必然带一条：
  「有 2 个能解包资源包的插件（unity-live2d-bundle、unity-spine-bundle）：…」
根因：catalog.mjs:522  resolveBundleProvider(plugins) 是 listBundleEntries 的第一句、无条件调用，
      provider.warning 被直接塞进 warnings
⇒ 它与"这根路径不存在/扫描失败"这类根级问题混在同一个数组里
```

**已经在做的规避**：根级问题单独出新字段 `rootWarning`（已完成，见接口清单 §catalog 行），
前端判"这根有没有问题"只认它、**不拿 warnings 拼因果**（拿它会拼出「因为有 2 个插件所以没模型」）。

**剩下这件事没做**（属破坏性变更，等有第二个消费方再动）：

```
把"全局能力说明"从 warnings 移出 → 顶层 capabilities（或 providers 字段）
warnings 从此只装"与本次请求相关的提示"
影响面：所有 warnings 消费方都要跟着改（前端 roster/list.js、url-params、接口文档、测试）
```

**判据（若将来做）**：一个路径正常的根，`warnings` 为空数组；`capabilities` 里有那两条插件说明。

## 八、旧 `prefix` 缓存：自动失效待频率数据

> 校验与诊断**已上线**：客户端 `1f123cf9`（miss warn 带 prefix / 已注册文件数 / 候选列表 + 候选去重）、
> 服务端 `a503f7b8`（命中时校验 prefix，只告警不改行为 + 9 条单测）。
> 原"时序竞争"描述已证伪（注册与首次 resolve 差 1ms、四轮实测 miss 均为 0）；
> 真正的机制是**同一事实存两份**：prefix 由插件算出，又被 `index.json` 抄了一份，命中时原样返回、不校验。

**剩下这一件（等数据，不是现在做）**

```
不自动失效的理由：单包解包 9~15s，误判一次就把用户已解好的包重解一遍，代价远大于"多几个 HTTP 往返"。
前置条件：先积累"缓存 prefix 与预期不符"这条 warn 的真实出现次数（日志已就位）。
把出现 ≥3 次且用户可感知变慢的场景再拿出来，决定要不要按 fp 失效单条缓存。
```

**已知边界**：warn 那层无自动化（peek 命中需凑齐含 pluginVersion 的指纹，换环境看运气且要动真实缓存）；
判据本身由纯函数单测钉死，外加"现存缓存全部一致"的门禁。
