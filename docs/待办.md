## 一、插件多语言运行时（`exec`）未实现

**目标**：`asset-provider` 不限于 JS，可用 Python 等子进程实现。

**现状**：抽象层已落地（`unpack/runtime/index.mjs` 选择器 + 门禁、`node-vm.mjs`、`exec.mjs` 骨架、
`config/plugin-runtime.json` 的 `allowExecRuntime`、12 条适配器用例），**`exec` 本体仍固定抛
`EXEC_RUNTIME_NOT_IMPLEMENTED`**。

**未做**：spawn 本体（超时杀、僵尸收、大 payload 走临时文件还是流）、帧协议实现
（设计稿在 `设计/插件运行时与多语言.md` §四）、一个真实的非 JS 插件。

**为什么故意不实现**：协议细节必须真实现才能定稿；先做「能跑但没想清楚」的半成品比不做更危险。
当前两个插件都是 node 运行时，没有「现在就要靠 exec 才能解开的包」。

**边界（做之前先认）**：插件进程必须能被宿主杀死（超时/内存越界），不留僵尸；帧协议要能承载进度与
错误码（不只回最终结果）；依赖自带（venv / `.deps`），不要求宿主全局装包。

## 二、事件流：`phase` 仍是后置的（真·实时进度需另一轮）

```
read / resolve / write 三段耗时在解包 worker 内部产生，主线程只有拿到最终 reply 才知道毫秒数
⇒ 三条 phase 事件与 done 同一时刻到达（实测 24.6s 处 13ms 内齐发）
⇒ 当前进度观感靠 queued/start + 2s 心跳维持；分段耗时只能看 done.phases
```

**要真·实时**：让 worker 在解包过程中增量上报，与 120s 硬超时、串行队列都要协调。

**已定的取舍（不在此跟踪，见 `设计/解包进度事件流.md`）**：保留"双端同时解包"；不做产物回传落盘；
不查服务端比浏览器慢 10 倍的原因。

## 三、清单缓存缺「生成者版本」：改解析代码不会失效

```
config/models/spine.<rootId>.json 是扫描结果的落盘缓存
失效判据只有 dirStamps（目录增删）——**解析代码改了不会失效**（已核实：无任何生成者版本字段）
现场：修好「atlas 首行 BOM 丢第一页」后界面仍是旧清单（textureCount 仍为 1），
      必须手工删掉 config/models/spine.nikke.json 才生效
```

**要做的**：给清单加「生成者版本」字段（解析器版本/内容摘要），读缓存时一并比对，不匹配即重建。
只靠目录签名不够——它只能感知文件增删，感知不到"我们对同一批文件的解析变了"。

## 四、后台形态探测会阻塞事件循环（实测，未修）

```
探测在服务端主线程同步解析包体（单包最大 40MB），按包分片阻塞：
  实测 8 包 / 4345ms（约 543ms/包），期间单次 HTTP 请求被压到 311ms
  曾观测到单批 43847ms；无头浏览器首次加载页面两次 30s 超时，批次结束即恢复
```

**影响**：探测由 catalog 请求触发，用户正常浏览时可能被拖慢。

**方向（按代价排）**：
1. 根治：把单包解析挪进 worker（改动面在探测模块边界）
2. 缓解：降低单包体积上限（超限留 `unknown`，不阻塞）
3. 缓解：仅在空闲时探测（无在途请求且距上次请求 > N 秒）

**判据**：探测批次运行时，`/api/ready` 与 `/api/catalog` 的 P95 延迟不高于无探测时 +10ms。

## 五、旧 `prefix` 缓存：自动失效待频率数据

> 校验与诊断**已上线**：客户端 `1f123cf9`（miss warn 带 prefix / 已注册文件数 / 候选列表）、
> 服务端 `a503f7b8`（命中时校验 prefix，只告警不改行为 + 9 条单测）。
> 原"时序竞争"描述已证伪；真正机制是**同一事实存两份**：prefix 由插件算出，又被 `index.json` 抄了一份，
> 命中时原样返回、不校验。

**剩下这一件（等数据，不是现在做）**：不自动失效的理由是单包解包 9~15s，误判一次就要重解，
代价远大于多几个 HTTP 往返。前置条件是先积累"缓存 prefix 与预期不符"这条 warn 的真实出现次数（日志已就位），
出现 ≥3 次且用户可感知变慢时再决定是否按 fp 失效单条缓存。

## 六、大包首帧体验：已量化，候选方向均未实施

**已测（headless + SwiftShader + 3 核）**：解包 8.1s（files=23）、主线程读包 + postMessage 3,918ms（19.3MB）、
PNG 传输 1,320ms（18.7MB）、散目录 23 个请求累计 3.4s（其中 14 个 motion 占大头）。
软渲染下的帧率数据不可信，**改渲染前必须真机复测**。

**候选方向（按职责）**：① 纹理由服务端按请求尺寸产出（省 1.5~2.5s CPU 侧）；② 首帧只画主体 + 纹理分批；
③ motion 时长预取延到首帧之后（散目录可省 2~3s）；④ worker 自己按 URL 拉包，不在主线程整包读（消掉 3,918ms）。

**不建议**：把 Live2D 初始化/解码/上传搬进解包 worker；继续优化 LZMA 解压；给 model2/model3.json 加前端缓存
（2.6KB 却 802ms 是服务端首次响应问题）。

## 附：已决定不做（不再跟踪，留个理由备查）

| 项 | 结论与理由 |
|---|---|
| 浏览器侧解包峰值准入 | 服务端表已宽松，前端再加一套估算等于又养一套要标定的系数，收益低、维护成本高。等真出现「前端解大包把页面顶崩」的实例，按那次实测做，不预先猜系数 |
| 浏览器解完回传产物、或本地成功就不预热 | ①实际感知不到双解包副作用（浏览器 1~2s 出画，服务端是后台任务且按 rel 去重）②"该谁解/何时解"分支一多，判错成本高于省下的 CPU ③回传要求服务端接受外部写入，信任边界复杂 |
| 查清「服务端比浏览器慢 10 倍」 | 部署差异属常态（浏览器按用户配置、服务端按部署配置），不为某一部署做优化；双解包下只影响缓存填充速度，不影响出画 |
