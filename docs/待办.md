## 一、显示缺陷

### 1.1 播放动作时画面「分裂」

**现象**：某类模型播放动作时，画面出现两个错位的形体（早期描述为「重影」，实际是**同一部件被画了两次、
位置错开**，不是半透明叠加）。

**已知**：
- 只在播放动作时出现；静止（暂停在某一帧）看不到 —— 说明与**每帧求值**有关，不是静态资源问题
- 与 PMA 预乘无关的线索：预乘错误通常表现为边缘发黑/发白，不会产生错位体

**排查方向（按可疑度排序）**：
1. 顶点属性槽位重叠：`pixi-app` / Spine 批次里 `a_position` 之外的槽（UV、color、dark color）是否被同一
   缓冲的两次写入覆盖 —— 分裂体常见于「第二组顶点用第一组的变换矩阵」
2. 双渲染：模型是否被同时挂在两个容器（stage + overlay canvas），其中一个用旧变换
3. 动作混合：`mixTime` / 多动画叠加时两条 skeleton 各画一遍（本项目有「播完接谁」的循环语义，需确认不是叠加）

**验收判据**：任选一个能复现的资源，暂停时截图与播放 1 秒后截图逐帧对比 ——
**存在且仅存在一个形体**；且切换动作、切换循环开关都不产生第二个。

### 1.2 部分 Spine 资源出现「眼圈 / 嘴圈」

**现象**：眼周、嘴周出现一圈异色描边（像描了线或透出底色）。

**已知证据**：
- 曾怀疑 PMA 预乘；**棕色尘埃2 的这类问题已修好**（修的是他们那批资源的预乘处理路径）
- 说明不是所有 spine 资源都中招 ⇒ 更可能是**资源本身的 alpha 通道语义差**（预乘 vs 直通混用），
  或某些部件的 atlas 区域边缘有半透明像素被双线性放大后露出来

**排查方向**：
1. 按游戏归类统计：哪些根会出现，是否集中在特定导出工具/版本
2. 对比 `pma` 开关（面板有「PMA 预乘」项）在三档下的差异 —— 若调它能让圈消失/出现，即锁定预乘路径
3. 检查 atlas 页的 `filter`（Linear/Nearest）：眼圈在 Linear 下更明显说明是边缘采样问题（需 padding/bleed 处理）

**验收判据**：同一模型、同一机位，开启/关闭预乘各截一张，眼圈在错误的那一档出现、正确档消失；
且修复后不影响已修好的棕色尘埃2。

没有任何「现在就要靠 exec 才能解开的包」。

**先把边界说清楚**：
- 插件进程必须能**被宿主杀死**（超时/内存越界），不能留僵尸

- 依赖自带（venv / `.deps`），不要求宿主全局装包

## 三、大包首次渲染的长任务（与 LZMA 解压无关）

**现象**：LZMA 解压搬进 Worker 后，主线程解压相关长任务已消失，但**解压之后**仍有 1.5s / 3.3s 的长任务。

**对照证据（关键）**：同页面点开 **LZ4** 包 `aijier_3`（解压后 42MB、同步解仅 **169ms**）⇒
页面线程直接占死 30s 超时。也就是说**大包的 live2d 初始化 + 首次渲染本身就是重活**，与压缩算法无关。

**范围**：61 个 LZMA 包解压后 2.76~33.4MB，加上 LZ4 的 42MB 包，都属这一类。

**尚未定位的一条**：LZMA 包 `aierdeliqi_5` 在"解压起步附近"有一条 **3362ms**（at=307ms），
与解压已不在同线程这一事实矛盾，嫌疑集中在主线程的 **Blob 重建 + VFS 注册**（8.28MB × 20 个文件）
或"worker 未就绪前先同步跑了一遍"。**需要分阶段打点定位，不许凭怀疑改代码。**

**方向（待定位后再定）**：
- 若是 Blob 重建 / VFS 注册 ⇒ 延迟建 Blob（真正取文件时再建）、或改成按需切片
- 若是渲染期 ⇒ 与上面"大包首次渲染"合并处理（可能要做首帧降级/分帧构建）

## 四、LZMA 解压内存膨胀 46 倍（已定位，暂缓处理）

**2026-10-29 用户机器 OOM 后调查，实测数据（勿重复测量，直接看这里）：**

```
单包 2.8MB 解压产物：RSS 52 → 176MB，峰值 +128MB ⇒ **膨胀 46 倍**（耗时 2285ms）
按比例推 21MB 包 ≈ 970MB，与 probe 缓存里的实测记录（21MB → 1195MB）吻合
```

**不是泄漏 —— 是"高水位不还给系统"**（这一条最容易被误判）：

```
同一进程反复解同一个包 5 次（每轮 global.gc + 等 300ms）：
  第1轮 净涨 55MB ｜ 第2~5轮 净涨 0~1MB ｜ 每轮 GC 后 heapUsed 仅 4MB（产物 2.8MB）
⇒ 对象都回收了，没有泄漏；但 RSS 从 51 涨到 106 后再也不回去
⇒ 那是 V8 保留的空闲堆页，操作系统层面收不回
⇒ 21MB 包会让该进程 RSS **长期停在 ~800MB~1GB**
```

**OOM 的真正机制：多个进程各自留一份高水位叠加**

```
8804 服务端 ／ 8899 测试实例 ／ chrome renderer ／ chrome worker（新加的 LZMA Worker）
／ DSH 宿主（1.4GB）／ 以及我们自己的批量测量（126 包全量扫、--repeat 3 子进程）
每个单看都"合理"，叠在 8GB 机器上就不够
```

**根因（代码层）**：`lib/lzma-d-min.js` 是 **worker 版构建**，`decompress` 返回**普通 Array**
（内部 `function o(e){var r=[];return r[e-1]=void 0,r}` 造的是 holey array），
2.8M 个小整数在 V8 里不是紧凑存储；随后 `Uint8Array.from(out)` 再复制一份。

**修复顺序（准入不是第一优先 —— 它只能防单次超限，防不了高水位留存）**：

```
1. 换解码器：写进**预分配 Uint8Array** 的 wasm 实现（不再产生 holey Array）
   ⇒ 峰值 46× → 3~5×，21MB 包高水位从 ~1GB 降到 ~150MB —— 这是根因修复
2. 浏览器 worker 侧按预测峰值限制：现在**完全没有准入**
   （plugin-host.js:700 注释明写"服务端 capacity 不参与前端解包准入"；
     唯一闸门 :297 只看**压缩后**大小 file.size > MAX_BUNDLE_BYTES）
3. 测量纪律：重活只在测试实例、串行、`--max-old-space-size` 设上限；
   禁止在用户正在用的实例上跑全量扫描（我这次跑 126 包扫就是叠加上去的因素之一）
```

#### 第 1 批测量结论（2026-10-29 复核，只测未改）

```
61 个 LZMA 包仍在（全在 azurlane_bundle 根；94 个 UnityFS = LZMA 61 / none 24 / LZ4 8 / LZ4HC 1）
LZMA 解压后：min 2.76 / p50 6.69 / p90 18.04 / max 33.40 MB
```

**46× 膨胀复现成立**（`huonululu_3` 2.76MB）：两次独立运行峰值增量 112.9 / 132.1MB ⇒ **40.3~47.2×**，
耗时 2.4~2.6s —— 与上面记的 128MB / 46× / 2.29s 落在同一波动带内。

**「不是泄漏、是高水位」也复现成立**：5 轮净涨 `+52.3 / +2.0 / +3.0 / +0.1 / −0.2` MB，
heapUsed 5.3~5.9MB，RSS 停在 ~115MB 不回落。

> ⚠️ **测量陷阱（复测时会踩）**：判「泄漏 vs 高水位」必须**多轮 GC 后再看 heapUsed**。
> 只做一次 `global.gc()` 会读到 `heapUsed 553MB`，看着像泄漏；再 GC 3 轮降到 5.5MB、
> `arrayBuffers 0` ⇒ 那是 GC 滞后，不是持有。

**基线表（`--basis inproc` 同进程串行 = 服务端形态）**

| 包 | 解压MB | 耗时ms | 峰值增量MB | 绝对峰值(HWM)MB |
|---|---|---|---|---|
| huonululu_3 | 2.80 | 2584 | 112.9 | 171.1 |
| dujiaoshou_6 | 7.90 | 5607 | 124.3 | 295.4 |
| xuefeng | 12.90 | 5764 | 184.4 | 479.8 |
| shengluyisi_2 | 20.90 | 5138 | 184.0 | 663.8 |
| z46_2 | 33.40 | 12786 | 334.4 | **998.3** |

> 「峰值增量」受进程已有高水位影响（inproc 串行累加）；**决定 OOM 的是「绝对峰值」那一列** ——
> 33.4MB 单包就把进程推到 998MB。

#### 两条新发现（第 2 批的输入）

**① 服务端 LZMA 峰值表存在，但余量是 1.0（无缓冲）**

```
plugins/unity-live2d-bundle/index.js:702  LZMA_PEAK_POINTS
  [[2.8,171],[5,244],[6.5,295],[8.5,419],[9.4,419],[17.1,452],[18.7,732],[21.4,732],[33.4,995]]
:706  const PEAK_MARGIN = 1.0;
```

注释给的理由是「表里存的是每包 3 轮独立干净进程的最大值，已是对最坏情况的直接测量，
再乘系数只是在猜抖动幅度」。**这个理由在表点足够密时成立**，但下表点并不密 —— 见 ②。

**② 表点稀疏导致实测低估：`xuefeng`（12.86MB）**

```
9.4MB → 419 ／ 17.1MB → 452    这两点之间跨 7.7MB 没有任何实测点
线性插值给 433.8 ⇒ 声明 434MB；而该包实测峰值在 479.8~506.6MB 之间（两次测量，待复核）
⇒ 至少低估 10%，按 506.6 算低估 17%
```

**根因不是 margin，是表点稀疏**：加 margin 只是掩盖。正确修法是
**补测 9.4~17.1MB 这段**（或在插值时取「较高邻居」而非线性，但那对 12.86MB 仍不够）。

**③ 顺带：解压过程实际有**三份**拷贝，不止两份**

```
解码器内部 Array（holey，`r[e-1]=void 0` 造）→ unityfs.js 的 `Uint8Array.from(out)`
→ 传入 target 时还有 `target.set(bytes, targetOffset)`
⇒ 2.8MB 包也要同时存在 3 份，这是 46× 的直接来源
```

#### 一处必须澄清的边界（避免第 2 批做错）

上面「修复顺序」第 2 条讲的是**浏览器 worker 侧**没有峰值准入，**与服务端有 LZMA 表不矛盾**：

```
服务端：已有 LZMA_PEAK_POINTS 专用表（z46_2 声明 996 vs 实测 998.3，准）
浏览器：src/web/infra/plugin-host.js:700 仍明写「服务端 capacity 不参与前端解包准入」，
        唯一闸门 :297 只看**压缩后**大小 file.size > MAX_BUNDLE_BYTES(2GB)
⇒ 两侧是两件事，浏览器侧那条**仍然完全没有准入**，第 2 批不能跳过
```

## 五、`stage.pause()` 之后 `frames` 仍在增长（未查清，待取证）

**现象**（2026-10-29 由前端成员在验收看门狗时偶然撞到，如实上报未深挖）：

```
spine 模型加载后调用 stage.pause() ⇒ st.frames 仍在涨（一次实测 1130 → 1252，涨 122）
而 canvas-engine.js:78 明确写着 `if (st.paused) return;  // 暂停：不再排帧`
⇒ 按代码不该涨，实测在涨 ⇒ 要么 stop 没生效，要么还有第三条路径在加 frames
```

**已排查（我做的，未到底）**：

```
项目里有**三套 rAF**：
  ① src/web/spine/canvas-engine.js:80   st.frameRaf（帧计数循环）—— stopFrameTick 会 cancelAnimationFrame ✅
  ② src/web/engine/render-frame.js:66   engine.animationId（引擎主循环）—— stopLoop 会 cancelAnimationFrame ✅
  ③ src/web/engine/gl-driver.js:55      refreshResolution 的一次性 rAF（不影响 frames）
stage.pause() 调用链：st.engine.stop() → stopLoop → cancelAnimationFrame；st.paused=true；stopFrameTick；repaintOnce（只 +1）
⇒ 两套循环都会被取消，理论上 frames 最多涨 1。涨 122 ⇒ 与代码矛盾，需实测取证
```

**下一步取证建议**：

```
· 在 pause() 后打点：分别记录 st.frameRaf / st.engine.animationId 是否仍非 0（有没有被重新排上）
· 怀疑方向：repaintOnce 被外部周期性调用；或 engine.stop 拿到的不是同一实例（重载后 st.engine 换了）
· 判据：pause 后 3 秒内 frames 增量 == 1 为正常（那一次是 repaintOnce 的补帧）
```

**影响**：看门狗的自愈动作是 `stage.pause(); stage.play()`。
若 pause 真的不生效，那这套"自愈"只是空转 —— 但现在误报已修，自愈不再被误触发，影响仅限于"真卡死时自愈可能无效"。
