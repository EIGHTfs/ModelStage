## 一、显示缺陷

### 1.1 播放动作时画面「分裂」

**现象**：某类模型播放动作时，画面出现两个错位的形体（早期描述为「重影」，实际是**同一部件被画了两次、
位置错开**，不是半透明叠加）。

**已知**：
- 只在播放动作时出现；静止（暂停在某一帧）看不到 —— 说明与**每帧求值**有关，不是静态资源问题
- 与 PMA 预乘无关的线索：预乘错误通常表现为边缘发黑/发白，不会产生错位体

**排查方向（按可疑度排序）**：
1. 顶点属性槽位重叠：`pixi-app` / Spine 批次里 `a_position` 之外的槽（UV、color、dark color）是否被同一
   缓冲的两次写入覆盖 —— 分裂体常见于「第二组顶点用第一组的变换矩阵」
2. 双渲染：模型是否被同时挂在两个容器（stage + overlay canvas），其中一个用旧变换
3. 动作混合：`mixTime` / 多动画叠加时两条 skeleton 各画一遍（本项目有「播完接谁」的循环语义，需确认不是叠加）

**验收判据**：任选一个能复现的资源，暂停时截图与播放 1 秒后截图逐帧对比 ——
**存在且仅存在一个形体**；且切换动作、切换循环开关都不产生第二个。

### 1.2 部分 Spine 资源出现「眼圈 / 嘴圈」

**现象**：眼周、嘴周出现一圈异色描边（像描了线或透出底色）。

**已知证据**：
- 曾怀疑 PMA 预乘；**棕色尘埃2 的这类问题已修好**（修的是他们那批资源的预乘处理路径）
- 说明不是所有 spine 资源都中招 ⇒ 更可能是**资源本身的 alpha 通道语义差**（预乘 vs 直通混用），
  或某些部件的 atlas 区域边缘有半透明像素被双线性放大后露出来

**排查方向**：
1. 按游戏归类统计：哪些根会出现，是否集中在特定导出工具/版本
2. 对比 `pma` 开关（面板有「PMA 预乘」项）在三档下的差异 —— 若调它能让圈消失/出现，即锁定预乘路径
3. 检查 atlas 页的 `filter`（Linear/Nearest）：眼圈在 Linear 下更明显说明是边缘采样问题（需 padding/bleed 处理）

**验收判据**：同一模型、同一机位，开启/关闭预乘各截一张，眼圈在错误的那一档出现、正确档消失；
且修复后不影响已修好的棕色尘埃2。

## 五、容器（资源包）相关的缺口

### 5.1 Cubism 2（`.moc`）容器不被支持 ⇒ 旧包点开必失败

**现象**：`azurlane_bundle` 根下的 `live2d/` 子目录里那批旧包（文件日期 2020-2023）点开报
「插件判定不处理该文件」（服务端 `reason: not-handled`）。

**实测证据**：
```
根层   aimierbeierding_2        4.6MB  → ✅ 解出 19 文件（model3.json）
嵌套   live2d/aimierbeierding_2 2.6MB  → ❌ not-handled
嵌套   live2d/aierdeliqi_5      2.2MB  → ❌ not-handled
嵌套   live2d/ailunsamuna_2            → ❌ not-handled
```
同名的根层与嵌套文件**体积不同**（4.6 vs 2.6MB），是两批不同年代的资源，不是 id 冲突。

**根因**：容器插件的 `canHandle` 按内容签名判型 ——
live2d 要求包内有 `moc3`、spine 要求包内有 `.skel`。这批旧包极可能是 **Cubism 2（`.moc`）**，
两种签名都不满足，于是两个插件都不认领。

**这不是回归**：收紧 `canHandle` 之前，live2d 插件会"硬认领"这类包，然后在 extract 阶段报
找不到 moc3；收紧之后直接说"没人能处理"，报错更早更准。**前后都加载不了**。

**要支持的话（新功能，非 bug）**：在 live2d 插件里补 Cubism 2 的提取路径
（`.moc` + `.mtn` + 贴图，参考 `DestinyChildLive2D` 那套结构），并让 `canHandle` 认 `.moc`。
需要配套 fixture 与等价验证。

## 九、UnityFS 的 LZMA 压缩分支未支持 ⇒ 约一半资源包打不开

**实测**（扫 azurlane_bundle 94 + nikke_2 29 = 123 个真实容器，走生产探针 `probeBundleBytes`）：

```
47(ETC2_RGBA8)  25 个包   正常
 4(RGBA32)       18 个包   正常
25(BC7)          15 个包   supported=false（不在 FORMATS 里，判得对）
 5(ARGB32)        1 个包   正常
—— 另有 64 个包 probe 直接失败（约 52%）——
  57 个  block[0] 使用 LZMA 压缩，本插件尚未支持该分支（已支持 none / LZ4）
   4 个  blocksInfo 使用 LZMA 压缩
   3 个  节点 CAB-xxx 越界：offset=3 size=117~611 / size=数据区大小
```

**根因（2026-10-28 调研更正，我原推断错了一处）**：

```
只补 LZMA 能救 **61 / 64**（95%）：blocksInfo 用 LZMA 的 4 个 + block 数据用 LZMA 的 57 个
剩下 3 个（aidang_2 / banrenma_2 / xianghe_2）**与 LZMA 无关**：
  实测头部 version=6、blocksInfo 的 csz == usz == 91（压缩类型 none，flags=0x40）
  ⇒ 它是**未压缩的** blocksInfo，不存在"被当明文读坏"这回事
  ⇒ 是 version 6 布局的独立解析缺陷（表现为节点表 offset=3、size 恰好等于数据区）
原待办里"三类可能同源"的推断作废；这 3 个要单独立项。
```

**为什么难**：Node 内置没有 LZMA（`zlib` 只有 gzip/deflate/brotli）。三条路：

```
① 自写 LZMA 解码器 —— 工作量大（LZMA 状态机 + 范围解码器，通常上千行）
② vendor 一个单文件 JS 实现（如 lzma-js / lzma-decode 的裁剪版）—— 注意许可与体积
③ 调系统 xz/lzma —— 不推荐：跨平台、noexec 挂载、Windows 缺失，且违背"不依赖外部工具"
```

**调研结论（见 docs/设计/2026-10-28UnityFS-LZMA支持调研.md）**：

```
格式：UnityFS 的 LZMA = [5 字节 props][raw LZMA1 流]，**没有** .lzma(alone) 的 8 字节长度
      技巧：自己补上 8 字节未压缩长度（小端）⇒ 任何标准 .lzma 解码器都能吃
      props 实测恒为 lc=3 lp=0 pb=2 dictSize=512KB（4 个样本一致）
选型：lzma@2.3.2 的 src/lzma-d-min.js = **现成 IIFE**、6956B、零依赖、MIT、vm 沙盒实测通过
      另两个候选已排除：xz-decompress 内含 WebAssembly；lzma-purejs 是多文件 CommonJS + 依赖 amdefine/commander
三个必须一起解决的代价：
  ① 慢：3.5~4.4s/包（LZ4 同量级约 150ms，慢 20~30 倍）
  ② 吃内存：解 8.68MB 实测 rss +344MB / heapUsed +241MB（28 倍）——
     因为库返回普通 Array（8.68M 元素）再 Uint8Array.from 复制一份
     ⇒ 插件的 estimateMemory 要为 LZMA 包单独放宽峰值，否则被内存准入直接拒掉
  ③ 解码器**不校验长度**：uncompressedSize 传错也不报错、静默解出错长度的数据
     ⇒ 实现里必须自己 if (out.length !== uncompressedSize) throw
另外：blocksInfo 与 block 可以用不同压缩（57 个包就是 blocksInfo=LZ4HC、block=LZMA）
      ⇒ 必须按**每个 block 自己的 flags** 判，不许按"整包压缩类型"一刀切
```

**结论：值得做，但必须与 worker / 内存准入放宽一起做** —— 否则会从"打不开"变成"卡死"。

## 十、大包首次渲染的长任务（与 LZMA 解压无关）

**现象**：LZMA 解压搬进 Worker 后，主线程解压相关长任务已消失，但**解压之后**仍有 1.5s / 3.3s 的长任务。

**范围**：61 个 LZMA 包解压后 2.76~33.4MB，加上 LZ4 的 42MB 包，都属这一类。

**尚未定位的一条**：LZMA 包 `aierdeliqi_5` 在"解压起步附近"有一条 **3362ms**（at=307ms），

## 十一、LZMA 解压内存膨胀 46 倍（已定位，暂缓处理）

**2026-10-29 用户机器 OOM 后调查，实测数据（勿重复测量，直接看这里）：**

```
单包 2.8MB 解压产物：RSS 52 → 176MB，峰值 +128MB ⇒ **膨胀 46 倍**（耗时 2285ms）
按比例推 21MB 包 ≈ 970MB，与 probe 缓存里的实测记录（21MB → 1195MB）吻合
```

**不是泄漏 —— 是"高水位不还给系统"**（这一条最容易被误判）：

```
同一进程反复解同一个包 5 次（每轮 global.gc + 等 300ms）：
  第1轮 净涨 55MB ｜ 第2~5轮 净涨 0~1MB ｜ 每轮 GC 后 heapUsed 仅 4MB（产物 2.8MB）
⇒ 对象都回收了，没有泄漏；但 RSS 从 51 涨到 106 后再也不回去
⇒ 那是 V8 保留的空闲堆页，操作系统层面收不回
⇒ 21MB 包会让该进程 RSS **长期停在 ~800MB~1GB**
```

**OOM 的真正机制：多个进程各自留一份高水位叠加**

```
8804 服务端 ／ 8899 测试实例 ／ chrome renderer ／ chrome worker（新加的 LZMA Worker）
／ DSH 宿主（1.4GB）／ 以及我们自己的批量测量（126 包全量扫、--repeat 3 子进程）
每个单看都"合理"，叠在 8GB 机器上就不够
```

**根因（代码层）**：`lib/lzma-d-min.js` 是 **worker 版构建**，`decompress` 返回**普通 Array**
（内部 `function o(e){var r=[];return r[e-1]=void 0,r}` 造的是 holey array），
2.8M 个小整数在 V8 里不是紧凑存储；随后 `Uint8Array.from(out)` 再复制一份。

**修复顺序（准入不是第一优先 —— 它只能防单次超限，防不了高水位留存）**：

```
1. 换解码器：写进**预分配 Uint8Array** 的 wasm 实现（不再产生 holey Array）
   ⇒ 峰值 46× → 3~5×，21MB 包高水位从 ~1GB 降到 ~150MB —— 这是根因修复
2. 浏览器 worker 侧按预测峰值限制：现在**完全没有准入**
   （plugin-host.js:700 注释明写"服务端 capacity 不参与前端解包准入"；
     唯一闸门 :297 只看**压缩后**大小 file.size > MAX_BUNDLE_BYTES）
3. 测量纪律：重活只在测试实例、串行、`--max-old-space-size` 设上限；
   禁止在用户正在用的实例上跑全量扫描（我这次跑 126 包扫就是叠加上去的因素之一）
```
