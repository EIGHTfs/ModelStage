## 一、显示缺陷

### 1.1 播放动作时画面「分裂」

**现象**：某类模型播放动作时，画面出现两个错位的形体（早期描述为「重影」，实际是**同一部件被画了两次、
位置错开**，不是半透明叠加）。

**已知**：
- 只在播放动作时出现；静止（暂停在某一帧）看不到 —— 说明与**每帧求值**有关，不是静态资源问题
- 与 PMA 预乘无关的线索：预乘错误通常表现为边缘发黑/发白，不会产生错位体

**排查方向（按可疑度排序）**：
1. 顶点属性槽位重叠：`pixi-app` / Spine 批次里 `a_position` 之外的槽（UV、color、dark color）是否被同一
   缓冲的两次写入覆盖 —— 分裂体常见于「第二组顶点用第一组的变换矩阵」
2. 双渲染：模型是否被同时挂在两个容器（stage + overlay canvas），其中一个用旧变换
3. 动作混合：`mixTime` / 多动画叠加时两条 skeleton 各画一遍（本项目有「播完接谁」的循环语义，需确认不是叠加）

**验收判据**：任选一个能复现的资源，暂停时截图与播放 1 秒后截图逐帧对比 ——
**存在且仅存在一个形体**；且切换动作、切换循环开关都不产生第二个。

### 1.2 部分 Spine 资源出现「眼圈 / 嘴圈」

**现象**：眼周、嘴周出现一圈异色描边（像描了线或透出底色）。

**已知证据**：
- 曾怀疑 PMA 预乘；**棕色尘埃2 的这类问题已修好**（修的是他们那批资源的预乘处理路径）
- 说明不是所有 spine 资源都中招 ⇒ 更可能是**资源本身的 alpha 通道语义差**（预乘 vs 直通混用），
  或某些部件的 atlas 区域边缘有半透明像素被双线性放大后露出来

**排查方向**：
1. 按游戏归类统计：哪些根会出现，是否集中在特定导出工具/版本
2. 对比 `pma` 开关（面板有「PMA 预乘」项）在三档下的差异 —— 若调它能让圈消失/出现，即锁定预乘路径
3. 检查 atlas 页的 `filter`（Linear/Nearest）：眼圈在 Linear 下更明显说明是边缘采样问题（需 padding/bleed 处理）

**验收判据**：同一模型、同一机位，开启/关闭预乘各截一张，眼圈在错误的那一档出现、正确档消失；
且修复后不影响已修好的棕色尘埃2。

```

  · exec 的 spawn 本体（超时杀、僵尸收、大 payload 走临时文件还是流、并发临时文件命名）
  · 帧协议实现（设计稿在 设计/插件运行时与多语言.md §四）

**故意不实现 spawn 的理由**：协议细节必须真实现才能定稿；先做「能跑但没想清楚」的半成品
比不做更危险 —— 它会让人以为协议已经可用。且当前两个插件都是 node 运行时，
没有任何「现在就要靠 exec 才能解开的包」。

**先把边界说清楚**：
- 插件进程必须能**被宿主杀死**（超时/内存越界），不能留僵尸
- 帧协议要能承载进度与错误码（不能只回最终结果）
- 依赖自带（venv / `.deps`），不要求宿主全局装包

## 三、大包首次渲染的长任务（已测一轮：CPU/IO 有真实开销，渲染侧需真机复测）

**测于 2026-10-30，环境：headless chrome + SwiftShader 软渲染 + 3 核** ⇒ 结论必须分两类看。

### 3.1 可信（纯 CPU / IO，与有没有 GPU 无关）

```
解包（worker 内）        unpack.source ≈ 8.1s（files=23）
主线程读包 + postMessage  3,918ms（19.3MB；plugin-host.js:129 读 arrayBuffer → :421 postMessage 给 worker）
PNG 传输                 18.7MB 的 texture_00.png fetch ≈ 1,320ms
散目录 23 个 HTTP 请求    累计 ≈ 3.4s（model3.json 只有 2.6KB 却 802ms；14 个 motion 各 230~283ms）
```

### 3.2 不可信（被软渲染放大，不能当真机判据）

```
纹理上传 / 绘制帧率：mount 后单条 2,148ms、散目录持续 ~125ms/帧（≈8fps）
⇒ SwiftShader 每帧都慢，几乎肯定是测量环境造成；**改渲染前必须真机复测**
```

### 3.3 候选方向（按职责归属，均未实施）

| 方向 | 归属 | 依据 | 备注 |
|---|---|---|---|
| ① 纹理尺寸由**服务端资产服务**按请求尺寸产出 | 服务端 | 传输+解码可省 1.5~2.5s（CPU 侧） | 解包仍只交原始文件，不改一个像素；需新增尺寸参数与缓存分档 |
| ② 首帧只画主体 + 纹理分批上传 | 渲染层 | 首帧更早可见 | **收益只能在真机量化** |
| ③ motion 时长预取延到首帧之后 | 前端装载 | 散目录实测可省 2~3s（3.4s 里 14 个 motion 占大头） | 底栏动作时长晚一拍显示 |
| ④ worker 自己按 URL 拉包，不在主线程整包读 | 前端装载 | 目标消掉那条 3,918ms | 需 worker 支持按 URL fetch；改动面在 worker 边界 |

**不建议**：把 Live2D 初始化/解码/上传搬进解包 worker（越界）；继续优化 LZMA 解压（解包已在 worker）；
给 model2/model3.json 加前端缓存（2.6KB 却 802ms 是服务端首次响应问题）。

### 3.4 一处口径校正（避免沿用错前提）

```
本轮曾有报告称「z46_2 是 NONE 5.8MB」「该根 LZMA 仅 4 个包」——**与实测不符**：

## 四、浏览器侧仍无峰值准入（暂缓：等真实案例再动）

> 服务端侧已处理完，不在此跟踪：解码器换预分配 `Uint8Array`（`6bcbb22`）、
> 峰值表换宽松整数、准入改 declared 单判（`measured` 只观测）。
> 细节见 `docs/设计/解包搬进worker线程.md` §4.1 与 `docs/参考/接口清单.md` §1.3。

**现状**：

```
唯一闸门 src/web/infra/plugin-host.js:297 只看**压缩后** file.size > MAX_BUNDLE_BYTES(2GB)
:700 注释仍明写「服务端 capacity 不参与前端解包准入」
⇒ 前端 worker 解包能把 renderer 进程顶穿，与服务端有没有峰值表无关
```

**方向（暂不实施）**：把同口径的峰值估算（解压后 MB → 峰值）搬到前端、在派 worker 前判一次。

**暂缓理由**：服务端表已宽松，前端再加一套估算等于又养一套要标定的系数，收益低、维护成本高。
等真的出现「前端解某个大包把页面顶崩」的实例，再按那次实测做，不预先猜系数。

**判据（若将来做）**：内存保护开启时超大包在前端被拒并说明原因；关闭后可重试；不误伤 61 个 LZMA 包里能解的那些。

## 五、`stage.pause()` 之后 `frames` 仍在增长（未查清，待取证）

**现象**（2026-10-29 由前端成员在验收看门狗时偶然撞到，如实上报未深挖）：

```
spine 模型加载后调用 stage.pause() ⇒ st.frames 仍在涨（一次实测 1130 → 1252，涨 122）
而 canvas-engine.js:78 明确写着 `if (st.paused) return;  // 暂停：不再排帧`
⇒ 按代码不该涨，实测在涨 ⇒ 要么 stop 没生效，要么还有第三条路径在加 frames
```

**已排查（我做的，未到底）**：

```
项目里有**三套 rAF**：
  ① src/web/spine/canvas-engine.js:80   st.frameRaf（帧计数循环）—— stopFrameTick 会 cancelAnimationFrame ✅
  ② src/web/engine/render-frame.js:66   engine.animationId（引擎主循环）—— stopLoop 会 cancelAnimationFrame ✅
  ③ src/web/engine/gl-driver.js:55      refreshResolution 的一次性 rAF（不影响 frames）
stage.pause() 调用链：st.engine.stop() → stopLoop → cancelAnimationFrame；st.paused=true；stopFrameTick；repaintOnce（只 +1）
⇒ 两套循环都会被取消，理论上 frames 最多涨 1。涨 122 ⇒ 与代码矛盾，需实测取证
```

**下一步取证建议**：

```
· 在 pause() 后打点：分别记录 st.frameRaf / st.engine.animationId 是否仍非 0（有没有被重新排上）
· 怀疑方向：repaintOnce 被外部周期性调用；或 engine.stop 拿到的不是同一实例（重载后 st.engine 换了）
· 判据：pause 后 3 秒内 frames 增量 == 1 为正常（那一次是 repaintOnce 的补帧）
```

**影响**：看门狗的自愈动作是 `stage.pause(); stage.play()`。
若 pause 真的不生效，那这套「自愈」只是空转 —— 但现在误报已修（`9739f3e` 让 hidden 时直接跳过），
自愈不再被误触发，影响仅限于「真卡死时自愈可能无效」。

## 六、`warnings` 里混装「通用能力说明」，与「这一根的问题」同流

**现状**（2026-10-30 由两次实测确认）：

```
GET /api/catalog?root=<任何根>  的 warnings 里必然带一条：
  「有 2 个能解包资源包的插件（unity-live2d-bundle、unity-spine-bundle）：…」
根因：catalog.mjs:522  resolveBundleProvider(plugins) 是 listBundleEntries 的第一句、无条件调用，
      provider.warning 被直接塞进 warnings
⇒ 它与"这根路径不存在/扫描失败"这类根级问题混在同一个数组里
```

**已经在做的规避**：根级问题单独出新字段 `rootWarning`（已完成，见接口清单 §catalog 行），
前端判"这根有没有问题"只认它、**不拿 warnings 拼因果**（拿它会拼出「因为有 2 个插件所以没模型」）。

**剩下这件事没做**（属破坏性变更，等有第二个消费方再动）：

```
把"全局能力说明"从 warnings 移出 → 顶层 capabilities（或 providers 字段）
warnings 从此只装"与本次请求相关的提示"
影响面：所有 warnings 消费方都要跟着改（前端 roster/list.js、url-params、接口文档、测试）
```

**判据（若将来做）**：一个路径正常的根，`warnings` 为空数组；`capabilities` 里有那两条插件说明。
