## 工作流约定

文档不是事后补的说明书，它和代码一起走。**两处强制点**：

| 时机 | 必做 |
|---|---|
| **每次下发任务** | 先把**设计写进 `docs/设计/`**（数据来源、视觉/行为规格、边界、验收判据），再下发实现。设计只存在于对话里等于没写 —— 接手的人看不到，验收也没有对照物 |
| **每次验收** | 除了跑测试与页面实测，必须核对**文档是否已同步**：新增/变更的行为有没有落进对应文档、被推翻的旧结论有没有删掉。文档没更新 ⇒ 验收不通过 |

配套两条：

- **实现偏离设计时必须回报并回写设计** —— 不能代码改了文档照旧，差异当场写回对应文档
- **修完的限制要从能力层「已知限制」删掉** —— 留着「未修」比不写更糟，读者会以为它还在

## 写作约定

这些约定是为了让文档**不随着时间变成谎言**：

| 约定 | 说明 |
|---|---|
| **只写结论，不写过程** | 不记录「谁在什么时候怎么排查的」；排查路径本身有价值时，把它写成**判据或警示**（如「往上找 overflow 祖先」），而不是叙事 |
| **不记人员归属** | 文档只记模块与职责，不记谁负责什么 |
| **同一事实只登记一处** | 其它地方**引用而非复制**；复制必然漂移 |
| **状态性描述必须可核对** | 写「已完成 / 未接线 / 待落地」时要能回答「什么时候、用什么方式核对的」；答不出来就别写状态，只写判据 |
| **不要给「永远」的承诺** | 「永远可用」「永不失效」这类话无法验证时不要写 |
| **数字要有出处** | 行数、键数、套件数、阈值都要能回溯核对方式 |
| **禁止指向参考对象代替写出内容** | 不写「详见某实现」就完事，要把结论本身写出来 |
