# 参考 · 渲染与纹理

> Spine 运行时接入要点、跨版本差异、以及 **PMA（预乘 alpha）与纹理上传**的规范行为。
> 本文结论均来自规范与实机实测，不是推测。遇到「发灰 / 发暗 / 边缘暗圈」可直接对号入座。

# 第一部分 · Spine 运行时接入

## 1.1 最常见的坑：「加载成功但画面全透明」

报错：`this.lastTexture.bind is not a function`（随后帧循环停止、`readPixels` 全 0）。

根因链：

1. **3.8 在解析 atlas 页头时就同步赋值并立刻调过滤**：
   ```js
   page.texture = textureLoader(line);
   page.texture.setFilters(page.minFilter, page.magFilter);
   ```
   ⇒ `textureLoader` **必须当场返回一个已可用、自带 `setFilters/setWraps/getImage/bind` 的对象**。
2. **batcher `flush()` 无条件调用 `bind()`**（4.1 前面多了保护 `if (!this.lastTexture) throw new Error("No texture set.")`）。

⇒ **任何非 `GLTexture` 的对象（1×1 canvas 占位、手搓的 `{getImage,...}`）一旦成为 `page.texture`，
第一帧 flush 就会 TypeError。** 占位可以存在，但**渲染前必须被真 `GLTexture` 覆盖**。

## 1.2 加载顺序（必须按此顺序）

| 步 | 做什么 | 关键点 |
|---|---|---|
| 1 | 选运行时版本（用模型 meta 的 `version`） | 缺失时相邻版本 ±1 降级 |
| 2 | **先把所有贴图加载完**（图 → `GLTexture`） | `spine.GLTexture \|\| spine.webgl.GLTexture` |
| 3 | 建 atlas | 3.8 传 loader；4.1 只传文本（见 1.5） |
| 4 | 解析骨架 | `SkeletonBinary(loader).readSkeletonData(u8)` 或 `SkeletonJson(loader)` |
| 5 | 建骨架与状态机 | `Skeleton(data)` → `AnimationStateData(data)` → `AnimationState(stateData)` |
| 6 | 初始化渲染器 | `new (spine.SceneRenderer \|\| spine.webgl.SceneRenderer)(canvas, gl)` |
| 7 | 相机 fit（包围盒，见 1.4） | |
| 8 | 每帧三步（见 1.3） | |

**最容易错的两点**：

- **贴图必须在构造 atlas 之前加载完**（3.8 的 loader 是同步的）
- `state.apply(skeleton)` 只是把动画参数写进骨架；**还必须 `updateWorldTransform`**（版本差异见 1.6）

## 1.3 每帧三步（`drawSkeleton` 自带 begin/end）

```
state.update(dt)                      // 推进动画时间
state.apply(skeleton)                 // 把动画写进骨架参数
skeleton.updateWorldTransform(2)      // 跨版本安全写法，见 1.6
renderer.drawSkeleton(skeleton, usePma)   // 内部 begin→draw→end
```

**不要手动 `renderer.begin()/end()`** —— 未配对会打乱 GL 状态。

跳帧/定位（`state.update(0)`）之后也要补调一次 `updateWorldTransform`，否则画面停在上一姿态。

## 1.4 相机 fit：用包围盒，不用 designSize

```
camera.position.x = bbox.x + bbox.w/2
camera.position.y = bbox.y + bbox.h/2
baseZoom = Math.max(viewportW / bbox.w, viewportH / bbox.h)
camera.zoom = baseZoom / userScale     // 若相机用 scale 则是 1/zoom（方向相反！）
camera.update()
```

`designSize`（`skeletonData.width/height`）只作兜底。

**两种自洽写法，不可混用**：

| 写法 | viewport | zoom | 说明 |
|---|---|---|---|
| **A（推荐）** | 视口像素（`clientWidth * dpr`） | `max(vw / bbox.w, vh / bbox.h)` | bbox 世界尺寸与视口像素直接相除，无需手工系数 |
| B | `bbox.w * 系数` | `1` | 视口本身就是「世界画框」，再加系数会双重放大 |

`renderer.resize(w, h)` 会重写 viewport ⇒ resize 之后要重设相机再 `camera.update()`。

三档取景（`fitMode`）只影响 bbox 怎么算，不影响上面的公式（详见[设计/相机](../设计/相机.md) §七）。

## 1.5 atlas 与贴图

- atlas 里的**页名就是文件名**（相对 atlas 所在目录）；要按 **URL 解析**拼路径，
  不能字符串硬拼（可能含 `../` 或子目录）。
- 图片 → 纹理：`img.src = URL.createObjectURL(new Blob([arrayBuffer], { type: 'image/png' }))`，
  加载完 `revokeObjectURL`；失败文案 `图片加载失败: <页名>`。
- 页缺失时可给 1×1 canvas 占位并 warn —— **仅限「想继续跑」，绝不能留到渲染**。
- 页名与文件接口的对应：`dir` 是骨架/atlas 所在目录，路径为 `dir + '/' + pageName`。

## 1.6 跨版本差异

| 行为 | 3.8 | 4.1+ |
|---|---|---|
| `TextureAtlas` 构造 | `(atlasText, textureLoader)`，**loader 不能为 null**，且构造时就调它 | `(atlasText)` 单参 |
| 页纹理绑定 | **没有 `page.setTexture()`**；只能 loader 返回，或手工 `page.texture = tex` 并自己补 `setFilters/setWraps` | 有 `page.setTexture(tex)`，且 `atlas.setTextures(...)` 可批量绑 |
| `updateWorldTransform` | **无参** | **要传 physics 参数** |
| 空纹理错误保护 | 无保护，直接 `TypeError: this.lastTexture.bind is not a function` | 先抛 `No texture set.` |
| 渲染器命名空间 | `spine.SceneRenderer`（通常也挂 `spine.webgl`） | 多为 `spine.webgl.SceneRenderer` |

**`updateWorldTransform` 逐版本实测签名**：

| 版本 | 签名 | 不传参的后果 |
|---|---|---|
| 3.6 / 3.7 / 3.8 | `()` | 正常（本就无参） |
| 4.0 / 4.1 | 未见 `(physics)` 形式 | 正常；多传的实参被忽略 |
| 4.2 / 4.3 | `(physics)` + 未传时 `throw new Error("physics is undefined")` | **抛错** |

⇒ **跨 3.6~4.3 的安全写法：`skeleton.updateWorldTransform(2)`**（`2` = `Physics.update`），无需版本分支。

**统一写法（两版一套逻辑）**：

```
1. 先加载全部页图 → GLTexture
2. 3.8：new TextureAtlas(text, name => texMap[name])
3. 4.1：new TextureAtlas(text) 后 pages.forEach(p => p.setTexture(texMap[p.name]))
4. 之后流程完全一致
```

## 1.7 多版本隔离：为什么不能用 `<script src>`

每个 `spine-webgl-<ver>.js` 顶层都是 `var spine = …`，用 `<script src>` 加载时后加载的会**覆盖全局 `spine`**。
先加载版本的类在运行期解析基类时会拿到新版本的类，典型报错：

```
TypeError: Class constructor Texture cannot be invoked without 'new'
```

**保留对象引用不够** —— 引用能保住对象，保不住类内部对全局 `spine` 的解析。

正解：把运行时源码文本当作**函数体**求值（而不是用 `<script>` 注入），
使源码顶层的 `var spine` 成为该函数作用域内的**局部绑定**，各版本的继承链互不影响。
实现上用「构造一个函数并取回其内部的 `spine` 局部变量」即可，不需要改动运行时源码本身。

## 1.8 常见报错与对策

| 报错 | 原因 | 对策 |
|---|---|---|
| `this.lastTexture.bind is not a function` | `page.texture` 不是真 `GLTexture` | 渲染前用真 `GLTexture` 覆盖；3.8 只能靠 loader 返回 |
| `No texture set.`（4.1） | 页没绑纹理 | `page.setTexture(tex)` 补齐 |
| `textureLoader cannot be null.`（3.8） | 构造 atlas 少传 loader | 传 `name => tex` |
| `TextureAtlas 解析失败` | atlas 文本格式/换行/页名 | 打印首几行对照 |
| `图片加载失败: <页名>` | 页名与文件路径不一致（最常见） | 用 URL 解析拼 `dir + '/' + pageName` |
| `skeleton skel 文件为空` | `.skel` 读到 0 字节 | 检查文件接口是否 404 |
| `运行时缺少核心类` / `脚本已加载但未导出 spine 对象` | 运行时路径错/损坏/版本不符 | 必需类：Skeleton / AnimationState / TextureAtlas / AtlasAttachmentLoader / SkeletonJson / SkeletonBinary / BlendMode / SceneRenderer 或 SkeletonRenderer / GLTexture / OrthoCamera |
| `setAnimation 找不到动画 "x"` | 名字不在 `skeletonData.animations` 里 | 用模型元数据返回的动作名 |
| 画面发灰/发暗 | `drawSkeleton(..., true)` 但纹理是 straight | 见第二部分 |

## 1.9 怎么判定渲染成功（不要只看「没报错」）

1. **别用 `readPixels` 判断渲染成功**：`preserveDrawingBuffer: false`（默认）时
   **必须在 `drawSkeleton` 之后同一帧立刻**读；跨帧再读**必然全 0**。这是假阴性，不是「没画出来」。
2. 更稳的三件事一起看：
   - `skeleton.bones.length / slots.length / drawables.count` 与模型元数据对得上
   - 渲染后同一帧 `readPixels` 统计**非透明像素占比 > 0**
   - **动作在动**：播放后隔 1s 再取一帧，两帧有像素差异
3. `state.apply` 后忘了 `updateWorldTransform` 会出现「渲染了但没有动作 / 姿势错」

## 1.10 皮肤能力的验证状态

舞台已提供 `getSkins()` / `setSkin(name)`，但当前资产库中模型 skin 数普遍为 1，
**多皮肤路径未经真实数据验证**，只有单皮肤路径被实测覆盖。

# 第二部分 · PMA（预乘 alpha）与纹理上传

## 2.1 最终落地方案

**上传统一 `UNPACK_PREMULTIPLY_ALPHA_WEBGL = false`，不做任何二次预乘。**

```js
gl.pixelStorei(gl.UNPACK_PREMULTIPLY_ALPHA_WEBGL, false);
const tex = new GLTexture(gl, entry.img);   // 原图直传，一次上传
```

**为什么**：浏览器解码 PNG 时**已经**把 alpha 乘进颜色通道（2D canvas 后备存储必须预乘）。所以：

| 上传口径 | 结果 |
|---|---|
| `UNPACK = true` | **再乘一次 ⇒ 双重预乘 ⇒ 眼白/高光被压暗成黑块** |
| `UNPACK = false` | 浏览器 un-premultiply 后上传 ⇒ 与混合口径匹配 ⇒ **正确** |

**实测铁证**（同一张图）：

```
UNPACK=false 上传 → 读回 r>a 占 89.32%      （直通）
UNPACK=true  上传 → 读回 r>a 占  0%，且 meanT = 55.59
                                  理论值 F × a/255 = 55.57   ← 预乘的定义式
⇒ 55.59 ≈ 55.57 证明 UNPACK=true 又乘了一次
```

## 2.2 ⚠️ 面板上的「像素检测」不可用来判断源图性质

那个探测用 `UNPACK=false` 上传后读回，**无论源图是什么，读到的必然是直通数据**（循环论证）。

**绝对不要**因为面板显示「非预乘」就去改上传口径。

## 2.3 `UNPACK_PREMULTIPLY_ALPHA_WEBGL` 到底控制什么

> **在把源数据上传到纹理的那一刻，是否把 alpha 乘进 RGB。**

| flag | 上传到 GPU 的字节 |
|---|---|
| `true` | 预乘后的数据（`r,g,b` 已被乘以 `a/255`） |
| `false` | 非预乘（直通）数据 |

WebGL 默认值是 `false`。

**源类型决定「浏览器会不会替你转换」**：

| 源类型 | `UNPACK=false` 时上传什么 |
|---|---|
| `HTMLImageElement` / `ImageBitmap`（PNG） | 浏览器 PNG 解码结果；默认实现里图片会先被预乘（canvas 需要），`texImage2D` 时按 flag 决定是否再处理 |
| **`HTMLCanvasElement`** | **⚠️ 浏览器会把 canvas 的预乘后备存储 un-premultiply 后上传**（见 2.4，本项目的坑源） |
| `Uint8Array`（原始数组） | **原样上传，不做任何 alpha 处理** |

## 2.4 🔴 最大的坑：`texImage2D(canvas)` 会把预乘数据除回去

**曾经为了实现「CPU 预乘」写了这条链路**：

```js
const img = ctx.getImageData(0, 0, w, h);
ctx.putImageData(await premultiplyImageData(img), 0, 0);   // 自己算预乘，写回 canvas
gl.pixelStorei(gl.UNPACK_PREMULTIPLY_ALPHA_WEBGL, false);
gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA, gl.RGBA, gl.UNSIGNED_BYTE, canvas);   // ← 致命
```

**为什么无效**：2D canvas 的后备存储是预乘的，而 `texImage2D(canvas)` 在 `UNPACK=false` 时：

```
canvas 内部（预乘）→ 浏览器 un-premultiply（除以 alpha）→ 上传到 GPU
```

⇒ **CPU 预乘被浏览器除回去了**。上传的仍是直通数据，而我们却按预乘混合去画
⇒ **半透明边缘和暗部发黑**。

日志上看起来「成功」（`cpuPremultiplied: true`、`uploadSource: canvas(premultiplied)`），
**但实际效果等于没做**。这是典型的「看起来做了、实际没做」的假成功。

**推论**：任何「先算进 canvas、再用 canvas 上传」的预乘方案都是无效的。

## 2.5 spine 官方 `GLTexture` 的三个事实

1. **官方 4.1 的 `GLTexture` 没有 `pma` 属性** —— 任何 `if ('pma' in tex)` 的判断在 4.1 下都是 `false`
2. **官方 `update()` 默认完全不动 `UNPACK_PREMULTIPLY_ALPHA_WEBGL`** —— 它用**调用时刻的 GL 状态**
3. **`restore()` 在构造函数里就被调用** ⇒ `new GLTexture(gl, source)` 返回时**上传已完成**；
   之后再改 GL 状态对它无效，除非显式再调 `update()`

## 2.6 视觉表现判别表

| 视觉表现 | 成因 |
|---|---|
| **半透明边缘一圈发黑 / 暗环** | 纹理是**预乘**的却被**再乘一次**（双重预乘）；或纹理直通却按预乘混合 |
| **边缘发白 / 发亮** | 纹理是**直通**的却被按直通混合画一张已预乘的图；或反之 |
| **面内大片区域整块发黑（不是边缘）** | **不是 PMA 问题** —— 纹理数据被覆盖/丢失（二次上传空数据、纹理页错配） |
| **整体偏暗但轮廓正常** | 颜色空间被转换两次（sRGB ↔ linear） |

**注意**：不能用 `max(r,g,b) > a + 16` 当「是否双重预乘」的判据 ——
双重预乘的后果是 `color × alpha²`，**RGB 变小但 `r ≤ a` 仍然成立**，这个判据抓不到「变暗」。
要用**与正确基准逐像素 diff**。

## 2.7 调试探针

```js
// 读画布实际像素，统计半透明区域的「亮度/alpha 比」
const canvas = document.querySelector('#stage canvas');
const gl = canvas.getContext('webgl2') || canvas.getContext('webgl');
const buf = new Uint8Array(canvas.width * canvas.height * 4);
gl.readPixels(0, 0, canvas.width, canvas.height, gl.RGBA, gl.UNSIGNED_BYTE, buf);
// 对 0<a<255 的像素统计平均 R 与平均 A

// 读上传时的实际 GL 状态（最直接）
gl.getParameter(gl.UNPACK_PREMULTIPLY_ALPHA_WEBGL)
```

**最强判据**：与已知正确的基准**逐像素 diff**，统计 95 分位差值。
