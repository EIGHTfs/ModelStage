# 架构 · 总览

> 本文描述**当前**架构：分层、模块归属、职责边界、核心概念与扩展点。
> 具体接口契约见 [契约目录](../契约/)，单项能力清单见 [能力层](能力层.md)。

---

## 一、设计原则

1. **接口由基础能力暴露，插件只依赖接口** —— 方向单一，不允许插件反向侵入核心内部
2. **插件不得修改全局对象**（不得 patch 加载器、不得持有内部对象引用）
3. **插件不得被核心反向调用其内部方法**；核心只调用契约里声明的方法
4. **插件失败必须可退化** —— 解析失败不影响其它模型的可用性
5. **契约只有一处权威** —— 写在契约文档里，代码按它对齐
6. **数据与渲染分离** —— 核心持有 Document（唯一数据源），渲染器只读它，编辑器只能通过 Command 改它
7. **扩展点提前留够** —— 插件按能力角色注册（`asset-provider` / `renderer` / `editor` / `exporter` / `panel`）
8. **插件之间零耦合** —— 共享状态一律收进核心（VirtualFS、Document），插件彼此不直接调用
9. **功能以本项目自身行为为准** —— 文档与验收只描述本项目的功能与行为，不把任何外部实现当准绳

**一句话**：**核心给插件开一扇门（暴露接口），插件从这扇门进出；墙上不许凿洞。**

## 二、分层

```
┌ App Shell            启动编排 / 生命周期 / 错误边界 / 状态订阅，拥有 DOM 与状态
└────────┬─────────────────────────────────────────
         │ 事件 / 状态
┌────────▼ 领域（无渲染细节）
│  Catalog（模型来源）· Selection（名册与选中）
│  Playback（动作/循环/速度）· Settings（面板值 → 能力项）
└────────┬─────────────────────────────────────────
         │ Document（ready）
┌────────▼ 渲染层
│  StageSurface —— 唯一拥有 canvas / GL / overlay / 尺寸 / DPR / 帧时钟
│    ├─ Renderer(Spine)   ├─ Renderer(Live2D)   └─ Renderer(3D, 将来)
│    activate(document)：串行、单点切面
│    capabilities 驱动面板；camera 由渲染器提供
└────────┬─────────────────────────────────────────
         │ AssetProvider / VirtualFS
┌────────▼ 资产层
│  VirtualFS · AssetProvider · Document 构建
└──────────────────────────────────────────
```

**数据流单向**：`插件解析 → VirtualFS → Document(ready) → activate → 渲染`。
任何「反向触达核心内部」的写法都是违规。

## 三、实际模块结构

```
src/web/
├── main.js          启动编排（568 行；只做装配与生命周期，不放业务细节）
├── app/             领域动作（16 个模块）：model-actions / transport-actions / ui-state /
│                    view-settings / anim-list / memory-guard / memory-budget / root-manager …
├── render/          渲染面：surface（几何/背景/切面/帧时钟）· spine · live2d · interaction
│   └── camera/      统一相机：index（语义）· constants（唯一参数来源）· spine（backend）
├── engine/          Spine 渲染引擎（20 个模块 + adapters/）：animation · textures · pma ·
│                    filters · skins · fit · frame-gate · player · appearance · pipeline …
├── spine/           Spine 舞台对外接口：canvas.js（唯一出口）+ canvas-{runtime,document,view,
│                    pixels,engine,api,api-groups,entry}.js
├── live2d/          Live2D 舞台：stage · stage-ctx · model · release · vfs-settings（12 个模块）
├── roster/          左栏名册：list · view · rows（三级树 / 搜索 / 懒加载）
├── panel/           右栏与底栏：schema（声明式）· panel-settings · view · transport · icons ·
│                    bg-source · dialog · slider · shell-controls · settings-io（18 个模块）
├── debug/           调试日志面板与诊断探针（8 个模块）
└── infra/           基础设施：api · vfs · document · plugin-host · ready（就绪信号）·
                     mem-stats · diag · shortcuts
```

> 目录按**职责**划分，不按「domain / ui」这种纯概念分层 —— 概念分层容易长出空目录，
> 而按改动一起发生的代码放在一起更实际。上表的「领域 / 渲染 / 资产」是**逻辑角色**，与目录不是一一对应。

### 3.1 职责边界（硬规则）

| 模块 | 可以 | 不可以 |
|---|---|---|
| `main.js` | 装配模块、订阅状态、挂 UI | 写具体渲染逻辑、自己量尺寸、自己算 DPR |
| `app/*` | 业务规则、调 API、产出 Document / 命令 | 碰 DOM 结构、碰引擎内部对象 |
| `render/surface` | 拥有 canvas / 覆盖层 / 尺寸 / DPR / 帧时钟 / `data-stage-mode` | 懂 Spine / Live2D 的具体加载 |
| `render/*` 渲染器 | 用 handle 画、暴露 camera / capabilities | 建 canvas、读 DOM 尺寸、写 `data-stage-mode` |
| `engine/*` | 纯引擎能力（动画/纹理/PMA/滤镜） | 读面板状态、改 DOM 样式 |
| `roster/` `panel/` `debug/` | 渲染 DOM、把用户意图转给 `app/*` | 直接改渲染器内部状态 |

## 四、核心概念

| 概念 | 职责 | 契约 |
|---|---|---|
| **StageSurface** | 画布、覆盖层、几何、DPR、z 序、可见性、帧时钟、切面状态机的唯一所有者 | 渲染面契约 §五 |
| **Renderer** | 把 ready 的 Document 画出来；暴露 `capabilities` 与 `camera` | 渲染面契约 §二 |
| **Document** | 运行时唯一数据源；渲染器/编辑器/导出器之间唯一的交流媒介 | 渲染面契约 §三 |
| **VirtualFS** | 资源位置解析的唯一入口，让内存文件与网络文件对渲染器长得一样 | 数据与接口契约 §1 |
| **AssetProvider** | 插件角色：容器 → 文件表 + 入口 | 插件契约 §四 |
| **能力键 / capabilities** | 面板只问「当前渲染器支持什么」，不猜引擎有没有该方法 | 渲染面契约 §四 |
| **就绪信号** | 给机器读的加载阶段状态机 | 交互与实现约束 §2 |

### 4.1 三条常被误解的边界

**① 相机归渲染器 ≠ Spine 专属**

Spine 与 Live2D 各有一个 2D 渲染器，各自提供相机 backend，**共用同一套统一相机与同一份常量**
（`render/camera/index.js` + `constants.js`）。「相机归渲染器」指的是**相机接口由渲染器暴露**
（`camera: 'ortho-2d'` 就是这一层），将来的 3D 渲染器自带一套透视/轨道相机。

**② `kind` 与 `source` 是两件事**

| 字段 | 取值 | 消费方 | 含义 |
|---|---|---|---|
| `kind` | `spine` / `live2d` | 渲染器 | 内容是什么，决定走哪条渲染分支 |
| `source` | `files` / `bundle` | AssetProvider | 资源怎么来，决定要不要解包 |

**容器不改变内容类型**：Live2D 资源包 → `kind:'live2d', source:'bundle'`。
**不允许**把 `bundle` 写进 `kind` —— 否则渲染器里会长出「bundle 其实等于 live2d」这类特判。

**③ 渲染器不碰 DOM**

渲染器拿到的是受控句柄（`{ canvas, overlay, requestRender(), onResize(cb), geometry() }`），
不是 DOM 元素。它不自己建 canvas、不读 `clientWidth`、不写 `data-stage-mode` ——
这几件事全归 Surface。违反后的典型症状是「几何全对但画面错位」。

## 五、统一模型来源：`ModelEntry`

两路扫描接口的输出形状不一致（唯一入口字段、版本字段、动作/皮肤字段各不同，Spine 侧缺 `kind`），
消费方必须各自适配。因此新增 `GET /api/catalog` 输出统一 `ModelEntry`：

```js
{
  id,                                  // 全局唯一
  kind: 'spine' | 'live2d',            // 内容类型（决定哪个渲染器）
  source: 'files' | 'bundle',          // 容器类型（决定要不要解包）
  rootId, rootName, name, srcDir,

  entry:  { url, name, size },         // 唯一渲染入口：.skel 或 .model3.json
  assets: [{ role, name, url, size }], // role: atlas | moc3 | texture | motion

  meta: {
    version,                           // Spine 版本 或 Cubism 版本（统一为数字）
    motions: [],                       // 两路统一叫 motions
    skins: [],                         // Spine 皮肤
    expressions: [],                   // Live2D 表情（语义不同，不合并）
    textureCount, fileSize,
    extras: {}                         // 各家私有字段统一塞这里
  },

  iconUrl,
  warnings: []                         // 例如 motions 为空需运行时枚举
}
```

规则：

- **`entry` 是唯一渲染入口** —— 渲染器只看它，不关心 skel / model3 差异
- **私有字段一律进 `meta.extras`**，不进公共层
- **`warnings` 显式化缺陷**，不用「字段为空」隐式表达
- **`kind` 不由 catalog 猜** —— 由提供者 `produces.kind` 声明；未声明则 `kind:null` + warning，渲染层拒绝装载

前端业务代码**只能**通过 `/api/catalog` 取模型清单（单路接口仅供诊断探针与测试），
门禁 `tool/check-single-source.mjs` 强制此约束。详见[数据与接口契约](../契约/数据与接口.md)第二部分。

## 六、渲染面切换：唯一入口

装载与卸载曾分散在各自分支里，于是出现两类必然的漏洞：切到 Spine 时忘了收 Live2D（两个模型叠加）、
切到 Live2D 时忘了藏 Spine 画布（加载期间两张画面同时可见）。

**这不是遗漏，是结构问题**：只要「每个分支各自负责清理对方」，新增一个渲染面就会再漏一次。

```js
async function activate(next) {          // next = { kind, doc }
  if (swapping) return;                  // 并发保护：同一时刻只允许一次切换
  swapping = true;
  const previous = activeKind;
  try {
    setStageMode('loading');             // ① 统一先遮住：任何方向都不会叠加
    await disposeActive();               // ② 统一卸载（幂等，按 activeKind 分派）
    const info = await mountKind(next);  // ③ 装载新内容
    setStageMode(next.kind);             // ④ 统一切面（只有这一处写 stageMode）
    activeKind = next.kind;
    return info;
  } catch (err) {
    setStageMode(previous || 'spine');   // ⑤ 失败回滚到切换前
    throw err;
  } finally {
    swapping = false;
  }
}
```

**三条硬约束**：

1. `data-stage-mode` 只允许在 `activate()` / `disposeActive()` 里写
2. 切换必须串行（`swapping` 保护），不允许两次装载交错
3. `dispose()` 必须幂等且自隐藏，不依赖调用方记得藏自己的画布

**已知体验取舍**：先遮后换会让切换瞬间短暂空白。
去掉空白的正解是「新内容首帧就绪后再换面 + 上层不透明遮盖」，当前采用简单可靠版本。

## 七、扩展点

### 7.1 五类插件角色

| 角色 | 核心暴露的接口 | 插件职责 | 现状 |
|---|---|---|---|
| `asset-provider` | `canHandle(file)` / `resolve(file)` + 宿主取资源能力 | 容器 → 文件映射 | **已落地** |
| `renderer` | `mount(document, host)` / `unmount()` | 渲染一类内容 | 核心内部实现，未开放注册 |
| `editor` | Document 读写 + `applyCommand(cmd)` | 修改模型数据 | 留位 |
| `exporter` | Document 只读 + 写输出 | 导出 skel/atlas/json/图片 | 留位 |
| `panel` | `mountPanel(slot)` | 往右栏/工具栏注入 UI | 留位 |

### 7.2 新增一个渲染面

```
1. 写 render/<kind>.js：capabilities + mount/unmount/dispose/isActive + camera + setSetting
2. main.js：surface.register(create<Kind>Renderer())
3. 面板零改动（按 capabilities 自动生成 / 不构建）
4. Document 契约不变（新增 kind 只是多一种内容类型）
```

**判据**：加 3D 渲染器时**不需要改 VirtualFS、不需要改资产提供者、不需要改面板 schema**。
若要改这些，说明扩展点没留够 —— 先补契约再实现。

### 7.3 加编辑器

不需要改渲染器、不需要改 VirtualFS、不需要改插件加载器，
只新增一个 `editor` 实现 + 补 Document 可写部分。

已知难点（属实现难度，不是架构缺口）：`.skel` 是二进制，编辑需可写表示与回写编码；撤销栈粒度需实测手感。

## 八、什么时候该抽一层（避免过度设计）

只有同时满足三条才算该抽：

1. 现在已经有**两处以上**重复实现（画布尺寸、可见性、帧循环这类）
2. 将来至少要加**一个新实现**（3D 渲染器、编辑器）
3. 抽出来后**单个文件变小且可独立测试**

不满足就不抽 —— 例如「播放/暂停」这类小逻辑留在领域层即可。

**明确不做的**：

- 不引入框架 / 构建工具（保持零依赖原生模块，无 `package.json`、无 `node_modules`）
- 不为单一实现抽接口
- 不做通用 DI 容器 / 事件总线（store + 直接调用足够）

## 九、已落地与仍开放

**已落地**：VirtualFS 两侧接入（Spine 与 Live2D 全文件类型）、Document 作为渲染器唯一入参、
`unmount`/`dispose` 分离、切面单点收敛、能力驱动面板 + 能力自检、`ModelEntry` 统一来源、
插件清单与角色机制、bundle 解包闭环、统一相机与钳制单点、可读引擎（无压缩切片）、
就绪信号、UI 状态统一工厂。

**仍开放**（详见[契约索引](../契约/README.md) §五）：

- 「内容选择 / 播放动作」类操作（皮肤、混合模式、动作选择）仍是面板 → 渲染器实例的直接调用，
  是扩成能力键还是在契约里显式豁免，口径待定
- `editor` / `exporter` / `panel` 三类插件角色只有注册位
- 背景图索引写盘的非原子性（真实缺陷未修）
