# 契约 · 条目状态与展示归属（entry-state）

> 定位：把「一个模型条目**显示成什么样**（徽标色/归属）与**装得动吗**（可装载预判/最近一次装载结果）」
> 收拢为**服务端唯一权威**，经接口暴露；插件只声明能力与颜色，前端只渲染字段。
> 现状的三份分散（前端 localStorage 失败缓存、catalog 内联 badgeAccent、resolve 里的即时判定）由本契约归一。

---

## 一、职责划分（谁说了算）

| 事实 | 唯一权威 | 暴露方式 |
|---|---|---|
| 谁认领什么格式、显示色、优先级（**含内置 spine/live2d 装载器**） | **提供者注册表**：插件清单（`fileKinds`/`accent`/`matchPriority`）+ 内置装载器同表登记（§一·五） | `GET /api/plugins`（内置项一并返回） |
| 条目的展示归属（色/提供者/候选） | **服务端 catalog**（由注册表声明聚合而成） | `entry.display`（§二） |
| 条目能不能装、为什么不能 | **服务端**（注册表 canHandle 聚合 + 形态判定 + 资产检查） | `entry.support`（§二） |
| 最近一次装载结果（失败原因、成功清痕） | **服务端条目状态存储**（§三） | `entry.loadResult` + `POST /api/entries/result` |
| 渲染 | **前端**（只按字段画，零判断） | — |

## 一·五、内置装载器纳入同一注册表（本次的核心补充）

现状是两套平行体系：目录型 spine/live2d 由**前端内置路径**直接装载（`kind` 判型、颜色按
`produces.kind` 反查插件、失败只进 localStorage），资源包才走插件接口。本契约把它们**并轨**：

```
· 内置 spine 装载器、内置 live2d 装载器各作为一个**提供者**登记进同一注册表：
    id：builtin-spine / builtin-live2d；accent 声明色；fileKinds：目录形态（如 'spine-dir'/'live2d-dir'）
· 对目录型条目做"可装载预判"（skel/atlas/贴图齐备与版本可读）由该提供者的判定负责，
  结果同样汇入 entry.support —— 不再散落在 probe.mjs + 前端各自判断
· 目录型装载成功/失败同样经 POST /api/entries/result 上报 loadResult（装载器侧上报），
  ⇒ 与资源包共用同一份存储、同一套失效规则、同一条一致性约束
· 前端选渲染器不再按 kind 硬编码分派：装载完成后由 loadResult.provider 决定挂哪个面
  （builtin-* 与插件提供者在这里是平权的）
· /api/plugins 返回内置项 ⇒ 前端查 label/accent 只有这一个来源（S7 一并覆盖）
```

不改变的东西：内置装载器**实现本体**（runtime 加载、Document 构建）不动，只是给它的
认领判定、结果上报与展示声明套上接口外壳；渲染面契约（Document/activate）不受影响。

**硬边界**（违反即契约违规）：

1. 前端代码里不出现任何运行时颜色字面量；颜色只来自 `entry.display.accent`。
2. 前端不再自建"装载失败缓存"（`bundle-failures.js` 的 localStorage 层由服务端状态取代，迁移见 §五）。
3. 服务端不猜：归属未定时 `accent = null`（前端中性色），**绝不**按候选首个或 `matchPriority` 涂色。
4. 装载结果的写入方只有一个：装载尝试的当事端（前端或后端解包 API）在完成时上报；**旁路观测不写状态**。

**聚合键必须是 `fileKinds`，不是 `produces.kind`**：

```
现状 catalog 按 produces.kind 反查"唯一声明该 kind 的插件"来决定目录型条目的颜色。
内置项一旦也声明 produces.kind='spine'，该 kind 的声明方就变成 2 个 ⇒ 现有散目录条目会全部掉成中性色（回归）。

定稿：内置项用独立形态标识（'spine-dir' / 'live2d-dir'），归属聚合按 **fileKinds 匹配条目形态**：
  · 插件：fileKinds = ['bundle']  ⇒ 只认领容器型
  · 内置：fileKinds = ['spine-dir'] / ['live2d-dir'] ⇒ 只认领对应目录型
两侧天然互斥，不会互相稀释颜色。
```

**内置项的 `version` 由判定模块内容派生（不人工递增）**：

```
失效规则① 用 `providerId@version` 作指纹。内置判定逻辑改了而版本号没改 ⇒ 指纹不变 ⇒ 不会触发重探测，
旧的"不支持"结论会一直挂着，S6 就失效不彻底。因此内置项的 version 取**判定模块内容的哈希**（启动时算一次），
改判据代码即自动换版本、自动触发一轮重探测；插件仍用自己的 plugin.json version（外部资产，版本由作者声明）。
```

## 二、catalog 条目新增/统一的字段（所有 kind 一视同仁）

目录型（spine/live2d 散文件）与容器型（资源包）走**同一形状**——这正是"本来就能加载的
live2d、spine 也可以通过接口管理"的落点：

```jsonc
{
  // 既有字段（id/kind/container/rootId/name/rel/meta/…）不动，新增：
  "display": {
    "accent": "#2b6cb0" | null,        // 徽标底色；null ⇒ 前端中性色（归属未定）
    "provider": "unity-spine-bundle" | null,   // 归属提供者（展示名由前端按 id 查 /api/plugins 的 label）
    "candidates": ["unity-spine-bundle", "unity-live2d-bundle"]  // 声明可认领该条目的插件，按 matchPriority 降序
  },
  "support": {
    "state": "ready" | "unknown" | "unsupported",
    // ready      目录型：资产检查通过（原 missingTextures 为空即 ready）
    // unknown    容器型：解包前判不出（不是坏事，只是"未验证"）
    // unsupported 服务端有把握"点了必失败"（如美术依赖包）——原因见 detail
    "detail": { "reason": "asset-dependency", "message": "……可读原因（与装载失败时的文案同源）" } | null
  },
  "loadResult": {                       // 最近一次**真实装载尝试**的结果；没试过 = null
    "result": "ok" | "failed",
    "reason": "asset-dependency" | "no-provider" | "tex-decode" | … ,  // 结构化码（不稳定文案不许进这里）
    "message": "……",
    "provider": "unity-spine-bundle" | null,   // 成功时=实际解出/装载它的插件；决定 display 重算
    "at": 1730275200000
  }
}
```

**一致性约束（服务端自己保证，前端不校验）**：

- `loadResult.result === 'ok'` ⇒ `display.provider` 必须等于 `loadResult.provider`、
  `display.accent` 必须等于该插件声明色、`support.state` 不得为 `unsupported`。
  ⇒ 也就是说：**"解包成功后的即时变色"根本不需要前端"刷一行"的特殊逻辑**——
  它只是这条不变量在存储层的自然结果；下一次任何读取（重渲染/搜索/刷新）都一致。
- 同一条目 `support.state === 'unsupported'` 与 `loadResult.result === 'ok'` 不能并存
  （后者存在说明"其实装得动"，前者的判定依据已过期，以 loadResult 为准重算）。

## 三、服务端条目状态存储（新增，权威数据）

```
位置：data/entry-states.json（写盘合并去抖；CIFS 上禁止一请求一写）
键：  **统一 `${rootId}/${rel}`**（目录型 rel = srcDir + 文件名；容器型 rel = 包相对路径）
     —— 不用条目 id：容器 id 是把 rel 里的 / 换成 _ 派生出来的、**不可逆**，不同 rel 可能撞键；
        `rootId/rel` 与 VFS 前缀同构，前缀比对直接可用
值：  loadResult（§二）+ 失效指纹 + `{ at, source:'server'|'client' }`
```

**写入定序**（两条路共用同一存储，必须定序，否则互相覆盖）：

```
· 写入方 = 装载尝试的当事端（服务端 resolve 或前端上报），一次尝试只走一条路 ⇒ 结构上不会双写
· 仍有"前端报成功后用户又触发服务端 resolve"的情形 ⇒ 以 at 更晚者胜（服务端以自己的时钟为准）
· 冲突兜底：incoming 的 at 不晚于已存记录 ⇒ 不覆盖，直接返回当前状态（HTTP 200 + 当前 entry）
· 服务端 resolve **失败也必须写**（failed）——否则列表永远显示"未试过"，
  S4 的"点击后错误文案与 ⚠ 同源"就断了
```

**失效规则**（三条；规则①的动作改为「作废 + 触发重探测」，不是常态轮询）：

| 规则 | 触发 | 动作 |
|---|---|---|
| ① 提供者集合指纹不符 | `providerId@version` 排序拼接变了 | 旧状态作废（回 `unknown`）+ **置"待探测"标记**，交给 §八 重探测 |
| ② 条目 size 变化 | 同名文件被替换 | 该条失效 |
| ③ 服务端重启 | 进程换代 | 从 json 读回；读不回 = 空表（可接受，重测即得） |

**① 的语义与触发时机（关键，别做成常驻任务）**：

```
· 指纹必须记录，不能省：它是"能力变过"的唯一判据。省掉它就只能无条件全量重扫 —— 那正是不要的形态。
· 判定发生在读取路径（recompute）：记录里的 providerFingerprint ≠ 当前注册表指纹 ⇒ 该结论不再可信。
· 动作只有两件事：(a) 旧状态作废，support 回 unknown（不再拿过期结论给用户挂 ⚠）；
                  (b) 置待探测标记，由 §八 任务消费。
· **平时零开销**：指纹没变 ⇒ 不探测、不读包。探测只在"插件装上/换版本/改了内置判据"之后跑一轮，
  按根串行、限速、跑完即停。
· 重探测完成后新结论带新指纹写回，此后回到零探测状态。
· 相比"整批丢弃"：不丢历史（谁在什么时候因为什么失败仍留在表里），且能力类结论
  （tex-format-unsupported 这类不来自形态探测的）也随重探测自愈，而不是等用户重试成功才消。
```

**接口**：

```
POST /api/entries/result
  请求 { key, result, reason?, message?, provider?, size? }
  响应 { ok, entry: { display, support, loadResult } }   ← 带回重算后的三字段
  语义：result:'ok' 清除既有失败并触发一致性重算；'failed' 覆盖式记最新一次。
        响应里就带回新字段 ⇒ 前端装载完成时**一次请求同时完成"上报"与"取回即时显示数据"**，
        不需要再拉 /api/catalog（这正是"要刷新才变色"的根治点：数据当场就在响应里，
        且写入方与权威存储是同一个，不存在"前端更新了行、存储还没更新"的两张皮）。

GET /api/entries/result?key=…
  单条查询（搜索、诊断、以及前端局部恢复用）。零扫描、零重建。
```

## 四、root 级警告的拆分（一并解决「warnings 混装」）

```
现在：catalog 响应的 warnings[] 里"通用能力说明"与"某个根的具体问题"同流，
      前端 rootWarning 只能整串展示，用户分不清哪条跟自己有关。

定稿：warnings[] 拆成两个字段——
  rootIssues:       [ { rootId, text } ]      // 该根的具体问题（路径不可达、扫描截断等）
  capabilityNotes:  [ text ]                   // 全局能力说明（如"超深目录未扫描"）
```

名册上按 `rootIssues` 在**对应根**的分组头显示 ⚠；`capabilityNotes` 只在调试面板列出，不打扰名册。

## 五、迁移映射（现状 → 契约）

| 现状实现 | 归宿 |
|---|---|
| `catalog.mjs` 的 `badgeAccent`/`displayProvider`/`providerCandidates` | 并入 `entry.display`（同数据源，改名收口） |
| 内置 spine/live2d 装载器（散目录直装：probe.mjs 判型 + 前端 surfaces 选面 + kind→颜色反查） | 登记为提供者 `builtin-spine`/`builtin-live2d`（§一·五）：认领判定与展示声明进注册表，装载结果经 `/api/entries/result` 上报；**实现本体不动** |
| `roster/bundle-failures.js`（localStorage 失败缓存 + 指纹失效） | **删除**，由 §三服务端存储取代；`refreshVariantFailure` 改为消费 `loadResult` |
| `meta.missingTextures`（目录型缺纹理标记） | 转为 `support.state:'unsupported'` + `detail.reason:'missing-textures'`；meta 原字段保留一版兼容，前端切换后移除 |
| `resolve` 的即时依赖包判定（`/api/unpack/resolve` 500 + asset-dependency） | 判定逻辑不动（shared/bundle-shape），但结果**同时写入存储**——下一次 catalog 直接带出 `support`，不用等到点击才知 |
| 根警告 `rootWarning` | §四拆分 |

## 六、验收（实现完成的定义）

```
S1  冷态点开一个从未解包过的 spine 资源包：resolve 成功 ⇒ 响应回 display.accent=蓝；
    该行当场变蓝；**不做任何整表重拉**（网络面板：除 resolve/upload 外 0 个 catalog 请求）。
S2  刷新页面：同一行仍是蓝色（存储侧与展示侧同源，不存在"内存有、下次没有"）。
S3  live2d 包同 S1/S2，色=紫。归属未定条目全链路中性色，任何时刻不被涂成候选色。
S4  美术依赖包：**已解包过或后台形态探测已完成**的条目，未点击时该行已带 support=unsupported + ⚠ 与可读原因；
    点击后错误文案与 ⚠ 悬浮文案同源（同一函数产出）。
    时序约定：容器型未探测时先给 `unknown`（catalog 同步路径不做包内解析），由**后台探测任务**补写；
    首次打开允许仍是 unknown，探测完成后下一次读取即带 ⚠。禁止为了首屏带 ⚠ 而在 catalog 同步路径解析包体。
S5  装载成功后该行 ⚠ 消失（loadResult:'ok' 清痕）。
S6  更换/升级插件（providerId@version 变）后：旧结论即刻不再挂 ⚠（support 回 unknown），
    并进入一轮重探测；探测跑完带新结论与新指纹。指纹未变时**不发生任何探测**。
S7  前端 grep 不到运行时颜色字面量与 localStorage 键 'modelstage-bundle-failures'；
    颜色判定、失败判定在 src/web 内无第二处实现。
S8  散目录 spine/live2d 条目同样带 display/support/loadResult 且行为一致
    （"能直接加载的模型也纳入接口管理"的验证点：故意挪走一个目录型模型的贴图 ⇒
     列表该条 support=unsupported('missing-textures')，装回来 ⇒ 消失）。
S8b 内置装载器在 /api/plugins 可见（id=builtin-spine/builtin-live2d，带 accent 与 label）；
    目录型条目装完后 loadResult.provider=builtin-*，渲染面按 provider 分派——
    src/web 内 kind→渲染器/颜色的硬编码分派表不复存在（选面读 loadResult.provider）。
S9  全量测试绿；entry-states 读写有单测（含三条失效规则与一致性约束的构造用例）。
S10 后台探测的"平时零开销"：提供者指纹未变化时，重启服务不产生任何包内解析
    （日志/计数佐证：探测任务启动次数 = 0）。
```

## 七、不变量（评审时逐条对照）

- INV-D1 展示三字段（display/support/loadResult）**只由服务端产出**；前端只渲染。
- INV-D2 `loadResult.ok` 与其后的 `display` 永远同源一致（由写入路径保证，非读取时拼装）。
- INV-D3 装载/解包主流程不因本契约改变：状态上报失败只记日志，**绝不阻塞装载**（旁路原则，同就绪通道）。
- INV-D4 未定归属恒为 `null` ⇒ 中性色；任何"按候选顺序猜一个色"的实现都是违规。
- INV-D5 `data/entry-states.json` 属运行数据不入库（gitignore），删表 = 全部回到"未试过"，功能不受损。
- INV-D6 提供者指纹**必须写入且必须参与读取判定**（规则①的判据）。它与 catalog 的读路径、
  前端上报路径、服务端解包路径三处都要接上 —— 只接一处等于没接（实测过这种断链：三处仅一处传指纹，
  规则①形同虚设）。这条要靠集成级用例钉住，纯函数单测自己构造 ctx 会测不出接线断裂。
- INV-D7 探测是**事件驱动**而非常驻轮询：只有"首次登记该根""提供者指纹变化""显式重探"三种入口能触发；
  任何按时间/帧循环触发的探测实现都是违规（同根数百包，常驻探测会把 IO 打满）。

## 八、后台形态探测（规则①与 S4 的执行者）

```
职责：把"这个容器包到底能不能装"从【点击才知道】变成【不必点击也有结论】。

触发时机（仅此三处，见 INV-D7）：
  a) 资源根首次登记 / 清单重建后（该根有容器条目且无结论）
  b) 提供者指纹变化 ⇒ 规则①置"待探测"标记，本任务消费
  c) 显式手动重探（调试入口，可选）

执行方式：
  · 按根串行、逐包限速（与解包准入的内存口径一致，不抢装载的资源）
  · 判定复用 src/shared/bundle-shape.mjs（形态与文案唯一一份，与装载失败同源）
  · 结果写 entry-states：新结论 + **当时的提供者指纹**（否则下次读取又会判"过期"，白探）
  · 跑完即停，不留常驻定时器

不做什么：
  · 不在 /api/catalog 的同步路径解析包体（同根数百包会把毫秒级拖成分钟级）
  · 不猜内容：探不出形态（读不了头/非 UnityFS）⇒ 保持 unknown，不写 unsupported
  · 不覆盖真实装载结果：loadResult 来自当事端上报（INV-D1/§一 硬边界 4），
    探测只填 support；二者冲突时按 §二 一致性约束重算
```
