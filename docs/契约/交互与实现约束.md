# 契约 · 交互与实现约束

> 本契约收纳四条**跨模块的硬约束**：事件驱动优先、就绪信号、禁止内联 CSS/JS、不变量清单。
> 它们不属于某一层，而是「所有代码都必须这样写」的底线。
>
> 关联：[渲染面契约](渲染面.md) · [状态契约](状态.md) · [数据与接口契约](数据与接口.md)

---

# 第一部分 · 事件驱动优先

> **能事件驱动就必须事件驱动；超时与轮询一律不许，连兜底都不许。**
> 例外只有三类（见 1.2 / 1.3 / 1.4）。新增代码违反本条款视为**设计缺陷**，不是「实现细节」。

## 1.1 优先级

```
① 事件驱动（渲染器/引擎/浏览器的原生完成回调、事件监听）      ← 能用就必须用
② 依附已有帧循环（在已在跑的那帧回调里顺便检查，不新增定时器）  ← 仅当「变化可感知但无事件」
③ 定时器（setInterval / setTimeout 轮询）                    ← 仅限「判据本身依赖时间」与测试脚本
```

### 什么算「轮询」

| 算 | 不算 |
|---|---|
| `setInterval(fn, N)` 周期性检查某个状态 | 在**已经跑着的 rAF** 回调里顺便检查（零额外唤醒） |
| `setTimeout(fn, N)` 用来「等某事完成」 | 一次性延时（防抖 200ms 合并、UI 动画时序） |
| 反复 `while` / 递归 `setTimeout` 查条件 | 事件监听（`addEventListener` / `on('finish')` / `addListener`） |

**关键区分**：**新增一个定时器**去做检查 = 违反；**在已有循环里顺便看一眼** = 不违反。

### 为什么（不是教条）

1. **定时器有固定延迟**：200ms 轮询的精度就是 ±200ms，事件驱动的精度是真实的完成时刻
2. **定时器会空转**：没事发生时也在唤醒事件循环，占 CPU（本机软件渲染，CPU 本来就紧）
3. **轮询有竞态**：状态可能在两次检查之间变化又变回，轮询会漏掉（表现成「偶发失败」，极难查）
4. **定时器泄漏**：忘记 `clearInterval` 会在组件销毁后继续跑，症状是「越用越卡」

## 1.2 例外一：判据本身依赖时间

**核心判定：看判据的形状，不看「实现起来哪个省事」。**

| 判据形状 | 例子 | 能否事件驱动 |
|---|---|---|
| **「某事发生了」**（正向、有主体） | 动作播完了、面板重建完了、请求返回了、过渡结束了、元素出现了 | ✅ **必须事件驱动** —— 事件天生表达的就是「某事发生了」 |
| **「某段时间内什么事都没发生」**（负向、时间性） | 卡死检测（帧计数 N 秒没涨）、暂停后帧数不涨 | ❌ **事件无法表达「没发生」** ⇒ 这是唯一允许用时间窗口的场合 |

**为什么负向判据必须用时间**：事件系统的语义是「某事发生了」，它**没有「某事没发生」的事件**。
要证明「4 秒内帧数没涨」，只能观察 4 秒。

**所以例外只有一类**：`判据 = 某时间窗口内无变化`。写例外代码时必须标明：

```js
// 时间窗口例外：判据是「4s 内帧数不涨」（负向观察），事件无法表达「没发生」，只能观察一段时间
```

**没标理由的一律按违反处理。**

## 1.3 例外二：测试脚本（超时是必须的）

**测试脚本允许超时与轮询，而且超时是必须的。**

理由：**测试的职责就是验证「事件能不能发生」**。如果被测代码的 bug 导致事件永远不发生，
**没有超时兜底就会永久卡住** —— 测试挂死的代价比「多一个定时器」大得多。

```
生产代码：事件驱动           ← 事件本该发生
测试代码：等事件 + 必须有超时  ← 因为要能发现「事件没发生」这种 bug
```

| 项 | 要求 |
|---|---|
| 超时 | **每个等待都必须带 `timeoutMs`**，没有例外（`waitStage` / `waitFor` / `waitStable` 全部支持，用默认值也行，但不能不设） |
| 超时后的输出 | 必须能看出**当时的状态**（如 `waitStage` 超时要带当前快照），否则只报「超时」等于没报 |
| 轮询间隔 | 允许（如 `waitFor` 内部 50ms 轮询），这是实现细节 |
| 唯一禁止 | **测试里无限期等待**（无超时的 `while` / 无 `timeoutMs` 的 `waitFor`） |

**与 1.2 是两回事**：1.2 说的是**被测内容**本身是时间性的；本条说的是**测试工具**允许用超时机制。

## 1.4 两类「既不是事件驱动也不是轮询」的写法

| # | 类别 | 性质 |
|---|---|---|
| **A** | **依附已有帧循环** | 在**已经跑着的 rAF** 里顺便检查（零额外唤醒），不算定时器。**被鼓励**，但要按时间或帧数节流，不能每次 rAF 都更新 UI |
| **B** | **传输层保活** | SSE 长连接的空闲会被中间代理/防火墙断开（30~60s），必须定期发注释行。与业务判据无关，是协议要求；**只允许出现在传输层代码**（`src/server/http/`），业务代码里出现同样写法即违反 |

## 1.5 事件能力清单（做功能前先查这张表）

| 需要等的「事」 | 用哪个事件 | 位置 |
|---|---|---|
| **动作播完（一次/一圈）** | Spine `AnimationState.addListener({ complete })`；Live2D `Live2DModel.on('motionFinish')` | 由 engine 适配层统一暴露 `onMotionComplete(cb)` |
| 模型装载完成 | `POST /api/unpack/resolve` 返回 / `materialize` resolve | `infra/plugin-host.js` |
| 面板重建完成 | `panel:rebuilt` CustomEvent | `panel/panel-settings.js` |
| 过渡（影院/侧栏）结束 | `waitStage(name,'settled')` + `retrackStage` 重算 | `infra/ready.js` + `app/topbar-actions.js` |
| 渲染帧推进 | `engine` 的 rAF（**已在跑**）→ 顺便检查，不新增定时器 | `engine/frame-gate.js` |
| 资源根/名册变化 | 各自 API 返回后触发 `refresh` | `app/model-actions.js` |
| 网络请求完成 | `infra/api.js` 的 Promise（含重试/去重） | `infra/api.js` |

**新增功能前先查这张表**；表里没有的，说明该事件能力**尚未实现** —— 应该先补能力，而不是退回轮询。

| 位置 | 用途 | 判定 | 处置 |
|---|---|---|---|

| `server/http/ready.mjs:140` | SSE heartbeat | ✅ **传输层保活**（非业务判据） | 保留（有注释） |

## 1.7 审查方式

```bash
grep -rn "setInterval(" src/ --include=*.js --include=*.mjs | grep -v "clearInterval"
# 注：test/ 与 tool/ 不在本条款约束内（测试需超时兜底，见 1.3）
```

# 第二部分 · 就绪信号

> 给**机器**读的加载阶段状态通道。与 `diag` 日志互补但**完全分离** ——
> 日志是给人看的流水，这里定义的是给测试脚本 / CI 读的状态机。
>
> 目的：把测试里「等固定时长 / 轮询 DOM / 猜中间态」换成「等明确的阶段边界」。

## 2.1 为什么与 diag 分离

| | diag 日志 | 就绪信号 |
|---|---|---|
| 形态 | 追加流水，环形缓冲 500 条 | 状态机，每个阶段仅保留最新值 |
| 消费方 | 人（调试面板） | 机器（测试脚本 / CI / AI） |
| 量级 | 大 | 小（阶段数固定） |
| 时序 | 有先后顺序，需自行重建状态 | **幂等**，任何时刻可读最新快照 |
| 失败语义 | 一条 warn/error 文本 | 显式 `failed` 状态 + 原因 |

混用的后果：面板被信号刷屏；测试要从流水里重建状态（脆弱且慢）。

## 2.2 阶段与分级

### 三级状态（每个组件通用）

| 级别 | 含义 | 典型判据 |
|---|---|---|
| `mounted` | 元素已插入 DOM 且引用可得 | `querySelector` 命中 |
| `settled` | **动画/布局稳定**，读到的几何值是终值 | transition 结束、两帧后几何不变 |
| `interactive` | 可安全交互（点击/键盘不会打偏） | 无 `pointer-events:none`、无 `data-pending`、动画已停 |

> 引入 `settled` 的原因：影院模式、侧边栏收展都带 transition，只判 `mounted` 会在动画中途读到中间坐标，
> 造成测试假红（已实际发生过）。

### 模型额外分级

| 级别 | 含义 | 判据 |
|---|---|---|
| `mounted` | 渲染器已创建、画布已挂入容器 | 画布 `isConnected` 且尺寸非零 |
| `painted` | **首帧已真正绘制** | 渲染器确认画过至少一帧（非「像素采样有颜色」这类弱证据） |
| `interactive` | 可播放动作/改设置 | 动作或动画清单非空且已绑定 |

### 失败态

任一阶段都可能进入 `failed`，必须携带 `reason`（可读原因）与 `at`。
**失败是正常信号，不是异常** —— 测试应能在失败瞬间报出原因，而不是等超时后说「没等到」。

## 2.3 阶段清单

| stage | 说明 |
|---|---|
| `shell` | 应用骨架可用（`__WEB__` 已建立） |
| `topbar` | 顶栏按钮就绪 |
| `sidebarLeft` | 左栏（名册容器）就绪 |
| `sidebarRight` | 右侧控制面板容器就绪 |
| `panel` | 面板 schema 已按当前渲染器能力构建完毕 |
| `bottombar` | 底栏控件就绪 |
| `debugPanel` | 调试日志浮层就绪 |
| `renderer` | 渲染器已实例化且能力声明可读 |
| `model` | 当前模型（额外含 `painted`） |

**新增阶段需在本表登记**，不允许随手加字符串。

## 2.4 快照格式

```jsonc
{
  "at": 1730000000000,          // 快照生成时间（ms）
  "rev": 42,                    // 单调递增版本号，每次任一阶段变化 +1
  "stages": {
    "shell":        { "state": "interactive", "at": 1730000000100 },
    "sidebarRight": { "state": "settled",     "at": 1730000000300 },
    "model":        { "state": "painted",     "at": 1730000002500,
                      "detail": { "kind": "live2d", "id": "bundle-…", "actions": 34 } },
    "renderer":     { "state": "failed",      "at": 1730000002600,
                      "reason": "运行时库加载失败：…" }
  }
}
```

规则：

- `state` ∈ `pending` | `mounted` | `painted` | `settled` | `interactive` | `failed`
  - `pending` = **尚未上报**（查一个已登记但还没报的阶段时返回它；等级最低，任何真实状态都能覆盖）
  - `painted` = 仅模型阶段使用的中间级
- 阶段只前进不后退（`failed` 除外，可覆盖任何状态）
- `detail` 可选，放该阶段的关键计数（动作数、尺寸等）
- **`rev` 必须单调递增**，测试据此判断快照是否过期

## 2.5 三条读取通道

### 页面内直读（Playwright / 浏览器控制台）

```js
__WEB__.ready()              // → 完整快照
__WEB__.ready('model')       // → 该阶段对象
```

### 快照 API（外部脚本 / CI）

```
GET /api/ready               → 完整快照
GET /api/ready?stage=model   → 单阶段
```

单阶段的两种非正常回复（语义必须区分）：

| 情况 | 回复 |
|---|---|
| 阶段名**已登记**但还没上报 | `200` + `{ "stage": "...", "state": "pending" }` |
| 阶段名**未登记**（调用方写错） | `400` + `{ "ok": false, "error": "未登记的阶段：…", "known": [ … ] }` |

### SSE 事件流

```
GET /api/ready/stream
```

- **连接建立时先推一条全量快照**（`event: snapshot`），再推增量（`event: update`）
- 这是最关键的一条：只推增量会让「晚连上的测试永远等不到」—— 死锁
- 每条 update 含 `{ stage, state, at, rev }`
- 断线由客户端重连，重连后仍然先收全量快照

## 2.6 硬约束（防止它变成新的假验收来源）

1. **信号只解决「何时读」，不解决「读到什么算对」**。阶段报 `interactive` 并不等于画面正确。
   ⇒ 验收规则：**等信号 → 再断言实际内容**（DOM 数量、引擎状态、像素签名、引擎侧队列实例等）。
2. **`painted` 不能用弱证据**。像素采样「有颜色」不能证明画过帧（历史事故：画布已 detach 但采样仍有值）。
   必须由渲染器给出「已绘制帧数 ≥ 1」这类硬计数。
3. **不允许自报即通过**：`ready()` 的字段不得被测试当作功能正确的证明，只能作为「可以开始断言了」的门铃。
4. **埋点只在上报点推进状态**，不允许在渲染循环里每帧写（会造成无谓上报与抖动）。

## 2.7 测试侧用法

```js
// 反例（盲等 / 轮询中间态）
for (let i = 0; i < 60 && !q('#btn-cinema'); i += 1) await sleep(150);
await waitFor(() => rect(header).bottom <= 0);

// 采用信号后
await waitStage('shell', 'interactive');          // 骨架可用
await waitStage('topbar', 'settled');             // 动画稳定，几何值为终值
await waitStage('model', 'painted');              // 首帧已绘
// 然后再断言实际内容
assert.equal(await count('[data-ctl]'), expected);
```

`waitStage` 由测试库提供：优先订阅 SSE，取不到时退回轮询 `/api/ready`（间隔 50ms、上限可配）。

## 2.8 验收判据

| 项 | 判据 |
|---|---|
| 快照幂等 | 任意时刻读 `/api/ready` 都返回完整快照，不依赖之前是否连过流 |
| 版本单调 | 连续操作 10 次后 `rev` 严格递增 |
| SSE 先推全量 | 页面已就绪**之后**才连流，仍能立刻收到完整快照（不能只等增量） |
| 失败可见 | 人为让模型加载失败 → 该阶段 `failed` 且带 `reason`，测试立即报错而非超时 |
| 分级真实 | 影院模式切换期间，`topbar` 在 `settled` 之前的几何值确实是中间值（证明分级不是摆设） |
| 不刷面板 | 信号不进入调试面板条目（面板里 `grep` 不到 ready 事件） |
| 不替代断言 | 故意让某组件自报 `interactive` 但内容为空 → 只等信号的测试应当**失败** |

# 第三部分 · 禁止内联 CSS 与 JS

> 起因：多次因内联样式 / 内联脚本导致**只有运行时才暴露**的显示问题，且都很难定位。

## 3.1 禁止的写法

| 禁止 | 例子 | 为什么 |
|---|---|---|
| **内联 `style` 属性** | `<div style="transform: scaleY(-1)">` | 优先级压过主题/类名，且无法被统一覆盖 |
| **内联 `<style>` 标签** | `<style>.x{color:#000}</style>` | 绕过主题变量，换主题不跟随 |
| **内联事件属性** | `<button onclick="doX()">` | 无法解绑、无法测试、CSP 不友好 |
| **内联 `<script>` 标签** | `<script>window.x=1</script>` | 执行时机不可控、无法被构建/压缩 |
| **`element.style.xxx = ...` 直接写设计令牌** | `el.style.color = '#000'` | 同上（动态计算值除外，见 3.3） |
| **`innerHTML` 拼样式/脚本** | `el.innerHTML = '<span style="...">'` | 双重问题：内联 + XSS 面 |

## 3.2 正确的写法

```
样式：写进 CSS 文件，用类名 + CSS 变量
  ✅ <div class="panel-diag">  +  .panel-diag { color: var(--color-text-secondary) }
  ❌ <div style="color:#9ca3af">

脚本：写成模块，用 addEventListener 绑定
  ✅ btn.addEventListener('click', onClick)   （在 JS 模块里）
  ❌ <button onclick="onClick()">

主题：只用 CSS 变量，不写字面色值
  ✅ color: var(--color-foreground)
  ❌ color: #fff
```

## 3.3 允许的例外（仅两种）

### 动态计算值

**必须由 JS 在运行时算出来的数值**，允许写 `element.style`：

```js
// ✅ 允许：位置/尺寸/进度这类「算出来的值」
el.style.transform = `translateX(${x}px)`;
el.style.width = `${pct}%`;
el.style.setProperty('--progress', `${pct}%`);

// ❌ 不允许：颜色/字体/边框/阴影这类「设计令牌」
el.style.color = '#9ca3af';
el.style.border = '1px solid #333';
```

**判据**：

- **值来自计算结果**（坐标、百分比、数值）→ 允许
- **值来自设计决策**（颜色、字号、圆角、间距）→ 必须走 CSS 变量

> 注意：**尺寸型内联样式**（`style.width` / `style.height`）还有额外的唯一写入者约束，见 4.5（INV-13）。

### 第三方库强制要求

若第三方库 API 只接受内联样式，**必须在调用处注释说明**，并**优先从 CSS 变量读值**再传进去：

```js
// 例外：该库只接受内联色值，无法走 CSS 变量（库 API 限制）
chart.setOption({ color: getComputedStyle(root).getPropertyValue('--color-primary') });
```

## 3.4 三次真实事故（都是内联/字面色值引起）

### 事故 1：画面翻转不正常

```js
// 内联 transform 覆盖了容器的 transform
el.style.transform = 'scaleY(-1)';
// 而父容器/主题也有 transform ⇒ 两者叠加后方向错乱，画面上下颠倒
```

**根因**：内联 `style` 的优先级高于类名，**破坏了外部已有的变换链**。

### 事故 2：棋盘格背景不正常

```js
// 用内联 background 拼棋盘格
el.style.backgroundImage = 'linear-gradient(...)';
// 而主题里也定义了 background ⇒ 内联覆盖后丢失了主题的配色/尺寸
```

**根因**：内联样式**绕过了主题变量**，换主题时这块不跟随。

### 事故 3：右边栏文字颜色不统一

```css
/* 诊断块用了语义错误的变量 */
color: var(--color-muted);   /* ← 这是「深色背景」的名字，不是文字色 */
```

**表现**：标签是黑字压在深色底上 ⇒ **DOM 里文本全在，但看不见**（渲染了、但不可见，最难查的一类）。

**根因**：没有专门的「文字色」令牌，误用了背景色令牌。修复时新建了 `--color-text-secondary`（五个主题各一份）。

## 3.5 验收

### grep 检查

```bash
# 内联 style 属性（排除 SVG 的合法用法和动态 setProperty）
grep -rn 'style="' src/web/ --include=*.js --include=*.html | grep -v 'setProperty'

# 内联事件
grep -rn 'onclick=\|onchange=\|oninput=' src/web/ --include=*.js --include=*.html

# 内联 <style> / <script> 标签
grep -rn '<style>\|<script>' src/web/ --include=*.js | grep -v '\.js"></script>'

# JS 里写死设计令牌
grep -rn "style\.\(color\|background\|border\)" src/web/ --include=*.js
grep -rn "'#[0-9a-fA-F]\{3,6\}'" src/web/ --include=*.js | grep -i "color\|background\|border"
```

### 人工验收（每次改 UI 必做）

| 项 | 判据 |
|---|---|
| **五个主题各切一遍** | 所有文字可见、颜色跟随主题、无「黑字压深底」 |
| **深浅主题对比** | `dark-cyan`（深底）与 `day-paper`（浅底）下都正常 |
| **无写死色值** | 改一个主题变量，相关元素颜色应跟着变（不跟随的说明有硬编码） |

## 3.6 为什么这条必须写成契约

| 内联/字面色值的问题 | 后果 |
|---|---|
| 优先级压过类名 | 外部想统一改样式改不动 |
| 绕过主题变量 | 换主题不跟随（事故 2、3） |
| 破坏已有变换链 | 画面错乱（事故 1） |
| **只有运行时才暴露** | `node --check`、单元测试、API 自检**全都发现不了** |
| 排查成本高 | 「DOM 里文本明明在，为什么看不见」—— 最难查的一类 |

**最后一条最关键**：这类问题**静态检查抓不到、单测抓不到、API 抓不到**，只能靠「打开页面看」或「切主题对比」。
所以必须**从写法上禁止**，而不是靠事后排查。

## 4.2 逐条

### ⭐ INV-01 控件落地只经当前渲染器

- **陈述**：任何面板控件的值变更，最终调用必须是 `state.currentRenderer.setSetting(key, value)`；
  不得出现对特定渲染器对象的直连（`stage.setXxx(...)`）。
- **依据**：舞台实例恒为 Spine，切到 Live2D 后调用仍打在隐藏画布上 ⇒ 表现为「只有 Spine 有效」。
- **违反后果**：控件在部分渲染模式下静默失效，且因为调用成功、无报错，测试与日志都看不出。
- **验证**：`renderer.setSetting` 的桩记录到对应 `key/value`，且舞台方法**未**被调用；手工在 Live2D 下改设置后读 `getSetting`。

### ⭐ INV-02 几何唯一来源

- **陈述**：`cssW/cssH/dpr/res` 只能由 `Surface.geometry()` 产出；渲染器与背景层不得自行读 `clientWidth` / `devicePixelRatio`。
- **依据**：曾有第二处维护画布尺寸且 DPR 口径与引擎不同 ⇒ 像素网格与 `gl.viewport` 错配，画面缩放偏移。
- **违反后果**：切换内容/分辨率后出现缩放错位与边缘裁切，且只在特定 DPR 下暴露。
- **验证**：`canvas.width === cssW × res`、`renderer.width === canvas.width`、`renderer.resolution === res` 三者在加载后与缩放拖动后均成立；静态 `grep devicePixelRatio` 仅命中 `render/surface.js`。

### ⭐ INV-03 钳制单点

- **陈述**：缩放范围钳制只发生在统一相机一处；引擎 backend 只读写值。
- **依据**：引擎内部原本也夹 `SCALE_MIN/MAX`，与统一相机重复 ⇒ 双重钳制改变手感。
- **违反后果**：达到边界时行为与预期不一致（步进被吞、无法到达 16）。
- **验证**：`renderer.camera.zoomTo(100)` → `16`；`engine.setCameraZoom(100)` → 仍 `100`；静态 `grep CAMERA.MIN|CAMERA.MAX src/web/engine/**` = 0。

### ⭐ INV-04 声明即可实现

- **陈述**：`capabilities.settings` 与 `capabilities.debugDraw` 的每一项，`setSetting` 必须返回 `true` 且 `getSetting` 不返回 `null`。
- **依据**：曾声明支持某项但无对应实现 ⇒ 面板点亮、点了无效。
- **违反后果**：能力声明退化为「愿望清单」，面板禁用逻辑失去意义。
- **验证**：`__WEB__.panelSelfCheck()` 的 `violations.length === 0`。

### INV-05 切换渲染器重算面板

- **陈述**：渲染器切换后，面板三态（可用/禁用/不构建）必须按新 `capabilities` 重算。
- **依据**：能力应用原只在装配时执行一次，那时 `currentRenderer` 未定。
- **验证**：切换前后 `panelSnapshot()` 的 disabled 集合不同（如 `debugDraw` 若干项由存在变不构建）。

### INV-06 一键一义

- **陈述**：一个 `capabilityKey` 只对应一种语义；不同语义必须用不同键。
- **依据**：纹理过滤与滤镜预设曾共用键 `filter` ⇒ 只支持前者的渲染器会把后者也点亮。
- **验证**：静态统计 `capabilityKey` 出现次数，任一计数 > 1 需说明理由（同义控件共用才允许）。

### INV-07 背景归属唯一

- **陈述**：`data-bg` 只由 `Surface.setBackground()` 写；渲染器不绘制背景、不改 `data-bg`。
- **依据**：曾有第二写入点 + 渲染器内自建背景层，两处状态互相覆盖。
- **验证**：静态 `grep data-bg` 仅命中 surface 与 CSS；三态切换后 `getBackgroundMode() === stage.dataset.bg`。

### INV-08 回显生效值

- **陈述**：面板显示的值来自 `getSetting(key)`，不是用户点击值。
- **依据**：不支持的项被点击后若仍显示新值，用户以为已生效。
- **验证**：未声明该能力的渲染模式下点击 → 控件回退到 `getSetting` 的生效值，且日志有 warn。

### ⭐ INV-09 交互目标与可见性解耦

- **陈述**：交互绑定 `surface.interactionTarget`（舞台区域），不绑定任何一块画布。
- **依据**：切面时非当前画布 `visibility:hidden` ⇒ 不参与命中测试；绑画布的监听器一次都收不到事件。
- **违反后果**：某一渲染模式下拖动/缩放完全无反应，而代码路径看起来正确。
- **验证**：`__WEB__.surface.interactionTarget === stage 元素`；两种模式下 `camera.scale()` 经真实事件后变化。

### INV-10 被取代的加载不产生未捕获拒绝

- **陈述**：装载被新选择取代时，错误必须转为 `lastError`，不得抛为未捕获的 Promise 拒绝。
- **违反后果**：污染控制台与零错误门禁，并可能让后续装载状态错乱。
- **验证**：连点两个模型后 `problems` 中无「动作脚本异常」。

### INV-11 参数无常量裸值

- **陈述**：相机与适配参数（`0.125 / 16 / 0.1 / 0.05` 等）只能来自 `render/camera/constants.js`；能力键、排除名单同理。
- **依据**：两端各自写死导致范围不一致（Live2D 曾为 `0.2~6`），调参要改多处。
- **验证**：静态 grep 逻辑文件中这些字面量（定义文件除外）= 0。

### ⭐ INV-12 数值判定优先于「没报错」

- **陈述**：任何「行为与既有实现一致」的结论必须由可比较数值给出（像素占比、`baseZoom`、`trackTime`、
  `transform` 值、逐项 `===`），且判据必须**已证明能变红**。
- **违反后果**：把「无报错」当验收 ⇒ 缺陷延迟暴露、修复方向错误、测试可信度被磨掉。
- **验证**：每条行为对齐交付附「新 vs 既有」数值对照表 + 一项反向验证（阈值改成不可能满足，确认为红）；
  断言失败输出需含 `expect / actual`。

### ⭐ INV-13 尺寸型内联样式唯一写入者

- **陈述**：任何元素的**尺寸型内联样式**（`style.width` / `style.height`，以及 canvas 的 `attr` 与 `style` 两套尺寸）
  只能由 `Surface` 写入。渲染器与覆盖层模块不得直接写这些属性，只能请求 Surface 更新（`setOverlayBox(cssW, cssH)` 一类接口）。
- **依据**：覆盖层容器同时被两处管理 —— Surface 建容器并给 `width/height:100%`，而渲染器又把容器写成内联 px。
  旋转后几何、渲染器、canvas backing 全部正确更新，**唯独容器的内联 px 停在旧值**；容器带 `overflow:hidden`，
  于是画布被裁在左上角、右侧露出棋盘格。真机实测：`#stage=1035x777`，而 overlay 的 `client` 仍是 `777x1035`。
- **违反后果**：几何正确但显示错误 —— 所有「检查几何是否更新」的排查手段**全部失效**，因为几何本来就是对的。
  缺陷表现为「画面错位但零错误、零异常」，且「手动重新加载模型」能临时恢复，极具误导性。
- **验证**：
  - 静态：全库扫 `style.width =` / `style.height =` 赋值点，白名单只允许 `render/surface.js` 的尺寸写入函数
  - 运行时：`overlay.clientWidth === geometry().cssW` 且 `overlay.clientHeight === geometry().cssH`，旋转/改视口后仍成立
  - 反向验证：注释掉 Surface 的尺寸同步赋值，必须复现「内联 px 停在旧值」
  - 排查指引：遇到「几何对但画面错」，**先量元素的 client 与内联 style**，不要继续怀疑几何链路

## 4.3 「没报错但行为已坏」实例集

| # | 现象 | 为什么零错误门禁看不出来 | 只有什么能抓到 |
|---|---|---|---|
| 1 | 装载每帧抛异常，画面空白 | 异常被 `catch` 吞进 `lastError` | `lastError === null` + `samplePixels().ratio` |
| 2 | 拆分把全局出口随 state 块搬走 | 全站 `window.__WEB__ && …` 静默短路，无报错 | `stageLog` 非空、看门狗计数在涨、调试日志实例已挂 |
| 3 | 底栏接线引用了已迁出函数 | 异常被 transport 的 `try/catch` 吞掉，点击无反应 | 点击后状态/数值变化（`data-*`、播放态、帧数） |
| 4 | 配置加载 / 自检未随迁 | 只体现在数据为空（名册 0 行、根状态 error） | 资源根数量、名册行数、`panelSelfCheck()` 可调用 |
| 5 | 防卡死检测「测不出停滞」 | 代码正常、只是测试时间窗不够 | 冻结期间 `ticks` 增量必须 ≥ 阈值的显式断言 |
| 6 | 样式表指向不存在的文件名 | 该模块此前从未被挂载，一接线才 404 | 页面零错误门禁（4xx 计入） |
| 7 | `loadingModel` 只被 set 从未被读 | 标志设了但没人查，等于没有防护 | 构造「重建中」状态看是否真跳过帧 |
| 8 | 切 PMA 档位后画面冻结 | 循环停了但不报错；**`debug().frames` 仍在涨** | `engine.isPlaying` + 两次像素指纹对比 |
| 9 | 「代码里有 resolve 调用」当作已接入 VFS | 调用写着但共享实例没装配，该路径从未执行 | `stats().hits` 增量 + 反向归零 |

> 第 2–4 条的共同点：**重构把「休眠依赖」激活**，而它们全部是静默失败。这类改动必须配行为断言。
>
> 第 7–9 条的共同点：**指标/结论与它要证明的事脱钩**。
> 第 8 条尤其要记住：`frames` 确实在涨，但它涨的原因与「画面有没有在动」无关 ——
> **「能观测」不等于「观测的是那件事」**。选判据时要问一句：这个数变了，一定是那件事发生了吗？
