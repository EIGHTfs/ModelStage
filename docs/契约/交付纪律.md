# 交付纪律（代码质量与复用）

> 适用于**所有**任务（功能 / 重构 / 修复 / 文档）。违反任一条的交付都算未完成，不因"功能能跑"而豁免。

---

## 一、不只是「功能完成」

```
每完成一小步，就用审计工具扫**本次 diff**（code_audit scope=diff），顺手优化本次触及的代码：
  · 短变量名：语义能明确就改（p → reqPath、el → element、c → color），只改动到的函数
  · 魔数：时间 / 尺寸 / 阈值提成命名常量并注释含义（数据表常量如 CRC 表、像素上限不动）
  · 重复调用：同一实参在同函数内重复调用的，合并成局部变量
不留"以后再清"的尾巴 —— 那一版永远不会来
```

**判据**：本次 diff 里新增/修改的代码，读的人不需要猜任何数字或名字的含义。

---

## 二、禁止相似功能多处实现

```
动手前先搜：这个功能是否已有同类实现（工厂 / 公共函数 / 纯函数库 / 既有注册模式）
  有 ⇒ 必须复用
  不能复用 ⇒ 交付时写明"为什么 X 不能用"，具体到 文件:函数名
```

**本项目真实反例**（都发生过，代价是两处真相、改一处漏一处）：

```
· Live2D 清单路径在两个模块各实现一遍（models.mjs 与 live2d.mjs）
· 内存条定位逻辑：舞台版与面板版各一套，改位置时漏掉一处
· DOM 工厂 el() 在 panel/dom.js、roster/rows.js、debug/panel.js 三处重复
```

---

## 三、新增功能优先并入既有工厂 / 公共层

```
优先顺序：扩展既有工厂的参数  >  并入既有公共函数  >  新增独立模块
不许因为"改既有代码麻烦"就新开一条并行路径 —— 并行路径 = 未来的两份真相
```

**判据**：交付时能列出「复用了 X（文件:函数）」。若一项都没复用，必须给出理由，而不是默认新建。

---

## 四、交付时必报的三项

```
1. 复用了哪些既有函数 / 工厂（文件:函数名）
2. 新增了什么，为什么必须新增
3. 本次顺手优化了什么（短名 / 魔数 / 重复调用），以及 diff 审计结果（blocker / warning 数）
```

---

## 五、与其它约束的关系

```
· 行为等价优先于整洁：重构只允许改结构，不改行为（判据写进各自任务）
· 顺手优化只做"触及范围"：不为了改名去动未被本次改动碰到的代码（防止 diff 失控）
· 与《交互与实现约束》《测试脚本结构》并列：那两份管"怎么写"，这份管"交付前做到什么程度"
```
---

## 六、验证不得打断正在使用的实例

```
· 用户在 8804 上看着页面时，**禁止**为验证而 `web.sh restart` 那个实例 ——
  一次重启会让页面所有在途请求失败，实测后果：Live2D 运行时脚本加载被打断 ⇒
  之后每次激活都失败，只能刷新（2026-10-27 真实事故）
· 优先用**独立实例**验证（独立端口 + 独立数据根）；确实必须重启主实例时：
  先确认没人正在用，且**一次改动只重启一次**（不要"改一行重启一次"地刷）
· 前端侧容错不能替代这条：瞬时失败不该被永久缓存（见 live2d/pixi-app.js 的 libsReady 修复），
  但"页面不会坏"不等于"可以随便重启"
```

## 七、改文件一律用 DSH 工具，禁止 shell 批量改

依据 `tool-usage-rules`（用户级 skill，2026-09-30 确立）：

```
读文件 = read 工具 ｜ 写文件 = write 工具 ｜ 改文件 = edit 工具 ｜ 搜内容 = grep 工具
bash 只用于跑命令、装依赖、跑测试 —— 不用它做读写文件
```

**这条对 Lead 自己也成立**。违反记录（本项目实测，都是同一类）：

```
· 用 python heredoc 批量替换改 src/web/** 与 docs/** —— 改完不看 diff，只能靠跑测试兜
· 用 `text[:start] + text[end:]` 按索引切片删代码，把区间内的其它定义一起删掉：
  一次删掉 ui-state.js 的导出、一次删掉 panel-settings.js 的 bindPluginPanelRebuild
  ⇒ 语法仍合法，直到运行时才炸（页面停在半初始化，0 个分组）
· 用 sed -i 改代码 —— CIFS 上还会把文件权限改成只读（踩过一次，得删文件重建）
```

**正确做法**：

```
✅ 一处改动 = 一次 edit：锚点必须唯一命中；命中不到就报错，绝不静默跳过或"大概改到了"
✅ 多文件批量改动 → 拆成多次 edit（每个文件一次），每次都能看 diff
✅ 大规模重构（真的需要）→ 先写方案、再逐个文件改，禁止一次脚本刷全仓
```

**改完必须做符号完整性检查**（尤其动初始化路径上的文件：`main.js` / `panel-settings.js` /
`spine.js` / `live2d.js`）：

```
1. 每个"被调用但可能刚被删"的函数名 grep 一遍：定义 1 处 + 调用 ≥1 处
2. node --check
3. 真跑一次页面，确认结构完整（面板组数、控件数、自检 violations 为空）
   —— 不看这一条就继续下一步，等于把错误往后传
```

## 八、成员先调研汇报，批准后才允许改代码

**成员（团队成员 / 子代理）不得直接动手改代码。** 每轮先交「调研汇报」，五项固定格式：

```
1. 现状   读到的具体位置（文件:行）+ 现在到底是什么行为（要引用原文，不是转述）
2. 根因   若在查问题：机制层面为什么这样（不是"我没注意"）
3. 方案   打算改哪些文件、改成什么样；**为什么不用别的做法**（至少比较一个替代方案）
4. 影响面 谁调用它、改错会破坏什么、要不要动测试
5. 不确定项 至少一条；确实没有就写"无"，但整节空白视为没做功课
```

Lead 批准后才允许 `edit`。**违反即打回，不计入进度。**

### 为什么立这条（本项目真实代价）

成员多次跳过调研直接改，代价都是"看起来能跑、实际失效"：

```
· 用索引切片删代码，把相邻定义一起删掉 ⇒ 页面停在半初始化（0 个分组）
· 把 uniform 写进不存在的属性（spine Shader 没有 uniforms）⇒ 值永远到不了 GL，
  表现却是"效果不生效"，白查好几轮
· 在 PIXI 里重复声明 uSampler / vTextureCoord ⇒ shader 编译失败（框架本来会注入）
· 占位符留在模板注释里 ⇒ 注入落进注释，GLSL 语法错但 node --check 全绿
```

这些错误**都能用一次 grep 本地 vendor 源码 + 通读 50 行上下文避免**。
调研汇报不是流程表演，它换掉的正是"改完再靠运气发现"的那几轮返工。

## 九、验收结束后必须关闭浏览器页面

**原因（实测，不是理论）**：headless 浏览器里停着一个 60 FPS 动画页，其 GPU 进程会**持续**吃满单核 ——
页面不可见也照跑，因为是软件 WebGL 在逐帧绘制。

```
2026-10-27 实测：一个验收后没关的标签 ⇒ GPU 进程 174% CPU
  3 核机器 load average 5.35（1.8 倍超载），持续数小时
  关掉会话后：5.35 → 3.80 → 2.27 → 1.85，GPU 进程瞬时占用 0%
```

**规则**

```
1. 每次用浏览器验完（截图 / 点击 / 探针），**立刻关闭会话**，不要留着标签
2. 验收报告里连带说明"已关闭浏览器会话"（让人知道 CPU 不会再被自己占着）
3. 长任务中途要再次验画面时，验完立即关，不要留到任务结束
4. 判断"现在还有没有在烧 CPU"必须看**瞬时值**：
   采两次 /proc/<pid>/stat 的 utime+stime 求差；
   `ps aux` 的 %CPU 是**进程生命期均值**，会把人带偏（实测：宿主显示 47.9%，瞬时其实是 64%）
```

**为什么写进交付纪律而不是随手提醒**：这条和"提交前跑审计"一样，属于**收尾动作**。
收尾动作不写进纪律，就一定会漏 —— 今天漏了两次，代价是用户机器半瘫几小时。

## 十、改动必须按「三端」分类汇报

**规则**：任何交付/验收汇报，改动清单**按三端分组**，不允许混成一串文件列表。

```
网页前端   src/web/**（含 panel / roster / render / engine 的浏览器侧）
服务端后端 src/server/**、tool/**（HTTP 路由、解包、缓存、CLI 工具）
插件端     plugins/**（含各插件自带的 lib/ 与依赖）
```

**为什么**：

```
① 三端的**验证方式不同**：前端要真机渲染截图；服务端要接口/单测；插件要 probe + 解包产物比对。
   混在一起写，验收时容易漏掉某一端的验证方式
② 三端的**风险面不同**：前端改错=画面不对；服务端改错=接口挂；插件改错=资源包打不开。
   分组后一眼能看出"这次动了几端"，从而判断该跑哪几套回归
③ 三端的**依赖策略不同**：插件按独立项目对待、可自带依赖；主项目不强求零依赖；
   前端不能引 npm（vm 沙盒 classic script，见 README「依赖形态」）
```

**格式**：

```
【网页前端】文件 → 改了什么 → 验证方式与结果
【服务端后端】…
【插件端】…
（某端没动就写"未改动"，不要省略 —— 省略会让人以为忘了检查）
```

这条属于收尾动作，和 §九 一样：不写进纪律就一定会漏。

## 十一、全量门禁只由 Lead 跑

**规则**：`node tool/test-all.mjs`（含 `--browser`）与全量 `node --test test/*.test.mjs`
**只由 Lead 执行**；成员不得跑全量门禁。

```
成员需要验证时：跑与本端相关的单套 —— node tool/test-all.mjs --only <名字>
或 node --test test/<具体文件>.test.mjs
```

**为什么**：

```
① 成员并行改文件时跑全量 ⇒ 读到的是别人刚写到一半的文件 ⇒ 假红。
   实测：某次 148/150（2 fail），随后连跑三次 150/150 全绿，用例名因为重跑而丢失
   排查成本 > 收益，而且会误导下一轮判断
② 全量要跑 2~5 分钟且吃 CPU/内存，多人同时跑会把机器拖慢（本机 3 核）
③ 只有 Lead 掌握"当前有没有人在改文件"的全局视图（list_agents）
④ 失败必须当场把 not ok 全文落盘，成员常因上下文耗尽丢掉这些信息
```

**Lead 侧配套**：

```
· 跑全量前先确认无成员在 running（list_agents）
· 失败时把 `not ok` 全文与用例名落盘（不许只看数量）
· 成员并行期间要验证，用 --only 隔离，不要跑全量
```
