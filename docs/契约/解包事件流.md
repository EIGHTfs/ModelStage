# 契约 · 解包进度事件流（`unpack/events/v1`）

> **状态：已评审定稿 · 未实现**。本文件只定义契约，不含实现；评审决定统一记在文末「修改记录」。
> 定稿不等于已落地：字段、事件、阈值已定死，实现须按本文，发现不符先改本文再改代码。

---

## 零、这份契约要解决什么

服务端解包的**耗时不具备可预期上界**，且随部署差异极大：

| 场景 | 实测值 | 来源 |
|---|---|---|
| 本机 anchors 包（33.4 MiB 解压后、LZMA） | `unpackMs` 9.4s，墙钟约 17.8s | `docs/设计/解包搬进worker线程.md` §7.0 |
| 同包走 SMB 读盘 | `phases.readMs` 可达数秒 | 同上（`readMs` / `pluginResolveMs` 分开记就是为此） |
| 更快的机器 | 可能 2s 级（尚无外部实测样本，只有"部署差异大"这一条观察） | 推断，不作为承诺值 |

客户端若用「总时长」判定失败，慢机器必然误判成失败并重试；而服务端其实还在正常解。
**本契约把失败判据从「总时长」改为「有没有进展」（按事件判定）。**

双解包暂时保留：浏览器自己解自己用；服务端解完写缓存，下次命中更快。本契约不取消任何一条路径。

## 一、协商：怎么开流

### 1.1 结论

**在 POST body 里加一个布尔字段**，不新增路由：

```
POST /api/unpack/resolve
{ rootId, rel, allowOverLimit?, stream?: true }
```

`stream` 为 `true` ⇒ 走事件流；**缺省 / false / 非布尔** ⇒ 走现状（一次性 JSON）。
协议形态**只由这一个字段单向决定**，服务端不提供 config/env 全局开关（见「修改记录」）。

### 1.2 为什么选它（而不是 `Accept: text/event-stream`）

| 考量 | body 字段 | Accept 头 |
|---|---|---|
| 与现有调用方式的一致性 | 同一条 POST + JSON body，客户端只多传一个字段 | 要改请求头策略，且 `api.js` 的封装目前不透传自定义头 |
| 中间层风险 | body 原样透传 | `Accept` 可能被反代/UA 改写或合并，一旦被改成 `*/*` 就静默退化 —— 而"静默退化"正是本契约要消灭的那类问题 |
| 服务端分流成本 | 读已解析的 body | 需另解析头并处理大小写/多值 |
| 未来扩展 | 可平滑再支持 Accept 作为别名（非破坏性） | — |

字段名定为 `stream`。

### 1.3 硬约束：不带协商 = 逐字同现状

```
同状态码（200/400/404/500 的分工完全不变）
同响应体（JSON 键集合不变，不新增/删除字段）
同 Content-Type（application/json）
不产生任何事件、不占用流、不改变耗时特征
```
这条是**回归判据**，不是"尽量"。

## 二、事件格式与字段

传输用 SSE 风格分帧（`event: <name>` + `data: <json>` + 空行）：

```
event: phase
data: {"name":"read","ms":1840}

```

为什么用 SSE 分帧而不是裸 NDJSON：SSE 有 `event:` 天然分类型、分帧规则明确（空行分隔、`data:` 前缀），
不必自己再约定"一行一 JSON"的转义与多行处理。
（注意这是 **POST 流**：浏览器原生 `EventSource` 只支持 GET，本流不能也不必用它 —— 客户端读法见设计文档 §四。）

**任何事件都不携带百分比与预计剩余时间**：服务端给不出可信的解压进度（LZMA 单块是一次性整段解），
假进度条比没有进度更糟。进度语义只有"到了哪一段"。

### 2.1 事件表

| 事件 | data 字段 | 字段来源 | 何时发 |
|---|---|---|---|
| `queued` | `{ waiting }` | `waiting` = 当前排队的解包任务数（**粗粒度、允许偏差**，只给"前面还堵着几个"的量感，不是精确位次） | 进入队列后发；不承诺随队列变化实时更新 |
| `start` | `{ fp, rootId, rel }` | `fp` = `fingerprintOf()`；`rootId`/`rel` = 请求参数 | 开始解包（worker 真正启动）时 |
| `phase` | `{ name, ms }` | 见 §2.2 映射 | **每段结束时**各发一条（不发段开始，见 §2.2） |
| `done` | `{ fp, hit, files, unpackMs, phases }` | `files` = 产物清单（同现有 `files` 字段）；`phases` = 现有 `phases` 对象原样。**服务端不发 `ok` 字段**（成功即 done 本身），客户端消费时统一补 `ok:true`，与失败形态 `{ok:false,reason,message}` 对齐 | 见下"两条 done 路径" |
| `error` | `{ reason, message }` | `reason` 见 §六 | 失败时；**之后必须关流** |
| `ping` | `{}` | — | 心跳，见 §三 |

> ⚠️ **`phase` 的已知限制（实现后实测，必须写清）**：`read` / `resolve` / `write` 三段的耗时都在
> **解包 worker 内部**产生，主线程只有拿到最终 reply 才知道毫秒数 ⇒ 三条 `phase` 事件实际会
> **与 `done` 同一时刻到达**（实测 24.6s 处三条齐发）。契约"每段结束时各发一条"字面成立，但
> **体感是后置的**，不能靠它做实时进度。
> 要真·实时进度，得让 worker 在解包过程中增量上报（另一轮改动）。
> ⇒ 当前进度显示的正确做法：`queued`/`start` + `ping` 维持"还在动"的观感，
> 真正的分段耗时看 `done.phases`。

**`done` 的两条路径（都必须发，不能只有落盘那一条）**：

```
① 命中缓存：stream:true 但 index.json 已在 ⇒ **立即发 done{ hit:true, … } 并关流**，
   不发 queued / start / phase。
   （否则命中场景整个流一帧都没有，客户端只能干等到停摆判据 —— 这是最严重的坑）
② 真正解包：解完落盘后发 done{ hit:false, … } 再关流。
```

**`hitOnly` + `stream` 的组合语义**（原契约未定义，实现时按此定稿）：

```
hitOnly:true 且 stream:true ⇒ **只查缓存，绝不解包**：
  · 命中 ⇒ 一帧 done{ hit:true, … } 后关流
  · 未命中 ⇒ 一帧 done{ hit:false, missReason } 后关流（不发 queued/start/phase）
理由：hitOnly 的语义就是"只问有没有"，与是否流式无关；把它实现成"会解包"会让调用方无法预测代价。
```

### 2.2 `phase.name` 与现有 `phases` 字段的映射（必须一一对应，避免两套词）

| `phase.name` | 对应现有字段 | 含义 |
|---|---|---|
| `read` | `phases.readMs` | 从磁盘读整包 |
| `resolve` | `phases.pluginResolveMs` | 插件解压/解析（worker 内） |
| `write` | `phases.writeMs` | 产物落盘 |

`phases` 里另有 `unpackWallMs` / `probeMs` / `totalMs` / `files` 四个值：**不发 `phase` 事件**，
只在 `done.phases` 里给全（它们的粒度不足以支撑进度显示，单独发只会增加噪音）。

`phase` **只发段结束、不发段开始**：段结束才有力气算 `ms`；段开始那一帧只能让进度早显示半秒，
代价是每段翻倍的事件量与一套 begin/end 配对状态。

## 三、心跳

**每 2 秒一条 `ping`**（`{}`）。

理由：没有心跳就无法区分"服务端在慢慢解"与"连接已经死了"。有了心跳，客户端只需判"多久没收到任何事件"。

运维注意：若反代 `proxy_read_timeout` 小于心跳间隔的若干倍，连接会被切；届时心跳间隔随反代一起调，不改停摆判据。

---

## 四、停止判据（客户端侧）

```
· 总时长：**无上限**（慢机器解 30s、60s 都属正常，不得据此判失败）
· 停摆：连续 **15 秒**没有任何帧（含 ping）⇒ 判定服务端已不再响应，中止
· 心跳 2s ⇒ 15s 容忍连续 7 个心跳丢失，够扛反代抖动
· **连接建立阶段也算在内**：停摆计时从发起 fetch 起就开始（不等响应头回来才起）
  —— 否则"服务端接了连接却迟迟不回响应头"这一段无人看守，会真挂死
```

**这条不是"超时"，任何文案与日志都不许写成 timeout/超时**：
它是"没进展"的传输层判据，与"业务失败"分家 —— 中止时记 `reason = 'stalled'`，
不得与 `insufficient-memory` 等业务 reason 混用，也不得复用"请求超时"那类既有 message。

---

## 五、断连语义

**一律「服务端继续解完并写缓存」**，不因客户端离开而中止解包。

理由：① 解到一半中止的产物没有价值，而解完的产物下次能命中；② 服务端无法可靠区分
"用户主动取消"与"网络抖了一下"，按前者处理会在网络抖动时白白丢掉已解的部分。

| 情形 | 服务端行为 | 客户端行为 |
|---|---|---|
| 用户主动取消（abort / 关页面） | 继续解完、写缓存；停止推送事件 | 放弃等待 |
| 网络断开（TCP 断、反代超时） | 同上 | 重连后**不带 `stream`** 先查缓存（`hitOnly`），命中即用 |
| 服务端重启（解包中） | 产物未落盘 ⇒ 缓存里没有 ⇒ 下次重新解 | 下次按未命中处理 |

**实现落点（否则"继续解完"会崩在写已关闭的响应上）**：

```
· routes 必须监听 res.on('close')：断开时把这个订阅者从 listeners 摘掉并停心跳
· 往已断开的 res 写事件（write 抛错 / ERR_STREAM_WRITE_AFTER_END）必须静默吞掉，不得冒泡成 500
· 摘除后解包任务继续跑完并落盘 —— 事件推不出去不影响缓存写入（产物写入不依赖连接）
```

`done` **不带 `abandoned` 之类"有没有人在听"的标记**：解包结果与监听者无关，加这个字段只会诱导实现去区分两种本来等价的结局。

## 六、失败与错误码

`error.reason` **复用现有 reason 清单**（取值来自 `src/server/unpack/*.mjs` 与 `routes.mjs`）：

```
bad-args / bad-json / bad-result / canhandle-threw / empty-files / empty-list / exception
file-missing / forced-fail / insufficient-memory / no-index / no-package / not-found
not-handled / over-limit-allowed / peek-failed / plugin-unavailable / read-failed
resolve-threw / source-changed / source-missing / source-unresolved / unpack-failed / worker-error
```

加上本契约新增的一个：

```
stalled   —— 客户端侧停摆判据（§四），不是服务端 reason，只出现在客户端日志
```

规则：

```
· error 事件之后**立刻关流**（否则客户端要等到停摆判据才反应过来）
· error 之后不得再发 done；done 之后不得再发 error
· 流内错误不再用 HTTP 状态码表达（HTTP 200 + error 事件），因为响应头在第一帧就已发出；
  带 stream 的请求若在**开流前**就失败（如 bad-args、not-found），仍按现状回 400/404 + JSON
  —— 这类错误不进入流，与 §1.3「不带协商逐字同现状」同构（见验收 E9）
```

## 七、兼容条款

| 组合 | 行为 |
|---|---|
| 新客户端 + 新服务端（带 `stream`） | 事件流 |
| 新客户端 + 新服务端（不带 `stream`） | 一次性 JSON（现状） |
| 老客户端（旧 JS、旧缓存里的 bundle） | 永远不带 `stream` ⇒ 现状 |
| 新客户端 + **老服务端**（不认识 `stream`） | 服务端忽略未知字段 ⇒ 回一次性 JSON。客户端必须靠 **`Content-Type`** 判断"这不是流"，回落为一次性解析，不得当成协议错误 |
| 多客户端同时等同一个 `fp` | 都收到同一批事件（广播），服务端只解一次；后来者也收 `queued{waiting}`（粗粒度，不发"瞬时精确 0"） |

## 八、验收条款（可测）

```
E1  不带 stream ⇒ 与改造前逐字相同：状态码、响应 JSON 键集合、Content-Type 均不变，且无事件帧
E2  带 stream 且未命中 ⇒ Content-Type 为 text/event-stream；2s 内至少收到一条事件（queued 或 start）
E3  带 stream 但命中缓存 ⇒ **首帧即 done{hit:true}**，全程无 queued/start/phase，随即关流
E4  静默期 ≥ 2s 必有一条 ping（连续 ping 的间隔都在 [1.5s, 3s] 内）
E5  停摆可观测：注入"worker 卡住 ≥ 15s" ⇒ 客户端中止且 reason='stalled'，日志里能查到，
    且该日志文案不含"超时/timeout"
E6  断连不丢产物：客户端在解包中途 abort ⇒ index.json 仍被写出，下次 hitOnly 查询命中
E7  多客户端：两个并发请求同一 fp ⇒ 都收到 done，且服务端 unpackCount 只 +1
E8  失败走事件：insufficient-memory ⇒ 流内 error 事件 + 关流（不是一次性 500）
E9  开流前失败仍用状态码：bad-args ⇒ 400 + JSON（无事件帧）
E10 兼容回落：模拟老服务端（不认 stream）⇒ 客户端按 Content-Type 回落到一次性解析且功能正常
```
