### C1.1 组数怎么取（**已经不写死**）

```
test/browser/panel-actions.js:300-301
  const expectedGroups = Number(document.documentElement.dataset.panelGroups || '0');
```

**结论**：组数是"页面自报的数字"，插件新增分组只要走 `groups` 这条路，`dataset.panelGroups` 自动跟着涨 ⇒ 这条断言**天然支持额外组**，S3 不需要改它。

### C1.3 控件默认值怎么验

```
test/browser/panel-actions.js:339   const defaults = window.__WEB__.panelDefaults
写入方：src/web/main.js:539（state.panelDefaults = state.panel.defaults）、:583（getter 暴露）
```

## C2 "内置 9 组必须都在 + 允许额外组"怎么落地

**结论**：**只改标题那一条断言**（:337 + :441-445）；组数断言（:300-306）本来就不用改。
另有三处看起来该放宽、实际**绝不能放宽**，以及一处"天然免检"必须显式补上。

### 可以/应该放宽

| 断言 | 现在 | 改成 | 依据 |
|---|---|---|---|
| 组标题 | 9 个逐字全等 | ① 9 个**必须都在**（子集断言）② 额外组必须 `plugin.` 前缀（设计 §七·一）③ 额外组排序在所有内置组之后 | `panel-actions.js:337,441-445`；设计 `插件插槽.md:167-174` |

建议的断言形态（伪代码，仍在 `runGroupTitles` 内）：

```
内置 9 个标题逐个 assert(titles.includes(t))          // 不许少
额外标题 = titles.filter(t => !BUILTIN.includes(t))
assert(额外标题.every(t => /^plugin\./.test(groupIdOf(t))))   // 需要 DOM 暴露 groupId（见下）
assert(内置 9 个的相对顺序 === 声明顺序)                       // 顺序不许乱
```

⚠️ 前置：现在 DOM 里只有标题文本，没有分组 id。要断言"前缀"，需要面板把 `data-group-id` 写到手风琴节点上
（`panel-settings.js:443` 附近）。这是**测试需要的一处实现增补**，不是纯测试改动。

### 绝不能放宽（硬约束）

| 约束 | 为什么不能松 | 依据 |
|---|---|---|
| `enabledIds === declaredWired` | 插件控件若"显示但不可点"，用户点了没反应；这条一旦放宽，"假控件"就合法了 | `:309`（`panelWired` 源 `src/web/app/ui-state.js:424-429`） |
| `disabledAllPending` | 未接线必须是唯一的 disabled 原因，否则"控件失灵"会被 data-pending 掩盖 | `:280` |
| `orphanCapabilities === 0` | 能力键没声明就构建 = 面板能选、渲染层不认 | `:310` |
| 分类门禁 `gateMiss === 0` | 插件控件也必须在四类里落一类；**"来自插件"不能作为免检理由** | `:241-265` |

### 一处"天然免检"，必须显式补

`orphanCapabilities` 的遍历用的是**静态表** `PANEL_GROUPS`（`:288-296` `for (const g of mod.PANEL_GROUPS)`），
而插件控件是渲染期合并出来的新数组（`src/web/panel/schema.js:410-451` `mergePluginControls` 返回 `{groups}`，**不改静态表**；
调用点 `src/web/panel/panel-settings.js:393`）。于是：

```
:293  const def = byId.get(id);
:294  if (!def || typeof def.capabilityKey !== 'string' ...) continue;   // 插件控件在这里被跳过
```

**结论**：插件控件的能力键**当前不受任何断言保护**（写错也不会红）。建议补一条独立断言：
"DOM 里每个 `data-ctl` 若属于某插件（id 带 `plugin.<pluginId>.` 或节点带 `data-plugin-id`），
其 capabilityKey 必须在 `caps.settings` 里" —— 这条不能依赖 `PANEL_GROUPS`。

### 另一处会误报的地方（写实现时注意）

`tool/check-wiring.mjs:176-179`（W2）会报"代码引用但 schema 没有"。若把插槽聚合结果塞进 `PANEL_GROUPS` 的**静态导出**，
W2 会对着插件控件报错。**建议维持现状：静态表不动，聚合只在渲染期发生**（`panel-settings.js:393` 已是这个形态）。

## C3 四类行为怎么写成机器可验证用例

**结论**：四类里 **3 类可以在 node 单测里跑（秒级、无需浏览器）**，只有"DOM 真的多/少了一个控件"必须浏览器。
前提是把插槽注册表做成 **DOM-free 模块** —— 实测 `src/web/infra/plugin-host.js` 在 node 里 import 直接抛 `window is not defined`，
而 `src/web/panel/schema.js` 可以 import（11 个导出、9 组，`mergePluginControls(PANEL_GROUPS, [], {})` 返回 `{added:0,rejected:0}`）。

| 行为 | 建议形态 | 关键断言 | 依据 |
|---|---|---|---|
| ① 注册（声明过才允许） | **服务端 node 单测** + **前端 node 单测** | 清单声明 `slots:['panel.group.设置']` ⇒ 允许；未声明 ⇒ 拒绝 + 有 warn 记录 | 清单校验入口 `src/server/plugins/registry.mjs:192`（`readPluginManifest`）/`:302`（`readPlugins`）；夹具先例 `test/fixtures/plugin-effects/*/plugin.json` |
| ② order 排序 | **node 单测**（纯函数） | 同插槽三次注册 order=100/50/1000 ⇒ 结果顺序 50,100,1000；同 order 按注册先后 | 现有合并**不做排序**（`schema.js:439` 取目标组、`:445` 直接 `concat`），排序是新逻辑，必须单测锁 |
| ③ disposer 回收 | **浏览器**（DOM 级）+ **node 单测**（注册表级） | 卸载后 DOM 里该控件消失、内置控件 id 序列不变；注册表 list 长度回退 | 现状**无 disposer**：`plugin-host.js:101` 的 `controlSections` 只 `push`（`:244`），全文件无 `unload/dispose/clear` 命中 ⇒ 卸载后控件不会消失（除刷新） |
| ④ 拒绝未声明插槽 | **node 单测**（注册表）+ **服务端单测**（清单） | 抛/返回拒绝原因 + 记一条 warn（不静默） | 设计 `插件插槽.md:62-63`"直接拒绝并记一条 warn" |
| ⑤ 注册**时机**（补充项） | **浏览器**（注册窗口在装载期） | 同步求值期注册 ⇒ 成功；`setTimeout`/`await` 后注册 ⇒ 被拒 + warn 里能看出是哪个插件 | `plugin-host.js:236-237`（`if (!pluginId) reject`）、`:262` 置位 / `:273` 清空（`loadingPluginId` 只在注入期有效） |

```

src/web/infra/plugin-host.js:244   controlSections.push({...});       // 无 disposer
src/web/infra/plugin-host.js:1362  controlSections: () => ...         // 只读导出
```

## C5 回归基线怎么守（不装插件时逐项一致）

**结论**：**项目没有任何快照/基线机制**。全仓 grep `baseline|golden|snapshot` 只命中无关的 `baselineBytes`（内存门槛）；
`runtime/test-results/<run>/<suite>.json` 只存**套件级元数据**（`suite/failed/total/problems/.../stdoutTail`），
`panel-actions.json` 的 `results` 是空数组 —— 逐条明细只存在于 stdout 文本里，没有结构化可比对物。

三种可选做法（我推荐 ①+③ 组合）：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| ① 运行期自证"基线=内置声明" | 新增一条断言：控件 id 序列 + 组标题序列 + `panelDefaults` 归一化后算 hash，与**从内置表推导出的期望**比对（不是与历史文件比） | 零新增文件、永不陈旧、插件贡献天然被排除 | 只能证明"与声明一致"，不能证明"与上一版一致" |
| ② 仓库内基线文件 | `test/baseline/panel-baseline.json`（首次生成、人工审一次），之后逐项比对 | 能跨版本守"确实没变" | 每次有意改面板都要手工更新基线；容易变成"改个数字就绿" |
| ③ 同会话前后自比 | 同一页面里先取基线（无插件）→ 挂插件 → 卸插件 → 再取，断言两次快照**逐项相等** | 真正验证"还原性"（设计 §六·4 的原话），不依赖任何外部文件 | 只能在浏览器套件里做；需要"装/卸插件"的测试通道 |

**建议**：①（静态结构）+ ③（还原性）覆盖设计验收 4/7 两条；②只在"确实要跨版本盯住"时再引入。
若引入 ②，请把基线文件放在 `test/baseline/` 并**只比对 id 序列与默认值**，不要比对像素/尺寸（那是几何测试的活，`panel-actions.js:660` 已有 rect 断言）。

## 我拿不准的

1. **插槽聚合点放哪层**：这条属前端侧结论，我没有那份文档前不敢定。我只看到一个硬约束：聚合结果**不能进 `PANEL_GROUPS` 静态导出**，
   否则 `tool/check-wiring.mjs:176-179`（W2）会把插件控件报成"代码引用但声明没有"。倾向维持现状（渲染期合并）。
2. **分组 id 要不要暴露到 DOM**：C2 要断言 `plugin.` 前缀，但现在手风琴节点只有标题文本（`panel-actions.js:441-443` 取 `textContent`）。
   要么加 `data-group-id`（实现增补），要么放弃前缀断言只断言"排在内置之后"。前者更强，但要动渲染代码。
3. **S5·4 "逐像素相同"**：现有测试基建没有像素比对（`check-console` 能截图，但仓内无 diff/感知哈希工具）。
   砍成"结构一致"是降级；真要逐像素得新做一套。需要你定取舍。
4. **新增浏览器套件要不要进默认门禁**：`BROWSER_SUITES` 里的套件默认不进 `--all`（`test-all.mjs:354-359`）。
   插槽的 DOM 行为若也默认不跑，就只能靠人记得 `--browser`；但把它加进默认门禁会拉长每次提交的门禁时间。
5. **"卸载后控件消失"目前是功能缺失**（`plugin-host.js` 的 `controlSections` 只增不减）。测试该按"先实现再补测"，
   还是先落一个 `skip` 标记的用例？我倾向**先实现**，因为 skip 的用例迟早被忘掉。

**纠正前端一处判断**：他们认为"装一个样例插件"缺少既有机制。实际是**半可配** ——
`pluginsDir` 固定跟随项目根（`paths.mjs:34`，注释写明"换数据根不能换实现"），
但**插件开关文件跟随数据根**（`paths.mjs:28` → `<dataRoot>/config/plugins.json`，形状 `{"disabled":[…]}`，
读取点 `registry.mjs:356`）⇒ 夹具插件**只对测试实例启用**是可行的，不必改代码；
只有"连插件物理目录也要隔离"才需要给 `pluginsDir` 加 env（我在 C4.1 列了三条路线与推荐顺序）。

### 与服务端（B）对齐：两条口径已写进我的断言

| 点 | 服务端结论 | 对测试断言的直接影响 |
|---|---|---|
| B1 字段白名单 | `readPluginManifest` 返回的是**手写对象字面量**，新字段不显式加就永远出不去 | S1 的 curl 断言必须先验"字段存在"：前端 `Array.isArray(p.slots) ? … : []` 会把漏加兜成空数组，**测不出服务端漏加** |
| B1/B4 降级口径 | 非法 `slots` **逐项丢弃 + warn**，不 `return null`（不整体干掉插件） | 断言必须写成"插件仍在列表 + `slotErrors` 有该项"；**不能断言"插件消失"**，否则会把正确实现判成红 |
| B3 内置两条 | 内置 provider 与磁盘插件同表下发，不能假设有 `slots` | 已并入 S1 第 1 条：「内置两条也要有空数组」 |
| B4 + 已定案 | 目录为准；未排期插槽**拒绝**（不是忽略）；顶层下发 `slotCatalog` | 已并入 S1 第 1/2/3 条 |
| B6 缓存 | 清单签名覆盖 `plugin.json` 的 `(mtime,size)` ⇒ 改插件不用重启，改服务端代码要重启 | 对测试的含义：**夹具插件改完必须 bump mtime 或重启测试实例**，否则拿到旧清单 —— 这类"改了没生效"最容易被误判成实现 bug |

服务端「对测试（预判）」两条我全部采纳：`readPluginManifest` 是纯函数可直接单测（我 C3①/C4 已列为主形态）；
"每个 provider 都有 `slots`/`slotErrors`"是"内置与插件平权"在响应层唯一的可回归口径（已进 S1）。

### 三份文档之间仍未统一的三处（需要拍板）

1. **S5·4 还原性怎么验**：我原写"无像素比对基建"，前端建议比 `#right-panel.outerHTML`。
   我采纳前端方案作**首选**（可自动 diff、不受软渲染噪声影响），但先决条件是**归一化**：
   `aria-expanded` 等交互态属性、任何含时间戳/计数的 `data-*` 必须在比对前剔除，
   否则"展开着比较、折叠着比较"会假红。真要"逐像素"，得另建感知哈希工具，建议第一版不做。
2. **样例插件注入路线**（C4.1 的 ①②③）：前端与服务端都没给方案。
   我的倾向：S1/S2 走 ①（模拟注册，零实现改动），S3 之前若仍未定就加 ③（env 覆盖 `pluginsDir`，改动 3 行、零污染）。
   ②（夹具插件放 `plugins/` + 开关文件）是"不改代码的端到端"，但它把风险转给了"主实例配置要有人维护"。
3. **诊断计数落哪个出口**：A5 建议补"注册数/回收数"，没说落 `dataset` 还是 `diag`。
   我这边要断言它就得先定出口：`dataset` 浏览器套件直接可读，`diag` 要读文件且跨进程。
   建议**只用 `dataset`**，否则同一事实两处表达（本项目已经踩过多次）。
