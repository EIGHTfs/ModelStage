## A1 · schema.js 的聚合点放哪一层最稳

**结论**：**保持现在的"装配期一次性合并"**（panel-settings.js），不要下移到 schema 常量，也不要放进 view.js 渲染期。
三层各管一件事，现有划分是对的：

| 层 | 该管什么 | 现状 |
|---|---|---|
| `schema.js` | **内置真相**（静态常量）+ **纯函数合并**（不改入参、返回新数组、不做 IO） | `PANEL_GROUPS` schema.js:45；`mergePluginControls` schema.js:410 |
| `panel-settings.js`（装配期） | 取插件声明 → 合并 → 能力过滤 → 挂载 → 写 dataset（**唯一一次**） | :393 / :436 / :444 / :442-443 |
| `view.js`（渲染期） | 只按传入的 groups 渲染，对"控件哪来的"无感知 | `mountPanel` :389，`renderGroup` :338，`renderControl` :319 |

**依据**
- schema.js:399-406 的注释已把"为什么不能原地改 PANEL_GROUPS"写死：`PANEL_GROUPS` 同时是
  ① uiState 派生 SPEC 的依据 ② 浏览器测试的"控件分类门禁"遍历对象 —— 原地改会让插件控件被门禁要求"显式归到三层优先级之一"，等于要求插件维护那张表。
- view.js:391 `const schema = Array.isArray(groups) && groups.length ? groups : PANEL_GROUPS;`
  ⇒ 渲染层已经接受外部传入的 groups；聚合塞进渲染期等于把"校验/拒绝日志/排序策略"混进纯渲染函数，且 `mountPanel` 每次重建都会重算一遍。
- panel-settings.js:442-443 把 `pluginControls / pluginControlsRejected / panelGroups` 写进 `dataset`，
  这是测试与排障读取的**唯一出口**；聚合若不在这一层，dataset 与真实渲染就会不同步。

**风险等级**：中（改错会连带 uiState SPEC 与浏览器测试基线）

**建议做法**
```
· schema.js 保持"纯函数"：mergePluginControls 签名不变，内部增加 order 排序与 plugin.<id>.<name> 前缀校验
· 装配期只做一次：sections → merge → applyCapabilities → mountPanel → 写 dataset（顺序别动）
· view.js 一行不改（它已经接受 groups 参数）；新增插槽如果只是"再多一个 section 来源"，
  就应该在装配期把 slot 内容读成同形状的 sections，而不是给 view 加分支
```

## A2 · 面板控件数被哪些断言依赖，改聚合会连带影响什么

**结论**：**真正会挂的只有"组名逐字相等"这一条**（`expectTitles` 全等比较）。
组数与控件数都已经是动态取值，插件加控件不会挂；**插件新建分组一定会挂**。

**依据**
| 断言点 | 位置 | 现状是否动态 |
|---|---|---|
| 组数 | test/browser/panel-actions.js:301 `Number(document.documentElement.dataset.panelGroups \|\| '0')` | **动态**（跟 dataset 走），加组/加控件都不会挂 |
| 手风琴逐组展开 | :453 `const count = qa('#right-panel .acc-trigger').length` | **动态** |
| 控件总数与插件控件数分离 | :198-201（`total` / `pluginControls` 两列并列） | **已分离**，插件控件单独统计 |
| **组名列表** | :337 `const expectTitles = ['动作','皮肤','播放','滤镜','PMA 预乘','运行时','主题背景','调试绘制','设置']` | **硬编码 9 个** |
| **组名比较** | :445 `JSON.stringify(titles) === JSON.stringify(expectTitles)` | **全等**（数量/顺序/文字任一变化即红） |

node 侧没有面板结构的断言（`grep PANEL_GROUPS\|mountPanel` 只命中 `test/browser/panel-actions.js`），
所以"改聚合"在单元测试层是零影响，影响面集中在浏览器测试这一条全等断言 + 两处文案（:444 的"与声明口径 9 组逐字一致"、:189/:452 注释里的"9 组"）。

**风险等级**：中（S3 必改；不改则"允许新建分组"必然红）

**建议做法**
```
· S2（只往既有分组加控件）：可以不改 expectTitles —— 组名没变，只有组内控件数变；:301/:453 自动跟随
· S3（允许新建分组）必须改：改为"前 N 项 === 内置 9 组（顺序一致）+ 尾部允许 plugin.* 额外组"
  并把 rec 的"期望值"文案从「9 组」改成「内置 9 组 + 插件 N 组」，否则报告读起来自相矛盾
· 不要放宽 :445 到"包含即可"（那会让内置组顺序漂移失去门禁）——顺序必须仍严格
· dataset.panelGroups 的语义（总数）保持不变，避免测试侧改两处
```

## A3 · ctx 现在由谁构造、什么时机，补三项会不会引入时序问题

**结论**：ctx 在 **mountPanel 内部、每次挂载时新建**（view.js:427），来源只有两类：入参（onSetting/initialValue/wiredIds）与闭包（wiredSet/disabledMap）。
补三项**不会崩**，但会引入**"数据陈旧"**类问题，不是"报错"类问题：

| 新字段 | 现成来源 | 时机风险 |
|---|---|---|
| `geometry` | `surface.geometry()`（surface.js:181，已返回 `{cssW, cssH, dpr, res}`） | **有**：ctx 是挂载时快照 ⇒ resize 后插件读到旧值。surface 有 `onResize(cb)`（surface.js:207-214）但面板没订阅 |
| `activeSurface` | 渲染面状态（surface-switch.js:14 的 `stageMode`）或 `state.currentRenderer.id` | **低**：换面会重建面板（main.js:518-520 → rebuildPanelFor），ctx 重新构造 |
| `document` | `state.selectedModel`（model-actions.js:551） | **有**：换模型**不重建面板**（只 refreshAnimations/setOptions），ctx 会停在旧模型 |

**依据**
- view.js:427-439 ctx 的四个字段全部是"函数式读当前值"或"快照集合"；其中 `wiredSet/disabledMap` 是挂载时的快照（view.js:416-424）。
- main.js:515 首帧 `rebuildPanelFor(state.currentRenderer)`；此时 `state.surface` 已可用（main.js:275 已在暴露 `stageMode()`）⇒ 首帧取 geometry 是安全的。
- surface.js:536 `geometry` 已从 surface 导出，`state.surface.geometry()` 可直接用，无需插件量 DOM。

**风险等级**：中（不崩，但"切模型后叠加层还按旧文档渲染"这类 bug 很难查）

**建议做法**
```
· props 用 **getter** 而不是快照：{ get geometry(){ return surface.geometry(); } }，外层 Object.freeze
  —— 设计文档 §4.1 要求"每次渲染重新计算并冻结"，getter 才同时满足"冻结对象"与"值新鲜"
· document 用 getter 读 state.selectedModel 的**只读摘要**（rootId/rel/kind/files），不要外传 model 引用
· 若坚持快照式：必须在两处补"插件控件局部重渲染"——换模型后（model-actions 里选中后）、resize 后
  （surface.onResize 订阅），且**只重渲染插件控件**，避免整面板重建打断手风琴展开态
```

## A4 · 插件脚本装载顺序与插槽注册时机（有没有竞态）

**结论**：**"面板先渲染、插件后注册"是常态，且已被一条事件链兜住**；但注册窗口有个硬边界 —— **异步注册会被丢弃**。
这条边界对插槽注册是**高风险**，必须在契约里写死。

**依据**
- 注入方式：`injectScript`（plugin-host.js:69-77）创建 `<script async=false>`，`loadPlugin` 按 `files[]` **串行 await**（:256-272）⇒ 插件脚本是经典脚本，注册发生在脚本求值期。
- 触发时机：`loadAll` 是**懒触发**（model-actions.js:153，首次点容器包时才调），而面板首帧在 main.js:515 更早
  ⇒ 首帧看到的 `host.controlSections()`（panel-settings.js:390）通常为空。
- 兜底链：装载完成派发 `spineviewer:plugins-loaded`（plugin-host.js:1277-1281）→ panel-settings.js:372-382 监听后 `rebuildPanelFor` + `pruneUnregistered`
  ⇒ **后注册会自动重渲染面板**，不需要插件自己触发。
- 硬边界：`loadingPluginId` 只在 `loadPlugin` 的注入期间赋值（:259），结束后清空（:266）；
  `registerControls` 用 `if (!pluginId) { warn('不在插件装载期内调用'); return false; }`（:236-237）
  ⇒ 插件若在 `setTimeout`/`Promise.then` 里注册，会被**拒绝并只留一条 warn**。

**风险等级**：高（新的 `slots.register` 若沿用这条路径，"晚注册"会被静默丢弃；而这正是插槽最容易出现的写法）

**建议做法**
```
· 契约里写死：slots.register 必须在插件脚本的**同步求值期**调用（与 registerControls 同一条边界）
· 不要用 loadingPluginId 这个瞬时变量做归属判据：改成"脚本注入期间设置 currentPlugin，
  并给每个插件保留 loaded 状态；注册时若 currentPlugin 为空但插件已 loaded，报可诊断的错误"
  （现在只能报"不在装载期内"，排查时看不出是哪个插件）
· 后注册 ⇒ 统一走 plugins-loaded 事件重渲染，不给插件"自己调 rebuildPanel"的入口
```

## A5 · disposer 回收：应该挂进哪一步才不漏

**结论**：**宿主现在没有任何"插件级 effect 列表"，也没有卸载/禁用路径**。
插槽 disposer 若只按设计 §4.2 挂在"插件卸载"上，实际只有"页面关闭"一个调用点 —— 等于没有回收语义。

**依据**
- `controlSections` 声明（plugin-host.js:101）→ 只有 `push`（:244）；对外 getter 返回副本（:1362）；**全文没有 delete/filter**。
- 插件生命周期只有 `loadState`（:107、:175-176、:256-289）：记录 loaded/error/files/ms，**没有 unload**。
- 全仓 grep `unload|disable|teardown|dispose` 在 plugin-host.js 里只命中 `worker.terminate()`（:424）。
- "禁用插件"= 改 `config/plugins.json` 后刷新页面（服务端 `/api/plugins` 决定注入哪些），前端没有运行时开关。
- 失败分支：`loadPlugin` 末尾（:283-288）会把"脚本失败/没有 register"记进 `error`，
  **但已 push 的 controlSections 不会回滚**（:279 还把"交过控件"算作 loaded 的依据）。

**风险等级**：高（设计文档自己说这是"最该先落地"的一条，而宿主缺容器）

**建议做法**
```
· plugin-host 内新增 per-plugin 容器：effects: Map<pluginId, Array<disposer>>，与 loadState 同生命周期
· slots.register 返回的 disposer 推入该插件数组；registerControls 也改成"注册即产出一个 disposer"，
  这样既有能力也进入统一回收（否则两套回收机制并存，迟早漂移）
· 逆序执行点（按优先级）：
    1) loadPlugin 失败/未生效分支（:283-288）—— 现在这里只记 error，应先回收
    2) 新增的 unloadPlugin(id) / unloadAll()（现在完全没有）
    3) 页面 unload（beforeunload 兜底，仅用于诊断计数，不做真实清理）
· 补一个可观测计数（dataset 或 diag）：注册数 / 回收数，否则"回收有没有生效"只能靠肉眼
```

## A6 · 热重载/刷新：旧 disposer 会不会残留

**结论**：**当前没有热重载** —— 插件脚本替换后必须**整页刷新**才生效。
整页刷新会销毁 JS 上下文 ⇒ 旧 disposer **不会残留**（它们连引用的宿主对象一起没了）。
但这也意味着"disposer 回收"在现网**没有任何可验证路径**（除了失败分支）。

**依据**
- `loadAll` 有 `loaded` 早退（plugin-host.js:1215）：`if (loaded) return {...}` ⇒ 一个页面生命周期内只装载一次。
- 没有"重新加载插件"入口（`grep 重新加载插件|reloadPlugins` 无结果）。
- `connectReloadApp`（panel-settings.js:672 / model-actions.js:682）回调里跑的是 `loadRoots({ skipRestore: true })`
  —— 重扫资源根，**不重注入插件脚本**，`pluginHost` 实例与 `controlSections` 原样保留。
- 若将来做"运行时重载"，现存三处会直接出问题：
  `controlSections`（:101，只增不减）、`providers`（Map）、`workerPool`（:368，按 providerId 缓存 worker）。

**风险等级**：中（当前被"整页刷新"兜住；一旦引入热重载就变成高）

**建议做法**
```
· 在设计里明确：第一版**不做热重载**，插件更新走"改文件 + 刷新页面"，并把这个决定写进插槽目录说明
  （否则使用者会以为改完插件就能热生效）
· 若要做，重载必须是成套动作，缺一不可：
    清 controlSections（按 pluginId）→ 逆序跑 disposer → providers.delete(id)
    → workerPool.get(id)?.worker.terminate() 并删除 → 重新注入脚本 → 派发 plugins-loaded 重渲染
· 触发条件也要定：现在没有任何"插件脚本变了"的检测（服务端 /api/plugins 也不带 mtime），
  要做就得服务端下发 files 的 mtime/hash
```

## 六条结论一句话汇总

```
A1 聚合点：留在装配期（panel-settings.js），schema 保持纯函数、view 保持无感知
A2 测试面：只有"组名全等"会挂（panel-actions.js:337/:445），组数与控件数已是动态
A3 ctx：mountPanel 内新建；geometry/document 会陈旧（resize、切模型不重建面板），建议用 getter
A4 竞态：面板先渲染是常态，plugins-loaded 已兜住；但**异步注册会被丢弃**，必须在契约里写死
A5 disposer：宿主没有插件级 effect 列表、没有卸载路径，controlSections 只增不减 ⇒ 需先补容器
A6 热重载：不存在，靠整页刷新；旧 disposer 不残留，但回收语义也因此无法验证
```

## 最高风险的两条

```
1) A5 —— 没有插件级 effect 容器，也没有卸载入口。插槽一旦能改界面，残留只能靠人肉排查；
   而现在的代码连"回收有没有执行"都无处观测。建议把"effects 容器 + unloadPlugin"作为 S1 的必做项，
   不要留到 S5。
2) A4 —— 注册窗口以 loadingPluginId 这个瞬时变量为界，异步注册被直接丢弃（只 warn）。
   插槽比控件更容易写成异步注册，落地前必须把这条写进契约，否则会出现"插件装了、控件不出现、日志只有一句warn"。
```

## 补测：重建与手风琴展开态（实测一次）

**方法**：在 8899 实例上打开页面，用真实的插件重建入口触发一次重建
——`window.dispatchEvent(new CustomEvent('spineviewer:plugins-loaded'))`
（这就是 panel-settings.js:372 监听的同一条路径，不是我造的入口），前后对比 `.acc-trigger[aria-expanded]`。

**结论：会丢，且回到 `defaultOpen` 的缺省态；而且这**现在就发生**，不是 S3 引入的新问题。**

```
缺省态（首次渲染）      动作:开 皮肤:收 播放:收 滤镜:收 PMA 预乘:收 运行时:收 主题背景:收 调试绘制:收 设置:开
                          ↑ 与 schema 的两处 defaultOpen（schema.js:49 / :222）一致
用户手动改              动作:收 皮肤:开      ← 收起「动作」、展开「皮肤」
触发一次重建后          动作:开 皮肤:收      ← **完全回到缺省态**，用户的展开/收起被丢弃
节点身份              .acc-trigger 被整体替换（旧节点已不在文档中）⇒ 展开态无处可存：它只写在 DOM 上
同步重建耗时            45ms（replaceChildren + 重建 9 组全部控件；不含后续异步刷新）
面板滚动位置            scrollTop 0 → 0（本页面板未产生滚动，**不能据此断言"长面板不跳"**）
```

**关键发现（比"会不会跳"更重要）**：重建入口**当前无条件执行**——
即使页面没有任何插件控件（实测 `dataset.pluginControls = "0"`、`panelGroups = "9"`），
派发该事件仍然整块重建面板。也就是说"首次点容器包 → 插件装载完成 → 展开态被重置"这条行为**今天就在发生**，
只是没人把"我展开的组怎么又收起来了"归因到它头上。

**对 S3 的含义**：S3 要允许插件新建分组，插件装载完成后**必然**需要一次重渲染 ⇒ 这条不能靠"跳过一次重建"绕过。
必须在下面两种做法里选一个（我建议 ②）：

```
① 仅当插件贡献非空时才重建：mergePluginControls 已有 added 计数（schema.js:410 起），added===0 就跳过 mountPanel。
   好处：省掉现状的无意义重置；坏处：S3 之后"真的有插件控件"时依然会重置，问题只是推迟
② 重建时保留展开态：mountPanel 前把当前 aria-expanded 收成 Map<groupId, boolean>，渲染时优先读它。
   好处：既覆盖"插件首次装载"也覆盖"换渲染面重建"（main.js:518-520 那条路径同样会重置）；
   坏处：面板层多一份"视图状态"，要与"视图状态不落盘"的既有约定区分清楚（只存内存、不写 localStorage）
```

**仍待补的一次实测**：长面板（9 组全展开）时重建前后的 `scrollTop` 与视觉跳动。
本次面板未产生滚动，这一项没有覆盖；建议 S3 验收里连同"展开态保持"一起实测一次。

### 与服务端（B）结论不一致的两处（附裁定结论）

```
① 插槽目录的**第二份**要不要存在前端？
   B4 建议目录作为 registry.mjs 常量表（服务端权威）。那么前端要不要也存一份做二次防御？
   结论：**不要**。前端只信 /api/plugins 每项自带的 slots[] + slotErrors[]，
   前端唯一的本地判断是"这个插槽名是否在该插件的声明里"（append/replace 的等级语义由服务端下发）。
   理由：目录一旦两份，扩 shadow 等级时必然出现"服务端放了、前端还拒"的幽灵 bug。

② 未开放插槽（toolbar/stage）到底是"拒绝"还是"忽略+warn"？
   B4 结论为拒绝并提示"阶段未到"（采纳：看着成功其实是空操作，最难排查）。
   但这要求 /api/plugins 能表达"目录里有、当前阶段未开"这个状态 —— 建议 slotErrors 的 why 用
   `stage-not-open` vs `not-in-catalog` 两个值，前端才能给出不同文案（一个是"等后续版本"，
   一个是"你写错了"）。若两者合成一个值，用户与我们都会被误导。
```
