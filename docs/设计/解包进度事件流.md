## 一、为什么选事件流，而不是 `202 Accepted` + 轮询

| 维度 | 事件流（本文） | 202 + 轮询 | 结论 |
|---|---|---|---|
| 进度粒度 | 服务端每段结束就推一条，前端可实时画 | 只能看到"轮到第几个/还剩多久"，段内无信息 | 事件流胜 |
| 额外状态 | 无（流本身就是状态载体） | 要在服务端维护 job 表（jobId → 状态/产物/过期清理），多一份生命周期 | 事件流胜 |
| 断连清理 | 连接断了只是少一个订阅者（解包照旧），无残留状态 | job 表要处理"客户端再也不会来问"的僵尸任务，要么超时回收要么定期扫 | 事件流胜 |
| 多客户端 | 天然广播（见 §五） | 多个客户端各拿自己的 jobId，服务端要多份 job 或做 job 复用 | 事件流胜 |
| 心跳/停摆判定 | 一条 `ping` 就够 | 每次轮询就是一个天然心跳，但也意味着"客户端在忙等" | 平 |
| 反代友好度 | **需要显式对策**（见 §三），chunked 可能被缓冲 | HTTP 短请求，反代不缓冲 | **轮询胜** |
| 实现复杂度 | 服务端加事件回调 + 写帧；客户端加增量解析 | 服务端加 job 表 + 路由；客户端加轮询与退避 | 相当 |

**选事件流的决定性理由**：本项目不需要"解包任务的持久状态"——解包的产物本身就是状态（`data/unpacked/<fp>/index.json`），
查询产物已有 `hitOnly` 通道。再加一张 job 表只会多一份要和缓存对齐的真相。
反代缓冲是唯一真实劣势，而它可以用三个响应头 + 一条验证命令解决（§三），代价远低于维护 job 表。

## 二、服务端怎么接

### 2.1 与现有串行队列、inflight 去重的关系

现状（`src/server/unpack/plugin-store.mjs`）：

```js
const inflight = new Map();                       // fp → Promise（同一包并发只解一次）
let chain = Promise.resolve();                    // 串行队列（promise 链，无长度概念）
const enqueue = opts.enqueue || ((fn) => {
  const next = chain.then(fn, fn);
  chain = next.then(() => undefined, () => undefined);
  return next;
});
```

**只有一处必须改，且是加法**：

```
inflight 目前只存 Promise，没法挂订阅者。
  方案 A（本文初稿）：改成存 { task, listeners: Set<fn> } —— 一个 fp 只解一次、遍历 listeners 推送。
  方案 B（**实际实现**）：新增一个**并列的** subscribers: Map<fp, Set<fn>>，
     inflight 的结构与 has/get/set/delete/finally 四处一行不动。
  选 B 的理由：A 要同步改那四处，风险大于收益；两者行为等价（同 fp 仍只解一次、事件广播给全部等待者）。
  ⇒ 实现已完成，本文保留 A 作为"如果重写会怎么做"的记录，但**以 B 为准**。
```

`queued.waiting` 不新增任何计数器：直接取 `inflight.size`（当前"在解 + 在等各 fp"的去重数量）。
串行队列 `chain` 是 promise 链、没有长度概念，**不为此加一个 pending 计数**（那是为"精确位次"付的代价，
而 waiting 只要"大概堵着几个"的量感，粗一点不误导）。队列深度对 waiting 的贡献，用 inflight.size 近似即可。

### 2.2 事件从哪一层发：**store 层产生，routes 层序列化**

```
store.resolve(req, { onEvent })     ← onEvent 可选；不传 ⇒ 与现在完全一样（不产生任何事件）
  ├ 事件内容（fp / phases / waiting / error.reason）只有 store 知道 ⇒ 由 store 调 onEvent(event)
  └ routes 只负责：把 event 拼成 SSE 帧 + res.write()，以及流生命周期（end / 错误兜底）
```

为什么不让 routes 自己拼事件：`phases` 在 store 内部产生（`readMs`/`pluginResolveMs`/`writeMs`），
路由层拿不到分段数据；若为发事件在 routes 再算一遍，就是**第二份真相**（本项目反复栽的坑）。

`onEvent` 缺省时 store 走**原路径**（一个 `if (onEvent)` 的分支），这条是"行为零变化"的落点。

### 2.2.1 命中路径也必须发一帧 done（否则命中场景整条流静默）

现状 `resolve()` 一进来就查缓存，命中直接 `return { hit:true, … }`，**根本不进解包分支**。
事件流若照搬这个结构，带 `stream:true` 的命中请求会"一个事件都不发就关流"，客户端只能干等 15s 停摆 ——
这是最容易漏、后果最重的一条，必须在设计里显式画出来：

```
resolve(req, { onEvent })
  stat → fp → readIndex → hitCheck
  命中分支：onEvent('done', { hit:true, fp, files, … }); 立即结束流   ← 不发 queued/start/phase
  未命中分支：才走 queued → start → phase* → done{hit:false} → 关流
```

对应契约验收 **E3**（首帧即 done）。落点：命中判断在 store 内，所以"命中要发 done"也由 store 触发，
不能等 routes 拿到返回值再补（routes 那层已经看不到"这是命中"这个事实的时机差）。

### 2.3 flush 与写帧

```
res.writeHead(200, { 'Content-Type': 'text/event-stream; charset=utf-8',
                     'Cache-Control': 'no-cache, no-transform',
                     'Connection': 'keep-alive',
                     'X-Accel-Buffering': 'no' })
res.flushHeaders()                       // 让头先出去，客户端才能开始读
帧：`event: ${name}\ndata: ${JSON.stringify(data)}\n\n`
每次 write 后无需显式 flush（Node 未设 cork 时立即写）；但**必须**禁掉压缩中间件对该路径的 gzip，
否则 chunk 会被攒到压缩块满才发出（表现为"进度一次性涌出来"，见 §三）。
```

### 2.4 日志与事件必须是两个通道

```
事件流：给客户端看进度（结构化、可丢弃 —— 丢了靠心跳判停摆即可恢复认知）
日志  ：runtime/model-stage-web.log + data/diag.jsonl（给排查看，含绝对路径等敏感上下文）
```
**不把日志塞进事件**：事件里的 `error.message` 要能直接展示给用户，不能带绝对路径；
而日志需要绝对路径。两者受众不同，混在一起就会出现"用户看到一串盘符"或"排查时只有一句人话"。

### 2.5 心跳与客户端断开

```
setInterval(2000) 发 ping
res.on('close') ⇒ 从 listeners 移除自己 + clearInterval（**不中止解包**，见契约 §五）
解包完成后：先发 done / error，再 res.end()，再清 interval
```

三个必须写全的落点（少一个就会崩在"往已断开的连接写事件"上）：

```
① 监听 res.on('close')：断开即把自己从 listeners 摘掉并 clearInterval
② 写事件必须容错，而且**光包 try/catch 不够**：
   对已销毁的连接 res.write() 通常**不同步抛错**，而是返回 false 并**异步发一个 'error'**
   （after-end 则是 ERR_STREAM_WRITE_AFTER_END，同样走 'error' 事件）。
   ⇒ 必须同时挂 res.on('error', 空操作)；try/catch 只兜同步抛的那部分。
   两者都是"客户端走了"的正常现象，不得冒泡成 500，更不能让解包任务跟着失败。
③ 摘除与吞错都不能影响落盘：产物写入不依赖连接，客户端断开后 store 照常解完写 index.json
```

定时器必须用 `unref()` 或在 close 时一定清掉，否则进程会被挂住（本项目有过定时器泄漏的教训）。

## 三、反代缓冲：对策与验证

NAS 部署上可能经过反代（本项目实际环境有 nginx 系反代）。chunked 响应被缓冲时的典型症状：
**整段进度在解包结束时一次性涌出来**，看起来像"没有进度"，但停摆判据会误判成卡死（其实是全被攒住了）。

```
对策（三个头一起给，缺一个都可能被某个中间层吃掉）：
  X-Accel-Buffering: no        nginx 专认，关它自己的 proxy_buffering
  Cache-Control: no-transform  禁止中间层改写/压缩
  Content-Encoding 不设        不要给这条路径开 gzip/br
另外：不要在反代上对 /api/unpack/ 配 proxy_read_timeout < 心跳间隔的若干倍
```

**验证方法（可复现，不靠"看起来正常"）**：

```bash
# -N 关掉 curl 自己的输出缓冲；每行带上到达时刻，就能看出是"持续到达"还是"最后一次性到达"
curl -N -X POST http://<host>:<port>/api/unpack/resolve \
  -H 'Content-Type: application/json' \
  -d '{"rootId":"<root>","rel":"<一个 20MB 级的包>","stream":true}' \
  | while IFS= read -r line; do printf '%s %s\n' "$(date +%s.%N | cut -c1-14)" "$line"; done
```
判读：相邻事件的时间戳应**分散**在解包全程；若全部挤在末尾 ⇒ 被缓冲，按上面三个头排查。
验证时**两组都测并记录**：直连端口（排除反代因素）与经过反代（真实路径）。
前者证明"服务端确实在发"，后者证明"反代没攒住"—— 只测后者时若失败，分不清是哪个原因。

## 四、客户端怎么读

```
① 起流
   fetch('/api/unpack/resolve', { method:'POST', body: JSON.stringify({...,stream:true}) })
   先判 Content-Type：不是 text/event-stream ⇒ **回落**为一次性 JSON 解析（老服务端，见契约 §七）

② 增量解析
   const reader = res.body.getReader(); const dec = new TextDecoder();
   按 '\n\n' 切帧，'event:' / 'data:' 两行拼装；不完整帧留在 buffer 里等下一块

③ 停摆计时器（本设计的核心）
   每收到**任意**一帧（含 ping）就 clearTimeout + 重设 15000ms
   连续 15s 无任何帧 ⇒ controller.abort() + 记 reason='stalled'
   ⚠️ 措辞铁律：这不是"超时"。代码 / 日志 / 界面一律不写 timeout、超时字样，只写"停摆 / 服务端无响应"
      —— 写成超时会把"慢但正常"重新拖回被误判的老坑
   ⚠️ 不设"总时长"上限：慢机器解 60s 也算正常（那正是本设计要消灭的东西）

④ 进度显示（phase→中文 的映射放前端一处常量表，服务端不下发界面措辞）
   queued → "排队中（前面约 {waiting} 个）"—— waiting 是粗量感，措辞带"约"，不假装精确
   start  → "开始解包"
   phase  → 按 name 映射"读盘中 / 解压中 / 写盘中"
            （不带百分比：服务端给不出可信的解压进度，假进度条比没有进度更糟）
   done   → 结束；error → 显示 message（不带绝对路径）
   服务端只管发 read / resolve / write 三个名字，界面措辞归前端 —— 否则服务端就侵入了展示层。

⑤ 与前台 hitOnly 的关系：**前台不动**
   前台装载仍走 hitOnly（查缓存命中就走、未命中就自己解），不接事件流。
   事件流先服务"后台预热/等待服务端解包"这条路径，等它稳定后再讨论前台是否改（不在本设计范围）。
```

## 五、多客户端等同一个 fp

```
请求 A：resolve(req) → inflight 里没有 ⇒ 建 task，listeners={A}
请求 B：同一 fp ⇒ 命中 inflight ⇒ **不新建 task**，listeners.add(B)，立即补发一条 queued{waiting}
A/B 都从同一个 task 的事件流里收（store 在 onEvent 处遍历 listeners）
task 完成 ⇒ inflight.delete(fp)（现有行为不变），listeners 全部收到 done
```
`waiting` 取 `inflight.size`（含自己这个 fp，粗粒度）。**不给 B 发"精确的 0"**：
B 加入时 A 已在解，"前面 0 个"听着精确但会误导（B 仍要等 A 解完）；给一个"大概堵着 N 个"的量感即可。
边界：B 在 A 已经收到 `phase` 之后才加入 ⇒ B 会缺前半段事件。**这是可接受的**：
B 只需要 `done`（拿产物），缺的进度对 B 没有意义。不为此重放历史事件（那要缓存全量事件，代价大且无收益）。

## 六、失败与边界

| 情形 | 行为 | 依据 |
|---|---|---|
| worker 崩溃 / 解包抛错 | `error{reason:'worker-error'或具体值}` + 关流 | 契约 §六 |
| 服务端进程重启（解包中） | 产物未落盘 ⇒ 缓存无 ⇒ 下次重新解；客户端停摆判据会先在 15s 后中止 | 契约 §五 |
| 事件丢失（网络丢包但连接没断） | 心跳补位：只要 ping 还在，客户端不会中止；缺了 phase 也不影响正确性（产物靠 done/files 拿） | 契约 §三 |
| 客户端中途刷新页面 | 连接断 ⇒ 服务端继续解完写缓存；刷新后走 hitOnly 查询，可能正好命中 | 契约 §五 |
| 反代 idle timeout < 心跳间隔 | 连接被切成"半死" ⇒ 客户端靠停摆判据发现 | §三 |

## 七、开关与回滚

```
不加运行时开关（env 与 config 都不加）：协议形态只由请求体的 `stream` 字段单向决定。
  服务端：只有 `stream:true` 才走事件流，其余一律现状 —— "不带这个字段"本身就是关掉
  客户端：不发 `stream` 即回到现状（老服务端按 Content-Type 回落，见契约 §七）
```

为什么不设开关：开关本身就是一条要长期维护的分支（两种响应形态 × 之后每一次改动都要顾），
而"回到现状"已经有更彻底的路径 —— 回退代码版本；且客户端不传 `stream` 时服务端行为与改造前逐字相同
（契约 §1.3），所以线上任何时候都能靠"不发这个字段"绕开新路径，不需要额外开关。

## 八、明确不做（防止顺手扩张）

```
· 不改渲染层（spine/、live2d/、render/ 一行不动）
· 不改前台 hitOnly 路径（前台装载策略本设计不变）
· 不动产物格式与指纹（index.json 字段、fingerprintOf 算法都不变）
· 不取消浏览器侧解包（双解包保留）
· 不做"服务端解包总时长上限"（慢机器慢是正常的，不许用超时掩盖）
· 不做百分比进度（服务端给不出可信百分比）
· 不引入 job 表 / 任务持久化（产物即状态）
```
