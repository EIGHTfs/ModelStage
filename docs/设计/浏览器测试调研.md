# 浏览器测试调研：哪些真的需要浏览器

> 状态：**调研稿（未改动任何测试）**。目的：先看清现状与可迁移比例，再决定怎么重写。
> 配套新规：**能静态扫/单元测/API 断言解决的，禁止起浏览器。**

## 一、要解决的问题

```
现状：浏览器注入测试共 10 个脚本、5188 行、94 条显式断言。
问题：其中相当一部分（控件清单、分组标题、localStorage 键名、/api/roots 的 CRUD 与错误码…）
      用脚本扫描 / node 单测 / HTTP 断言就能验完，却要起一次无头 chromium。
目标：只把**真正依赖浏览器**的断言留在浏览器里，其余迁出去。
```

### 4.1 为什么迁移比例不高（如实说）

```
因为这套浏览器测试的主体确实是"渲染与交互"：
spine-actions(13) + engine-b1 + debug-drag(12) + f3(5) + f1(4) + anim(15) + f2(6) + panel(24) + roster(31)
——这些断言的对象就是"浏览器把页面跑起来之后的状态"，静态扫描替代不了。
```

### 4.2 迁移的真正收益在别处

```
现状：浏览器套件**默认不进自动门禁**（要 --browser）⇒ 迁出的这些断言平时**根本没人跑**。
迁移后它们进入 node 默认门禁（套件 30 → 34），等于从「从不执行」变成「每次执行」。
—— 收益不是"少起几次浏览器"，而是"这批断言终于真的在跑"（P5 实测见 §五·5.2：总耗时没有明显下降）。
```


**关于"耗时是否下降"**——如实说：**没有可用的前后同口径基线**。

```
· 改动前**没有跑过**"10 套一次跑完"的全量，历史只有零散的单套 --only 数字
  （f4 8152ms / roster 85081ms / panel 19979ms / anim 38487ms / f2 43693ms，均为单套单跑）；
· 本次是"全量串跑"，两者口径不同（单跑多算一次实例启动、串跑有前后套件争用），**不能相减**；
· 因此不给"降了 X%" 这种数字。能确定的是：删掉的只是脚本里几十行契约断言，
  而每套的耗时由 chromium 启动 + 页面装载 + 模型/数据加载主导（最慢三套 spine/roster/anim 合计 225s，
  它们本次一行未改）——**耗时不是这次迁移的收益来源**。
```

**收益在哪**：迁出的断言从"只在 `--browser` 时执行"变成"每次 node 门禁都执行"（套件 30 → 34，
每次 `--all` 多跑 24 个 node 测试，本次合计约 4s 量级），覆盖从"虚"变"实"。

**本次两条失败（都不是本批引入；相关套件本次一行未改）**：

```
debug-drag  ③ 拖动不影响日志滚动：scrollTop 前=220 后=235（期望"前后相同"）
spine-actions  0 舞台/WebGL 上下文：stage=false context=undefined
```
两套在迁移期间从未改动（`git log` 可核），失败形态更像数据/环境相关（spine 那套没建出舞台、drag 那套滚动位置有偏移），
本轮如实记录，未做处理。
