## 一、目标与判据

**目标**：修真实的可维护性/健壮性问题，不是把分数刷高。

```
评分只作参考（同一口径下前后对比），不作为验收目标
真实优化 = 改完之后：同样的输入行为不变、代码更容易改、故障面更小
不豁免 —— 真问题就修，不靠豁免压数字
误报自行忽略 —— 下面第三节列明「判定为误报/不修」的规则与理由
```

**顺手清理政策（2026-10-26 追加）**：

```
短变量名 与 魔数 不做全仓扫荡，但**本次改动触及的函数/代码块内要顺手解决**：
  · 短变量名：语义能明确时改（p → paths、c → char、el → element）；
    仅限改动触及的作用域，不要为了改名去动未触碰的代码
  · 魔数：只提取**真正的时间/尺寸/阈值**（超时毫秒、上限字节、帧率、视口）；
    数据表常量（CRC 表 0xedb88320、像素 255、字符串表项）不提取
  · 判据：改完这一处，读代码的人不用再去猜这个数字/名字是什么意思
```

**验收口径**（每步都要能复现）：

```
1. 行为等价：纯函数拆分 → 拆分前后用同一批输入跑，输出逐字节相同
   UI/流程拆分 → 页面快照或对应浏览器脚本断言不变（只跑受影响的那一套）
2. 针对性验证：不跑全量；改哪个模块跑哪个套件 + node --check
3. 审计对比：同口径 full 审计，只看目标规则的条数变化，不追总分
```

## 三、判定为误报 / 不修（附理由，逐条可复核）

| 规则 | 为什么不修 |
|---|---|
| `magic-number-smart` | **不全仓扫荡**：数据表常量（`0xedb88320` CRC 表、`19` 字符串表项、`255` 像素上限、`42` 测试样例）不提取；但**改动触及的函数里**出现的时间/尺寸/阈值魔数要顺手提成命名常量。 |
| `io-risk` 的 🟡 低风险 313 条 | 命中几乎全是「启动路径上的同步 I/O（一次性初始化）」。本项目零依赖、启动即读配置/清单，同步读是**刻意选择**（异步化会让启动路径变复杂且无收益）。只有 🟠 中风险（**循环内**同步 I/O）才修。 |
| `variable-min-length` | **不全仓扫荡**：未触碰代码里的 `c`/`m`/`w` 保留；但**改动触及的函数里**语义能明确的短名要顺手改（`p` → `paths`、`el` → `element`）。 |
| `comment-density` 10 条 | 本项目的注释约定是「讲为什么、讲踩过的坑」，注释密度高是**刻意**的（见 `code-detailed-comments`）。按这条规则删注释会直接损失可维护性。 |
| `button/*` 26 条 | 页面用事件委托（`view.js` 父级监听 + `e.target` 分发），审计已另有 `button/event-delegation-detected` 3 条承认覆盖；`docs/*.md` 里的按钮是文档示例，不是代码。 |
| `folder/total-count` | 「38 个源码目录」是**嵌套**目录计数（顶层只有 9 个：src/plugins/tool/test/docs/config/data/runtime/avatars），不存在"混入解包产物"。 |
| `private-file-in-repo` `.env.example` | 是纯模板（值全空、只有注释），无凭据。但里面有两处「与旧版行为一致」和已删除的 `server.mjs` 引用 —— 措辞要清，文件保留。 |
| `paths/hardcoded-absolute-path` 里 `web.sh` 的探测列表 | `/usr/local/bin/node`、`/usr/bin/node` 是**按顺序探测的兜底候选**（NAS 重启后 `/var/packages` 可能失效），不是写死依赖。属于 `tool-self-detection` 的正确做法。 |
| `memory-bomb` 的大部分 | 解析 UnityFS 资源包**必须**整包读入（格式要求顺序解析），改成流式要重写解析器。真正的优化点是「读之前先做内存准入」，这件事项目已有（capacity + checkUnpackMemory）。 |
