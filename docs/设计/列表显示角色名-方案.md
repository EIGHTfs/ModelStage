# 左侧列表显示 `__data` 角色名 —— 方案（修正版）

> **上一版的两个错误已修正**：
> ① 我说「拿不到 181 个真实样本」是错的 —— 样本在 `资源/棕色尘埃 2/`，是我找错了位置
> ② 总耗时与内存策略都错了：真实规模是 **~2~4 分钟**（不是一个数量级的小），且**超大包会 OOM**

## 一、真实样本（实测，非估算）

```
位置：资源/棕色尘埃 2/<hash1>/<hash2>/__data
n=181  合计 7006 MB
p25=14.9  p50=22.0  p75=29.6  p95=93.8  max=1297.0 (MB)
>50MB：22 个，合计 3748 MB
```

**注**：`find "$DIR"` 用变量传路径时因目录名含空格漏了匹配，改用 `find -print0` + 绝对路径才拿到全量。
这类"路径含空格导致少统计"的坑会让结论整体偏移，值得在实施时也注意。

## 二、实测耗时（**预热后**，真实包分位抽样）

| 包大小 | 读盘 | 解压 | 合计 | blocks | 全量解压量 |
|---|---|---|---|---|---|
| **15.0 MB** | 24.6 ms | 253 ms | **279.8 ms** | 593 | 74.1 MB |
| **22.0 MB** | 159.7 ms | 430.5 ms | **592.2 ms** | 1002 | 125.2 MB |
| **29.9 MB** | 207.9 ms | 440.6 ms | **658.0 ms** | 955 | 119.3 MB |
| **97.1 MB** | 672.7 ms | 1134 ms | **1815.5 ms** | 2304 | 288.0 MB |
| **1297 MB** | — | — | **不可行**（见 §三） | 38894 | **4862 MB** |

**⚠️ 预热是必须的**：首次跑会被 JIT + 沙箱加载放大十倍（我第一次测出 1177ms，预热后 87ms）。
上面的数字都是**同一进程内先跑 3 次**之后的稳定值。

**解压后的数据量比原包大 3~5 倍**（22MB 包 → 解压 125MB），这是内存压力的真正来源，
不是"文件多大就吃多少内存"。

## 三、硬约束：超大包会 OOM，且"只读头尾"也救不了

对 **1297 MB** 那个包实测：

```
只读头（4KB）+ 尾（4MB）→ readHeader 成功，但耗时 15847 ms（15.8 秒）
原因：blocks=38894，readHeader 要解压并遍历整个 blocksInfo；且"长度正确的 buffer"要 1297MB
全量解压需 4862 MB ⇒ 必然 OOM（node 默认堆上限远低于此）
只读头尾这一步的进程 RSS 已经 1365 MB（因为要分配 1297MB 的 buffer）
```

**结论**：**>100MB 的包不该进取名流程**。不是"慢"，是"会把服务端拖死"。

## 四、"只读够用字节"能做到什么（实测边界）

| 目标 | 需要解压 | 实测 | 可行性 |
|---|---|---|---|
| 容器头 + blocksInfo（节点表/blocks 表） | **0**（只读头尾） | 10~14 ms（≤97MB）；**15.8s（1297MB）** | ✅ 但超大包仍不可行 |
| **CAB 对象表**（1250 个对象） | **前 8 块 = 1 MB** | **148 ms**（15MB 包） | ✅ **成立** |
| **TextAsset 的 `m_Name`**（骨架名） | **需要该对象的数据区** | ❌ 现有 API 拿不到 | ⚠️ **需要改插件暴露对象偏移** |

**关键发现**：这批包的 `blocks` 是 **593~38894**（标准 128KB 切块，全部 LZ4），
**不是**我上一版基于 `AssetBundls` 样本得出的"blocks=1"。

所以「只解压一部分」在**对象表这层是成立的**（1MB vs 74MB，**降 70 倍**）。
**但 TextAsset 的 `m_Name` 在对象数据区**，而 `serialized.parse` 返回的对象记录里
**没有暴露 `byteOffset`**，无法直接定位它落在哪一块。

⇒ **要走"只取名字"的轻量路，必须给插件加一个"按 pathId 取对象数据偏移"的能力**（约半天工作量）。
**不改这一层，就只能全量解压。**

## 五、修正后的总耗时估算

按实测分位 × 181 个真实包（**不含 max 那个，它在阈值外**）：

```
≤50MB 的 159 个：中位 592 ms  →  ≈ 94 秒
>50MB 的  22 个：p95 1816 ms →  ≈ 40 秒
合计 ≈ 2.2 分钟（单线程、串行）
```

**若含 1297MB 那个**：直接 OOM，不能算进"耗时"，只能算进"必须跳过"。

**与我上一版"9~15 秒"的差距**：上一版用 `AssetBundls` 的小样本（1.7MB 中位）外推，
而真实 BD2 包中位是 **22MB**（13 倍），且解压后数据量是原包 3~5 倍。**这是数量级的错误，我认。**

**与 lead 实测"4 分钟以上"的差异**：我这组是预热后的稳定值（p50 592ms vs lead 1401ms），
差异可能来自机器状态与是否首次。**按保守取 3~5 分钟做规划更安全。**

## 六、修正后的方案

### 方案 A：后台全量取名（**修正为：不推荐**）

```
× 3~5 分钟后台占用
× 22 个 >50MB 的包吃掉大部分时间与内存（3748MB 解压量）
× 必须设阈值跳过超大包，否则 OOM
× 首次进入列表要等几分钟才全有名字
```

**不推荐。**

### 方案 B：按"当前展开的游戏 / 可见区域"取名（**推荐**）

```
做法：
  ① catalog 保持 `__data`，列表立刻可用
  ② 只为**当前可见或当前展开分组**的条目取名（典型 10~30 个）
  ③ 结果落盘缓存；用户滚到别处再取那一批
  ④ 超大包（>阈值）直接跳过，保持 `__data` 并标注"（过大，未取名）"

成本：
  · 首批 10~30 个 × 中位 592ms ≈ 6~18 秒（后台，不阻塞）
  · 缓存命中后 0
  · 峰值内存：单包解压量（最大到 p95 的 288MB）

优点：**不赌 181 个包全跑完**；用户看到的顺序就是取的顺序；
      超大包不参与，OOM 风险可枚举
缺点：没滚到的地方仍是 `__data`
```

### 方案 C：先只显示"包大小 + 短 hash"，名字二期再做

```
做法：不动解析，列表显示 `__data · 22MB · a1d30d`
成本：0（catalog 已有 size 与 rel）
优点：**立刻可区分**，零风险，零解析
缺点：不是"角色名"，是"能区分"
```

**这个方案的价值**：它能在**今天**解决"一屏十几个同名"的问题，
而角色名作为二期增强。**如果目标只是"能区分"，C 的成本是 0。**

## 七、推荐

**分两步走**：

```
第一步（立刻做）：方案 C —— 列表显示 `__data · 22MB · a1d30d`
   · 改一处：catalog 条目的展示名拼上 size 与 rel 的短 hash
   · 零解析、零内存风险、零后台任务

第二步（角色名，按需）：方案 B —— 可见区域取名 + 缓存 + 阈值
   · 需要先给插件加"按 pathId 取对象偏移"（否则只能全量解压）
   · 阈值与内存策略见 §八
```

**理由**：C 用 10 分钟解决"无法区分"，B 要半天且带 OOM 风险；
先让用户可用，再决定是否值得为"更好看的名字"付出这半天。

## 八、阈值与资源纪律（方案 B 实施时必须遵守）

| 项 | 取值 | 理由 |
|---|---|---|
| **单包字节上限** | **100 MB** | 实测 97MB 包耗时 1.8s / 解压 288MB 已接近可接受上限；1297MB 包**必须跳过** |
| **单次取名批大小** | **20** | 20 × 592ms ≈ 12 秒；再大用户会觉得"点了没反应" |
| **并发** | **1** | 单包解压峰值 288MB，并发 2 就 576MB；且解压是纯 CPU，并发不加速 |
| **失败不重试** | 失败即记 `null` + 原因 | 避免"坏包被反复重试"形成风暴；重试只在显式刷新时发生 |
| **内存保护** | 取名前查 `capacity.mjs` 的可用内存 | 复用既有探测，不另造 |
| **超阈值行为** | 保持 `__data`，名字后缀标注「过大未取名」 | 静默跳过会让用户以为是解析失败 |

## 九、缓存

| 项 | 取值 |
|---|---|
| 位置 | `config/bundle-names.json` |
| 结构 | `{ "<rootId>/<rel>": { name, source, mtimeMs, size, skipped? } }` |
| 失效 | `mtimeMs` / `size` 变化即失效 |
| 跳过标记 | 超阈值 / 解析失败也写一条（`name: null, reason`），避免每次重试 |

## 十、未验证 / 不确定

```
1. "只解压前 1MB 拿对象表 → 再定位 TextAsset 数据"这条路**没跑通到底**：
   对象表能拿到（objects=1250），但 TextAsset 的 byteOffset 现有 API 不暴露
   ⇒ 需要改插件才能验证"只解压 2~3 块是否够"
2. 1297MB 包"只读头尾 15.8 秒"是在我建了 1297MB buffer 的前提下测的；
   若改成"只 mmap 头尾"可能更快，但 node 没有现成的部分读 API，需自己实现
3. 22 个 >50MB 包的耗时分布只测了 p95 一个（1816ms），其余未逐包测

```
