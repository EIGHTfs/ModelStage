# 设计 · 解包内存预估

> 解决一件事：**「这个包解出来要吃多少内存」怎么算准。**
> 契约侧（谁声明、核心怎么用）见[插件契约](../契约/插件.md) §2.2；本文讲模型本身与数据依据。

---

## 一、为什么原来的算法不准

原实现：`peak = 源包大小 × 分段倍数`（×20 / ×26 / ×15）。只有**一个变量**，而真实峰值由**要搬进内存的东西**决定。

**实测反例**：

```
42MB 包（源 41.98，解压 42.0）→ 峰值 348MB
19MB 包（源 19.27，解压 42.11）→ 峰值 368MB   ← 源包小一半，峰值反而更高
```

两个包真实代价几乎相同（差 6%），原算法却给出 630 与 501（差 26%）。

**偏差实测**（19 包样本）：

| | P50 | P90 | max | min |
|---|---|---|---|---|
| 原算法 | **+26.7%** | +81.0% | **+94.1%** | **−30.5%** |

**这不只是"偏保守"，是双向都错**：

- 小包**低估 30%** ⇒ 误放行到 OOM 边缘（安全缺陷）
- 大包**高估 94%** ⇒ 把本来能解的包直接拒了（可用性缺陷）

## 二、换变量：用「解压后容器大小」

19 包 × 2 次测量的线性拟合（因变量取两次的**上包络**）：

| 自变量 | 拟合 | R² | 残差 P50 / P90 / max | MAPE |
|---|---|---|---|---|
| 源包大小 | `6.70x + 102.4` | **0.695** | 9.7 / 35.6 / **136.5** | 5.9% |
| ΣRGBA | `3.03x + 113.9` | 0.942 | 6.6 / 23.6 / 45.6 | 3.9% |
| **解压容器** | **`6.09x + 102.9`** | **0.971** | **4.2 / 10.5 / 37.9** | **2.5%** |
| 解压容器 + ΣRGBA | `6.79, −0.36, 101.9` | 0.972 | 5.5 / 10.2 / 36.9 | 2.7% |

**三条结论**：

1. **最强的单变量是解压后容器大小**（R² 0.971）。物理上说得通：解压容器 ⊇ 纹理压缩数据 + moc3 + 动作，
   它就是「要被搬进内存的东西」的真身。
2. **二元模型里 ΣRGBA 系数变负**（−0.36）⇒ 在「解压容器」之后它没有增量解释力
   （共线性：纹理数据本身就在容器里）⇒ **一个变量就够，不要加第二个**。
3. **固定项 ≈ 103MB**（node 基础 + VM 沙箱 + 收尾 GC 滞后 + Blob 累积），与包无关
   ⇒ 「小包倍数高」的谜团到此解开：**是固定项摊不掉，不是纹理的问题**。

## 三、模型：分段 + 安全垫

均值拟合已经很准（MAPE 2.5%），但准入判据要求**上包络**（宁可高估不可低估）。
最终取「分段 + 15% 安全垫」：

| 解压容器 | 样本数 | 实测 max | **判据值（max × 1.15）** |
|---|---|---|---|
| ≤ 5MB | 1 | 128 | **147** |
| 5 ~ 13MB | 14 | 208 | **239** |
| 13 ~ 21MB | 2 | 232 | **267** |
| 21 ~ 43MB | 2 | 368 | **423** |
| > 43MB | — | — | **`7.0 × uncomp + 118`**（外推，与 43MB 处连续） |

### 3.1 为什么加 15% 而不是贴着实测 max

**因为样本在段内分布不均**（`≤5MB` 只有 1 个样本、`13~21MB` 只有 2 个）。
用单个样本的 max 当整段上界，等于拿一个点当边界 —— 新包一来就可能漏。15% 是把「段内未知」的余量摊掉。

**为什么不用拟合均值 + 系数**：线性公式在离群点（同构成却高 25% 的包）上必然要么低估要么把整条线抬高。
分段能局部吸收，且形态与现有实现一致（分段表，易维护）。

### 3.2 安全垫不给「实测回填」用

见第四节：一旦某包实测过，直接用实测值，不再套公式。

---

## 四、实测回填：让重复访问零误差

**机制**：每次解包完成后，把**实测峰值**写进该包的 probe 缓存（同一指纹、同一目录）。
下次同一包（指纹相同）命中缓存，直接用实测值，不再套模型。

```
首次遇到某包  → 用分段模型（上包络，宁高不低）
再次遇到      → 用上次实测峰值 × 小安全系数（如 1.05，覆盖环境波动）
```

**这解决两个问题**：

1. **离群包自动纠正** —— 同构成却高 25% 的包，第一次可能被判高估，第二次起就用真值，不需要公式去拟合异常
2. **人工维护归零** —— 分段表只是「冷启动的初值」，真实值由运行自己积累

**纪律**：回填的是**上包络**（同一包多次实测取最大），不是最后一次。

---

## 五、probe 必须轻量：只读块表，不解压

实测 probe 成本：P50 **20ms** / P90 56ms / max **173ms**。

**173ms 那个包（LZ4 压缩块）慢 8 倍的原因**：现有 probe 在 LZ4 分支会**解压整包**。

**关键洞察**：算「解压后容器大小」只需要 **blocksInfo 表**（每块的压缩/解压尺寸），
**不需要真的解压数据块**。做到这一点后成本预计与未压缩包同量级（**5~20ms**），
相对解包本身（1.4~10s）是 1% 量级，准入前 probe 完全可以接受。

```
要求：新增/改造的 probe 路径必须能在**不解压**的前提下返回 decompressedBytes
      （对 NONE 分支本来就零拷贝；对 LZ4 分支只读块表求和）
```

## 六、缓存落点

复用既有指纹，**不新增回收路径**：

```
指纹：sha1(rootId \0 rel \0 size \0 round(mtimeMs) \0 pluginId \0 version).slice(0,16)
落点：data/unpacked/<fp>/probe.json
内容：{ decompressedBytes, rgbaBytes, probeMs, measuredPeakBytes?, measuredAt? }
```

- **命中逻辑**：先读 `probe.json`；没有才 probe（与 `index.json` 同一模式）
- **失效**：源包 size/mtime 变 或 插件版本变 ⇒ 指纹变 ⇒ 自然重建，不需要额外失效逻辑
- **回收**：跟着 `data/unpacked/` 既有 LRU 与上限走（20 目录 / 8GB）

## 七、验收判据

| 项 | 判据 |
|---|---|
| **零低估** | 用全部 19 个已测样本回验，**不得有任何样本被低估**（预估 ≥ 实测） |
| 上包络不超 | 高估 ≤ **25%**（15% 安全垫 + 10% 抖动余量）|
| 变量正确 | 判据输入是**解压后容器大小**，代码里不得再出现「源包大小 × 倍数」 |
| 三段回落 | ① 插件 `peakBytes` 直采信 ② 有 `decompressedBytes` 按模型算 ③ 无声明回落源包分段 |
| 安全垫不重复 | 声明了 `peakBytes` 时**不再叠加** 15% |
| probe 轻量 | 单包 probe ≤ 50ms（P90），LZ4 包不得再解压整包 |
| 缓存生效 | 同一包连续 resolve 3 次，probe 只执行 1 次 |
| 回填生效 | 同一包解包 2 次后，判据改用实测值（可用日志或 probe.json 字段核对）|
| 无回归 | 现有插件（不声明 memory）行为不变；全量 22 套绿 |

## 八、数据来源

19 包 × 2 次测量的原始数据（源包 / ΣRGBA / 解压容器 / resS / 纹理构成 / 动作数 / probeMs / 两次峰值）。
测量口径：每次前重启服务重置 VmHWM + 清 `data/unpacked/`，带 `allowOverLimit` 以测得真实峰值。

**样本覆盖**：1024² / 2048² / 3072² / 4096²，1~2 张纹理，ΣRGBA 8~80MB ⇒ 纹理构成差异被覆盖到（这是分得出变量的前提）。

## 九、口径归属：预估是**插件**的事，不是核心的事（2026-10-25 修订）

初版把「源包大小 → 峰值」的拟合模型放在核心（`capacity.mjs` 的分段表）。**这是错的**：
不同插件的容器结构完全不同（UnityFS 块表、ZIP 中央目录、纯目录……），
用一张核心侧的通用表去套所有插件，必然对谁都不准，而且每加一个插件就要重标定一次。

**改为：预估口径由插件声明，核心只做比较。**

```
① 插件声明 peakBytes（字节）      → 核心直接采信，不叠加任何安全垫
② 插件没声明                     → 核心回落「源包大小 × 分段倍数」（粗估兜底，既有行为）
③ 核心不再维护任何「解压容器分段模型」
```

推论：

- 插件算得准不准，是插件自己的责任（不同插件可以各用各的方法）
- 核心侧只剩两个数字的**比较**：`声明峰值 vs 预算`
- 新插件接入不需要核心改任何系数

### 9.1 顺带去掉预热的时间门槛

原实现有一条 `WARMUP_MAX_EST_SEC = 6`：预估解包耗时超过 6 秒就不预热。

实测后果是**反效果**：19.3MB 的包预估 9.6 秒 ⇒ 永远跳过预热 ⇒
服务端缓存永远空 ⇒ 每次加载都回落前端解包（还要把整包读进浏览器内存）。
而服务端为这次判断付出的 probe / 内存读取**每次都白跑**。

所以删除该门槛：**`allowWarmup` 只由内存决定，不看时间**。
预估耗时仍作为参考信息上报（日志里能看「这个包大概多久」），但不参与任何判断。

> 阈值换算（供理解为什么以前全跳过）：`est > 6s` ⇔ 源包 > **15.4 MB**。
> 现有资源包里 19.3 / 20.9 / 42 MB 全在此列。
