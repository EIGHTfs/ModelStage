# 名册渲染成本测量（P3）

> 目的：回答「466 变体全量重建到底多慢」，为「要不要做 keyed diff」提供实测依据。
> **本轮只测量，不改任何产品代码**；下一轮才谈优化。
> 所有数字均为本轮现场实测，**未引用任何历史注释里的旧值**。

**打点方式（运行时注入，未改源码）**：

```
· render 边界 = 包 Element.prototype.replaceChildren（仅 #roster-list），
  起点 = replaceChildren 被调用，终点 = queueMicrotask（render 是纯同步函数，微任务必在其后）

· 帧间隔    = requestAnimationFrame 循环自记时间戳，取相邻差值
```

> 口径说明：render 计时窗口包含 `replaceChildren` + 全部 `append` + render 尾部的

> —— 这点在 §四的结论里很关键。

## 二、结果总表

| 场景 | render 次数 | 中位 | p95 | 最长 | longtask 数 | 最长 longtask | 最差帧间隔 | 折算瞬时 FPS |
|---|---|---|---|---|---|---|---|---|
| **① 冷进入**（首次触发全量加载，7 根并发 → 增量渲染） | 6 | 36.0 ms | 104.9 ms | 104.9 ms | **5** | **216 ms** | 217.6 ms | ~4.6 fps |
| **② 搜索连打 5 字符**（a→ai→aid→aida→aidan，间隔 150ms） | 5 | 1.7 ms | 25.7 ms | 25.7 ms | **1** | 102 ms | 114.0 ms | ~8.8 fps |

各场景的 render 行数（`renderNodes`，即 render 结束时 `#roster-list` 的子元素数）：

```

② 5 字符      1092 → 170 → 7 → 7 → 7             （随关键词收窄快速变小）
③ 清空        3                                    （全部收起，只剩游戏行）

```

689 变体重建三次重复值：`19.1 / 14.4 / 15.8 ms`（中位 **15.8 ms**），每次 1 个 longtask（84 / 55 / 60 ms）。

## 三、逐场景观察

**① 冷进入最重，但是一次性的。**
7 个资源根并发请求，每加载完一个就重画一次（6 次 render），其中两次触发了 100ms+ 的渲染（647 行、1092 行）。
5 个 longtask 全部集中在约 1.4 秒内（`start` 20102→21451ms），最长 216ms，最差帧间隔 217.6ms。

**② 搜索连打，只有首字符贵。**
5 个字符各触发 1 次 render（没有额外的调度抖动）。首字符 `a` 命中 689 变体 → 25.7ms + 1 个 102ms longtask；
之后 `ai`(107 变体, 170 行) / `aid`(3 变体, 7 行) 都是 1–2ms，**没有任何 longtask**。

**③ 清空搜索几乎免费。**
0.5ms、0 个 longtask、最差帧间隔 17.9ms（即没有掉帧）。因为收起态只渲染 3 个游戏行 —— 清空**不是**全量重建。

**补充：全量重建本身比 longtask 小得多。**
同为 1092 行 DOM，render 只占 **15.8ms**，而同一次交互的 longtask 是 **55–84ms**。
render 计时窗口已包含 DOM 构建 + 快照序列化，所以**剩下的 40–68ms 落在 render 之外的同一宏任务里**
（搜索过滤计算、状态保存、面板联动等）。

## 四、结论（这些数字说明什么）

```
1. **render() 不是瓶颈。** 1092 行 DOM 全量重建中位 15.8ms，约等于一帧（16.7ms），
   在 60fps 预算内。它没有出现旧注释里那种 100~250ms 的量级。

2. **真正的耗时大头在 render 之外。** 同一次交互 longtask 55~84ms，而 render 只占 15.8ms
   ⇒ 约 74% 的时间花在 render 窗口之外（过滤/快照/状态/联动）。
   这意味着**只优化 render 的 DOM 构建，天花板很低**。

3. **用户可感知的卡顿只有两处，都很短：**
   · 冷进入：约 0.2 秒掉到 ~5fps（一次性，加载期间，用户预期之内）
   · 搜索首字符：约 0.1 秒掉到 ~9fps（一次性，之后每次输入 1~2ms 无感）

4. **日常交互（连续打字、清空搜索）没有真实卡顿**：5 次输入里只有 1 个 longtask，
   清空搜索 0 个 longtask、0 掉帧。

5. 关于「466 变体全量重建」这个提法本身：**全量重建只在两种时机发生** ——
   首次加载、以及搜索关键词从"无"变"有"（或反向）的那一次。
   连续打字时每次 render 的行数是递减的（1092 → 170 → 7），不是每次都重建 466 变体。
```

**一句话**：**render() 本身不是瓶颈（15.8ms/1092 行），搜索与清空场景均无真实卡顿；
唯一会掉帧的是冷进入（一次性 0.2s）和搜索首字符（一次性 0.1s）。**

> 按本轮要求，**未做 keyed diff 收益估算，也未写任何优化方案** —— 等看完这些数字再定下一轮做什么。

## 五、测量本身的误差与边界

```
· 冷进入无法从"页面导航第一帧"开始打点（注入时机只能是页面已加载后），
  所以表中①是「首次触发全量数据加载」这一过程，不是浏览器导航全过程。
  它比真正的冷导航少了首屏骨架渲染，但同样包含 689 变体的全量重建，作为上界参考是够的。
· render 终点取 queueMicrotask 边界：若某次 render 之后同一宏任务里还有同步工作，
  那部分不计入 render 时间（§四第 2 点的结论正是由这个差值得到的）。
· 第一次测「清空→输入 a」时得到过 61.5ms 的单次值，高于后续三次（19.1/14.4/15.8）。
  推测是首次含指纹初始化后的重画等一次性工作；因此表中的稳定值取三次重复的中位。
· headless 环境与真实窗口的合成器行为可能有差异，绝对 FPS 数字仅供相对比较。
```
