# 插件插槽：分阶段实施骨架

> 状态：**阶段骨架，等待调研补充细节**。设计依据见 [插件插槽](插件插槽.md)。
> 每个阶段必须能独立验证、独立回退；上一阶段不通过不进入下一阶段。

---

## 分阶段原则

```
① 每阶段一个可观测的验收动作（curl / 浏览器测试 / 截图），不靠"代码看着对"
② 每阶段结束时主链行为与开工前一致（不装插件时界面逐项不变）
③ 后一阶段只在前一阶段验收通过后开始；不允许"先铺开再一起调"
④ 每阶段单独提交，提交信息写明本阶段验收结果
```

---

## S1 · 插槽注册表与清单校验（无界面变化）

**做什么**

```
· 前端：window.ModelStagePlugins.slots.register / 插槽表 / disposer 列表（此阶段只登记，不渲染）
· 服务端：plugin.json 校验新增 slots 字段（字符串数组），对照插槽目录校验风险等级
· /api/plugins 下发每个插件声明的插槽与风险等级
· 未在清单声明的插槽 → 注册时拒绝 + warn（不静默忽略）
```

**验收**

```
1. curl /api/plugins：能读到 slots 与 risk（无插件声明时为空数组，不报错）
2. 单测：未声明插槽注册被拒绝、已声明通过、风险等级不符被拒绝
3. 不装插件时界面零变化（面板控件数/顺序与开工前一致）
```

**回退**：删掉注册表与校验，界面本来就没变。

---

## S2 · 列表插槽接入右栏（只往既有分组加控件）

**做什么**

```
· schema.js 从静态常量改为"内置表 + 插槽聚合"
· panel/view.js 渲染时合并插槽贡献；order 排序；id 冲突拒绝
· 既有 registerControls 改造成往 panel.group.<name> 注册（行为不变）
· 插件自定义设置键按清单声明并入 capabilities.settings（§8.3）
```

**验收**

```
1. 样例插件往「设置」组加一个开关：面板出现该控件、位置在组内末尾（order 缺省）
2. 控件值能存住并回读（刷新后保持）
3. 卸载插件：控件消失，内置控件逐项不变
4. 浏览器测试：内置 9 组仍全在、控件数 = 内置 + 插件
```

**回退**：恢复 schema 为静态常量，插槽贡献不参与渲染。

---

## S3 · 允许插件新建分组

**做什么**

```
· 分组 id 强制 plugin.<pluginId>.<name>；内置组 order 0~99、插件组缺省 1000
· 与内置组同名允许但诊断提示；id 冲突拒绝
· 浏览器测试断言改为"内置 9 组必须都在 + 允许额外组"
```

**验收**

```
1. 样例插件新建分组：出现在面板中、排在内置组之后、标题正确
2. 内置 9 组仍在且顺序不变
3. 与内置组同名：出现且诊断日志有提示
4. 浏览器测试通过（断言已改）
```

**回退**：拒绝新建分组（只保留往既有组加控件）。

---

## S4 · owner props 扩展（geometry / activeSurface / document）

**做什么**

```
· 现有 ctx（isWired / initialValue / onSetting / disabledReason）保持不变
· 补 geometry（cssW / cssH / dpr）、activeSurface（spine / live2d / null）、document（只读摘要）
· 每次渲染重新计算并冻结，插件不得持有跨渲染引用
```

**验收**

```
1. 样例插件控件按 activeSurface 显示/隐藏（切到 live2d 时隐藏，切回 spine 时出现）
2. 叠加类用法能拿到 geometry（在 canvas 尺寸变化后数值跟着变）
3. 面板既有控件行为零变化（回归浏览器测试）
```

**回退**：从 ctx 移除三项新增字段（插件侧降级为不可用）。

---

## S5 · 键值插槽与单值插槽

**做什么**

```
· panel.control.<key>（key 强制 plugin.<pluginId>.<key>）：按控件 id 占位/替换
· panel.brand（单值）：后注册覆盖先注册，卸载还原
```

**验收**

```
1. 键值插槽替换某内置控件的选项集：面板显示新选项、原控件不再出现
2. 单值插槽换品牌名：显示新文本；卸载后还原为 ModelStage
3. 两个插件抢同一 key：后注册者被拒绝并给出冲突双方
4. 卸载后截图与安装前逐像素相同（还原性）
```

**回退**：关闭这两类插槽（保留列表插槽）。

## 调研要回答的问题（派给成员，落盘后回填本文）

```
A 前端侧
  · schema.js 的聚合点应该放在哪一层（schema / view / 装配期），为什么
  · 面板控件数被哪些测试断言依赖，改动会连带影响什么
  · ctx 现在由谁构造、在什么时机，补三个字段会不会引入时序问题
  · 插件脚本的装载顺序与插槽注册时机（经典脚本，非 ESM）会不会有竞态

B 服务端侧
  · plugin.json 现有校验在哪、加 slots / settings 字段的校验成本与兼容性
  · /api/plugins 现有响应形状，新增字段会不会影响既有消费方
  · 风险等级（append / replace / shadow）如何与插槽目录对照校验
  · 老插件（无 slots 字段）必须零改动可用

C 测试与回归面
  · 现有浏览器测试的基线（组数、控件数、默认值）分别断言什么
  · 如何为"注册/排序/回收/拒绝"四类行为写可验证用例（不靠肉眼）
  · 哪些断言必须改成"内置必在 + 允许额外"，哪些不能放宽
```
