## 一、现状盘点

| 前提 | 现状 | 判断 |
|---|---|---|
| 渲染面注册表 | `src/web/render/surfaces.js` 的 `SURFACES`：加新面 = 加一行 + 写 `render/<kind>.js` + `register()` 一次；未知 kind 一律返回 `null`，不回落 | ✅ 已有 |
| 舞台生命周期 | `createStageSurface({root, log}).activate(document)` 单一入口；卸载契约 `unmount` / `dispose`（未实现 unmount 时回落 dispose） | ✅ 已有 |
| resize 分发 | `resizeCbs` 回调集，舞台统一触发 | ✅ 已有 |
| **相机** | `createCamera({kind, backend, log})` 已是带 kind 的工厂；但 `backend` 契约被写死成 **2D 语义**：`getScale / setScale / pan / resetView` | ❌ **缺口** |
| **交互** | `attachStageInteraction({canvas, stage, options})` 对外只有 `zoomStep / zoomTo / panBy / reset` —— **全是 2D 视图操作** | ❌ **缺口** |
| 布局分区 | `header` / `left-panel` / `right-panel` / `stage` / 底部条各自定位，无统一「5 区」命名 | ⚠️ 命名层面 |

**结论**：注册与生命周期这两块最难的已经就位；真正堵 3D 的是**相机与交互被写成了 2D/spine 专用**。

## 二、三项改动（按依赖排序）

### A · 相机：从「2D 视图操作」到「能力 + 原语」

**问题**：`backend` 必须提供 `getScale/setScale/pan`，3D 的轨道相机没有"缩放比例"这个量，硬凑只能造假数据。

**改法**：把能力显式声明，交互层按能力派发，不再假设"一定有 scale"。

```js
// 相机对外契约（新）
{
  capabilities: ['zoom', 'pan', 'reset'],        // 2D（spine / live2d）
  // capabilities: ['orbit', 'zoom', 'reset'],   // 3D 未来实现
  zoomTo(value) {}, zoomStep(dir) {},
  panBy(dx, dy) {}, orbitBy(yaw, pitch) {},
  resetView(keepDistance) {},
  clamp(value) {},                                // 唯一钳制点，保持现状
}
```

**关键**：`limitsFor(kind)` 保留（按 kind 取限位），只是限位的**含义**由能力决定（2D 是 scale 区间，3D 是距离/俯仰区间）。

### B · 交互：拆成「手势识别」与「策略」

**问题**：`interaction.js` 把「鼠标事件 → 平移/缩放」写在一起，3D 的左键拖拽是"转视角"不是"平移画布"，混在一个文件必然互相踩。

**改法**：两层。

```js
// 第一层（公共，与 3D 无关）：识别手势 → 语义事件
onDragStart / onDrag(dx, dy) / onWheel(delta) / onPinch(scale) / onDoubleClick / onReset

// 第二层（每面一个策略，注册在 SURFACES 上）：
strategy: {
  capabilities: [...],                  // 与相机能力对齐
  handleDrag(dx, dy), handleWheel(d), handlePinch(s), reset(), dispose(),
}
```

`attachStageInteraction` 只负责第一层；第二层由 `SURFACES` 里对应 kind 提供。这样 3D 的实现完全独立于 spine/live2d。

### C · 布局：给 5 区命名（只是命名，不改视觉）

```css
/* 目标：body 是 5 区网格，舞台占中间 */
.app-shell { display: grid; grid-template-areas:
  "header header header"
  "left   stage  right"
  "footer footer footer"; }
#app-header { grid-area: header }
#left-panel { grid-area: left }
#stage      { grid-area: stage }
#right-panel{ grid-area: right }
#transport  { grid-area: footer }
```

**视觉零变化**是硬要求（现有绝对定位/尺寸不变，只把容器关系显式化）。目的是将来 3D 需要的位置（视图立方、轴指示、模式切换）有明确锚点。

## 三、怎么证明"前提成立"（不写 3D 也能验）

```
加一个 stub 渲染面 `render/demo-3d.js`：
  · 不画任何东西（或只画一个坐标轴）
  · SURFACES 加一行 { id:'demo-3d', kind:'demo-3d', capabilities:['orbit','zoom'], strategy:{...} }
  · 验证四件事：
    ① 注册后能被 activate（走通单一入口 + 卸载契约）
    ② 交互按 capabilities 派发：orbit 生效、pan 不被调用
    ③ resize 正常触发
    ④ **spine / live2d 行为完全不变**（现有套件 + 页面出画）
```

**stub 的意义**：它证明"3D 插得进来"，而不需要真的写 3D 渲染器。验完可以留着（当架构回归用例）或删掉。

## 四、风险与边界

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 抽象改动破坏现有 spine/live2d 渲染 | 中 | 白屏/错位 | A/B 都是"契约层重排"，先让现有套件全绿；页面逐面出画对照 |
| `capabilities` 设计过度，将来 3D 用不上 | 中 | 白做一层 | 只声明**现在已知需要**的能力（orbit/zoom/pan/reset），不预设更多 |
| 布局改 grid 导致视觉位移 | 中 | 用户可见变化 | C 单独一步做，改完逐区截图比对 |
| 抽象层变成第二套真相 | 低 | 两份实现漂移 | 交互层只做手势识别，不做具体视图操作 |

**边界条件**：
- 未知 kind → 仍返回 `null`（现有约束不变）
- `capabilities` 为空 / 缺失 → 按 2D 默认（zoom/pan/reset），保证旧面不受影响
- 相机 backend 未提供某能力对应方法 → 该手势静默忽略（不抛错），日志记一条

## 五、不做什么

```
✗ 不写 3D 渲染（不引 three.js、不做 glTF/GLB 加载、不做光照/材质）
✗ 不改任何可见 UI（C 只加容器关系与 grid-area，视觉必须一致）
✗ 不动解包链（texdecode / astc / worker）
✗ 不做多舞台并排（一台一模型，保持现状）
```
