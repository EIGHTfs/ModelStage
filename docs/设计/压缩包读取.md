# 设计 · 压缩包读取（**决定不做**）

> **状态：不做**（2026-10-26 定）。本文保留探索记录，供以后需要时直接接手。

## 一、最终决定

**不做独立的"压缩包读取"功能。**

理由：压缩包解析 + 内容分流 + 缓存，是一套与现有机制**并行**的复杂逻辑；
而「**解包成文件夹**」之后，现有的资源根扫描、混合内容识别、解包缓存、内存准入全部自动适用 ——
写一套新的解析路径，复杂度远大于收益。

```
不做的   一个 ZIP 混装 live2d / spine / live2d 资源包 → 工具内直接读
改成     用户自己解包成文件夹 → 当作普通资源根加入（现有能力已支持混装）
```

## 二、需求与方向的原记录

### T14 · 压缩包读取（一个 ZIP 里混装 live2d / spine / live2d 资源包）

**状态**：❌ **最终决定：不做**（2026-10-26）
**理由（用户定）**：写一套压缩包解析 + 分流 + 缓存逻辑，不如直接让用户**解包成文件夹**。
  解包成文件夹之后，现有的资源根扫描、混合内容识别、缓存、内存准入全都自动适用，
  而"压缩包读取"会引入一条与这些机制并行的新路径，复杂度远大于收益。

**本节以下为历史探索记录，保留备查（不再实施）**

**用户 2026-10-25 提出的需求 + 方向裁定**：
```
需求：想要个压缩包读取插件，里面的内容既可以是 live2d、spine，
      也可以是 live2d 资源包，而资源包需要依赖插件。

方向（用户裁定）：
      **不用插件**。服务端本身就把「压缩包」视作「文件夹」。
      并反问：文件夹下面多个压缩包，算几个资源根合适？
```

#### 方向：ZIP = 文件夹（不引入插件通道）

```
上传/放入 ZIP → 服务端解包到 data/archives/<archiveId>/ → 得到一个**真目录**
→ 注册成一个资源根（就是把该目录登记进 resources.json）
→ 之后完全复用现有链路：扫描 / manifest 签名 / catalog / 名册 / VFS / 渲染
```

**bundle 内容天然复用**：解出来的 `.bundle` 文件就是现有的「容器单文件模型」，走 `/api/unpack/resolve` + unity-live2d-bundle 插件 —— **零改动**。

⇒ 这条方向比"扩展插件契约（一容器多模型）"改动小得多，且不需要动 G1/G2 契约。

#### 「多个 ZIP 算几个资源根」—— 建议：**一 ZIP = 一资源根**

理由是它对齐「资源根」的既有语义，且零改动：

| 理由 | 说明 |
|---|---|
| 资源根的语义 = 可独立管理的来源 | ZIP 天然是一个独立来源（能单独删、单独重扫、单独禁用） |
| 扫描链路零改动 | 解包后是**真目录**，`catalog` / `manifest-stamp` / 名册全都不用改 |
| 想合并已支持 | 现有「**同名根合并**」就是先例：`azurlane` + `azurlane_spine` + `azurlane_bundle` 三个根合并成一个左栏节点（245 角色 / 332 变体）。用户若希望几个包显示成一个节点，只需同名 |
| 不自动按目录合并 | 若同一目录下 3 个 ZIP 自动合成一个节点，用户删其中一个时不好理解"删的是整个根还是其中一包" |

**命名约定**：
```
rootId  = 由 zip 文件名派生（去扩展名 + 冲突加后缀），全局唯一
root.name = zip 文件名（去扩展名）       ← 左栏显示这个
可选：父目录名作为分组标签（只是展示，不影响扫描）
```

#### 要新建的四块（都在服务端，不动插件）

```
① ZIP 解析        全仓**零 ZIP 能力**（grep 确认）。零依赖 ⇒ 自己写中央目录 + inflateRaw
                  ~250 行。要明确支持/拒绝哪些变体（ZIP64、data descriptor、加密、分卷）
② 归档导入        接收 ZIP → 校验（大小/entry 数/路径安全）→ 解包到 data/archives/<id>/ → 登记资源根
③ 生命周期        删除资源根时是否连解包产物一起删；原 ZIP 是否保留（保留占双份空间）
④ zip slip 防护   条目名可能含 ../ ⇒ 规范化 + 拒绝逃逸
```

#### 风险

```
① 内存：已知 19MB 包 → 451MB 峰值。ZIP 里多个 bundle ⇒ 峰值叠加
   ⇒ **必须先做 T4 流式解包**
② ZIP 变体：ZIP64 / data descriptor / 加密 / 分卷 —— 自写解析要明确边界，拒绝时给可读原因
③ 判型歧义：同一模型可能同时有 raw live2d 与 bundle 两种形态 ⇒ 都列出，还是优先某种
④ 磁盘：解包产物占盘，要确认 LRU / 清理策略
⑤ 嵌套 ZIP：建**只展一层**，内层 ZIP 当普通文件（不递归）
```

#### 分期（暂缓，排到 T4 之后）

```
前置：T4 流式解包
一期：服务端能力 + 手工把 ZIP 放进某个目录 → 验证判型 / 混合内容 / 同名合并
二期：上传 UI（拖拽 + 进度 + 错误呈现）
三期：归档的资源根管理（重扫 / 删除 / 改名，直接复用现有资源根面板）
```

## 三、为什么"解包成文件夹"就够了

| 关注点 | 压缩包读取 | 解包成文件夹 |
|---|---|---|
| 混合内容识别 | 要自己分流（按扩展名/目录/内容探测） | 现有扫描按文件形态识别，本来就支持混装 |
| 缓存 | 要设计一套压缩包级缓存 | 现有 `data/unpacked` 按资源包指纹缓存 |
| 内存准入 | 要评估"读整个 ZIP"的峰值 | 现有 capacity 按源包大小 + 插件声明峰值 |
| 内存保护/防卡死 | 新路径要各自再实现一遍 | 复用现有 |

一行结论：**压缩包只是"还没解开的文件夹"，交给解压工具比交给程序更合适。**
