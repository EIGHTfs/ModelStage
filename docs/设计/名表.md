# 设计 · 名表（v2 索引表）

> **状态：已排期，分 5 步实施（见 §九）。第 1~2 步已下发。**
> 当前生效的是 v1 名表（`config/names/<game>.json`）。本文描述的是把「名表 + 匹配表 + 头像目录」
> 三件合并成一份本地索引表的重设计，实施前不要按本文操作。
>
> 相关：接口见[参考/接口清单](../参考/接口清单.md) §一；资源根配置见 `config/resources.json`。

---

## 一、要解决的痛点

| # | 痛点 | 事实 |
|---|---|---|
| P1 | **主键脆弱**：名表以资源目录名（多为拼音）为键 | 部分目录是后缀变体（`_ii` / `_new` / 罗马数字），上游表无此键 ⇒ 界面回退显示拼音 |
| P2 | **中文名依赖上游数据** | `nameZh` 全部由上游 JSON 转出，上游缺则空 |
| P3 | **头像与资源仓绑定** | 头像目录被删则全破图；头像源仓与资源仓分离 |
| P4 | **新游戏接入全靠手工写转换器** | 每个游戏一个导入脚本，重复劳动 |
| P5 | **覆盖率无运行时记录** | 头像/名字命中数只在生成时算一次，运行时无感知 |

## 二、核心思路

```
一个 config/index/ 目录，本地手工维护：
  每游戏一个索引文件，记录「资源键 → 角色 ID → 多语言名称 → 头像」

角色 ID 用各游戏原生稳定 ID（数字 ID / ship id / 前缀 ID / 角色代码）
资源目录名降级为「匹配线索」
名称支持多语言，本地手工补的永远优先于上游（重跑不覆盖）
头像本地化，运行期零外仓依赖
上游数据只当初始导入的原料，之后本地表是权威源
```

## 三、数据模型

```jsonc
// config/index/<game>.index.json
{
  "_meta": {
    "v": 2,
    "game": "碧蓝航线",
    "idSemantics": "ship_id",                  // 本游戏角色 ID 的语义（按游戏异构）
    "roots": ["azurlane", "azurlane_spine"],   // 本索引服务的资源根
    "normalize": "strip-suffix:_ii,_new,_hx + roman-numerals",   // 归一化规则（按游戏可配）
    "updatedAt": "…"
  },
  "characters": {
    "62": {                                     // 角色 ID（各游戏原生 ID 的字符串形式）
      "name": [                                 // 角色名：数组，元素为各语言名
        { "lang": "zh", "text": "阿尔比恩" },
        { "lang": "en", "text": "Albion" }
      ],
      "costumes": {                             // 皮肤：皮肤 ID → 多语言名（同结构）
        "3": { "name": [ { "lang": "zh", "text": "晨光里的事故" } ] }
      },
      "avatar": "62.png",                       // 头像文件名（相对头像库；无则省略）
      "tags": ["轻巡"]                          // 可选，树内筛选用
    }
  },
  "byAsset": {                                  // 资源键归一化 → { 角色ID, 皮肤ID? }
    "aerbien_3":      { "char": "62", "costume": "3", "how": "upstream" },
    "dahuangfengii_2": { "char": "97", "costume": "2", "how": "manual" }
  }
}
```

**多语言名称约定**：

- 角色名与皮肤名统一用 `name` **数组**表达，元素为 `{ lang, text }`
- 语言字段**可缺**（某语言没有就不写该元素），但**至少一个** —— 校验对空数组报错拦截
- 界面显示顺序：当前界面语言 → 中文 → 数组第一个元素；全部缺失才回退资源目录名

**要点**：

- **一份文件管全部**：角色、皮肤、多语言名、头像文件名、资源键匹配都在里面，
  界面与服务端只读它，不再拼「名表 + 匹配表 + 头像目录」三件
- `byAsset` 的键是**归一化后的资源键**，规则写在 `_meta.normalize`（按游戏可配）
- `how` 字段标记来源（`upstream` / `fuzzy` / `manual`），导入工具重跑时**保留 manual 条目**
- **v1 兼容**：`config/names/*.json` 保留只读，读索引表失败时回退 v1，迁移期双轨

## 四、头像本地化

```
组织：<游戏>/<角色ID>.png（皮肤级头像 <角色ID>_<皮肤ID>.png，可选）
暂存：单独一个私有仓存全部游戏头像，不进主项目仓（主仓保持轻量）
部署：本机拉到固定位置，resources.json 的头像根指向它
```

**三条提取路**（一次性工具，提取后可删）：

1. 资源目录自带 `icon.png` → 首扫时拷入
2. 仓内头像目录 → 全量拷入并按索引表重命名为 `<角色ID>.png`
3. 无源 → 占位图（界面兜底，不阻塞）

**纪律**：头像仓只进 png 与清单 json（每游戏一份 `<角色ID> → 文件名` 映射），不混入代码。

### 4.1 头像根**可配置**，不假设它在主仓内

主仓在 CIFS/SMB 挂载上（工作区即如此），而该挂载**不允许 chmod** ⇒ `git init` / `git clone`
在写 `.git/config.lock` 时必然失败（`Operation not permitted`）。
所以「头像仓就在主仓内 `avatars/`」是个坏假设 —— 它在那块文件系统上根本建不起来。

```
优先级：--avatar-root <dir>  >  环境变量 MODELSTAGE_AVATAR_ROOT  >  <主仓>/avatars（默认占位）
```

部署时把头像仓 clone 到任意可写位置，再用上面任一方式指过去即可；
`<主仓>/avatars/` 只作本地默认与占位，**不存在也不需要是 git 仓**。

**位置归属**：
- 提取工具 = 项目工具，放 `tool/extract-avatars.mjs`（**不能放在 `avatars/` 里** —— 那个目录整体被 gitignore，放进去等于不入库）
- 头像仓自身的说明 = 文档 `docs/参考/头像仓.md`（随主仓入库；头像仓 clone 到别处时不需要它也在仓内）

## 五、已定决策

| # | 决策 |
|---|---|
| D1 | **角色 ID 语义按游戏异构**：接受。`_meta.idSemantics` 写明每游戏 ID 语义；界面只显示名字不显示 ID，异构无碍 |
| D2 | **头像不入主仓，入单独私有仓**。主仓 index 只存 `avatar` 文件名，文件本体在头像仓 |
| D3 | **多语言名用 `name` 数组**（元素 `{lang, text}`）：子字段可缺，数组不能为空 |
| D4 | **界面补录暂不做**：本期只做「未命中红点提示 + 手工改 index.json」，不做写回端点 |
| D5 | **游戏内本地化表可导入**：从游戏自带的多语言 Excel/JSON 表抽角色名作 index 初稿（`how: upstream`），人工再补 |

## 六、扩展新游戏的最小步骤

```
1. 克隆资源仓到本机（资源仓与项目仓分离，资源不进项目 git）
2. 写 config/index/<game>.index.json 初稿：_meta（idSemantics / roots / normalize）+ 名字源
3. 头像：跑对应提取器进头像仓的 <game>/（或置空占位），头像仓推送、本机拉取
4. resources.json 加根，names 字段改指新 index（v2 读 index、缺则回退 v1）
5. 界面跑通：byAsset 命中项正常聚合，未命中项红点提示 → 手工补 byAsset（how: manual）
```

## 九、现状实测与迁移映射（2026-10-26 核对代码）

### 9.1 v1 真实结构（不是"待调研"，是已经在了）

`config/names/<game>.json` 的顶层与 v2 **同构**（`_meta` / `characters` / `byAsset`），
所以 v2 是 **schema 演进（specVersion 1 → 2）**，不是换容器：

| 文件 | 游戏 | 角色数 | byAsset 数 |
|---|---|---|---|
| `azurlane.json` | 碧蓝航线 | 2558 | 2557 |
| `bd2.json` | 棕色尘埃2 | 231 | 421 |
| `dcg.json` | 天命之子 | 2583 | 2583 |

v1 条目实样（碧蓝 `22`）：

```jsonc
"characters": { "22": { "name": "22", "nameZh": "", "costume": "", "npc": false, "assets": ["22"], "icon": "22.png" } },
"byAsset":    { "22": "22" }        // 资源键 → 角色 ID（**字符串**）
```

### 9.2 字段映射（迁移必须逐条对上，漏一个就丢数据）

| v1 | v2 | 处理 |
|---|---|---|
| `name`（字符串）| `name`（`[{lang,text}]` 数组）| 包成 `[{lang:'zh', text: nameZh \|\| name}]`；`nameZh` 为空时用 `name` |
| `nameZh`（独立字段）| 并入上条数組み | 不再单独存在 |
| `costume`（字符串）| `costumes`：皮肤 ID → `{name:[...]}` | 单值 → 需要一个皮肤 ID 才能建键；v1 无皮肤 ID ⇒ **记入 `_meta.migrateNotes` 待补**，不猜 |
| `icon` | `avatar` | 直接改名 |
| `assets`（数组）| **删除** | 实测 **0 个消费方**；其信息已由 `byAsset` 的键承载 |
| `npc`（布尔）| **删除** | 它唯一的真实用途是 `roster/list.js:205` 的排序键（普通角色在前、NPC 在后）。该区分判定为多余 ⇒ 字段与排序一并删，名册全部按显示名排序（bd2 的 24 个 NPC 会混回普通顺序，已知的可接受变化）|
| `byAsset[id]`（字符串）| `{char, costume?, how}` | **兼容读取**：`typeof v === 'string' ? v : v.char`（见 9.3）|
| `_meta` | 加 `idSemantics` / `roots` / `normalize` | 保留原有 `spec/specVersion/game/source/generatedAt/counts` |

**迁移实现备注（第 1 步落地时定下的两处取舍）**：

1. **`costume` 单字符串：只记进 `_meta.migrateNotes`，不在角色条目上加临时字段。**
   理由：`costume` 在 v1 里是"这一条皮肤的名字"（如天命之子 `c000_10` 的 `Mysterious`），
   没有皮肤 ID 就建不出 `costumes{皮肤ID→…}` 的键；而给它加一个临时字段（如 `_pendingCostumeName`）
   会让每个角色条目多一个**只能被导入工具消费、界面完全不认**的字段，
   等于在 v2 的模型里留一个半成品形状。
   实际写成 `_meta.migrateNotes.costumeWithoutSkinId = { note, distinctValues, byValue }`，
   `byValue` 是"皮肤名字 → 有多少条"的聚合分布（碧蓝 1504 种、棕尘 195 种、天命 1036 种）——
   导入工具据此可以按名字反查游戏内皮肤表补 ID，不用逐条扫 5000+ 角色。
2. **`assets` 补全 `byAsset` 的实测结果**：碧蓝补 164 条、棕尘补 2 条、天命补 0 条（标 `how: manual`）。
   补全后 byAsset 条数 2721 / 423 / 2583；`upstream` 仍保持 v1 原有的 2557 / 421 / 2583。

另：迁移后**三张表的名字条数全部是 1 条**（2558 / 231 / 2583，无空数组）——
因为 v1 只有一个 `nameZh` 槽位，v2 的多语言能力现在用不上，等导入工具从游戏内多语言表补第二语言。

### 9.3 兼容读取（迁移期必须双读，否则碧蓝 2557 条一次性读不出来）

`src/web/roster/list.js:87` 现在是：

```js
const id = index.byAsset[key];     // v1：值就是 id
```

v2 的值是对象，必须写成「字符串当 id、对象取 `.char`」，且 `costume` 一并取出。
这一处不改，v2 数据一上线 roster 就整片失效 —— 而它只在浏览器里才暴露，静态门禁看不到。

### 9.4 新增决策

| # | 决策 |
|---|---|
| **D6** | ~~`npc` 在 v2 保留~~ → **改为删除**：该字段的唯一真实用途是名册排序键（`list.js:205` 普通角色在前、NPC 在后），该区分判定为多余 ⇒ 字段、排序、导入工具与 spec 里的 npc 一并清掉，名册统一按显示名排序 |
| **D7** | `assets` 在 v2 删除：实测零消费方，信息由 `byAsset` 键承载；迁移时用它**补全 `byAsset` 缺失项**（v1 里 `characters[id].assets` 有、`byAsset` 没有的键） |
| **D8** | `byAsset` 值升为对象，`how` 缺省按来源标：v1 迁移来的标 `upstream`；补全项标 `manual` |

### 9.5 实施顺序（每步可独立验收，不要一口气做到 5）

| 步 | 内容 | 验收 |
|---|---|---|
| **1** | spec 升 v2（schema + `check` 拦空 `name` 数组）+ v1 迁移函数 | 三张表迁移后 spec 全过；**角色数/名字条数逐项与 v1 相等**；空 `name` 数组被 check 拦红 |
| **2** | 头像仓结构 + 清单 json + 主仓 `.gitignore` | 头像仓只有 png 与清单 json；主仓 `git status` 不出现它 |
| **3** | 服务端两块：名表读取（index 优先、v1 兜底）+ 头像 URL 解析 | 只有 index 时能读；只有 v1 时能读；两个都没有时明确报错不静默 |
| **4** | 角色树聚合键改造 + 未命中红点与 `how` 提示 + 9.3 的兼容读 | 未命中项有红点；命中项名字取 index 而非目录名 |
| **5** | 导入工具 `import-index-<game>` + `resources.json` 路径切换 | 重跑导入不覆盖 `how: manual` 的条目 |
