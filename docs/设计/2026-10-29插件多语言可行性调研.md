## 零、结论先行

**建议做，但形态收窄为「仅服务端侧的子进程通道」，且它是第 2 阶段的事 —— 第 1 阶段（运行时抽象）尚欠。**

三条核心判断：

```
① 「多语言」= A 类（插件用 Python 写），不是 B/C。有原文依据，见 §1。
② **技术完全可行**：UnityPy 1.25.4 在本机真装成了（71MB），真包解开，产物与我们 JS 实现**逐项一致**。
③ 但**现在不该急着做**：真正的前置债是"运行时抽象"，而它还没做；
   且我们自研的 JS 解析已经不落后（126/126 包全通过），Python 的边际收益不在"能解包"，
   而在"覆盖我们还没实现的格式 + LZMA 性能反超（实测快 5~7 倍）"。详见 §5。
```

## 三、沙盒能不能跑 Python —— 实测

### 3.1 环境实测（不是假设）

```
/bin/python3        → Python 3.8.15，**没有 pip**（No module named pip），有 ensurepip 可引导
                      无 gcc / cc / clang / make（DSM 无编译链）
<Python310 套件目录>/bin/python3.10  → Python 3.10.20 + pip 23.0.1   ✅ 可用
<Python314 套件目录>/bin/python3.14  → Python 3.14.7  + pip 26.2.1   ✅ 可用
<Python2 套件目录>/...                      → Python 2.7（与本议题无关）
DSH 套件内（target/.local/bin）                 → 无 python、无 pip
```

⇒ 真要用 Python，**不能假设 `python3` 就是能用的那个**：系统那个 3.8 连 pip 都没有。
必须在插件里显式探测（`python310` / `python314` / `python3` 依次试），并把探测结果报给用户。

### 3.2 子进程帧协议的成本实测（非常便宜）

用 `spawn + 行 JSON 帧` 跑了一次真往返：

```
spawn → 首帧往返: 32ms       （含 python 解释器启动）
常驻后每帧往返: 0.30ms       （10 次平均，纯管道 JSON 开销）
中文路径在帧里传输: 无乱码 ✅ （本项目路径大量中文，这条必须实测过）
python 裸启动: 0.03~0.04s
```

⇒ **协议本身不是成本**。既有文档估"冷启 50~120ms"，实测比它更快（本机轻）。

### 3.3 浏览器侧：原理上不成立

浏览器里没有 Python 运行时。唯一可能是 WASM 版 Python（Pyodide），而：

```
· Pyodide 运行时本身数十 MB，启动秒级
· UnityPy 还依赖 Pillow / numpy 等 C 扩展 —— 这些在 Pyodide 下多数没有可用轮子
⇒ 浏览器侧用 Python 做资产解析：**不成立**，且与"页面加载要快"直接冲突
```

**这一条没有争议：浏览器侧插件继续限定 JS。** 现有前端插件全是渲染/效果类，也不需要 Python。

## 四、UnityPy 真装实测（用户授权）

既有文档 §五 写的是"首次运行 `pip install --target`"，但没验证过**本机能不能装**。这次实测，结论比文档乐观，但埋着两个硬坑。

### 4.1 结果：装成功，且能解我们的包

```
安装命令（实测可用）：
  <Python310 套件目录>/bin/python3.10 -m pip install \
      --target <可执行卷上的目录>/deps UnityPy --no-cache-dir

结果：UnityPy **1.25.4** import 成功，deps 体积 **71MB**
```

依赖链（全部装到插件目录，主项目不受影响）：
`Pillow, lz4, brotli, texture2ddecoder, etcpak, astc-encoder-py, fmod_toolkit, fsspec, attrs, tpk_ar, archspec, typing_extensions`

### 4.2 真包对账：与我们的 JS 实现**逐项一致**

```
aierdeliqi_5（LZMA 包，2.11MB）
  JS 侧（上轮实测）  ：6809 对象 / physics3 1299B / texture_00 2048² fmt47 / texture_01 1024² fmt47
  UnityPy 侧（本次） ：6809 对象 / physics3 1299B / texture_00 2048² fmt47 / texture_01 1024² fmt47   ✅ 完全一致

ailunsamuna_2（LZMA 包，2 块）
  JS 侧              ：objects=2863 / physics3 49733B / texture_00 2048² fmt47
  UnityPy 侧         ：2863 对象 / physics3 49733B / texture_00 2048² fmt47                          ✅ 完全一致
```

⇒ **UnityPy 能正确解我们手上的包**，且结论与自研实现互相印证（这本身也是一次有价值的交叉验证）。

### 4.3 性能：LZMA 包上 **UnityPy 快 5~7 倍**

```
UnityPy  load + 列对象：aierdeliqi_5 0.61s ／ ailunsamuna_2 0.30s
我们 JS  ：同两个包 resolve 10.3s ／ 12.9s（含纹理解码/PNG 编码）
          其中仅 LZMA 解压一步就要 3.5~4.4s（上轮实测）
```

口径说明：这两组不完全等价（JS 侧含纹理→PNG 编码，UnityPy 侧只列对象）。
但**同一件事"解开 LZMA 块"上，UnityPy（C 扩展）比我们的纯 JS 快一个量级**是确定的 ——
这正好是我们上一轮记下的最大性能债（`docs/设计/2026-10-28UnityFS-LZMA支持调研.md` §五风险 1）。

## 五、两个硬坑（**部署层面，比协议难得多**）

### 坑 ①：`/tmp` 是 **noexec**，C 扩展直接加载失败

第一次按常规装到 `/tmp` 后 import 立刻炸：

```
ImportError: <依赖目录>/_brotli.cpython-310-x86_64-linux-gnu.so:
failed to map segment from shared object
```

`mount` 实测：`tmpfs on /tmp type tmpfs (rw,nosuid,nodev,noexec)`

⇒ **Python 插件的依赖目录必须放在可执行的卷上**（本项目 `/volume1` 的 btrfs 挂载没有 noexec）。
这条会直接影响插件的安装目录设计：**不能在 /tmp 建 venv/.deps**，也不能放在任何 noexec 挂载点。

### 坑 ②：系统 python3 没有 pip，且没有编译链

```
/bin/python3 → No module named pip
gcc / cc / clang / make → 全部不存在
```

所以：
- 必须用 `python310` / `python314`（套件带的），且要在插件里**探测**而不是写死
- 任何"只有 sdist、需要编译"的包在本机**装不上**。本次实测：`etcpak` / `astc-encoder-py` 提供的是 **`cp37-abi3`** 轮子（stable ABI，跨版本通用 ✅），所以躲过了编译 —— 但这是运气，不是保证

**第三条隐性约束**：磁盘。项目所在数据卷已用 **91%（剩 2.9G）**，单个 Python 插件的 `.deps` 就是 71MB 起（UnityPy 全套）。多装几个插件要注意。

## 七、收益判断（这条决定"值不值得"）

**先说反面**（为什么不急）：

```
· 我们自研的 JS 解析现在**已 126/126 包全通过**（LZMA 补齐 + version 6 修完）。
  既有文档 10-27 写"自研不该继续加厚、该上 UnityPy"时，前提是 64/123 包打不开 —— **这个前提没了**。
· 现有两个插件的产物契约（entry.json / model3.json / files 视图）已经稳定，
  重写成 Python 是**重写而非增强**，收益必须先证明"多解出来的东西有人用"。
· 加一条 Python 通道 = 加一整类部署失败模式（解释器探测、noexec、71MB 依赖、磁盘 91% 满）。
  这些成本落在**每一次安装/迁移**上，而不是一次性。
```

**再说正面**（什么情况下值得）：

```
① 覆盖率：UnityPy 覆盖的 Unity 版本/压缩类型/资源类型远宽于自研。
   如果将来遇到我们解析不了的新包型（比如 LZ4HC 之外的压缩、更新的 typetree 变体），
   与其继续逆向，不如直接上 UnityPy —— 这是"未来保险"，不是当下痛点。
② 性能：LZMA 上实测快 5~7 倍（0.3~0.6s vs 3.5~4.4s）。
   这个债我们上轮已经明确记下（内存 241MB + 慢 20~30 倍 vs LZ4）。
   如果 LZMA 包在真实使用中占比上升，UnityPy 通道就是现成解法。
③ 交叉验证：本次对账已经证明"两套实现能互相印证"，这对排查"模型打不开到底是包坏了还是我们解析错了"很有价值。
```

### 我给的判断

```
**不建议现在做**（不是"不能做"）。理由排序：
  ① 前置换没还：runtime 抽象未落地（grep runtime 0 命中），先做这个是纯重构、无风险
  ② 收益前提已变：自研 126/126 全通过，UnityPy 从"救火"降级为"未来保险 + LZMA 加速"
  ③ 成本偏"每次部署都付"：解释器探测 + noexec 检查 + 71MB 依赖 + 磁盘 91%

**如果一定要排期，只做前两步**（runtime 字段 + 适配器接口 + node-vm 适配器）。
这两步是纯重构、有独立验收、且无论将来做不做 Python 都不浪费（顺便把"插件运行时"这件事说清楚了）。
Python 适配器等到"真的遇到解不开的包"或"LZMA 性能成为实际投诉"时再上。

**唯一可能让我改口的情形**：如果你觉得 LZMA 包 3.5~4.4s 的解压 + 241MB 峰值内存
会实际影响体验（第 2/3 步的 worker/内存准入已经做了，但解压本身仍慢），
那"UnityPy 子进程"是比"继续优化纯 JS LZMA"更划算的路 —— 因为对方是 C 扩展。
```
