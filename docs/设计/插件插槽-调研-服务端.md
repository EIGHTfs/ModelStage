# 插件插槽 · 服务端侧调研（S1 服务端部分）

> 范围：只回答「服务端要动什么、代价多大、会不会撞到既有行为」。
> 前端与测试两块见另两份调研；本文末尾留了给对方文档的交叉意见位。
> 依据全部来自当前工作区代码（行号以本次读取为准），**未改任何代码**。

先给两个贯穿全文的事实，后面每条都靠它们：

**事实 A：清单读取是「逐字段白名单」**。`readPluginManifest` 返回的是一个**手写的对象字面量**
（`src/server/plugins/registry.mjs:236-289`），只有列出来的字段会出去。
清单里多写的键**不会报错，也不会透传** —— 直接被丢掉。
⇒ 新字段必须**手工加一行**，否则前端永远拿不到（这不是 bug，是刻意的收敛面）。

**事实 B：设计稿里的 `src/server/routes/plugins.mjs` 不存在**。
`/api/plugins` 的处理在 `src/server/routes/data.mjs:27-36`（`apiBasics` 里一串 if）。
插槽设计 §五 第 2 条的文件名要改，否则后续照文档改会找不到文件。

## B1 · plugin.json 现在在哪校验、校验到什么程度；加 `slots` / `settings` 的成本与兼容性

### 结论

校验分**两处，职责不同、不重复**：

| 处 | 位置 | 干什么 | 失败后果 |
|---|---|---|---|
| 运行时（服务端） | `src/server/plugins/registry.mjs:192 readPluginManifest` | 决定**这个插件能不能注册**：`provides` 合法（`:130 validateProvides`）、`effects` 合法（`:78 validateEffects`）、`id` 与目录名一致（`:203`）、`runtime` 归一（`:200`） | 返回 `null` ⇒ 该插件**整体不出现**在 `/api/plugins`（并打一条 warn） |
| 开发期（工具） | `tool/check-plugin.mjs:176-216`（A1~A7 行） | 同样的清单规则 + 后续 B/C 段（vm 编译、产物契约…） | 红行，退出码非 0（门禁） |

**校验程度的真实口径**（都是"宽松 + 降级"，不是"严格 + 拒绝"）：

```
`accent`    非法值 → null（不报错、不猜颜色）        registry.mjs:264-271
`matchPriority` 非数字 → 0                          registry.mjs:277
`label`     缺 → null                              registry.mjs:238
`version`   缺 → null                              registry.mjs:240
`files`     声明了但不存在 → 只有 check-plugin 报 B1a；运行时**不管**
```

### 加 `slots` / `settings` 的成本

- **两处各加一段**（合计约 30~45 行）：`readPluginManifest` 里加字段 + `check-plugin.mjs` 加 1~2 行检查。
- **纯增量**：不改任何既有字段的解析，不动 `validateProvides`/`validateEffects`。
- **`settings` 要真校验**（类型/枚举值/默认值合法性），比 `slots` 贵：
  `slots` 是"字符串数组 + 在插槽目录里"，`settings` 是"数组 of 对象，每个对象有 key/type/options/default"。
  粗估：`slots` 15 行、`settings` 40~60 行（含类型校验与默认值落在 options 内的检查）。

### 依据

- `registry.mjs:192-235`（`readPluginManifest` 的入口：读文件 → `resolveLoadFiles` → 禁用判断 → `validateProvides`）
- `registry.mjs:236-289`（返回对象：逐字段白名单，事实 A）
- `registry.mjs:130-134`（`validateProvides`：未知角色 → 返回可读原因）
- `tool/check-plugin.mjs:176-216`（A1~A7：可解析 / 必填 / provides / id 一致 / 角色合法 / produces.kind / fileKinds / effects）

### 风险

1. **`settings` 校验若太严会把插件整体干掉**：`readPluginManifest` 现在只有 `provides`/`effects` 两条会返回 `null`，
   其余全部降级。若 `settings` 也走"非法即 null"，一个手滑的 option 会让整个插件从列表消失 ——
   用户看到的是"插件没了"，比"设置项没生效"难查得多。
2. **`settings.key` 与 `capabilities.settings` 的命名冲突**：`readPluginManifest` 返回对象里
   **已经有 `effects`**（`:288`），而 `effects` 又会被并入能力键（见 B5）。两条通道往同一个白名单里塞字符串，
   若 `settings.key` 不强制前缀（§8.2 只对 `panel.control` 提了前缀），会和渲染器原生键（`fps`/`dpr`）撞名。

### 建议做法

```
· `slots`：非法项**逐项丢弃 + warn**（保留插件），不回 null —— 与 accent 的降级模式一致
· `settings`：非法项同样逐项丢弃 + warn；只有"整个 settings 不是数组"才算插件级错误（且仍降级为空数组）
· 两条都必须在 readPluginManifest 里显式加字段（否则前端拿不到，事实 A）
· `settings.key` 强制 `plugin.<pluginId>.<key>` 形式（与 §8.2 的 panel.control 同规则），
  在清单校验期就校验格式 —— 与能力键白名单同构，冲突在装之前就能报
```

## B2 · 老插件（无 `slots` / `settings`）必须零改动可用

### 结论

**天然满足，不需要任何兼容代码**。现有实现的态度是"**缺字段 = 用缺省值；多字段 = 丢掉**"：

```
缺 slots      ⇒ 前端 Array.isArray(p.slots) 为 false ⇒ 当空数组
缺 settings   ⇒ 同上
多写一个没实现的键 ⇒ readPluginManifest 不读它 ⇒ 不出现、不报错
```

三个真实插件（`unity-spine-bundle` / `unity-live2d-bundle` / `unitypy-bundle`）的 `plugin.json`
都**没有** `slots` / `settings`，加字段后它们的行为逐字不变 —— 因为它们读到的返回对象里
只会多出 `slots: []` / `settings: []` 两个空数组。

### 依据

- `registry.mjs:236-289`（缺字段走三元/可选链，全部有缺省值：事实 A 的同一处）
- `registry.mjs:203`（`id` 与目录名一致：**唯一强校验**，老插件都已满足）
- 三份 `plugins/*/plugin.json` 现状（无 `slots` / `settings` 键）

### 风险

**唯一的坑是"前端把 `undefined` 当 `false` 判断"**：`/api/plugins` 若给 `slots: []`，
前端各处 `p.slots && p.slots.length` 都是安全的；但若某处写成 `if ('slots' in p)` 就会对老插件误判为"声明了"。
当前 `plugin-host.js` 的消费模式是 `Array.isArray(p.x) ? ... : 缺省`（`:1261`、`:1263`），安全。

### 建议做法

```
· 服务端一律给**空数组**（不是 null、不省略），前端一律 `Array.isArray(...) ? ... : []`
· 在 check-plugin 里加一条 A8「slots/settings 可以缺，但写了就必须合法」，
  让"老插件零改动"这条口径变成可回归的断言，而不是口头约定
```

## B3 · `/api/plugins` 现有响应形状与消费方；新增字段会不会撞到既有消费方

### 结论

响应形状（`routes/data.mjs:27-36`）：

```json
{ "ok": true, "dir": "plugins", "plugins": [ … ], "roles": { … } }
```

`plugins[]` 每项的字段（全部来自 `readPluginManifest`，`registry.mjs:236-289`）：

```
id name label provides version assets fileKinds accent matchPriority produces
errorCodes files runtime entry frameProtocol interpreter depsDir requestTimeoutMs
effects manifest
```
外加内置提供者那两条（`readBuiltinProviders`，`builtin-providers.json`）带的 `builtin: true`。

**消费方只有两处**（`grep` 全 `src/web`）：

| 消费方 | 读哪些字段 | 用途 |
|---|---|---|
| `src/web/infra/plugin-host.js:1251-1334` | `builtin` / `runtime` / `provides` / `effects` / `fileKinds` | 装载分流（内置/exec 跳过注入）、能力键白名单、候选过滤、`plugin.load` 诊断 |
| `src/web/roster/*`（徽标着色） | `accent` / `matchPriority` | 列表颜色与排序 |

**新增 `slots` / `risk` / `settings` 不会撞任何既有消费方** —— 前端只读它认识的字段，
多出来的键在 JS 里天然被忽略。**唯一要小心的是响应体积**：
`settings` 若带完整 options 表，每个插件多几百字节；当前 5 个插件不构成问题。

### 依据

- `src/server/routes/data.mjs:27-36`（响应形状）
- `src/web/infra/plugin-host.js:1251-1253`（`builtin` / `runtime` 分流）
- `src/web/infra/plugin-host.js:1261`、`:1263`（`provides` / `effects` 登记）
- `src/web/infra/plugin-host.js:1289`、`:1311`、`:1332-1334`（`fileKinds` 过滤 / `provides` 判定 / 重新投影）
- `src/server/plugins/builtin-providers.json`（内置两条：`id/name/label/accent/matchPriority/fileKinds/produces`）

### 风险

1. **内置提供者没有 `slots`**：`readBuiltinProviders` 走同一张表（`builtin-providers.json`），
   它的字段集与插件不同（没有 `files`/`runtime`）。若插槽校验假设"每个 provider 都有 slots 数组"，
   内置两条会变成"非法项"。**必须按 `Array.isArray` 兜底，不能假设存在**。
2. **`roles` 与 `slots` 语义重叠的错觉**：`roles` 是"角色 → 插件 id"，插槽是"插件 → 想占哪些位置"。
   两者都描述归属，但**不能合并**（角色是能力声明，插槽是 UI 占位），文档层面要说清。

### 建议做法

```
· 每项固定给 `slots: []` / `risk: {}` 或 `slots: [{name, risk}]`（二选一，不要时有时无）
· 内置两条也给空数组（同一套兜底），不要为 builtin 写特例
· settings 只下发 {key, type, label, options, default}，不要下发"校验规则"之类内部结构
· 在 /api/plugins 的响应上加一行 `"_slotsVersion": 1`（可选）——
  将来插槽目录扩到 shadow 时，前端能判断服务端是否已支持新等级，而不是靠猜
```

## B4 · 风险等级（append/replace/shadow）与"插槽目录"的对照校验放哪一步；拒绝时的错误形状

### 结论

**放清单校验期（`readPluginManifest`），且必须与插槽目录同源**。理由是按设计稿自己定的目标
（"装之前就能看到它会遮蔽什么"，`插件插槽.md:56-58`）：

```
清单校验期（采用）：/api/plugins 能**预告**；缺点是要把插槽目录搬进服务端（见下）
首次注册期（不采用）：只有运行到注册才知道，违背"装之前可见"
两者都做（不采用）：同一事实两处表达，必然漂移（本项目已多轮踩过）
```

**插槽目录放哪**：目前插槽目录只存在于**设计文档表格**（`插件插槽.md:46-53`）。
服务端要校验就必须有一份**可执行的目录**。三条路：

| 做法 | 优点 | 缺点 |
|---|---|---|
| A. 新建 `src/server/plugins/slot-catalog.json` | 与 `builtin-providers.json` 同构，改目录不用改代码 | 多一个文件要维护，且与设计文档不同步 |
| **B. 常量表放 `registry.mjs`（推荐）** | 零新文件；与 `PLUGIN_ROLES`（`:16`）同一模式 | 改目录要改代码（但目录本来就该受控） |
| C. 从前端 schema 反向导出 | 单一事实源 | 服务端要读前端文件，层次反了 |

**拒绝时的错误形状**（要让 `/api/plugins` 能预告）：

```jsonc
// 建议：不拒绝整个插件，只丢弃非法项并随响应带出来
"slots": [
  { "name": "panel.group.设置", "risk": "append" }        // 通过
],
"slotErrors": [
  { "name": "panel.brand", "why": "risk-mismatch",
    "want": "replace", "declared": "append",
    "hint": "panel.brand 会覆盖原生品牌名，必须声明 replace 才能注册" }
]
```
若照现状"非法即 `return null`"，用户看到的是**插件整体消失**——与 §五 第 6 条"下发插槽与风险等级供预告"的目标相反。

### 依据

- `插件插槽.md:46-53`（插槽树 + 风险三档）
- `插件插槽.md:56-62`（风险语义 + "未声明插槽注册时拒绝并 warn"）
- `插件插槽.md:120-122`（§五 第 2 条：清单校验新增 slots，对照插槽目录校验风险等级）
- `registry.mjs:16`（`PLUGIN_ROLES` 常量表：目录类事实放代码里的既有先例）
- `registry.mjs:203`（`id` 不一致 → 只是 warn 不 fail，可见"尽量不整体拒绝"的既有倾向）
- `registry.mjs:82`（`hasPanelRole`：`effects` 只对 panel 角色校验 —— slots 应沿用同一前置条件）

### 风险

1. **`risk` 的缺省值是最容易出错的地方**：插件声明 `panel.brand` 但**没写 risk** 时，
   算 append 还是按目录的 replace？两种都对、但必须**写死一种**并让 check-plugin 断言。
   建议：**以目录为准**（`risk` 字段只作"我知道它是高风险"的显式确认，不参与判定）——
   这样插件写错 risk 也不会让高风险插槽被当 append 放过去。
2. **`panel.group.<name>` 是动态名字**（分组名由插件定），目录只能给出前缀规则；
   校验必须是"前缀 + 风险对照"，不能用精确名字表。
3. **未排期的插槽（`stage.overlay` / `toolbar.actions`）被声明时要"拒绝"，不是"忽略 + warn"**（已定案，见文末「已定案口径」第 4 条）：
   忽略会让插件作者以为"我声明了、只是还没渲染"，实际永远不会生效 —— 那种"看着成功其实是空操作"最难查。
   拒绝时错误必须写清"该插槽尚未开放（阶段 S3+）"，让作者知道是**阶段未到**而不是自己写错。

### 建议做法

```
· 插槽目录 = registry.mjs 里一张常量表（name 或 prefix + 允许的 risk 集合 + 说明）
· 校验在 readPluginManifest 里、且在 hasPanelRole 之后（非 panel 插件声明的 slots 直接忽略 + warn）
· 非法项进 `slotErrors`（不 return null），随 /api/plugins 下发
· risk 以**目录为准**，清单里的 risk 只作显式确认（不一致时按目录 + 记 warn，不改变允许与否）
· check-plugin 加一条 A9：slots 名必须在目录里、risk 与目录一致（这就是回归门禁）
```

## B5 · §8.3 的 `settings` 声明如何并入 `capabilities.settings`

### 结论

**已经有现成的并入点，而且是同一模式**：`src/web/panel/panel-settings.js:317-329` 的
`withPluginCapabilities(capabilities, effectIds)` —— 把插件**注册成功**的 effect id
追加进渲染器的 `capabilities.settings` 白名单（返回新对象，不污染渲染器自己的声明）。

```
渲染器声明（白名单本体）
  spine  : src/web/render/spine.js:194-195   capabilities.settings = SETTINGS.slice()
  live2d : src/web/render/live2d.js:335      settings: ['textureFilter','fps','dpr','presetFilter','animation','speed']
  ↓
并入插件键
  panel-settings.js:327  { ...capabilities, settings: [...capabilities.settings, ...effectIds] }
  ↓
消费（唯一通道）
  src/web/app/renderer-setting.js:29-33  rendererSupports(key) → capabilities.settings.includes(key)
```

⇒ `settings` 走**同一条**：把清单里的 `settings[].key` 追加进那个数组即可，
**不需要新机制**。区别只有：`effects` 是"注册成功后并入"（运行期），
`settings` 是"清单声明即在"（校验期）—— 这正是 §8.3 想要的。

### 依据

- `src/web/panel/panel-settings.js:317-329`（`withPluginCapabilities`：唯一并入点，含"为什么必须拷贝"的注释）
- `src/web/app/renderer-setting.js:27-33`（`rendererSupports`：白名单唯一消费点）
- `src/web/render/spine.js:194-195`、`src/web/render/live2d.js:335`（白名单本体在渲染器实现里）
- `插件插槽.md:194-214`（§8.3：清单声明 + 校验在清单阶段 + "白名单本来就是能力键集合，插件键直接并入"）

### 风险

1. **两个来源、同一数组**：`effects`（运行期注册）与 `settings`（清单声明）都往 `capabilities.settings` 里塞。
   若同一个 key 两边都有，会重复（`includes` 不影响正确性，但诊断日志会重复）。
2. **`settings.key` 与渲染器原生键撞名**：插件声明 `{"key":"fps"}` 就等于接管了 fps 控件的白名单判定
   （不改变渲染行为，但"面板能选"会变成真的）。必须强制前缀（见 B1 建议）。
3. **`withPluginCapabilities` 是 `panel-settings.js` 里的私有函数**，它现在只吃 `effectIds: string[]`。
   加 settings 要改签名（或再包一层），改动会落在**前端**（不在本次服务端范围，但接口要约定好）。

### 建议做法

```
· 服务端只负责"校验 + 下发" settings 声明；**并入动作仍在前端**（渲染器白名单是前端事实）
· 下发的 settings[].key 必须是 `plugin.<id>.<key>`（前缀把撞名从"可能"变成"不可能"）
· 前端并入时去重（Set）后再展开，避免 effects 与 settings 同 key 出现两遍
· 服务端不下发"能力矩阵"，只下发键与类型 —— 白名单最终仍由渲染器说了算
```

## B6 · 缓存与失效：新增字段后缓存键要不要跟着变；改插件不重启会不会读到旧形状

### 结论

**要区分两种"缓存"**，它们的失效条件完全不同：

| 缓存 | 键 | 改 `plugin.json` 内容 | 改 `registry.mjs` 代码 |
|---|---|---|---|
| 插件清单缓存 `readPluginsCache`（`registry.mjs:322`） | `pluginsSignature()`：目录路径 + 开关文件 `(mtime,size)` + **每个 plugin.json 的 `(mtime,size)`**（`:329-345`） | ✅ **自动失效**（mtime 变） | ❌ **不失效**（签名只看文件 mtime，不看代码） |
| Node 模块缓存（`import` 级别） | 模块路径 | — | ❌ **必须重启进程** |

⇒ **落地顺序上的两个不同答案**：

```
· 改插件（加 slots/settings 字段）→ **不重启服务端**就能读到新清单（签名变即重扫）
· 改服务端代码（readPluginManifest 加字段）→ **必须重启**才能生效（代码在模块缓存里）
```

所以"新增字段后缓存键要不要跟着变"的答案是：**不用变**。签名已经覆盖了"清单内容变了"这件事；
而"代码变了"本来就要重启，与缓存键无关。

### 依据

- `registry.mjs:322-327`（`readPluginsCache` 与服务端注释"不能只看目录 mtime"）
- `registry.mjs:329-345`（`pluginsSignature`：逐项 `statSync(plugin.json)` 取 `mtimeMs:size`）
- `registry.mjs:302-313`（`readPlugins`：签名不符才重建，命中返回 `list.slice()`）

### 风险

1. **`(mtime,size)` 是弱指纹**：同一秒内改内容且**大小不变**（例如把 `"slots":[]` 改成 `"slots":[ ]`）
   在粗粒度 mtime 文件系统上可能不变 ⇒ 读到旧清单。CIFS 上 mtime 粒度实测是**秒级**，
   本项目已经因为 CIFS 时间戳踩过坑（`mark_edit` 的 `settleMs` 就是为它加的）。
2. **`list.slice()` 是浅拷贝**：返回的数组是新数组，但**元素对象是共享的**。
   若将来有人 `push` 进某项的 `slots` 数组，会污染缓存。目前无人这么做，但插槽聚合（S2+）容易引入这种写法。
3. **内置提供者的版本哈希是独立的**：`builtinVersionHash()`（`registry.mjs:542`）按判定模块内容哈希派生，
   与插槽无关，不会被 slots 改动影响 —— 这是对的，但要意识到"两个失效机制并存"。

### 建议做法

```
· 不加新缓存层；复用 pluginsSignature（已经覆盖清单内容变化）
· 想更稳可把签名里的 size 换成内容 hash（代价：每次请求 stat 变成读文件，5 个插件可接受）——
  但 CIFS 上读文件比 stat 贵一个量级，**建议只对 plugin.json < 8KB 的小文件做**，或干脆不做
· 未来做插槽聚合时，**只读不写**缓存里的对象（要改就深拷贝）
· 文档里写清"改插件不用重启 / 改服务端代码要重启"，否则调试时会出现"我改了怎么没变"的经典误判
```
