# 设计 · 测试脚本结构

> 规范 `test/*.js`（浏览器注入式回归脚本）的组织形态。
> 触发原因：8 个文件的单函数行数触到审计阈值，但**真正的问题不是审计**——见第一节。

---

## 一、现状与真问题

每个测试文件都是**一个大 IIFE**：

```js
(async () => {
  // [wait-ready] 生成块
  // … 三百到五百行：找模型、逐条用例、断言、日志 …
})();
```

审计按「一个函数」计，于是报出 253 ~ 547 行的超长函数。

**但审计只是症状。真问题是三个**：

| 问题 | 后果 |
|---|---|
| 一个巨大函数体，失败时只有一个堆栈点 | 报错后要人肉读几百行才能定位是哪条用例 |
| 用例之间共享一个作用域 | 想给单条用例加 skip 只能整段 `try/catch`，会把「跳过」和「失败」混成一件事（历史上真的发生过 13 条退化成 1 条 `skipped`）|
| 同一套辅助逻辑在每个文件里复制一遍 | 改一处要改八处，且八处必然漂移 |

所以拆分的目的是**让失败可定位、让 skip 可落地、让辅助逻辑单一来源**，不是为了消审计数字。

---

## 二、目标结构

```
test/<suite>.js
  ├─ (async () => { … })()        ← 只做编排：按顺序 await runXxx()，累计结果，最后汇总
  ├─ async function runXxx(ctx)   ← 一组用例一个函数（≤50 行代码）
  └─ async function runYyy(ctx)   ← 同上
```

**编排函数的职责只剩三件**：

```
① 准备共享上下文（模型、DOM 句柄、日志器）
② 依次 await 每个 runXxx()，把各自的断言结果并进总账
③ 输出结果对象（形状不变，见 §四）
```

### 2.1 用例分组的判据

按**契约条款**分组，不按代码顺序切：

```
runBasicPlayback()    ← 播放/暂停/切动作
runLoopToggle()       ← 循环开关两条
runSyncWithPanel()    ← 右栏与底栏同步
runSkipGuard()        ← 数据缺失时的跳过
```

理由：失败时「哪个契约条款挂了」一眼可见，比「第 213 行挂了」有用得多。

### 2.2 禁止无脑机械拆分（硬规矩）

**拆分的依据是「用例边界」这个语义事实，不是行数、不是括号配对、不是模式匹配。**

已经踩过的三次坑，全部源自「想用机械手段绕过理解」：

```
① 按行数平均切        → 切点落在一条用例中间，中间态被劈成两半
② 按花括号配对切      → section 收尾括号处错位（roster-actions）
③ 按「最后一个 })()」定位 → 文件里有内层自执行结构时定位错（f1-controls）
                         症状：SyntaxError: Unexpected token ')'，连试 4 次都失败
```

**禁止清单**：

| 禁止 | 为什么 |
|---|---|
| 按行数 / 目标行数反推切点 | 切点由用例边界决定，不由行数决定 |
| 为压到 50 行而把**一条用例**切成两半 | 中间态散落，语义断裂；读者要跨两个函数才拼得出一个用例 |
| 用模式匹配猜边界（花括号配对 / 最后一个 `})()` / 正则） | 文件结构一变就失效，且失效方式隐蔽（语法通过但用例没跑到）|
| 不理解就动手 | 边界看错的后果是「total 刚好凑上、但某条用例其实没跑」—— 最难发现 |

**正确姿势**：

```
① 先读全文，认出错在哪几条用例之间（语义边界）
② 打出精确行号，人工核对
③ 按行号切片
④ 单跑，确认 total 与用例名都没变
```

**关于「压不到 50 行」**：

```
先问：是不是这条用例本身就该拆成两条？
  是   → 按判据拆（取状态 / 断言 A / 断言 B），且中间态要有明确载体（小上下文对象）
  不是 → 就在那一处写明「为什么它必须超过 50 行」
        （比硬切碎成三个互不相干的小函数更好读）
```

**一条底线**：拆完如果**比拆之前更难读**，那就不要拆 —— 记录下来说明原因。
拆分的目的是**让失败可定位**，不是为了把数字做小。数字只是这个目的的副产品。

## 三、硬约束

### 3.1 `[wait-ready]` 生成块：不许手改，但**必须整块移出 IIFE**

```
// [wait-ready] begin —— 由 test/lib/wait-ready.mjs 生成，勿手改（改源头后跑 apply-wait-ready）
…
// [wait-ready] end
```

这段是**生成的**，实测**每个文件 140 行**（`f2-topbar` 第 9~149 行、`f3-reveal` 第 13~153 行）。

**关键**：它原本贴在 IIFE 内部。只把用例体搬成 `runXxx` 之后，IIFE 仍有 145~170 行 ⇒
`max-function-length` blocker **不会消失**。

所以正确做法是：

```
把生成块**整块**移到 IIFE 之外（文件顶层），内容一字不改，每文件仍恰好 1 处 begin 标记
⇒ IIFE 降到 ~70 行，blocker 消失；helper 仍在同一脚本作用域内，行为不变
```

**允许与禁止**：

| 动作 | 允许？ |
|---|---|
| 整块移到 IIFE 之前（顶层） | ✅ **必须做**，否则拆了也没用 |
| 手改块内任何一行 | ❌ 改源头 `test/lib/wait-ready.mjs` 再跑 `node tool/apply-wait-ready.mjs` |
| 把块切开、或复制进各个 `runXxx` | ❌ 会产生多份生成物，下次重新生成必冲突 |

### 3.1b 三条实测坑（拆分前先看）

```
① 跨段共享的 helper 必须先提共享作用域
   实例：anim-list 的 checkList 定义在「Spine」段内、却被「Live2D」段调用
   ⇒ 直接按段搬会 ReferenceError。先把它提到 IIFE 顶层（或 test/lib/）再拆。

② 「IIFE 内闭包」形态会踩 TDZ
   const 定义被插到 return 之后 ⇒ Cannot access before initialization
   ⇒ 不要在 return 之后定义任何东西。

③ 按花括号配对做机械改写时，IIFE 尾部边界容易错位
   实例：roster-actions 有 12 个 section(名字, async () => {…})，天然分组，
   但机械改写会在最后一个 section 的收尾括号处错位
   ⇒ 这类文件改用「按 section 调用逐段搬」而不是「按花括号配对切」。

④ 机械改写依赖「唯一标记」，而有些文件里标记并不唯一
   实例：f1-controls 存在**内层自执行结构**（第 191 行有一个缩进 2 的 `})();`，
   属 ① 段内部的立即执行箭头函数，不是 IIFE 结尾）
   ⇒ 用 `line.strip() in ('})()', '})();')` 判定时，191 行会被命中，
     把内层当成 IIFE 结尾去拼 ⇒ `SyntaxError: Unexpected token ')'`（连试 4 次失败）

   **根因是「strip 后比较」这一步本身就会骗自己** —— 缩进被抹掉，
   内层收尾与文件收尾长得一模一样。
   ⇒ 只要文件里出现第二处自执行收尾（**不论缩进**），就**放弃模式匹配**，
     改用「行号硬定位」：先打出五组精确行号再人工确认，然后按行号切片。
   ⇒ 判「唯一」时要用 `grep -n` 看**原始缩进**，不要 strip。
```

⑤ 有些文件里有用例整体包在一个**裸块** `{ … }` 里
   实例：f1-controls 第 164 行一个裸 `{`、第 413 行闭合，① ② ③ ④ 四条用例全在块内
   ⇒ 拆的时候要把裸块去掉，块内声明的 `clickId/hint/log` 提到 IIFE 顶层
   ⇒ 不清掉会切出**带孤立花括号的函数** —— 与 ④ 是同一类 SyntaxError 风险

⑥ 切 wait-ready 段要从 **`begin` 注释行**起，不含 IIFE 开头那行
   实例：f4-roots 拼装时把原 `(async () => {` 一起塞进了生成块
   ⇒ 文件里出现**两个 IIFE 开括号**，末尾只闭合一个 ⇒ `SyntaxError: Unexpected end of input`

⑦ 跨段共享的**可变状态**必须提成 state 对象（比裸块隐蔽得多）
   实例：f4-roots 有 4 个 `let`（probeId / probePath / groupsAfterAdd / addFormOpened）
   被多段读写（一段写 4 处、另一段写 1 处、其余段读）
   ⇒ 若按普通上下文解构传进函数，**函数内赋值不回传**，后续用例读到旧值
   ⇒ 症状是「语法通过、total 也对，但某条用例行为悄悄变了」—— 比裸块错危险得多
     （裸块错了至少语法报错；这个不报错）

⑧ 变量替换要区分**简写属性位置**与表达式位置
   实例：汇总段 `summary: { ..., probeId }` 是简写属性
   替换成 `P.probeId` ⇒ `SyntaxError: Unexpected token '.'`
   正确写法：`probeId: P.probeId`

⑨ `const w = window.__WEB__` 的**一次性快照**会让「等就绪」的守卫循环失效
   实例：f4 / f2 / f3 三个文件都这么写，而 f4 的 `mgr = () => w.rootManager`
   页面未就绪时 `w` 是 `undefined` ⇒ `mgr()` 一求值就抛 `TypeError`
   而等待循环的条件正是 `!mgr()` ⇒ **第一次求值就抛，那个 80×150ms 的等待从来没生效过**

   症状：冷启动跑该套偶发 `TypeError: Cannot read properties of undefined (reading 'rootManager')`；
        页面预热后重跑就正常 —— 极易被误判成「headless 启动慢」。
   修法：
     for (let i = 0; i < 80 && !window.__WEB__; i += 1) await sleep(150);
     const w = window.__WEB__ || {};
   ⇒ 先等它出现再快照，`|| {}` 兜底让后续取属性不抛。

⑩ 同名行不止一处时，定位必须用**缩进 + 行号区间**双条件
   实例：`grep "const w = window.__WEB__"` 会命中 wait-ready 块内 `readySnap` 函数体里
   缩进 4 的那行（那里 `await` 非法）⇒ `SyntaxError: await is only valid in async functions`
   ⇒ 目标行是缩进 2、在 IIFE 内；只用 grep 定位会改错地方。

⑪ 把 IIFE 顶层的 `return <汇总>` 搬进子函数时，**短路语义会丢**
   实例：spine-actions 原文件末尾 `return JSON.stringify({total: results.length, skipped: ...})`
   是 **IIFE 顶层 return**，作用是**终止整个套件**；
   搬进 `runPreflight` 后它只是「结束这个函数」，返回值被丢弃
   ⇒ 后面 13 条用例继续跑、各自 skip ⇒ `total = 1 + 13 = 14`（基准 13 被打破）
   ⇒ 而 `failed` 仍是 0，**看不出异常**
   修法：让子函数返回 `{ wholeSkip, payload }`，编排处 `if (pre.wholeSkip) return pre.payload;`
   教训：**这条只有跑「环境缺数据」路径才会暴露** —— 自证不能只验正常路径。

⑫ 扫「跨段可变状态」不能只看缩进
   实例：spine-actions 的 `r38` / `r41` 是**顶格 `let`**（在裸块外），
   被两段赋值、汇总段读取；只扫「缩进 2 的 let」会漏掉 ⇒ 运行期 `ReferenceError`
   ⇒ 判定依据是「声明区间 + 被谁引用」，不是缩进层级。

⑬ **汇总段是最容易被忘的消费方**
   实例：anim-list 汇总段读 `spineModel: spine ? spine.model.name : null`，
   而 `spine` 是 `runSpineList` 内的局部变量 ⇒ `ReferenceError: spine is not defined`
   修法：用 `P` 对象承载（`P.spine` / `P.l2d`），两段写、汇总读
   ⇒ 拆完必须逐个检查**汇总段读的每个名字**属于哪一层作用域。

⑭ 定位「工厂的返回语句」不能用通用的 `return {`
   实例：用「找第一个 `return {`」定位 `makeListHelpers` 的返回行，
   实际命中了 `pickSpine` 内部的 `return { root: r.id, model: m };`
   ⇒ checkList 被截断、声明行丢失 ⇒ `ReferenceError: checkList is not defined`
   ⇒ 用更具体的模式（如 `return { pickSpine`）定位。

⑮ 替换脚本前先确认真实缩进
   实例：按「2 空格缩进」匹配汇总段两行，实际是 4 空格 ⇒ 两行没被替换，白跑一轮测试
   ⇒ 先 `cat -A` 看真实缩进，或用「包含某子串」代替「^ {2}前缀」匹配。

⑯ 拆成**两个工厂**时，工厂之间会形成隐式依赖
   实例：`makeListHelpers` 里的 `charKeysOf` 用了 `makeBasicHelpers` 的 `gameOf`
   ⇒ list 工厂解构漏了 `gameOf` ⇒ `ReferenceError: gameOf is not defined`
     （被段内 `section()` 捕获成一条失败项，不是崩掉，容易看漏）
   ⇒ 工厂之间要像跨文件依赖一样**显式列出**，并在编排处注明「basic 必须先 assign」。

⑰ **「把声明提到前面」是最容易犯的时序错**（本条最危险）
   实例：roster-actions 原顺序是
     `初始态段（242-264）→ GAME_NAMES 计算（265-284）→ if skip → for 循环`
   有人为了"声明都放一起"把 `pickGameNames` 提到 `runInitialState` 之前
   ⇒ 初始态段还没跑，页面状态不同 ⇒ **挑出 0 个游戏 ⇒ total 从 33 掉到 13**
   ⇒ 声明的位置往往隐含**执行顺序依赖**；拆函数不是重排顺序，要**保持原执行次序**。
   ⇒ 自保手段：改完先看 `total` 是否与基准一致 —— 这类错通常会让 total 变小。

⑱ **「文件顶层可见」≠「在 C 里」**
   实例：`waitStable` 属于 wait-ready 生成块（已外移到文件顶层）⇒ 函数内**直接可见**，
   但 C 里没有它 ⇒ 从 C 解构得到 `undefined` ⇒ `waitStable is not a function`
   ⇒ 更糟的是它被函数内的 `try/catch` 吞掉，只表现为「挑不出游戏」
   ⇒ 只有**确实塞进 C 的名字**才能解构；顶层可见的直接用即可。

⑲ 临时插桩的 `throw` 必须在 `return` 之前
   实例：把 `throw` 插在 `return` 之后（不可达）⇒ 插桩后什么都没发生，
   误判成「这段代码没执行」
   ⇒ 插桩也要检查可达性，否则得到的是假结论。

### 3.1d 动手前必做：逐段做**语法级**校验

**这一步能在动手前就抓出「边界差一行」这种最隐蔽的错。**

#### 首选方法：把每段包进函数跑 `node --check`

```
把候选段单独包成：
  async function __seg() {
  <该段原文>
  }
写进临时文件 → node --check → 通过则边界正确
```

**为什么这是首选**：它是**真正的语法级判定**，模板字符串、正则、注释都不会误判。

#### 净深度只作快速预筛，不能作判据

```
对每段统计花括号/圆括号/方括号的净深度：=0 看着对、≠0 就试 ±1~2
```

**但纯算净深度会被多行模板字符串骗**：

```
实例：f4-roots 的 S1 段（202–233）首次算出净深度 -1
      实际是第 232 行那段多行模板串里的 `}` 被当成了代码括号
      ⇒ 净深度 -1 是假警报，该段其实是平衡的
```

#### 边界差一行的后果

```
「语法通过、total 也对，但某条用例的收尾语句落到了下一个函数里」
⇒ 运行期不报错，只是行为悄悄变了
⇒ 这种错靠跑测试不一定抓得到，必须在动手前用语法级校验挡掉
```

#### 实测有效的两个实例

```
f1-controls ③ 段止行：275–344 净深度 = 1（不平衡）、275–345 = 0 ✓
                     （345 那个 `}` 是段内某块的闭合，必须跟着走）
f4-roots    10 段：全部包进 async function 跑 node --check，全 ✓
```

**判定用哪种拆法**（先看这个，别一上来就写脚本）：

```
文件里顶格 `})()` / `})();` 只有一处，且 wait-ready 块只有一处
  → 可以按标记机械改写
否则（有内层自执行结构、或标记重复）
  → 行号硬定位 + 人工确认边界，再按行号切片
```

**行号清单要先打出来核对**（五组）：

```
IIFE 起 ／ wait-ready 终 ／ 每条用例起 ／ 汇总 return 起 ／ 文件末
```

### 3.1c 用例边界怎么定

```
· 有分节注释的文件（f2 / f3 / anim-list / roster）→ 按分节注释分组
· 没有分节注释的文件（f1-controls / f4-roots / panel-actions / spine-actions）
  → 用例边界必须**人工读全文**确定，无法脚本化（324~547 行/个）
```

**分组依据始终是「契约条款」，不是代码顺序** —— 见 §2.1。

### 3.2 用例数一条都不能少

拆分前后每套的 `total` 必须完全一致：

| 套件 | 基准 total |
|---|---|
| `anim-list` | 16（含 1 skip）|
| `f1-controls` | 4 |
| `f2-topbar` | 7 |
| `f3-reveal` | 5 |
| `f4-roots` | 8 |
| `panel-actions` | 25 |
| `roster-actions` | 33（含 1 skip）|
| `spine-actions` | 13 |

**`total` 变小 = 静默丢用例**，比拆分失败严重得多。

### 3.3 注入形态不变

这些文件由 `tool/test-all.mjs` 注入浏览器执行。拆分后仍然必须是**自执行**的（IIFE 或等价的立即执行形态），
不能改成 `export` / 需要外部调用的形态 —— 那会让 runner 的注入契约失效。

### 3.4 共享辅助逻辑提到 `test/lib/`

同一段逻辑在多个文件里出现时，提到 `test/lib/` 下一份。已有的例子：

```
test/lib/wait-ready.mjs          就绪信号等待（生成块源头）
test/lib/...                     新增的公共断言/取数辅助
```

**不允许**为了「少改」而在两个文件里各留一份实现 —— 那就是漂移的起点。

### 3.5 单函数行数：两档口径，别把 warning 当 blocker

审计对函数长度有**两档**（实测锚点）：

```
50 行起              → warning（不拦提交，但拉低评分）
101 行（非注释）      → 仍是 warning（runSpineList 实测）
369 行               → blocker（f2 拆分前实测）
```

> **精确阈值未文档化，以审计实报为准。** 之前有处误判：f2 那个 blocker 是
> **圈复杂度 54**（`max-cyclomatic-complexity`），不是函数长度 —— 别把两类规则混为一谈。

**判定顺序**：

```
① blocker 必须清零 —— 这是硬门槛
② 50~100 行的 warning：先看是不是该再分组（按用例边界，不是按行数切）
③ 确实拆不动（一条用例本身就是一条长断言）→ **在函数处写明为什么不拆**
   不许为凑数字硬切（见 §2.2）
```

**为什么不许硬切**：60 行但 3 条独立判据的函数，比切成三个 20 行、
每个都要跨函数拼中间态的函数**更好读也更好定位**。目标是让失败可定位，不是让数字变小。

## 四、结果对象形状不变

runner 依赖这个形状，拆分不能动它：

```js
{ ok: true, total, failed, failing: [...], problems: [...] }
```

## 七、分层与自动化边界（2026-10-26 定）

浏览器套件验证的是**运行时行为**，要真实 chrome + 页面渲染，慢、吃资源、依赖本机环境。
所以不再让它们进自动门禁，改为分层：

| 层 | 位置 | 何时跑 | 内容 |
|---|---|---|---|
| **自动门禁** | `test/*.test.mjs`（node-test）| 每次改动自动跑 | 契约、数据、缓存、重试、日志、背景存储等纯 node 事实 |
| **浏览器套件** | `test/browser/*.js` | **手动单跑**（`--only <名字>`）| DOM 接线、真实渲染、真实交互、时序 |
| **静态门禁** | `tool/check-*.mjs` | 每次改动自动跑 | 单一真相源、插件契约、权限、内联样式等一致性事实 |

```
node tool/test-all.mjs                  # 默认：13 套 node-test（快，任何环境可跑）
node tool/test-all.mjs --only f3-reveal # 单跑一个浏览器套件（开发时最常见）
node tool/test-all.mjs --browser        # 显式把所有浏览器套件纳入（慢，别在自动流程里用）
```

**改了浏览器套件但默认不跑时，runner 会明确打一行提示** —— 静默跳过等于「改了却没测」，
那正是本项目最想避免的问题：要么跑，要么明确告诉人没跑。

### 7.1 为什么不是「全部换成静态检查」

按断言类型盘点（现状 9 套浏览器脚本）：

| 断言类型 | 能否静态化 | 说明 |
|---|---|---|
| 控件清单：schema 声明 vs 代码接线 | ✅ 能 | 读 `panel/schema.js` 的声明 + 扫绑定代码，对照规则表即可 |
| 契约一致性（能力键 / 状态键 / 接口形状） | ✅ 已有 | `tool/check-single-source.mjs` + `tool/lib/contract-checks.mjs` |
| `disabled` / `data-pending` 标记 | ✅ 能 | 从源码读属性声明，不必渲染 |
| 区域 rect / 布局几何 | ⚠️ 部分 | 读 CSS 变量与断点表能算期望值，但算不出真实渲染结果 |
| **真实渲染**（canvas 像素 / WebGL / Spine·Live2D 出图） | ❌ 不能 | 必须真实浏览器 |
| **真实交互**（点击→状态迁移 / 竞态 / 时序） | ❌ 不能 | 需浏览器；`test/helpers/dom-shim.mjs` 只能覆盖纯状态机那部分 |

**结论：约一半断言可静态化，另一半（渲染出图、真实交互）替不掉。**

所以边界是「**静态门禁管一致性，浏览器脚本管渲染与交互**」，不是把后者删掉。

### 7.2 待做的静态门禁（尚未实现）

参照同类项目 `scripts/check-drift.js` 的形态（零依赖、规则表驱动、退出码、必须能用已知 bug 自证报红）：

```
tool/check-wiring.mjs   扫 panel/schema.js 的控件声明 ↔ 扫代码里的绑定/handler
                        · 声明了但没有任何绑定 → 报（对应 f1「声明 vs 接线」那条）
                        · 绑定了但没声明 → 报（面板重建会丢它）
                        · disabled/pending 标记与声明不符 → 报
```

在这条门禁落地之前，**这部分事实仍只能靠手动单跑浏览器套件确认**，
不要当成「已经有门禁保着」。
