# 设计 · 解包时序与缓存

> 依据：`data/logs/diag-20261026-172933.json`（139 条，含两次资源包加载）

## 一、实测时序（两个模型都复现，不是偶发）

```
+ 9.17s  插件装载完成（unity-live2d-bundle）
+ 9.18s  正在解包 aijier_3…            ← 前端开始本地解包
+13.57s  回落前端解包（23 文件，4313ms）  ← 前端自己解完
+13.63s  Live2D 装载 → +14.63s 已渲染
+15.88s  预热完成：aijier_3（已有缓存，206ms）  ← **服务端此刻有缓存**

+71.28s  正在解包 adaerbote_3…
+75.36s  回落前端解包（39 文件，3983ms）
+79.53s  预热完成：adaerbote_3（已有缓存，361ms）
```

**同一个资源（同 rootId + rel），前端在 9.18s 查命中说没有，服务端在 15.88s 说早就有。**

## 二、三个缺陷

### ① 命中查询失败被**静默吞掉**（首因）

`plugin-host.js` 的回落分支：

```js
catch (e) {
  if (e && e.reason && e.reason !== 'server-miss') say.warn(...);   // 只有带 reason 才告警
  won = null;                                                      // 其余一律当"没命中"
}
```

fetch 层异常（网络未就绪、服务刚起、连接被复用打断）**没有 `reason`** ⇒ 不告警、不留痕迹，
直接回落本地解包。日志里完全看不到"查询失败"，正是这个原因 —— **排查时无法区分「真的没缓存」和「查询炸了」**。

### ② 预热启动太晚（必然赶不上）

```
warmup → fetchCapacity → requestIdleCallback(timeout 3000) → setTimeout(2000) → 才发 resolve
```

最坏 5s 后才开始预热；而页面在 9s 就已经要加载了。
⇒ **首次打开任何新资源，缓存必然来不及**，前端只能本地解包。

### ③ 结果是重复劳动

前端解一遍（4.3s，19.3MB 包），服务端随后命中（206ms）。
服务端缓存若已存在，这 4.3s 完全是白花；若不存在，两边还会各解一次（CPU 与峰值内存翻倍）。

## 三、目标形态：两条解包路径，同一个缓存

**不限制服务端解包，也不逼前台等它。** 谁解都行，关键是**解出来的东西要能被下次取到**。

```
查缓存 ──命中──→ 直接取产物（137ms 量级）
      └─未命中─→ 前端本地解（4.3s，快）──→ 把产物写进服务端缓存
                                              ↑
                          服务端解包（预热等场景）也写进同一个缓存
```

### 核心：缓存有两个写入者

| 写入者 | 什么时候 | 为什么 |
|---|---|---|
| 服务端解包 | 预热、深链接等 | 服务端是解包原生能力，不该禁用 |
| **前端解包（新增）** | 前台未命中时 | 前端解得快（4.3s vs 服务端 10s，后者慢在逐文件写 SMB）；解完顺手持久化，下次就命中 |

**这两条都必须落到同一个 `(rootId, rel)` 缓存键上**，否则"写进去了却查不到"。

### 要做的三件

#### ① 前端解包后落盘（新增能力）

```
前端解出文件表后，POST 给服务端一个"存缓存"接口：
  POST /api/unpack/store  { rootId, rel, files:[{name, bytes}] }
  · 指纹由**服务端**算（它拿得到源包，避免前端重复实现 hash ⇒ 键不一致）
  · 落盘失败不影响本次加载（本轮数据已在内存里可用），只记 diag
  · 写缓存是"顺手做"，不阻塞渲染
```

#### ② 修好"正确取回缓存"

```
· hitOnly 查询不再有 1.5s 超时（已删）
· 命中后按文件取产物的路径要验证：连取 23~39 个文件、并发 4、失败重试
· 三种结果都要落 diag（命中 / 未命中 / 查询失败）—— 已加
· 验收要能证明"同一个键写进去、下一次一定查得到"（同一 rootId+rel 连跑两次）
```

#### ②b 服务端预算不足 ⇒ 浏览器接手解包（分工口径）

```
· 服务端内存准入只决定「服务端要不要解 / 面板显示多少」，**不参与前端解包准入**
· 服务端算下来不够 ⇒ 由浏览器解包，而不是拒绝装载
· 浏览器侧的保护是它自己的：JS 堆预检（preflightLoad）+ 长操作监控（越线中止、已完成部分保留）
```

为什么：42MB 资源包服务端解包峰值 630MB，会被服务端自身准入拒绝；
而同一台机器的浏览器解同一个包只要 4.3s 且渲染正常。曾经前端还额外拿
「服务端可用内存 × 0.5」当自己的上限，结果是**有缓存也装不了、能解也不给解**。

#### ③ 不设任何时间门槛

```
· 前台不按秒数判死、不"等 N 秒改走另一条路"
· 服务端解包不因预估耗时被跳过（只看内存准入）
· 缓存写入不设超时判据（失败只记日志）
```

## 四、验收

```
1. 冷加载未缓存包：第一次走前端解（~4.3s），diag 出现 unpack.store（落盘成功）
2. 同一包第二次加载：unpack.source = "解包命中缓存"，< 500ms
3. 服务端解包路径仍可用（预热/直接调接口），不因本次改动被禁用或降级
4. 键一致性：前端落盘的包，服务端 hitOnly 查询能查到（同一 rootId+rel）
5. 落盘失败（人为写不进去）：本次加载不受影响，diag 有记录
6. 无时间门槛：解包路径上不存在"超时/超过 N 秒 ⇒ 改走另一条路"的分支
```
