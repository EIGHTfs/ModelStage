# LZMA 大包解压不冻 UI —— 三条路线论证

> 结论先行：**推荐 A（Worker 化）**。理由是实测数据把 B 否掉了 —— 服务端解同一个包比前端慢
> **2.6~3 倍**，B 既不冻 UI、又把等待时间拉长近 3 倍。C 只能算"不静默"，不能算"不冻"。
> 但 A 的改动面明显大于 B/C，所以先落这份论证，等批准再动手。

---

## 一、实测数据（本机，node 直跑插件 lib，同一 V8 算法层）

命令：`node tool/.tmp-lzma-bench.mjs <包文件…>`（临时脚本，不 commit）

### 1.1 前端同步解压耗时（决定阈值）

| 包 | 压缩 | **解压后** | 算法 | 同步耗时 | ms/MB |
|---|---|---|---|---|---|
| huonululu_3 | 0.98 MB | **2.76 MB** | LZMA | **1717 ms** | 622 |
| weiyan_2 | 1.00 MB | **5.01 MB** | LZMA | **1907 ms** | 381 |
| aierdeliqi_5 | 2.11 MB | **8.28 MB** | LZMA | **3859 ms** | 466 |
| aierdeliqi_4 | 4.04 MB | **17.09 MB** | LZMA | **8336 ms** | 488 |
| z46_2 | 5.85 MB | **33.40 MB** | LZMA | **10281 ms** | 308 |
| aijier_3 | 19.27 MB | **42.11 MB** | **LZ4** | **169 ms** | 4 |
| longfeng_2 | 14.02 MB | 14.02 MB | none | 8 ms | ~0 |

**结论：LZMA 约 300~620 ms/MB（解压后），中位 ~470 ms/MB；LZ4 是 ~4 ms/MB，快两个数量级。**

### 1.2 LZMA 包的体积分布（决定"分流"有没有空间）

扫 `工作区/live2d/live2d`（75 个 UnityFS 包）：

```
算法分布：LZMA 61 个 · none 6 个 · LZ4 7 个 · LZ4HC 1 个
LZMA 解压后体积范围：**2.76 MB ~ 33.40 MB**（最小 huonululu_3，最大 z46_2）
```

**关键推论**：最小的 LZMA 包也要 **1717 ms**。
⇒ 若阈值取"≤300 ms 用户能忍"，**61 个包全部超标**；取 ≤1s 也全部超标。
⇒ **"小包本地解、大包走别路"这个分流策略对 LZMA 没有实用空间** —— 要么全本地（都冻 ≥1.7s），要么全走另一条路。

### 1.3 服务端解同一个包（路线 B 的核心数据）

`POST /api/unpack/resolve`（cache miss，首次解包，含写盘）：

| 包 | 解压后 | **前端** | **服务端** | 服务端/前端 |
|---|---|---|---|---|
| aierdeliqi_5 | 8.28 MB | **3859 ms** | **11616 ms** | **3.0×** |
| aierdeliqi_4 | 17.09 MB | **8336 ms** | **21373 ms** | **2.6×** |

（服务端 phases：`pluginResolveMs` 6594/11271 + `unpackWallMs` 11506/21284 —— 慢在 vm 沙箱里跑插件 + 写盘）

**这条数据是决定性的**：路线 B 的收益是"主线程不冻"，代价是"用户等待 ×3"。
而且服务端命中缓存（二次访问）才 <500ms —— 首次访问依然要等 11~21 秒。

## 二、三条路线对比

| | A. Worker 化 | B. 大包改走服务端 | C. 进度提示 + 分片让帧 |
|---|---|---|---|
| **主线程冻不冻** | ✅ 不冻（解压在 worker 线程） | ✅ 不冻（前端只等 fetch） | ❌ 照冻 4~10 秒 |
| **用户总等待** | 不变（3.9s / 8.3s） | ❌ **×2.6~3**（11.6s / 21.4s） | 不变 |
| **改动面** | `src/web/plugin/*`（新建 worker 入口）+ `plugin-host.js` 的本地通道 | `plugin-host.js` 一处路由判断（~50 行） | `plugin-host.js` 提示（~20 行） |
| **要不要新通道** | **要**：postMessage 协议 + 宿主接口的影子实现 | 不要 | 不要 |
| **关键风险** | ① classic script 不能在 module worker 里直接 import ② 插件 lib 依赖 `globalThis.__ULB__` 与宿主回调 ③ **LZMA 返回普通 Array**，过 postMessage 会被结构化克隆成 Array（不是 Uint8Array），下游按字节数组处理会错 ④ 跨 realm 的 `instanceof` 全失效 | 服务端排队/准入另一位在做；首次等待 ×3；服务端内存峰值更高（`peakEstMb` 192/267 vs 前端 JS 堆） | 无技术风险，但**没有任何实质改善**：LZMA 是一次性同步调用，**不可中断、不可分片** |
| **行数量级** | **~350~500 行**（worker 载入器 + 消息协议 + 类型归一 + 两条路复用） | **~50 行** | **~20 行** |
| **是否保留"本地解包"这条路** | ✅ 保留（这正是它唯一不可替代的价值） | ❌ 等于把本地解包这条路废掉大半 | ✅ 保留 |

### 为什么 B 不可取（不只是"慢一点"）

```
1. 实测服务端比前端慢 2.6~3 倍（vm 沙箱 + 写盘），不是"排队等待"那么轻。
2. 现状代码注释（plugin-host.js:638-641）已经因为这件事**主动放弃了前台服务端解包**：
   「前台只问有没有缓存，绝不在前台让服务端解包…实测服务端解一个 42MB 资源包要 11.4s，
     而前端只要 4.3s —— 前台等它只会让首次加载从 4.3s 变成 16s」
   ⇒ 走 B 等于把这条已被实测否掉的路径重新打开。
3. 服务端还要吃内存峰值（192/267MB 起），而浏览器解包恰恰是"不受服务端内存预算限制"的那条路。
```

### 为什么 C 不能单独用

```
LZMA 解码器（lzma-d-min.js）的 decompress 是**一次性同步调用**：内部虽然有分片循环，
但它自己用 setTimeout 续跑是为了"不阻塞太久"，而 vendor 版在我们这里是**同步走完**（.lzma alone 路径）。
它没有暴露进度回调、也没有中止入口 ⇒ "分片让帧"无从下手。
C 能做的只有"解之前先弹个提示"，冻还是冻 —— 属于"不静默"，不属于"不冻"。
```

## 三、推荐：A（Worker），但要按这个顺序做

```
第 0 步（无论选哪条都要做，且能独立交付）
  · 提示：解压前写一条状态行 + 调试日志（"正在本地解包 X（LZMA，解压后 8.3MB，预计 4 秒）"），
    解完再写一条。改动 ~20 行，不动任何逻辑。
  · LZMA 返回 Array 的归一：在调用点（unityfs 的 lzmaDecompress 返回处）统一转 Uint8Array，
    这是 ④ 的前置条件，单独也值得做（跨 realm 前先在自己这边归一）。

第 1 步（A 的骨架）
  · 新建 src/web/plugin/unpack-worker.js（classic worker，不用 module worker：
    插件 lib 全是 classic script、靠 globalThis.__ULB__ 串起来，classic worker + importScripts 最贴合）
  · 消息协议只有三种：{t:'unpack', id, rel, bytes, providerId} / {t:'done', id, files:[{path,bytes}]} /
    {t:'fail', id, code, message} —— 不把整个 VirtualFS 搬进 worker
  · 主线程侧：plugin-host 的 localPath() 里，按"包体积 ≥ 阈值"决定走 worker 还是原地同步

第 2 步（收口）
  · worker 里只跑"插件 resolve"这一步（读字节在主线程做，fetch/VFS 不必进 worker）
  · 产物回主线程后照旧 registerResolved(vfs, …)，VFS/面板/渲染链路一行不改
```

**阈值建议**：`解压后体积 ≥ 2 MB` 就走 worker（≈ ≥1.2s 的冻，已经肉眼可感）。
不按"≤300ms 才同步"来切 —— 按 1.3 节的分布，那等于"永远走 worker"，反过来把阈值定成
"所有 LZMA 都走 worker、非 LZMA 都同步"也完全合理，反而更简单（判据用 `flags & 0x3f === 1`）。

### 我建议的判据（二选一，倾向后者）

```
① 按解压后体积：summary.decompressedBytes >= 2MB ⇒ worker
   · 优点：不关心算法，LZ4/none 天然不会被误伤
   · 缺点：仍要读 header 才知道体积（本地已有 blocksSummary，成本 ~0）
② 按压缩算法：blocks 的 flags 低 6 位 === 1（LZMA）⇒ worker
   · 优点：判据与"为什么慢"直接对应，一行判断；且实测 61 个 LZMA 包**全部** ≥2.76MB，
     与体积判据的结论完全重合
   · 缺点：将来若出现"小 LZMA 包"会多走一次 worker（无害，只是多一次 postMessage）
```

## 四、改动面与影响

```
src/web/plugin/unpack-worker.js     新建（~150 行：载入 5 个 lib + 消息循环 + 类型归一）
src/web/infra/plugin-host.js        localPath() 加分派（~60 行：建 worker / 发消息 / 等结果 / 失败回落同步）
src/web/infra/plugin-host.js        本地通道入口的提示（~20 行，第 0 步）
plugins/unity-*/lib/*               **不改**（LZMA 实现已提交，只调用）
src/server/*                        **不改**
```

**不改的**：VFS、渲染链路、面板 schema、`resolveFromServer`、内存监控、`registerResolved`。

**新增风险点（实现时必须验）**：
```
· worker 里没有 DOM/window ⇒ 插件 lib 若碰 window 会炸（待实测：目前 unityfs/bytes/lzma 都不碰）
· postMessage 结构化克隆：Uint8Array 会被克隆成 Uint8Array ✓，但 **Array 还是 Array**
  ⇒ 必须在 worker 出来前统一转 Uint8Array
· 内存：worker 里解一份、主线程再收一份，峰值翻倍（8.28MB → 两份 8MB，可接受；33MB 包要注意）
```
