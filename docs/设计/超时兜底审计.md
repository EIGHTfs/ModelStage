# 超时兜底审计（按 skill: event-driven-no-timeout-fallback）

> 范围：`src/` 全部产品代码（排除 test、vendor、live2d 运行时 min.js）。只审计，未改代码。
> 判据来自 skill：超时是否是"产品语义"（改变用户看到什么、有明确失败态）还是"兜底"（只是防止卡死、静默放弃）。

## 一、结论汇总

| # | 位置 | 形态 | 判定 |
|---|---|---|---|
| 1 | `src/web/infra/ready.js` `trackModelStage` / `trackElementStage` / `trackElementWhenReady` | 轮询 + 超时后**静默 `stop()`** | ❌ **坏兜底**（超时=放弃观察，`interactive` 没到就没人知道） |
| 2 | `src/web/infra/plugin-host-unpack.mjs` `ensureUnpackWorker` 8000ms | 等 worker `ready` 超时 → `resolve(false)`，**无日志无事件** | ❌ **坏兜底**（"provider 不可用"由定时器裁决，事后无法归因） |
| 3 | `src/server/unpack/worker-client.mjs` 120000ms | 超时 → terminate + 重建 + `reject(带原因文案)` | ✅ 兜底但合格（可观测 + 自恢复） |
| 4 | `src/web/infra/api.js` `idleMs` 15000ms（连续无帧） | 无帧 → abort → `{ok:false, reason:'stalled', message:'服务端停摆（15s 无任何帧）'}` | ✅ **合法语义**（是 idle 不是总时长，有明确失败态与文案） |
| 5 | `src/web/panel/panel-settings.js` `DOC_FILES_TIMEOUT_MS` 6000ms | 超时 → `finally` 释放 pending + `stageLog('warn', …)` | ⚠️ 兜底但合格（有原因、可重试）；用户侧只表现为"清单一直空"，缺可见提示 |
| 6 | `src/server/unpack/runtime/exec.mjs` 请求超时 | 超时 → SIGTERM → 3s → SIGKILL + `fail` 帧 | ✅ **合法语义**（外部进程不可控） |
| 7 | `ready.js` flush 去抖、`panel-settings` `setTimeout(0)` 让出、`infra/schedule.js` | 合并 / 让出主线程 | ✅ 非兜底（定时器不承担流程推进） |
| 8 | `src/web/debug/race-probe.js`、browser 测试的 `waitFor(timeoutMs)` | 诊断与测试 | ✅ 合法（超时=失败，且失败信心里带当前状态） |

**真问题只有 1 和 2**；3~8 要么是产品语义，要么是合格的兜底（有失败态、可恢复、可归因）。

## 二、问题 1：就绪阶段靠"轮询 + 超时静默放弃"

```
现状：
  · trackModelStage 每 MODEL_POLL_MS 采样帧与动作数，凑齐就 markStage('interactive')
  · trackElementStage 轮询元素几何，凑齐就 markStage('interactive')
  · 两者超时分支都只有 `{ stop(); return; }` —— 既不打日志、也不 markStage('failed')

后果：
  · 'interactive' 永远不到时，阶段停在 'painted'，**没有任何记录**说明"为什么没到"
  · 排查时只能看到"状态没变"，看不出是"渲染没完成"还是"观察提前放弃"
```

```
按 skill 应该这样（二选一或都做）：
  a) 渲染面在真正 settled / interactive 时**派发事件**，把轮询降级为兜底；
  b) 轮询超时必须显式失败：`markStage(name, 'failed', { reason: 'timeout', snapshot })`
     或至少记一条 warn，带上"卡在哪一步"（当前 state、已等多久、最后观测值）
```

## 三、问题 2：worker 就绪超时静默判不可用

```
现状：
  const timer = setTimeout(() => resolve(false), 8000);   // 载 lib 超时 ⇒ 判不可用
  · 超时后没有任何日志/诊断事件
  · 而 worker 协议本身有 ready / fail 两条消息 —— 正常情况下不该靠定时器裁决

后果：
  · "插件不可用"可能与"worker 没起来 / lib 404 / 沙箱异常"混在一起，事后无法区分
```

```
按 skill 应该这样：
  · 超时分支先记一条可读诊断（reason: 'worker 未在 8s 内 ready'），再 resolve(false)
  · 区分三种结局：ready(有 provider) / ready(无 provider) / 未就绪（超时或 error）
```

## 四、不动的部分（避免误删）

```
· api.js 的 idle 停摆判定：**必须保留**——服务端真的可能停摆，且它有明确失败态与文案；
  它不是"防卡死的兜底"，是"把停摆告诉用户"的产品语义
· worker-client 的 120s：保留——它同时做了 terminate + 重建 + 带原因的 reject，
  属于"可观测且自恢复"的兜底；若要更严格，可把"worker error/exit 立即 reject 全部 pending"
  补上，让 120s 只作为最后一道
· exec.mjs 子进程超时：保留——外部进程不可控
· 去抖 / 让出主线程的 setTimeout：保留——它们不承担流程推进
```
