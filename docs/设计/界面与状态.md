# 设计 · 界面与状态

> 本文描述界面层的两块设计：**UI 状态统一工厂**（状态怎么声明、读回、回填）与**主题/背景色板**（视觉取值）。
> 状态的**强制约束**在[状态契约](../契约/状态.md)，本文只讲设计与取舍理由。

---

# 第一部分 · UI 状态统一工厂

## 1.1 设计目标与边界

**目标**：让「一个 UI 状态项」从声明到落盘只有一条路径，且**任何时刻都能把当前生效值重新画到界面上**。

**边界**：

| 归工厂管 | 不归工厂管 |
|---|---|
| 需要跨刷新保留的控件值与布局态 | 一次性动作（导出/导入/恢复默认） |
| 值的校验、默认值、落盘、迁移 | 控件长什么样（那是 schema 与 CSS 的事） |
| 重建后的显示态回填 | 当前动作（是模型属性，不该跨模型记住） |

## 1.2 工厂形状

`app/ui-state.js` 是**唯一的状态工厂**（由原 `view-settings.js` 改造而来，不是新建平行层 —— 见 1.7）。

```js
const SPEC = [
  { key: 'animLoop', store: 'panel', id: 'ctl-anim-loop', default: false,
    validate: (v) => typeof v === 'boolean',
    capability: null },
  { key: 'theme',    store: 'theme', id: 'ctl-theme', default: 'dark-cyan',
    validate: (v) => THEME_IDS.includes(v) },
  { key: 'skin',     store: 'panel', id: 'ctl-skin-list', default: '',
    capability: 'skin' },
  // … 每个受持久化的控件一条
];
```

**对外 API**：

| 方法 | 职责 |
|---|---|
| `loadAll()` | 一次性读全部 → 校验 → 非法回落默认 → 填满内存（**纯内存，不碰 DOM**） |
| `getValue(id)` / `getAll()` | 读当前值 |
| `set(id, value)` | 校验 → 记值 → `apply()` → `render()` → 去抖写盘 |
| `commit(id, value, {render})` | 记录**生效值**（渲染器钳制/回退后使用），不再 apply（防递归） |
| `applyAll({render})` | 幂等重放：按当前能力过滤后 apply + 可选 render |
| `flush()` | 立即写盘（去抖未到点时由页面隐藏事件触发） |
| `setApplySkip(ids)` | 声明「有专门恢复通道 / 重建代价高」的项，applyAll 时跳过 |
| `registerAppliers(map)` | 注册 apply / render 实现（避免工厂 import 业务模块成环） |

**三个硬规则**（详见[状态契约](../契约/状态.md) §二）：

1. **单一真相源** —— 显示值 == 生效值 == 工厂里的值
2. **读回早于首次渲染** —— `loadAll` 必须在第一次面板 DOM 构建之前完成
3. **apply 与 render 分离** —— `apply` 幂等可重复；`render` 能对已存在的 DOM 重放

## 1.3 三个时机

```
【启动】
  ① loadAll()                读存储 → 校验 → 非法回落默认（纯内存）
  ② rebuildPanelFor()        第 1 次构建面板 DOM —— 此时控件从 SPEC 读到的是「用户值」而非默认值
  ③ applyAll({render:true})  生效 + 回填显示（幂等）
  ④ 订阅 panel:rebuilt

【面板重建（换渲染面 / 任何未来重建）】
  ⑤ mountPanel 完成 → 派发 panel:rebuilt
  ⑥ applyAll({render:true})  ← 显示态自动重放（这是「值对但显示错」这类故障的根治点）

【用户改设置】
  ⑦ set(id, value) → 校验 → apply → render → 去抖写盘（150ms）
  ⑧ visibilitychange / pagehide → flush()（避免「改完秒关页面」丢最后一次）
```

**关键差异**：② 发生在 ③ 之前，但 ② 时**已经有值** —— 旧实现是 ② 拿到 schema 默认、③ 之后用一次性命令补，
一旦 ② 再次发生（重建）补丁就丢了。

## 1.4 槽位划分

一个存储键内按用途分槽，**各槽独立、一个坏不连累另一个**：

```
modelstage-settings-v2
├── panel   各控件值（不含主题与背景模式，避免双份存储）
├── theme   uiTheme
├── bgMode  background{ mode, color, imageUrl }
├── debug   { collapsed, panelPos, logLevels }
└── layout  { leftVisible, rightVisible }
```

另外两个独立键：

```
modelstage.tree-state.v1    左栏树展开态 + 上次选中的模型（结构一字不改）
modelstage.dirpicker.last   目录选择器上次位置
```

**一个槽位一条红线**：`tree-state.v1` 的结构（`lastByGame{游戏:变体id}` + 兼容 `lastModelId`）
**只改由谁读写，不改结构** —— 改结构等于让用户上次选中的模型丢失。

## 1.5 默认值权威与断言

```
默认值的唯一来源 = schema.js 的 defaultOn / defaultValue
SPEC 的 default 从 schema 派生，不独立写一份
启动时断言 SPEC.default === schema.default，不一致直接报错
```

**为什么还要断言**：派生可能被后来的改动破坏（有人图省事在 SPEC 里直接写字面量），
**断言是唯一能发现这种破坏的手段**。

**两条派生规则**（不补会漏掉关键控件）：

| 规则 | 不补的后果 |
|---|---|
| **没写 `defaultOn` 的开关也算有状态**（默认 false） | 这类控件根本进不了工厂 ⇒ 漏掉真实控件 |
| **取值域同时认 `values` 与 `options[].value`** | 下拉/胶囊用 `options` 时非法值校验被静默跳过 |

**校验的类型基准不能用 `defaultValue` 推断** —— 取值域可以混类型（如 DPR 是 `['auto', 1, 1.5, 2]`），
有取值域时以域为准，无域才按默认值类型校验。

### 1.5.1 插件控件如何参与默认值与断言（panel 类型）

插件控件既然进了设置工厂（`uiState.registerSpecItems`），就必须遵守同一条"默认值唯一来源"：

```
· 面板档位控件（segmented）的默认值 = options[0]（第 0 档即"关"）
· 开关（toggle）的默认值 = false
· plugin.json 的 params[].default **不是**面板默认值，它只是"设置值缺失时的 uniform 兜底"
  ——两者冲突时以档位（options[0]）为准
```

理由：工厂 §1.5 要求"默认值唯一来源，不许写两份"。插件控件若能自己声明面板默认值，
就会出现"schema 说关、plugin.json 说轻"的两份真相，而「恢复默认」只认前者 ⇒ 用户看到值跳变。

**强制断言（不满足则拒绝登记 + 记 diag）**：

```
registerSpecItems() 对每个入表项计算 defaultValue；算不出来（档位控件缺 options / 开关缺 defaultOn）
⇒ 拒绝进 SPEC，并把 { id, reason } 放进返回值 skipped
⇒ 调用方（panel-settings）逐条 stageLog('warn', '插件控件未进入设置工厂：…')
```

为什么不静默放过：控件在面板上看得见、却不在 SPEC 里，表现为「恢复默认」跳过它、
导出设置里也没有它 —— 这种"半接管"比彻底不支持更难排查。

**孤儿键清理**：插件被真删掉之后，存档里它的键要消失（而不是永久残留）。
判据是 SPEC 本身（= 当前所有有效控件），时机必须是**插件声明全部交完之后**
（`spineviewer:plugins-loaded` 之后、且已完成一次面板重建）——
在那之前 SPEC 里可能只是"还没来得及登记"，早清会误删用户已设好的值。


## 1.6 能力过滤与「保留不生效」

```
读回值不被当前渲染面支持（如 Live2D 面不支持 skin）
  ⇒ 值保留
  ⇒ 不 apply、不 render
  ⇒ 切回支持的面时再 apply
```

**禁止回落默认** —— 回落默认等于永久丢失用户选择。用户在 Spine 面设了皮肤，
切到 Live2D（不支持）再切回 Spine，皮肤必须还在。

实现：SPEC 里声明 `capability` 键，`applyAll` 时按当前渲染器能力过滤。

**另一类延迟 apply**：依赖模型数据的项（皮肤列表、动作列表）在启动时模型还没加载 ⇒
按 `phase` 分两段，后者在 `panel:refresh-animations` 之后补一次。

## 1.7 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 新建一层工厂 vs 改造现有偏好模块 | **改造** `view-settings.js` | 它已是唯一的偏好存储入口，结构 `{uiTheme, background, panel}` 已覆盖绝大多数状态项；新建平行层会立刻产生「两套都读、谁先谁后」的新坑 |
| SPEC 如何拿到 apply/render 实现 | **注册表注入**（`registerAppliers`） | 若 SPEC 直接 `apply: (v) => applyAnimLoop(v)`，会形成 `ui-state → transport-actions → …` 与 `panel-settings → ui-state` 的循环 import（本项目曾被循环 import 坑到整页崩溃） |
| 渲染器回退请求值时怎么记 | 新增 `commit()` | 要把**生效值**记进工厂，但不能走 `set()`（会再次 apply，无限递归） |
| 有专门恢复通道的项（MSAA/主题/背景） | `setApplySkip` 跨调用生效 | 否则每次面板重建的 `applyAll` 都会重新建上下文，启动白等数秒 |
| 旧键迁移 | **只删不搬**（`purgeLegacyKeys`） | 不需要兼容已下线的实现；但保留删除动作，避免旧数据永久占着 localStorage |
| 调试浮层的迁移时机 | **读取即迁**（幂等，非一次性标志） | 浮层挂载可能早于 `loadAll`，一次性标志一旦置位就不再重试 ⇒ 位置永远回落默认 |

## 1.8 模型属性的边界：换模型必须清哪三个

**引擎上有三个字段属于「当前模型」，不是「当前会话」**。换模型时必须清，否则旧模型的值会被
当成新模型的状态用出去（`getSetting` 回显、纹理重建重放、时长查表都会读到它）。

| 字段 | 位置 | 不清会怎样 |
|---|---|---|
| `animationName` | `engine/player.js` | `getSetting('animation')` 回显旧动作名；`appearance.rebuildTextures` 里 `if (engine.animationName) engine.setAnimation(...)` 会把旧动作**真的应用到新模型** |
| `activeSkins` | 同上 | `appearance.rebuildTextures` 里 `if (engine.activeSkins.length) engine.setSkins(...)` 用旧模型的皮肤名去套新模型 |
| `durations` | 同上 | `currentDuration()` 按动作名查这张表 ⇒ 循环推进的时长判断用旧模型的数字 |

**清零位置**：

```
· clearSkeleton()（卸载路径）—— 已清
· loadModel()（换模型路径）—— **必须在 disposeContent() 之后、bindModel() 之前显式清**
· rebuildTextures()（同一模型换口径）—— **不能清**：它依赖 animationName/activeSkins
  把"重建前的状态"重放回来
```

**判断依据**：`loadModel` 是「换内容」，`rebuildTextures` 是「同一内容换口径」。
前者清模型属性，后者保留 —— 这也是为什么不能简单地把清零塞进 `disposeContent()`
（两条路径都会调它）。

## 1.9 明确不做

- **不持久化「当前动作」** —— 动作是模型属性，跟着模型走更自然；记住跨模型的动作名反而反直觉
- **不新建 localStorage 键** —— 新状态一律进已有键的对应槽位
- **不在工厂里碰 DOM** —— `loadAll` 必须是纯内存操作

# 第二部分 · 主题与背景

## 2.1 五套主题

变量名统一为 `--color-*`，定义在 `[data-ui-theme="<id>"]` 块里；切换主题只改 `html[data-ui-theme]` 属性。

| 主题 id | 名称 | background | foreground | card | primary | primary-fg | secondary | muted | muted-fg | border |
|---|---|---|---|---|---|---|---|---|---|---|
| `dark-cyan` | 深空青 | `#131416` | `#e9ebed` | `#1f2326` | `#1fc0c5` | `#0a0a0c` | `#2a2f33` | `#23272a` | `#9ca3af` | `#353a3e` |
| `eye-gray` | 暖陶暗色 | `#262624` | `#f0eee9` | `#30302e` | `#d97757` | `#1f1d1a` | `#3a3936` | `#2e2d2b` | `#b0aea5` | `#4a4843` |
| `day-paper` | 日间纸 | `#f4f1ea` | `#262420` | `#fbf9f4` | `#0e8a8f` | `#ffffff` | `#e7e2d7` | `#ece8de` | `#5c574b` | `#d8d2c4` |
| `neon-violet` | 霓虹夜 | `#0b0814` | `#ece8f7` | `#16111f` | `#a855f7` | `#160a22` | `#221a30` | `#1a1426` | `#b0a6cc` | `#352b49` |
| `cloud-blue` | 云蓝 | `#eef2f7` | `#16202e` | `#fbfcfe` | `#2563eb` | `#ffffff` | `#e2e8f0` | `#e6ebf2` | `#4f5e78` | `#cbd5e1` |

默认主题：`dark-cyan`。

**令牌语义必须用对**：配色只用 `--color-*` 变量，不写字面色值。
特别注意**背景色令牌不能当文字色用**（`--color-muted` 是「深色背景」的名字，不是文字色）——
用错的表现是「DOM 里文本全在，但看不见」，属最难查的一类。文字色走 `--color-text-secondary` 这类专用令牌。

## 2.2 背景模式

| 值 | 名称 | 实现 | 默认 |
|---|---|---|---|
| `checkerboard` | 棋盘格 | 壳层棋盘底纹 | ✅ |
| `solid` | 纯色 | 舞台容器 `background: var(--stage-solid)` | |
| `transparent` | 透明 | 舞台容器背景透明，露出页面底色（随主题变化） | |
| `custom` | 自定义 | 已上传的自定义图（`/api/backgrounds`），设为时 `data-bg="custom"` | |

**背景的唯一写入口是 `Surface.setBackground()`**（见[渲染面契约](../契约/渲染面.md) INV-07）；
渲染器不画背景、不改 `data-bg`。

## 2.3 背景列表的两种来源

界面上的背景列表由**两类来源合并**呈现，共用同一套数据与渲染层（`panel/bg-source.js`）：

| 来源 | 数据 | 特点 |
|---|---|---|
| **内置纯色预设** | 服务端 `data/backgrounds/solids.json`（5 个默认，可增删改名） | 单行 + 右侧 `⋯` 菜单；色块 40×32 |
| **自定义背景图** | 服务端 `data/backgrounds/`（上传的图片） | 缩略图 56×32 `object-fit:cover`；删除需二次确认 |

**匹配按颜色值，不按预设 id** —— 颜色的唯一真相是 `background.color`，
所以预设删掉/改名都不影响已选颜色；两个同色预设只有第一个打勾。

## 2.4 纯色预设的交互取舍

- **行高 38px，单行 + 右侧 `⋯` 菜单**（而非两行布局）：两行要占约 320px，单行约 180px
- **删除确认分两种**：纯色预设**直接删**（可从默认恢复）；自定义图**要确认**（删了就没了，
  确认框默认焦点在「取消」）
- **触屏可用**：操作按钮高度 ≥44px，`⋯` 点击区 ≥32×32（不使用只能 hover 的交互）
