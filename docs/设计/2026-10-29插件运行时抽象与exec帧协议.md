# 插件运行时抽象与 exec 帧协议（第 1 步：契约定稿）

> 本轮只做**运行时抽象 + 协议定稿**，**不接任何真可执行**（`exec` 适配器固定抛 `EXEC_RUNTIME_NOT_IMPLEMENTED`）。
> 取证 2026-10-29 04:10–04:35 ｜ 基线 HEAD `12f369f`

## 零、为什么是「任意可执行」而不是「专为 Python」

用户已确认「Python 等」包含 Go/Rust 等编译型语言。这个选择让方案**变简单**而不是变复杂：

| 维度 | 专为 Python | 任意可执行（选定） |
|---|---|---|
| 解释器探测 | 必须处理（本机实测：`/bin/python3` **没有 pip**，只有套件带的 `python310`/`python314` 能用） | **不需要** —— 插件自己带入口 |
| 依赖安装 | 要管 pip / venv / abi3 轮子 / 编译链（本机 **无 gcc/cc/make**） | **不需要** —— 依赖由插件作者自己解决 |
| 平台差异 | Python 版本矩阵 | 只剩"可执行文件能不能在本平台跑" |
| 语言覆盖 | 只有 Python | Go / Rust / Python / shell 一视同仁 |

上一轮调研的三条实测，正好是这个形态的成本依据：

```
① 帧协议本身极便宜：spawn→首帧 32ms、常驻每帧 0.30ms、中文路径无乱码
② /tmp 是 noexec（C 扩展会 failed to map segment）⇒ **可执行文件也不能放 /tmp**
③ UnityPy 真解包与我们 JS 产物逐项一致，LZMA 上快 5~7 倍（将来若接 Python 的收益证据）
```

## 一、清单字段（向后兼容，缺省 = 现状）

```jsonc
{
  "id": "some-plugin",
  "provides": ["asset-provider"],

  "runtime": "node",        // 可选；缺省 "node"。另可 "exec"
  "entry": "index.js",      // node：入口脚本（也是 files[] 的最后一项）
                            // exec：**相对插件目录**的可执行路径，如 "bin/unpack"
  "frameProtocol": 1        // 仅 exec 必需；协议版本，当前只支持 1
}
```

### 字段语义与缺省

| 字段 | node | exec | 缺省 |
|---|---|---|---|
| `runtime` | `"node"` | `"exec"` | `"node"`（零行为变化） |
| `entry` | 忽略（入口由 `files[]` 顺序决定） | **必需**，相对插件目录，禁绝对路径与 `..` | `null` |
| `frameProtocol` | 忽略 | **必需**，必须是 `1` | `null` |
| `files` | **必需**（按序加载的 js） | **忽略**（不加载任何 js） | — |

**为什么 `files` 在 exec 下要显式忽略**：`registry.mjs` 原来有一行 `files 为空时用 entry 兜底`，
若不按 runtime 分流，`entry: "bin/unpack"` 会被当 js 读进沙盒，报一堆看不懂的语法错。
代码里已按 `runtime === 'exec'` 分流（`src/server/plugins/registry.mjs`）。

## 二、适配器统一接口

```js
// src/server/unpack/runtime/index.mjs —— 上层（plugin-runner）只认这个
load(meta, ctx) → { ok: true, api } | { ok: false, error, code? }
dispose()       → void
```

其中 `api` 需提供：

```
canHandle(file)      → boolean            （纯判定；同步；不得有副作用）
resolve(file)        → { prefix, entry, files }
explainReject?(file) → { code, message }  （可选：不认领时说明原因）
estimateMemory?(...) → {...}              （可选：自报内存代价）
```

两种运行时的适配器（`runtime/node-vm.mjs` / `runtime/exec.mjs`）必须同形，上层无感。

`ctx` 约定：`{ pluginsDir, root }`，并允许注入 `execAllowed`（测试与上层复用同一判定，不重复读盘）。

## 三、帧协议（v1）

### 3.1 传输形态

```
· 宿主 spawn 插件声明的 entry，设置 cwd = 插件目录
· 三根管道全用：stdin(宿主→插件) / stdout(插件→宿主) / stderr(插件日志)
· 帧 = **一行一个 JSON**（UTF-8，以 \n 结尾）；不含任何二进制
· 插件在 stdout 上**只能写帧**；任何非帧输出（调试 print）必须走 stderr
```

**为什么是"行 JSON"而不是长度前缀**：实测每帧往返 0.30ms，行 JSON 的实现复杂度最低
（跨 chunk 拼行是唯一要小心的点），且天然支持人工用 `echo '…' | ./plugin` 调试。
长度前缀（类 LSP）在大 payload 上才有优势，而 v1 **不通过管道传 payload**（见 3.3）。

### 3.2 帧格式

**请求（宿主 → 插件）**

```json
{"id":1,"method":"handshake","protocol":1}
{"id":2,"method":"canHandle","rootId":"azurlane_bundle","rel":"live2d/x","absPath":"/…/x","size":2213909}
{"id":3,"method":"resolve","rootId":"azurlane_bundle","rel":"live2d/x","absPath":"/…/x","size":2213909}
{"id":4,"method":"shutdown"}
```

**响应（插件 → 宿主）**

```json
{"id":1,"ok":true,"protocol":1,"pluginVersion":"1.0.0"}
{"id":2,"ok":true,"handled":true}
{"id":3,"ok":true,"prefix":"vfs://<pluginId>/<rootId>/<dir>/","entry":"model3.json",
 "files":[{"name":"moc3.moc3","tmpPath":"/…/a3f1.bin","size":4953024},
          {"name":"texture_00.png","tmpPath":"/…/b7c2.bin","size":1834241}]}
{"id":2,"ok":false,"code":"EXEC_PLUGIN_BAD_REQUEST","message":"…"}
```

硬约定：

```
· id 由宿主生成、插件原样回填；宿主按 id 匹配（不按顺序）
· 未知 method ⇒ ok:false + code:"EXEC_PLUGIN_UNKNOWN_METHOD"（不要静默忽略）
· 插件崩溃/退出 ⇒ 宿主把**所有在途请求**判失败（不能等超时）
· stderr 每行原样进宿主日志（带插件前缀），不解析
```

### 3.3 大 payload：走**临时文件**，不走管道

一个包解压后几 MB～几十 MB（实测 `aierdeliqi_5` 解压 8.6MB、`aidong_2` 类 17MB+）。
v1 的取舍：

```
✅ 采用：插件把产物写到自己创建的临时目录，帧里只传 tmpPath + size
❌ 不用：stdout 传二进制（粘包/编码/内存三头问题）
❌ 不用：base64 塞 JSON（20MB → 27MB 文本，慢且吃两倍内存）
```

**临时目录的命名与清理**（这是必须写死的，否则必然漏清理）：

```
· 每次 resolve 由**宿主**预先分配一个目录：<root>/runtime/exec-tmp/<pluginId>/<requestId>/
  通过帧字段 tmpDir 传给插件（插件不自己选位置）
· 宿主管生命周期：产物被 unpackFile 消费完（落盘/转 Blob 之后）**立即整目录删除**，
  异常路径（超时/崩溃/中止）在 finally 里删
· 插件只允许在该 tmpDir 内写文件；写出界外属违约，宿主不做额外防护（信任模型见 §五）
· 目录必须落在**可执行卷**上（/tmp 是 noexec，见 §六）
```

### 3.4 超时与中止

```
· 每次请求宿主侧设超时：canHandle 默认 2s、resolve 默认 120s（可配置）
· 超时处理顺序：**先 SIGTERM → 宽限 5s → SIGKILL**（与项目既有 kill 纪律一致）
· 收到 SIGTERM 后插件应尽快退出；宿主在宽限期内等待 'exit' 事件
· 中止（用户取消）走同一条路：先 TERM 后 KILL
· 超时/中止后，该 worker 标记为"不可用"：**下一个请求重新 spawn**（不重启同一个脏进程）
```

### 3.5 崩溃与僵尸

```
· 一个插件一个 worker（常驻）；空闲 N 秒（默认 300s）后主动 shutdown → 退出
· 宿主监听 'exit'：非 0 退出码 ⇒ 记日志（含 stderr 尾部）+ 标记 worker 失效
· **不自动无限重启**：同一插件连续崩溃 3 次 ⇒ 熔断，后续请求直接返回错误（附最近错误）
· 僵尸防护：
  · spawn 时不 detach；宿主进程退出前对所有存活 worker 发 SIGTERM 并等待
  · 注册 process.on('exit') 兜底 kill（同步调用，不让它们变成孤儿）
  · 子进程内也必须处理 SIGTERM（否则 TERM 无效，只能等 KILL）
```

### 3.6 握手

```
第一帧必须是 handshake：宿主发 {"method":"handshake","protocol":1}
插件回 {"ok":true,"protocol":1,...}
· 协议号不匹配 ⇒ 宿主立即 TERM + 拒绝该插件（错误码 EXEC_PROTOCOL_MISMATCH）
· 握手超时（默认 10s）⇒ 同上
```

**为什么要握手而不是"第一帧直接 canHandle"**：插件可能在启动时加载大依赖（如 import UnityPy，
实测 python 冷启 + import 可到秒级）。握手把"启动"与"第一次干活"分开，超时口径才准确。

## 四、安全边界（**这是本设计最重要的一节**）

### 4.1 两种运行时的安全模型**完全不同**

```
node（vm 沙盒）：
  插件是**进程内的 JS**，只拿到一个注入的全局对象。
  它能干的事受限于我们给它放了什么（bytes / TextEncoder / 打桩的 fetch）。
  注意：`vm` **不是安全边界**（Node 官方明确写了），但它的"默认约束力"远高于子进程。

exec（子进程）：
  插件是**你机器上的一个陌生可执行文件**，以**当前服务进程的权限**运行。
  它可以：读你所有可读的文件、连任意网络、读环境变量（含密钥）、
          写任意可写目录、跑任意别的命令、fork 更多进程。
  宿主**无法**在进程内部约束它 —— 唯一真正的约束是操作系统层面的用户/容器隔离。
```

### 4.2 因此：默认关闭，必须显式开启

```
· 未开启时，runtime:"exec" 的插件**装载直接被拒**（不是降级、不是警告后继续）
· 开启方式（二选一）：
    ① config/plugin-runtime.json  →  {"allowExecRuntime": true}
    ② 环境变量 MODELSTAGE_ALLOW_EXEC_PLUGINS=1
· 判定失败（文件不存在/JSON 写坏）一律按**未开启**处理（失败要保守）
· 拒绝时的文案必须包含"这意味着什么"：
    "exec 通道意味着该插件可以执行任意本地命令（读写你的文件、发起网络请求），
     只应对你信任的插件开启。"
```

### 4.3 开启后的残余风险（写清，不粉饰）

```
· 插件与主服务**同权限**：没有降权、没有 seccomp、没有文件系统沙箱
· 想真正隔离只有两条路（都不在本步范围）：
    ① 容器化：插件跑在独立容器，只有输入目录只读挂载 + 产物目录可写
    ② 降权：以专用低权限用户 spawn（setuid / sudo -u），并限制其可读范围
· 第 2 步实现时，至少要做到：
    - entry 必须是插件目录内的相对路径（已实现校验，禁绝对路径与 `..`）
    - 不继承不必要的环境变量（白名单透传，别把宿主 env 整份给它）
    - 记录每次 spawn 的命令行与耗时（可审计）
```

## 五、已知未验证平台（**不许假设可用**）

```
本设计的实测只在 **Synology DSM 7.x / x86_64 / btrfs** 上做过。
Windows 与 macOS **完全未验证**，其中至少这几条需要重新确认：
· Windows 没有 POSIX 信号：SIGTERM 语义不同（Node 上 kill 会直接 TerminateProcess），
  "先 TERM 后 KILL" 的宽限期设计在 Windows 上不成立
· 可执行文件后缀/权限位（.exe、chmod +x）平台差异
· 路径分隔符与中文路径编码（本机实测 UTF-8 无乱码，Windows 代码页未验）
⇒ 第 2 步实现前，先明确"是否支持 Windows"，不支持就要给出明确拒绝而不是跑一半坏掉。
```

## 六、部署约束（从上一轮实测直接继承）

```
① **可执行文件与依赖不能放 /tmp**：/tmp 是 tmpfs + noexec，
   C 扩展会 `failed to map segment from shared object`（实测），可执行文件同理跑不起来。
   插件目录、tmpDir 都必须落在可执行卷（本项目为 /volume1 的 btrfs，无 noexec）。
② 磁盘：/volume1/VirtualDSM 已用 91%（剩 2.9G）。exec 插件自带运行时/依赖会显著占空间，
   安装前应检查剩余空间并给出可读提示。
③ 插件目录内的一切产物（bin/、.deps/、venv/）应 gitignore，不入库。
```
