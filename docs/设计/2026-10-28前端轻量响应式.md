# 前端轻量响应式（零依赖）设计

> 决策来源：在「转 Vue / 手工增量优化 / 自建响应式」三者中选定**自建**。
> 判据：Vue 的收益上限低（项目已有声明式骨架），代价确定（构建链、测试口径、审计基线、插件宿主冲突）。
> 本设计只做「调度内核 + 键订阅」，**不引入虚拟 DOM、不改变任何 DOM 契约**。

---

## 一、现状（实测）

```
ui-state.js          534 行：SPEC（值/默认/能力/持久化）+ 一堆 get/ set，**无任何通知机制**
roster/view.js       562 行：第 60-110 行已有一套 rAF 合批（pending 标志 / 兜底定时器 / flushRender）
                            注释里写明三条硬约束：不漏最后一帧 / 不闪烁 / 状态不丢
panel-settings.js    694 行：rebuildPanelFor 全量重算三态 + 重跑能力自检（切换渲染器时触发）
roster/rows.js       163 行：行渲染工厂（纯函数）
```

结论：**「合批调度」已经从实践里长出来了，但被锁在 roster 一个文件里，且只支持"整个列表重绘"这一种粒度。**
缺的是两样：

1. 可复用的调度内核（现在只有 roster 内部那份，面板/状态行要自己再写一遍就会漂移）
2. 键级订阅（现在改一个面板值 → 要么全量重建，要么手工点对点刷新）

---

## 二、设计

### 2.1 两个小模块（各约 30 行）

**`src/web/infra/schedule.js`** —— 调度内核（从 roster/view.js 抽出，行为一字不改）

```js
// 语义：同一帧内多次 request 只执行一次；不漏最后一帧；后台标签页有兜底
export function createScheduler(run) → { request(), flush(), cancel() }
```

必须保留 roster 已验证的三条性质：

```
① 不漏最后一帧：pending 只在真正 run() 之后清除
② 不闪烁：同帧多次 request 只跑一次
③ 后台标签页兜底：rAF 不触发时用定时器兜底（否则后台切回会看到旧内容）
```

**`src/web/infra/store.js`** —— 键值 + 订阅

```js
export function createStore() → { get(k), set(k, v), subscribe(k, fn), flush() }
```

四条硬约束：

```
① Object.is 同值不通知 —— 否则订阅者里的写回会形成环路
② rAF 合批 —— 一帧内 set 同一个 key 多次，订阅者只被通知一次
③ 订阅者异常隔离 —— 单个订阅者抛错不能影响其它订阅者，且必须上报（不能静默吞）
④ 不做持久化 —— 持久化仍归 ui-state（职责不混，否则会变成第二套 SPEC）
```

**明确不做**：虚拟 DOM、模板编译、自动依赖收集（Proxy）、组件生命周期。
订阅者自己决定改哪个节点 —— 这是「零依赖且不改动现有 DOM 契约」的前提。

### 2.2 接入策略：先量，再决定接哪

**不先铺开接入。** 先做一次「DOM 写放大」测量，用数据决定接入点。

测量方法（运行时打点，**不改代码**）：

```
在浏览器里 patch 三个写入口，按来源堆栈第一帧聚合，采样 10 秒：
  · document.createElement
  · Node.prototype.textContent 的 setter
  · Element.prototype.setAttribute
输出：每个来源文件每秒的写次数 Top 10
```

判据：

```
· 若某来源存在「同一节点在同一帧内被写 ≥2 次」⇒ 有真实收益，接 store
· 若没有明显重复（都是各写一次）⇒ **不接入**，只落两个模块骨架 + 文档写明"暂无接入点"
```

这条判据必须严格执行：**没有测量就不许调整代码结构**（本项目已因"凭感觉优化"返工过）。

### 2.3 候选接入点（按预期收益排序，仍需测量确认）

| 候选 | 现状 | 预期收益 |
|---|---|---|
| 面板读数（FPS / 内存 / 状态行） | 定时器直接写 DOM | 中：高频，但每次只写一个文本节点 |
| 面板控件三态（rebuildPanelFor） | 全量重建 57 控件 | 中：但只在切换渲染器时触发，频率低 |
| 名册重绘 | 已合批，但仍是全量替换 | 高：466 变体，若按 id diff 可少建节点 |
| 皮肤/动作列表 | 切模型时全量重建 | 低 |

## 三、验收标准

```
1. 两个模块各自 ≤40 行（含注释），零依赖，不改任何 DOM 契约与 data-* 属性
2. schedule.js 抽出后 roster 行为零变化：用现有回归（f3-reveal / panel-actions / f1-controls）+ 
   人工核对——展开/收起/搜索/选中/滚动位置在合批前后一致
3. store.js 单测（node --test，用 DOM 垫片）：
   · 同值 set 不通知
   · 同帧多次 set 只通知一次
   · 订阅者抛错不影响其它订阅者，且错误被上报
   · unsubscribe 后不再收到通知
4. 测量报告：附"写放大 Top 10"实测表；若结论是"暂无接入点"，如实写进文档，不做无收益改造
5. 全量 node --test：95/95 pass 0 fail
6. 浏览器实测：面板/名册/调试图层渲染正常（截图核对选中 modelId 与画面一致）
```

---

## 四、边界（明确不做）

```
· 不引入任何外部依赖、不加 package.json、不加构建步骤
· 不改 ui-state 的 SPEC 语义（它仍是唯一权威；store 只是变更通道）
· 不做自动依赖收集（Proxy）—— 隐式行为会让"为什么这个节点更新了"变得不可查
· 不在本轮改造 roster 的 diff（那是独立一步，需单独测量与验证）
```
