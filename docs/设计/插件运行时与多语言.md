# 插件运行时与多语言支持（含 UnityPy 预研）

> 调研日期：2026-10-27 ｜ 触发：希望插件不受限于 nodejs，未来多半要用 **UnityPy**（Python）
> 结论先行：**可行，且应该做；但必须先做「运行时抽象」，再做 Python 适配器**。
> 当前 `plugin-runner.mjs` 连"多个 JS 插件"都还不支持（写死单插件），这是前置债。

---

## 一、现状（代码实测）

| 事实 | 位置 | 含义 |
|---|---|---|
| node 侧只支持**一个**插件 | `src/server/unpack/plugin-runner.mjs`：`PLUGIN_ID = 'unity-live2d-bundle'`、`PLUGIN_DIR` 写死、`LIB_FILES` 14 个写死 | 换插件要改代码，不是"按目录发现" |
| node 侧用 `vm` 沙箱跑经典脚本 | 同上：`vm.createContext` + 按序 `runInContext` | 只能跑 JS；且官方文档明确 `vm` **不是安全边界** |
| 浏览器侧用经典脚本 + 宿主注入 | `src/web/infra/plugin-host.js` | 前端插件只能是 JS（浏览器里没有别的选择） |
| 插件性能特征 | plugin-runner 注释实测：沙盒 0.9ms、lib 41ms、index.js 6.4ms（合计 58ms 装载），resolve 本体秒级 | 装载便宜，真正贵的是解析 |

**所以多语言问题要拆成两半**：

```
浏览器侧（渲染/效果类插件）  只能是 JS —— 这条不放开，也没必要放开
服务端侧（资产解析类插件）    可以多语言 —— UnityPy 属于这一类
```

## 二、三条路线对比

### A. 子进程 + 帧协议（推荐）

```
主进程 spawn 插件自带的可执行入口（python3 plugins/<id>/main.py）
两侧用长度前缀 JSON 帧通信（类 LSP / Content-Length 风格）
大二进制不走 stdout：写临时目录，帧里只传路径
```

| 维度 | 评估 |
|---|---|
| 可行性 | ✅ 直接调用系统 python3（本机 `/bin/python3` 已有）；插件自带 venv 或 `pip install --target` 到插件目录 |
| 启动开销 | 冷启 ~50~120ms（python + import UnityPy 更贵）；**常驻 worker 可摊薄到 0** |
| 隔离性 | ✅ 真进程隔离（比 vm 沙箱更接近"安全边界"） |
| 依赖 | ✅ 插件自己带依赖，项目主体仍可保持零依赖 |
| 崩溃影响 | ✅ 子进程崩了主服务不受影响（vm 里死循环会拖住事件循环） |
| 复杂度 | 中：要定协议、管生命周期、超时、崩溃重试 |

### B. 嵌 WASM Python（Pyodide）

```
不推荐。Pyodide 运行时数十 MB，启动秒级；UnityPy 还依赖 numpy/Pillow 等
⇒ 包体与启动成本都远超收益，且与"零依赖主项目"相冲。
```

### C. 不放开，用 JS 重写 UnityPy 那部分能力

```
现状其实已经这么做了一部分：plugins/unity-live2d-bundle/lib/unityfs.js 就是自己解析 UnityFS。
但 UnityPy 覆盖的引擎版本 / 压缩类型 / 资源类型远比自研宽；
"以后多半需要 UnityPy"这个判断成立，就不该继续加厚自研解析器。
```

**结论：选 A。** 顺带解决三个既有问题：运行时通用化、真隔离、多依赖共存。

## 三、要做的前置：运行时抽象

现在的 `plugin-runner.mjs` 写死单插件，先改成**按 plugin.json 选适配器**：

```jsonc
// plugin.json 新增可选字段
{
  "id": "some-plugin",
  "runtime": "node" | "python",   // 缺省 "node"（向后兼容现有插件）
  "entry": "index.js" | "main.py" // 缺省按 runtime 取约定名
}
```

```
server/plugins/runtime/
  index.mjs        ← 按 runtime 字段返回适配器；统一接口
  node-vm.mjs      ← 现有 vm 沙箱（通用化：目录/lib 从 plugin.json 读，不再写死）
  python-worker.mjs← 新增：子进程 + 帧协议
```

**统一接口**（两种 runtime 必须同形，上层无感）：

```
load(pluginDir, manifest) → { canHandle(file), resolve(file), dispose(), stats() }
canHandle(file)  → boolean（纯判定，不得有副作用）
resolve(file)    → { prefix, entry, files: Map<name, bytes> }   // 或 files 为落盘路径列表
dispose()        → 释放（子进程 kill / 沙箱丢弃）
```

## 四、子进程帧协议草案（Python 适配器）

```
请求（主进程 → 子进程，stdin）
  {"id":1,"method":"canHandle","rootId":"...","rel":"...","absPath":"...","size":20205522}

响应（子进程 → stdout）
  {"id":1,"ok":true,"handled":true}
  {"id":1,"ok":true,"prefix":"vfs://...","entry":"model3.json",
   "files":[{"name":"moc3.moc3","tmpPath":"<插件临时目录>/a.bin","size":4953024}]}

错误
  {"id":1,"ok":false,"code":"ULB_ERR_CONTAINER_PARSE","message":"..."}

进度（子进程 → stdout，**可选能力**，同一 id 可发多帧）
  {"id":1,"progress":{"phase":"read","ms":1200}}      // ms = 自收到该请求起的相对毫秒
  {"id":1,"progress":{"phase":"resolve","ms":3400}}
  {"id":1,"progress":{"phase":"write","ms":4800}}
```

硬约束（写进契约时逐条落）：

```
① 帧格式固定：每帧一行 JSON（UTF-8）+ 以 \n 结尾；解析方必须支持跨 chunk 拼行
② 二进制走 tmpPath：帧里**只传路径与大小**，不上 base64（20MB 包 base64 会慢且吃内存）
③ 超时必须双向：主进程对每次请求设超时并 kill；子进程侧也要设内部上限
④ 崩溃重试一次：异常退出后重启一次，仍失败则该插件的后续请求直接返回错误（不无限重启）
⑤ 常驻：同一插件一个 worker，空闲 N 秒后退出（避免常驻 python 吃内存）
⑥ 编码：统一 UTF-8，路径含中文要显式 encode/decode（本项目路径大量中文，踩过）
```

进度帧的四条硬约束（**加进度帧不能破坏上面六条**，尤其 ③④）：

```
⑦ 进度帧**不终结请求**：它只是"这个 id 现在跑到哪了"的旁路信息，
   同一 id 后面仍会收到真正的响应/错误帧。解析方**必须**先判 progress 再判响应，
   否则会把一条进度帧当成响应 ⇒ 请求提前 settle 成"返回值缺 prefix/entry"。
⑧ 进度是**可选能力**：插件可以完全不发（老插件零改动照常用）。
   主进程没注册进度回调时静默丢弃，不报错、不影响结果与超时。
⑨ 重复/乱序**无害**：同一 phase 发多次以**最后一次**为准（先到的是粗估，后到的是终值）；
   不认识的 phase 名一律忽略并记 debug（不报错、不中断请求）——
   这样插件可以自由加分档，老主进程遇到新档名也不会炸。
   **白名单的唯一来源**：`src/server/unpack/runtime/exec.mjs` 的 `PROGRESS_PHASES`
   （档名 + 每档语义都在那张表里）。本文**不复述名单** —— 新增/改名档位只改代码，
   文档只解释"为什么要有进度、怎么消费"，避免两处各写一份后漏改一处。
⑩ 频率上限：插件侧每 200ms 最多一帧（防"每解一个对象发一帧"把 stdout 打满、反而拖慢解包）；
   主进程侧忽略**同 phase 同 ms** 的重复帧（同毫秒同档没有新信息）。
```

**为什么需要进度帧**（实测背景）：三段 phase（档名与语义见上述 `PROGRESS_PHASES`）原先由主进程在解包**全部完成后**
一次性 fire，三条与 done 挤在 13ms 内 —— 用户看到的是"一直转圈，然后突然全好"，
12 秒里到底卡在"读包 / 解容器 / 解纹理 / 写盘"哪一段完全看不出来。
进度帧让**子进程自己**在每个自然边界上报，主进程原样转发（`onProgress` 回调）。
node 运行时的插件是**进程内**执行、天然同步，拿不到中间边界，
所以这条能力按"可选"设计：node 路径行为完全不变（仍一次性三条）。

## 五、UnityPy 插件落地前提（具体到能开工）

```
依赖安装：插件目录内自带依赖，不打进主项目
  plugins/<id>/requirements.txt  →  首次运行 pip install --target plugins/<id>/.deps
  运行时 PYTHONPATH=plugins/<id>/.deps:. 启动
ABI 风险：UnityPy 依赖 Pillow / numpy（wheel 有平台依赖）→ 记录安装到插件目录，主项目不受影响
体积：.deps 可能上百 MB → 必须 gitignore（与 config/models/ 同类处理）
版本：插件 README 写清 UnityPy 版本与已实测的 Unity 版本范围
```

## 六、风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| python 冷启 + import 耗时 | 首次解包可能 +1~3s | 常驻 worker + 预热（选中模型时后台拉起） |
| worker 泄漏 | 内存累积 | 空闲超时退出 + 主进程持有 pid 表，退出时统一 kill |
| 插件自带依赖体积 | 磁盘 | `.deps/` gitignore；README 给安装命令，不随仓库分发 |
| 协议实现出错（粘包/半帧） | 请求挂死 | 单测覆盖：分片写入、空行、超长行、并发两请求 |
| 平台差异（本机 vs 别的机器） | 装不上 | 启动时探测 python3 与依赖，缺失时报可读错误并降级（该插件禁用，不影响其它插件） |

---

## 七、建议顺序（每步都能独立验收）

```
第 0 步  plugin-runner 通用化：按 plugin.json 的 runtime/entry 装载，现有 unity-live2d-bundle 行为不变
         （判据：/api/unpack/resolve 输出与改前逐字段一致）
第 1 步  抽出 runtime 适配器接口 + node-vm 适配器（纯重构，行为不变）
第 2 步  新增 python-worker 适配器 + 一个**最小 python 插件**（只做 canHandle 返回 false，验证链路）
第 3 步  用 python 插件实现 UnityFS 容器识别（对照 unity-live2d-bundle 的结果，验证协议正确）
第 4 步  接 UnityPy 做真实解包，与 JS 版本的产物比对（同包同文件，逐字节或逐文件大小）
```

## 八、与「画质增强即时生效」的关系（另一个独立约束）

用户明确要求：**切换画质增强档位不能触发模型重新加载**，必须一眼看出区别。

这条属于渲染期约束，与 runtime 无关，但同样要写进契约：

```
· 效果只能是 uniform 热更新（Spine 改片元 uniform / Live2D 改 PIXI Filter 的 uniforms）
· 禁止为了实现效果而重建 skeleton / 重新解包 / 重传纹理
· 判据：切换档位期间 diag 里不得出现 model.mount、unpack.* 事件；
        从点击到画面变化 ≤ 2 帧（≈33ms @60fps）
```

---

## 九、结论

```
① 多语言支持：**可行且应当做**，方案是「子进程 + 行 JSON 帧 + 二进制走临时文件」
② 但前置债必须先还：plugin-runner 目前写死单插件，先通用化 + 抽适配器
③ 浏览器侧插件仍限定 JS（渲染/效果类），不在这次放开范围
④ 零依赖从"硬约束"降为"现状保持"：主项目仍零依赖，插件可自带依赖（含 venv/.deps）
⑤ UnityPy 是最合适的第一个 Python 插件，建议按 §七 分 5 步，每步可独立验收
```
